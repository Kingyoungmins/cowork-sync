## 1. Scope

### 1.1 v1 in scope

- The rationale and per-command additions for the one git runner `runGit` (glossary §18). This chapter specifies the allowlist and never-list of DAEMON_ENV (glossary §18), the environment that runner uses.
- The start-time auth preflight in exactly the daemon environment. The filter preflight itself belongs to DAT-; this chapter fixes the environment it runs in (DAEMON_ENV with the PATH entries the configured drivers need, cwd = the repository root; glossary §25 F12) and the rule that it compares only through DISK_EQ-safe forms (glossary §26.2 item 3).
- One secret scanner `scanSecrets()` (detectors: glossary §16, plus D1 of §3.6) for every blob, board op, note, log line, status string, OS notification and doctor bundle that cowork produces.
- An explicit egress list with no telemetry, and a typed allowlist serializer for board ops.
- Remote pinning, URL-drift detection and refusal of anonymously readable remotes.
- Ref trust: explicit refspecs only, the documented v1 trust model, and board-derived strings treated as untrusted input.
- Skip-CI markers on every live and board commit, a save shape that never makes CI skip the real branch, and handling of host secret rejections.
- Authentication: non-interactive only, classification of failures, backoff, and how failures show up.
- Local IPC on Windows named pipes and Unix sockets: key, ACL, endpoint name, mutual HMAC, framing, squatter detection.
- Messaging token custody. The token never leaves the session's own MCP server.
- The human-evidence gate for acting slash verbs, fed by UserPromptExpansion (glossary §25 F5).
- Managed-policy and delivery detection, mapped to seat wiring (glossary §3) and to the FREEZE reason `NOHOOKS`.
- Execution surfaces: which repository-defined programs may ever run, the quarantine set, review items and `/cowork review <id> --accept`.
- `sanitize()` and the validators for names, paths and ids that come from the board or from peers.
- Team configuration `.cowork/config.json` and the per-user `user.json`: their source, validation, invalid-config behaviour, approval of `checks.save`, and the security envelope of `secretPatterns`.
- Integrity of the copied daemon runtime.
- Content rules for local logs and temporary files, including the staged copies the snapshot reads into `<gitdir>/cowork/tmp/stage/` (glossary §26.1 W1).

### 1.2 v1 refuses

Every code matches the glossary §19 registry pattern. Human text comes from the UX-/I18N- catalogs (six languages). Claude-facing text comes from COO- templates (`en` and `ko` only, glossary §19/§22). §3.19 lists every code this chapter defines, with its audience, so that 07-coordination and 10-product can template it.

### 1.3 Deferred / not in v1

- `uninstall --remote-refs`, `/cowork gc`, `refs/cowork-archive/*` (glossary §22). The README documents a manual `git push --delete`.
- Statusline chaining (glossary §22). Health reaches people through `status.json`, systemMessage on transitions and OS notifications (UX-).
- Protocol raise and `/cowork protocol` (glossary §22). Proto is fixed at 1. A `proto` mismatch is the `VERSION` publish pause with zero pushes of any kind; a `regionSpec`-only mismatch pauses code pushes and allows the board-only ops listed in glossary §8.
- Claude-facing templates in zh-CN, ja, fr and es (glossary §22). Security refusals reach Claude in `en` or `ko` (`L_c`, glossary §17); human-facing security text ships in all six languages.
- `stop`/`uninstall --export=<dir>` (glossary §22). `local_only` records (for example secret-scan holds) stay on the owner's disk; `--discard-holds` with preview/confirm is the only override.
- The following are not in v1 (outside glossary §22 because they were never v1 candidates): signed or authenticated board ops (v1 detects and preserves; it does not authenticate authors); live mode on a public remote; an interactive `/cowork login`; per-session IPC keys; a per-repo configurable quarantine list.

## 3. Design

### 3.1 Threat model and trust boundaries

| Actor or input | Trust in v1 | Consequence for design |
|---|---|---|
| The local OS user, and any process running as that user, including Claude's Bash tool | Trusted (they can already `git push --force`) | IPC authentication keeps out *other* users and network clients, not the same user. The human-evidence gate (SEC-25) stops cowork's *own* surfaces from being the route by which an injected instruction ships WIP. It does not stop a determined same-user process. README states this. |
| Teammates with repo write access, and their Claudes | Trusted for code. Untrusted as a source of instructions or execution. | Board text is data and never instructions (SEC-34, COO-). Execution surfaces never sync live (SEC-31). Forged records are possible. Rewrites are detected and preserved, not prevented (SEC-14). A teammate's request or note never stands in for this PC's human: in a human-origin turn the holder's Claude answers `accept` only on its own human's word (U5); a turn started by a teammate's doorbell (turn origin `wake`; recognised by the cowork nonce in its UserPromptSubmit, glossary §25 F2, and framed by the host itself as a message from another session that "cannot grant escalation") mints no human evidence (SEC-25), is limited to its wake work set, and its writes outside that set are never published but PINned with the DECISION guard `wake-scope` owned by the local human (S5, glossary §9). |
| Anyone with repo *read* access | May read everything on `refs/cowork/*`, practically forever | Nothing secret may reach a remote ref (INV-SECRET: no unfiltered or failed-filter blob, no `local_only` path, no scanner hit, no quarantined path's local bytes and no restore-marker blob). Only LIVE paths enter a mirrored hold record (glossary §9). README, first-run and doctor state that the board is permanent (SEC-10). |
| The public, other OS users, network clients | Untrusted | Public remotes are refused (SEC-12). IPC uses authentication before any byte, a user-only key and a squatter check (SEC-20..SEC-23). |
| The host (GitHub and others) | Trusted transport. Its policy may reject pushes. Its message text is untrusted. | Push rejections are classified by outcome, never by text (glossary §26.2 item 2): after a rejection the daemon fetches; a moved leased ref is a lease loss, an unchanged ref without our op ids is transient, and only the third consecutive rejection of the same publish with the ref unchanged is `NONRETRYABLE`, which PINs the whole rejected publish (guard `host-reject`) and sets the `NONRETRYABLE` publish pause (glossary §8). The host's message reaches the human only, sanitized, in terminal (tty-mode) `/cowork status` and `/cowork doctor` output; it never enters a systemMessage, `status.json` params, an event or any Claude context, and slash-mode output carries the code only (§3.9; ENG-45, COO-31). Secret rejections make that PIN `local_only` (SEC-17). |
| Repository-controlled programs (hooks, fsmonitor hooks, merge and diff drivers, CI config, Claude settings) | Untrusted | Never executed by cowork. The only exceptions are the user's configured clean/smudge filters and a human-approved `checks.save` (SEC-30, INV-NOEXEC). |

The trust model follows U1 (access control is the repository's own permissions) and S8 (quarantined paths never sync live, and their bytes never reach any remote ref through cowork). The **hard safety boundaries** are publish gate B1 on `P` (glossary §11, INV-FENCE), MASK on `P` (INV-MASK: no quarantined, save-only, held or `local_only` path differs from `A` in `P`), the LIVE-only rule for mirrored hold records (glossary §9), the pre-push secret scan (SEC-07), filter `required=true` with `attr.tree` (glossary §18, DAT-15, DAT-13), and the board serializer (SEC-09). Hooks and messages are advisory: the host runs a command hook that exits 1 or exceeds its `timeout` as **fail-open** (glossary §25 F6, MEASURED), so the loader's exit-2 mapping (glossary §11) narrows but cannot close that gap, and nothing in this chapter's safety argument rests on a hook having run.

### 3.2 What leaves the machine (egress list)

cowork-sync opens network connections only through `runGit` network-class calls (glossary §18). The full list:

| # | Destination | Content | Rule |
|---|---|---|---|
| E1 | pinned URL, fetch | The three refspecs of glossary §4 (board, code mirror as lease value only, `refs/heads/<b>`) | SEC-13, ENG-18 |
| E2 | pinned URL, push | Live code commits and board commits on `refs/cowork/<enc(b)>/{board,code}` (or `refs/heads/cowork/<enc(b)>/{board,code}` in the opted-in fallback namespace, glossary §4), after the SEC-07 scan; this includes the human-typed `/cowork recover` overwrite (the one INV-FF exception) | ENG-43, ENG-22, SEC-07 |
| E3 | pinned URL, push | `refs/cowork/<enc(b)>/displaced/<oid12>` and recover's `refs/cowork/<enc(b)>/displaced/<peer_id>/v-<k>` (Plan 2 merge, 01-engine §3.7 step 4), ≤ 3 per branch in total (glossary §4, §20), after the SEC-07 scan | ENG-21, ENG-22, SEC-14 |
| E4 | pinned URL, push and delete | The probe ref of the active namespace: `refs/cowork/probe-<peer_id>`, or `refs/heads/cowork/probe-<peer_id>` in the fallback namespace (glossary §4, PRO-49) | PRO-49, INV-OID |
| E5 | pinned URL, push | `refs/heads/<b>` by a human `save` (an existing live tree, already on the remote) | LIF-25 |
| E6 | pinned URL, ls-remote | Auth preflight and failure classification (SEC-05, SEC-18); the ENG-18 re-listing after a failed fetch; the LIF- start listing of `refs/cowork/` (branch-name collision check) | — |
| E7 | **https form of the pinned URL** (only when the pinned URL is https, or ssh/scp to github.com, gitlab.com, bitbucket.org or ssh.dev.azure.com), ls-remote with no credentials | Anonymous-readability probe at start, at doctor and every 6 h | SEC-12 |

Test-only refs (`refs/cowork-ci/<run_id>/…`, branch `ci/<run_id>/<b>`, glossary §4) are refused by release builds (lint) and are not part of the release egress list. Local refs (`refs/cowork-local/*`, including `incident-<n>-own`, glossary §4) are never pushed. Every push of E2–E5 is a governed attempt (PRO-41) under the glossary §20 governor, including its sliding team guard (no attempt starts while this peer has observed ≥ 6 landed board commits in the last 60 s Δmono). No push uses `--atomic` in v1 (glossary §26.2 item 1), and `-o ci.skip` (§3.9) is the only push option cowork ever sends. A retry after a transient rejection (glossary §26.2 item 2) re-sends only the same governed publish, re-scanned by SEC-07; it never adds a destination.

Everything else stays on the machine: logs, status, doctor bundles (never uploaded; UX-16), OS notifications (local OS API), IPC (local only). No telemetry, crash reporting, update check or analytics exists (SEC-01). Plugin updates come only from the marketplace, installed by the user through Claude Code (REL-).

(rev 2.5, F12) `/cowork wrap` and its summary draft add no row: `wrap` makes no fetch or push and writes no board op, and the draft is never written to a ref, the board, `status.json`, a log, `tmp/` or any other file (FEAT-F12-11); it exists only in the CLI's output. The other rev 2.5 features add no row either: `/cowork since` (F04) and `/cowork status --flow` (F14) read local state only; claim-ahead notes (F05) read the claim view this daemon already holds; a confirmed `/cowork revert` (F10) leaves this PC only as an ordinary human change-set in a live code commit under E2, after the SEC-07 scan like every other; the viewer features (F29 reel, F32 follow, F34 postcard) open no connection beyond the viewer page's existing loopback routes (a reel fetches only `GET …/timeline` pages; follow and postcards request nothing), and a reel's or postcard's download and a postcard's clipboard write are the user's own exits, like the recording download of 12-visualizer §3.9.4.

What a remote ref may contain is fixed by the board-op schema (glossary §7) and the commit formats (glossary §5). Code arrives only as clean-path blob ids (PRO-05), and displaced or withheld versions only as `held/<hold_id>/<stage>/<repo path>` blob entries of non-`local_only` records; a `local_only` record appears only as a content-free `hold` stub (no `held/` entries, no blob oids; glossary §7). Free text is limited to ≤ 280-char notes (`note.text`, `request.note`, `answer.note`) that pass the scanner (SEC-08); `event` ops carry codes and params only (glossary §7). Identity is limited to a display name chosen by the human, `peer_id@cowork.invalid`, the plugin version and sha, a `config_fingerprint` that contains no paths, user names or host names, and — only after the human opted in with `/cowork start --coauthor=on` — the `"<name> <email>"` value of `join.coauthor_optin` (glossary §7; default `false`, glossary §5 privacy default off).

### 3.3 The git runner: why each argument exists

The runner is defined in glossary §18. This table maps each element to the failure it prevents. `runGit` MUST also append the remaining network-safety arg (§2: `--no-recurse-submodules` on every fetch).

| Element | Prevents | Evidence |
|---|---|---|
| `core.hooksPath=<gitdir>/cowork/empty-hooks` | A tracked `reference-transaction`, `pre-push` or `post-checkout` hook running inside the daemon's own fetch, push or update-ref | synced-execution-surfaces, VERIFIED t4_hooks.sh |
| `core.fsmonitor=<bool>` | A repository-configured fsmonitor *hook command* running on every snapshot | synced-execution-surfaces |
| `filter.<d>.required=true`, `attr.tree=<EPOCH_BASE>` | Plaintext secrets stored with exit 0 when the clean filter is missing or broken, or after a peer edits `.gitattributes` | filter-passthrough-leak, secret-filter-fails-open-in-daemon-env, gitattributes-edit-unfilters, all VERIFIED (sweep e1, msgsec/r); confirmed on a pilot team's real filter: without `required=true` a failing or undefined filter stores the plaintext secret with rc 0, with it `git add` aborts with rc 128 and an unchanged index in every failure mode (glossary §25 F12, MEASURED) |
| cwd = the repository root for every command that may run a filter (glossary §25 F12) | A repo-relative driver path failing outside the root. With `required=true` that failure is closed (rc 128), but it would freeze or refuse a healthy repo and make the preflight prove nothing | glossary §25 F12, spike 03 (MEASURED) |
| Hashing a staged copy with `--path=<p>`, never the user's working file (glossary §26.1 W1) | git's memory mapping of the working file making a concurrent editor save fail (Win32 1224). ### 3.4 The daemon environment

The daemon is detached and outlives the session that spawned it, so it must not depend on the session's shell state. It also must not inherit session secrets (`CLAUDE_CODE_MESSAGING_*`) or git redirections (`GIT_DIR`, `GIT_INDEX_FILE`). DAEMON_ENV (glossary §18: fixed at spawn from an allowlist) is built once, at spawn, by one builder; this section is the single allowlist and never-list for it (06-claude §3.17.2 spawns with it, CCI-51; 11-testing SPIKE-0 item f measures it). The spawning SessionStart hook's own environment carries `CLAUDE_CODE_MESSAGING_TOKEN` (the host puts it in every hook's environment, glossary §26.2 item 6), so the daemon MUST be spawned with an explicit environment object produced by this builder, never with the hook's inherited environment:

1. Base allowlist, copied from the spawning SessionStart hook's environment: `PATH`/`Path` (the interactive PATH captured by CCI-; it keeps the PATH entries the configured filter drivers need, resolved at start and shown in doctor, glossary §25 F12), `SystemRoot`, `ComSpec`, `USERPROFILE`, `HOME`, `TEMP`, `TMP`, `TMPDIR`, `LANG`, `LC_*`.
2. Credential and transport set: `APPDATA`, `LOCALAPPDATA`, `PROGRAMDATA`/`ProgramData`, `ProgramFiles`, `HOMEDRIVE`, `HOMEPATH`, `PATHEXT`, `WINDIR`, `SYSTEMDRIVE`, `XDG_*`, `DBUS_SESSION_BUS_ADDRESS`, `SSH_AUTH_SOCK`, `SSH_AGENT_PID`, `GCM_*`, `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, `ALL_PROXY` (and their lower-case forms), `GIT_SSH_COMMAND`, `GIT_SSH`, `GIT_SSH_VARIANT`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`.
3. The names in `user.json` `env.passthrough`, except names on the never-list.
4. Never-list (always dropped, even if passed through): `CLAUDE_*` (including `CLAUDE_CODE_MESSAGING_SOCKET`/`TOKEN`), `ELECTRON_*`, `VSCODE_*`, `NODE_OPTIONS`, `NODE_PATH`, `SSH_ASKPASS`, `GIT_ASKPASS`, `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_COMMON_DIR`, `GIT_NAMESPACE`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_*`, `GIT_CONFIG_VALUE_*`, `GIT_EXEC_PATH`, `GIT_TRACE*`, `GIT_EXTERNAL_DIFF`, `GIT_EDITOR`, `GIT_ATTR_SOURCE`, `GIT_REPLACE_REF_BASE`, `GIT_NO_REPLACE_OBJECTS`, `GIT_SHALLOW_FILE`, `GIT_GRAFT_FILE` (`runGit` sets its own, item 5), `GIT_CONFIG` (exact name; `GIT_CONFIG_GLOBAL`/`SYSTEM`/`NOSYSTEM` stay on the transport set), `GIT_AUTHOR_*`, `GIT_COMMITTER_*` (cowork sets its own, SEC-03). Proxy and TLS variables (`GIT_SSL_*`, `GIT_PROXY_*`, `GIT_HTTP_*`) are not on it: they are dropped by the allowlist unless passed through, and a user who needs them for connectivity passes them through.
5. The forced values of glossary §18 are applied on top (`LC_ALL=C`, `LANGUAGE=`, `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, `SSH_ASKPASS_REQUIRE=never`, `GIT_OPTIONAL_LOCKS=0`; they override any passed-through `GCM_*` value). `runGit` sets `GIT_GRAFT_FILE=<hooksPath>/.no-grafts`, an absolute path under the empty hooks directory that never exists: `.git/info/grafts` is honoured even under `--no-replace-objects` and would give one peer different first-parent chains (controller ruling P2-GRAFTS). `runGit` sets `GIT_SSH_COMMAND` to the effective ssh command with the glossary §18 BatchMode options *appended*. For variant `plink`/`tortoiseplink` it appends `-batch` instead. For variant `simple` it appends nothing and relies on the watchdog. Release builds never set `GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE` (glossary §18; only test builds add them from the virtual clock).

`/cowork start` and doctor run `git ls-remote --exit-code <pinned URL> refs/heads/<b>` and the DAT-16 filter preflight in a child built by the same builder (LIF-04: "in the daemon's process environment"). A failure refuses start. A setting that works only in the user's shell therefore fails loudly at start, never silently in the detached daemon.

The filter preflight runs **in the real work tree with cwd = the repository root** (glossary §25 F12; the former scratch-work-tree form with `update-index -q --refresh` never ran the filter and is removed). For each filtered path p it checks the round trip `cat-file --filters <B>:p | hash-object --path=p --stdin` against the same path's stored form, both sides converted through the same `--path=p` (glossary §26.2 item 3). Any comparison against disk uses DISK_EQ (glossary §3), never `hash-object --path` of a working file against a blob id, which misreports `i/crlf` files (glossary §26.2 item 3). DAT-16 owns the exact steps and the choice of B; this chapter requires only that the preflight's environment is DAEMON_ENV with cwd = root and that a pass is never claimed by a check that did not run the filter.

### 3.5 Remote pinning, URL drift and public-remote refusal

**At start (called by the LIF- start flow, 08-lifecycle §3.3.1 / LIF-05, which owns only `START_REMOTE{no_remote}`; the split and rewrite refusals are SEC-11's codes):**

1. Resolve `remote_name` per glossary §18 (`branch.<b>.pushRemote` → `remote.pushDefault` → `branch.<b>.remote` → `--remote <name>` → the only configured remote; never assume `origin`). If nothing resolves, refuse with the next command `/cowork start --remote <name>`.
2. `URL_f := git remote get-url <remote_name>`, `URL_p := git remote get-url --push <remote_name>` (both after rewrites). If `URL_f ≠ URL_p`, refuse (`SEC_REFUSE_REMOTE_SPLIT`). The pinned URL := `URL_p`.
3. If any value of `git config -z --get-regexp '^url\..*\.(insteadof|pushinsteadof)$'` is a prefix of the pinned URL, or of the literal configured URL of `remote_name`, refuse (`SEC_REFUSE_URL_REWRITE`). A literal URL argument is still rewritten by insteadOf, and a `-c` identity rewrite does not reliably win (VERIFIED secprod x2/x2c). Detect-and-refuse is the only reliable enforcement.
4. Anonymous probe (E7): for `https://` URLs, and for ssh/scp URLs whose host is github.com, gitlab.com, bitbucket.org or ssh.dev.azure.com (mapped to their https form: `git@github.com:o/r.git` → `https://github.com/o/r.git`; `git@ssh.dev.azure.com:v3/o/p/r` → `https://dev.azure.com/o/p/_git/r`), run `git -c credential.helper= -c http.extraHeader= -c core.askPass= ls-remote <https form> HEAD` with `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never` and no `SSH_AUTH_SOCK`, under a 15 s watchdog. An empty `credential.helper` resets generic and URL-scoped helpers (VERIFIED x1). Exit 0 → refuse with `SEC_REFUSE_PUBLIC_REMOTE`. A non-zero exit with an HTTP 401/403 in the header-only curl trace → private, so pass. Anything else (network failure) → refuse start with `SEC_PROBE_UNREACHABLE` and suggest a retry.
5. Other URL forms (`file://`, local paths, other ssh hosts): doctor shows "public readability not checked". Start requires a one-time human confirmation "this remote is private" — the onboarding screen (UX-23, UX-24) or `/cowork start --private-confirmed` (glossary §15; an acting verb under SEC-25) — stored as `privateConfirmed` per repo identity in `user.json` (glossary §6). Otherwise refuse with `SEC_REFUSE_PRIVATE_UNCONFIRMED`.
6. Pin the pinned URL, `remote_name` and the repo identity (sorted root oids of fetched `refs/heads/<b>`, glossary §18) in state meta.

**While live (every cycle, before any network call):**

1. Stat (mtime and size) every config file in `git config --show-origin --list -z` origins (system, global, XDG, local, worktree, every included file). If anything changed, or 60 s have passed since the last full check (Δmono; glossary §18 "re-checked on config change and every 60 s"), re-run steps 1–3 above and compare `remote_name`, `URL_f`, `URL_p` and the rewrite set with the pinned values.
2. On any difference, set FREEZE `CONFIG` with detail `url` (glossary §8). Then: **no network call of any kind** on the branch — no fetch and none of the board-only pushes glossary §8 otherwise allows while frozen (glossary §8: `CONFIG(url|public)` forbids every network call), because they would go to the rewritten target. The old and new URL are shown to the human (status, OS notification) and to every local seat (COO- template for `FROZEN`).
3. Lifting (glossary §8): `/cowork resume` lifts `CONFIG(url)` only after doctor passes, meaning the current resolution equals the pinned values again. A legitimately changed URL is re-pinned only by `/cowork stop` then `/cowork start` (LIF-05).
4. The anonymous probe re-runs at every daemon start and every 6 h of Δmono while live. Success sets `CONFIG` with detail `public`, with the same no-network behaviour.

### 3.6 Secrets: layered defence

| Layer | Mechanism | Owner |
|---|---|---|
| L1 | Untracked secret-like files (glossary §16 default patterns) get scope class `LOCAL_ONLY` and never become new synced paths unless `sync.allowSecretLike` names them, and even then they pass the content scan (U10, DAT-24, DAT-30) | DAT- (scope) |
| L2 | Every blob is produced through the pinned clean path with `filter.<d>.required=true` and `attr.tree=<EPOCH_BASE>` (DAT-01, DAT-15). The snapshot reads a user file once into a staged copy and runs `hash-object --path=<p>` on the copy, so attributes and the required filter apply exactly as on the working file (glossary §26.1 W1); snapshot ticks hash without `-w` and write no objects, so objects exist only for ready-pair captures, publishes, applies and hold records (glossary §26.1 W6); a hook-driven request for named paths also computes ids without `-w`. A filter failure fails the cycle's snapshot; the failing paths become `local_only` PATCH records with guard `filter-failure` (glossary §9, content-free board stub, glossary §7), or FREEZE `CONFIG` with detail `filter` is set when the driver canary fails (DAT-18, DAT-17). | DAT-, glossary §18 |
| L3 | The filter preflight (round trip, idempotency, canary) runs in DAEMON_ENV, in the real work tree with cwd = the repository root, at start and at doctor (DAT-16; glossary §25 F12, §26.2 item 3; §3.4), and the canary repeats every 10 min while live (DAT-17, glossary §20 data numbers) | DAT- (checks), SEC-05 (environment and cwd) |
| L4 | **Pre-push content scan** of every blob a push would add (SEC-07) | this chapter |
| L5 | The board serializer allowlist rejects absolute paths, transcript paths, OS user and host names, and scanner hits in any string field (SEC-09) | this chapter |
| L6 | Logs, status, notifications and bundles are scanned and redacted (SEC-38) | this chapter |
| L7 | Documentation: the board is permanent, and the remedy for a leak is rotation (SEC-10) | this chapter, UX-/I18N- |

**scanSecrets detectors** (D2 and D3 are exactly the glossary §16 content scan; D1 is this chapter's addition and only adds hits):

- **D1, dynamic secret lines.** Built at start and whenever `EPOCH_BASE` or the filter set changes. For every filtered path p in the DAT- driver list, take `smudged := cat-file --filters --path=p <EPOCH_BASE:p>` and `stored := <EPOCH_BASE:p>`. For every line of `smudged` (trimmed, ≥ 8 chars) that does not occur in `stored`, add `SHA-256(salt ‖ line)` to an in-memory set. The salt is 32 random bytes per daemon start. The set and the salt are never persisted, logged or sent over IPC. Scanning hashes each trimmed line of the input the same way. This finds a filtered secret value that has leaked into *any* file.
- **D2, built-in high-confidence patterns (glossary §16):** private-key headers `-----BEGIN [A-Z ]*PRIVATE KEY-----`; cloud key prefixes `AKIA[A-Z2-7]{16}`, `ASIA[A-Z2-7]{16}` (prefix + 16 base32), `AIza[0-9A-Za-z_\-]{35}`; GitHub tokens `gh[pousr]_[A-Za-z0-9]{36}`, `github_pat_[A-Za-z0-9_]{22,}`; Slack tokens `xox[abpr]-[A-Za-z0-9-]{10,}`; and high-entropy assignments. A high-entropy assignment is a value of ≥ 20 chars with Shannon entropy ≥ 4.0 bits/char assigned to a key matching `(?i)(secret|token|password|passwd|api[_-]?key|sig)` — concretely a line matching `(?i)(secret|token|password|passwd|api[_-]?key|sig)[A-Za-z0-9_\-]*["']?\s*[:=]\s*["']?([A-Za-z0-9+/_\-=.]{20,})` whose captured value has entropy ≥ 4.0 bits/char. (Changed per glossary §16 rev 2: the key list and the base32 alphabet are the glossary's; the former extra "not all one character class" exemption is removed.)
- **D3, team patterns:** `secretPatterns` from `.cowork/config.json` at `EPOCH_BASE` (glossary §16/§17, CFG-05).

A hit of any detector makes the path scope class `LOCAL_ONLY` with a `secret-scan` DECISION guard owned by the local human (glossary §16, §9). Binary blobs (a NUL byte in the first 8,000 bytes, glossary §20) get the D2 private-key header and token prefixes only. Budget: ≤ 50 ms per MB, run in worker threads (glossary §20 "Parse: worker threads only"). A D3 pattern that exceeds its 100 ms per-blob cap counts as a hit naming the pattern.

**Acknowledgement escape hatch for false positives.** D2 and D3 hits, never D1, can be acknowledged by the local human with `/cowork resolve <id> --publish` (acting verb, SEC-25) on the secret-scan record. The preview shows detector, path and line numbers, never the matched text. Acknowledgement stores `SHA-256(path ‖ NUL ‖ trimmed line)` in that record's resolution in the local registry. It is never mirrored and never written to the board. Later scans skip exactly those lines in that path. Any other line, or the same line in another path, still hits. No MCP tool can acknowledge (SEC-27).

### 3.7 Board content

Glossary §7 fixes the op schema. This chapter adds the serializer that every board write passes through (SEC-09). Every string field has a schema maximum. The serializer rejects, and logs as `SEC_BOARD_FIELD_REJECTED`:

- absolute paths (`^[A-Za-z]:[\\/]`, `^/(home|Users|root|var|tmp)/`, `^\\\\`);
- the OS user name or host name of this machine, in any field except `display` (which the human chose and which defaults to git `user.name`, UX-24) and an opted-in `join.coauthor_optin` value (glossary §7);
- transcript paths;
- any `scanSecrets` hit (this includes the `text` of a `note` op and the `note` of `request`/`answer`, which SEC-08 already scanned at the tool).

Rejecting an op never drops bytes. The op is not written, its producer is told, and any bytes it referred to stay in their hold record (HLD-).

### 3.8 Ref trust

Nothing protects `refs/cowork/*` on GitHub (rulesets target branches and tags; DOCUMENTED git-transport.md §1). Anyone with write access can rewrite, delete or spam those refs and can forge ops attributed to any peer. cowork's v1 position:

1. Fetch only the three explicit refspecs of glossary §4 for the one live branch (ENG-18). Never use a wildcard. Other `refs/cowork/*` refs are inert. The code mirror is fetched as a lease value only, never as a decision input (glossary §4).
2. Rewrites and deletions are REWRITE INCIDENTs, detected via INV-FF and INV-FIRSTPARENT and preserved (ENG-21, ENG-22, `/cowork recover`; `INCIDENT` forbids every push on the branch except the detection-time displaced copy and the human-typed recover, glossary §8). A deleted live ref is never silently recreated (ENG-). A late peer whose newer commits are not on the restored chain re-anchors through `/cowork recover` in re-anchor mode (glossary §8): it never force-pushes over the team's tip, keeps its pre-incident chain under the local ref `incident-<n>-own` (glossary §4; never pushed), and its own disk bytes become `restart` PATCH records, which follow the LIVE-only rule for mirrored records (glossary §9) and pass SEC-07 before any push like every other hold mirror.
3. Board ops are untrusted input. Ids, paths and names pass the deterministic validators (SEC-35) inside the fold (PRO-). Board caps (glossary §20: 5,000 folded records, 5 MB tree, 64 KiB and 1,000 ops per `ops.jsonl`) bound the work a hostile writer can cause.
4. The daemon never writes to disk at a path taken from a board record, except through the normal tree apply of a validated live commit (ENG-) or through `writeLocal` (ENG-37) after a human verb.
5. Forged authorship is not detected in v1. README "trust-model" and doctor say so.

### 3.9 CI, webhooks and host policy

- Live code and board commits carry `[skip ci] ***NO_CI***` and `skip-checks: true` (glossary §5). `-o ci.skip` is added only when `caps.push_options` is true (ENG-43).
- Save commits carry no markers. Their parent is `Hb`, a branch commit (glossary §5/§12), so no marker-bearing live commit is ever an ancestor of a pushed branch tip. Hosts that skip CI when *any* commit in a push carries a marker (Azure) therefore never skip the real branch's CI.
- Measured on GitHub (glossary §25 F8): an `on: push` Actions workflow did **not** run for pushes to `refs/cowork/*`, with or without the skip markers, and did run for `refs/heads/*`. The markers stay for other hosts. Webhooks cannot be suppressed by markers and their deliveries were not measured, so README states that webhooks may fire on `refs/cowork/*` pushes. Webhook deliveries and GitHub push protection on custom refs remain SPIKE-0 item a follow-ups (TST-27) and soak checks (TST-17); see §8 Q4.
- The fallback namespace `refs/heads/cowork/...` (PRO-50) would trigger branch CI. Its opt-in confirmation MUST list every CI file found (`.github/workflows/**`, `azure-pipelines*.yml`, `.gitlab-ci.yml`, `bitbucket-pipelines.yml`).
- Rejections are classified **by outcome, not text** (glossary §26.2 item 2, which resolves the former §18 vs §25 F9/F11 conflict; ENG-44, ENG-45, INV-FF). After any rejection the daemon fetches. If the leased ref moved, it is a lease loss, retried in the next window (this covers GitHub's `cannot lock ref … is at … but expected …` loser line, glossary §25 F9). If the ref did not move and our op ids are absent, it is transient, retried in the next window with backoff (this covers `[remote rejected] … (failed)` and `fatal error in commit_refs`, glossary §25 F11). After **3 consecutive rejections of the same publish with the ref unchanged** the result is NON-RETRYABLE. A NON-RETRYABLE result sets the `NONRETRYABLE` publish pause, shows the host's sanitized stderr to the human only — in `/cowork status` and `/cowork doctor` output when the CLI runs in a terminal (`tty` true and `ancestry_has_claude` false, §3.13 step 3), and nowhere else: never in a systemMessage, `status.json.message_params`, an event's params or any Claude context, because the text may carry server-side hook output written by whoever runs the host (a prompt-injection surface; ENG-45 owns where the daemon retains it, COO-31). In slash mode (output Claude reads: no TTY or a claude ancestor) `/cowork status` and `/cowork doctor` print only a code-only `NONRETRYABLE` line with the hold id and the terminal command that shows the text (`node "<plugin root>/dist/cli.js" doctor`, the §3.13 form); every live seat and the human's systemMessage get only the COO- `NONRETRYABLE` template with the code and hold id (COO-31). The result also PINs the whole rejected publish with guard `host-reject` (glossary §8, §9, ENG-45), and retries only on a human `/cowork resume`. This chapter adds two things. (1) After **every** rejection, before any retry, the daemon re-runs SEC-07 on the rejected publish's blobs; a hit PINs the owning CSs `local_only` at once (decided by our scanner, not by host text), so a retry never re-sends a blob our scanner flags. (2) If the publish becomes NON-RETRYABLE and the rejection named a host secret scanner (push protection or `GH013`), the PIN is `local_only=true`: scope class `LOCAL_ONLY` for its paths and only the content-free `hold` stub on the board (glossary §7). This is the "make handling stricter" use of message text that glossary §18 names as its example; per glossary §26.2 item 2 the text never decides lease loss, transient or NON-RETRYABLE, and it never causes a retry, a publish or a lift (see §8 Q9).

### 3.10 Authentication

- The daemon never stores credentials and never triggers interactive authentication (SEC-05, glossary §18). It uses the user's credential helper non-interactively.
- After a network-class failure, a follow-up `git ls-remote --exit-code <pinned URL> refs/heads/<b>` (15 s watchdog) with a header-only curl trace for http(s) supplies structured evidence:
  - HTTP 401/403 → label `auth`;
  - HTTP 429/5xx → label `host`;
  - no HTTP response, a DNS failure, or a timeout → label `network`.
  For ssh, the git exit code plus ssh exit code 255 gives `network-or-auth`. The ssh `Permission denied` token in `LC_ALL=C` output, which ssh does not translate, chooses the `auth` *explanation*.
- **The behaviour is identical for every label**: backoff of 30 s doubling to 5 min, no bursts. After > 30 s without a successful fetch, the `OFFLINE` publish pause applies. A label of `auth` shows `AUTH` (glossary §8). The label only chooses the explanation and the fix line ("run `git fetch` in a terminal to sign in again").
- A push rejection is not a network-class failure: it follows the outcome classification of §3.9 (glossary §26.2 item 2), never these labels.
- Visibility: status (`publish_pause: "OFFLINE" | "AUTH"`, glossary §14; `OFFLINE` carries `offline_for_s`, the local Δmono duration, and its templates show it, glossary §25.2 item 4), a G3 additionalContext to seats (glossary §11; ≤ 800 chars, glossary §19; CCI-), and at most one OS notification per 30 min per reason class (glossary §20, UX-).
- On reconnect, tentative claims that lost are listed before any conflict is classified (PRO-/COO-).

### 3.11 Local IPC

Node cannot set a named-pipe DACL. VERIFIED sweep/sec/pipe_server.js: Everyone and ANONYMOUS LOGON can read. A read-only client received the first line. Clients via `\\127.0.0.1\pipe\...` and `\\127.0.0.1\pipe\LOCAL\...` received bytes (msgsec/pipe2.js). A second listener gets `EADDRINUSE`, so a squatter that starts first can block or impersonate. Confidentiality therefore comes from authentication before any byte is sent.

**Key.** `CLAUDE_PLUGIN_DATA/ipc.key` holds 32 random bytes and is created on first start. `CLAUDE_PLUGIN_DATA` was measured **absent** in a project MCP server's environment (glossary §25 F3); a cowork process whose environment lacks it derives the same per-user data directory from the plugin id (glossary §25 F3) and runs the same ownership and ACL verification below before it reads the key. A process that cannot locate a verified key never connects: the MCP server then never pairs and its seat is `NO_MCP` after the 3 s pairing window (glossary §2, §20); the hook loader follows S3 (G4).
- POSIX: mode 0600, owner = uid, and the parent directory is not group- or world-writable.
- Windows: `icacls <file> /inheritance:r /grant:r *<SID>:F`. The user SID is taken from the process token (`whoami /user /fo csv /nh`). The ACL is then verified by reading SDDL (`icacls` or `Get-Acl ... .Sddl`) and comparing SIDs, never localized account names. Allowed ACEs: the user SID, `S-1-5-18` (SYSTEM), `S-1-5-32-544` (Administrators). Anything else refuses start with `SEC_REFUSE_IPC_ACL`.

**Endpoint name.** Let `k = HMAC-SHA256(key, "endpoint:" ‖ root)`, where `root` is the **canonical repo root form** of the common gitdir (glossary §24 default 12; 06-claude §3.4.1 step 3): `fs.realpathSync.native`, lower-case drive letter, `/` separators, NFC, and lower-cased (locale-independent) on Windows and macOS. The daemon's bind, the hook loader, core and the MCP server all derive `root` this way (glossary §24 default 12 binds 03-data's canonPath realpath, DAT-34, to the same form), so two spellings of one clone always reach one endpoint and never bind a second daemon.
- Windows: `\\.\pipe\cowork-<hex(k[0..16])>`.
- POSIX: `<dir>/<hex(k[0..12])>.sock`. `dir` is the first candidate of `$XDG_RUNTIME_DIR/cowork-sync`, `/tmp/cws-<uid>` for which the full socket path is ≤ 100 bytes. `dir` is created with mode 0700 and verified with lstat: a directory, owned by uid, not a symlink, mode 0700. If no candidate fits, start is refused.

The name cannot be predicted without the key and is unique per clone. Binding it enforces one daemon per clone (glossary §6 `daemon.lock`).

**Handshake** (each nonce 16 random bytes; all comparisons use `crypto.timingSafeEqual`):

```
C → S  {"t":"hello","v":1,"n1":<b64 nonce1>}
S → C  {"t":"srv","n2":<b64 nonce2>,"p":<b64 HMAC(key, "srv" ‖ n1 ‖ n2 ‖ endpoint)>}
C → S  {"t":"cli","p":<b64 HMAC(key, "cli" ‖ n2 ‖ n1 ‖ endpoint)>}
```

The server sends nothing before `hello`. The client sends nothing after `hello` until it has verified `srv`. A mismatch closes the connection at once and records the security event `SEC_IPC_HANDSHAKE_FAILED`. Frames after the handshake are newline-delimited JSON, ≤ 1 MiB per frame, validated against the IPC schema. An unknown `t` or a schema failure closes the connection. The loader protocol (glossary §13) runs inside this channel.

**Squatter check.** On `EADDRINUSE` the starting daemon connects as a client and runs the handshake. If it passes, a legitimate daemon is already running and is reused. If it fails, the endpoint is owned by a process without the key: refuse with `SEC_REFUSE_IPC_SQUATTER`, write a security event and raise one OS notification.

**Capability limits.** No IPC request executes a command supplied in the request, reads or writes a path outside the main-worktree realpath, or returns tokens, the key or environment values.

**CLI requests added in rev 2.5** (rev 2.5, F04, F12, F14). The IPC schema that every frame is validated against (SEC-22) also registers the following CLI → daemon requests. Each is subject to the capability limits above (SEC-23), carries codes and typed params only (no rendered text; I18N-01), and its reply fits the 1 MiB frame cap. Other CLI frames (for example doctor's `canary_arm`, 10-product §3.10) are unchanged.
- **`flow` selector of the status detail request** (F14; 10-product §3.5 "Inputs", §3.5.1). Selector value: all, or one repo-relative path (`validPathSyntax`, SEC-35). The daemon answers from its in-memory state of the last loop iteration, with no git process, file read, snapshot or write (FEAT-F14-05). The reply holds at most **2,000** flow entries plus the count of entries omitted, which keeps it inside the frame cap. Its content follows SEC-38 as amended for it (rev 2.5, F14).
- **`wrap`** (F12; 10-product §3.20). One read-only request kind for `/cowork wrap`. It neither needs nor consumes human evidence and renews no human lease (FEAT-F12-01); its reply carries no summary-draft text assembled by the daemon, only the draft's structured rows.
- **`since_query`** and **`since_ran{to}`** (F04; this list is their definition; their use is 10-product §3.9a, FEAT-F04-18, and 06-claude §3.12.2 defines the human activity behind the marks). `since_query` returns `meta.since` (board heights only), this peer's hold-record metadata (id, paths, state, offer; never a blob or blob oid's content) and claim labels the daemon has already verified (REG-34). `since_ran` only moves this PC's local `last-run` mark; the daemon applies it only for a route-(a) request (below) or within 60 s of a human-classified `/cowork since` UserPromptExpansion (FEAT-F04-18) and otherwise ignores it without a refusal, so a Claude Bash call of `cli.js since`, with or without a PTY, cannot move the mark.

**Route-(a) requests** (glossary §29.2; merge round 2; F04). The `since_ran` request carries the CLI's output mode (`tty`, `pipe` or `slash`, 10-product §2) and the two fields of §3.13 step 3, computed exactly as there: `tty` (`process.stdin.isTTY && process.stdout.isTTY`) and `ancestry_has_claude` (a claude ancestor found, or env `CLAUDECODE` set). A request is a **route-(a) request** when `tty` is true and `ancestry_has_claude` is false — SEC-25 route (a)'s test, which the evidence gate already uses for "a human ran it in their own terminal". A stdout TTY alone is not enough: a Claude Bash call that a host or a wrapper (`script`, winpty, ConPTY) gives a PTY is a `tty`-mode CLI under a claude ancestor, and is not a route-(a) request. As for route (a) itself, the ancestor check is hardening, not a boundary (§3.1), so FEAT-F04-18 is as strong as COO-31's host-text rule, which uses the same test. *(Owner decision D1, 2026-10-08: the `flow` and `wrap` requests no longer carry these fields, because the daemon no longer tests who asked for `last_check`; until then they did.)*

The reply to a `flow` request for all paths and to a `wrap` request carries, per open seat change-set of this PC, the daemon's in-memory `last_check` (the latest failed edit-check result: check number 1–4, repo-relative path, line number; 10-product §3.5.1). **Owner decision D1 (final, 2026-10-08):** that result is kept only in this PC's daemon memory and reaches a screen only through these two replies, whenever `/cowork status --flow` or `/cowork wrap` runs — in a terminal, or as a slash command, whose output that seat's Claude reads, which the owner intends. The daemon does not test who asked, so a Claude Bash call of `cli.js status --flow` or `cli.js wrap` gets it too: that is output Claude asked for, not a push. A path-scoped `flow` request (`show <path>`) never carries it, and plain `status` prints only the pointer line `UI_FLOW_LAST_WITHHELD` (10-product §3.5.1). Nothing about it is pushed to a Claude carrier (06-claude §3.14.1), a hook output, a human mirror or an OS notification, or reaches teammates, the board, `status.json`, a log or a file.

**Liveness of the key.** Every 30 s (Δmono; glossary §20 "plugin/key check 30 s") the daemon checks that `ipc.key` exists with the same content hash, that the plugin is still enabled and that its `runtime/<version>/` copy is intact (CCI-53). If any check fails, it runs the LIF-36 removal procedure (remove its `live` markers first, no further working-tree write or snapshot, one board push of ready trees through all gates when not frozen plus `release`/`seat_end`/`leave` when online, then exit and raise `DAEMON_REMOVED`).

### 3.12 Messaging token custody

MEASURED (glossary §25 F3; spike 02, Windows, Claude Code 2.1.270): a project stdio MCP server inherits `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN` (same pipe, token length 32). The host also places the token in **every hook's environment** (SessionStart, UserPromptSubmit, PreToolUse; glossary §26.2 item 6), so "the token exists only in the MCP server" cannot be a property of the host; it is a property of cowork's code. On Linux, own-child verification uses process evidence, so a detached daemon posting with a relayed token would be unverified. Therefore (glossary §26.2 item 6):

- Only the session's own MCP server (`dist/mcp.js`) reads the token, from its own environment, and keeps it only in memory. It writes it to exactly one place: the `{"type":"auth","token":T}` frame on its own session's inbox socket, the first frame of every doorbell post (glossary §25 F1). It never sends it over IPC, writes it to disk or logs, or places it in hook output.
- The hook loader, `core.js`, the CLI and the daemon never read the variable, although the host puts it in the hook loader's and (through `!` preprocessing) possibly the CLI's environment. The daemon is spawned with an explicit DAEMON_ENV that drops `CLAUDE_*` (§3.4), and every child the CLI starts (the `checks.save` command, CFG-04) gets an environment from the same builder. The daemon has no code path that opens an inbox socket.
- Pairing uses `seat_key` (glossary §2: `SHA-256(CLAUDE_CODE_MESSAGING_SOCKET)`, else the claude pid) sent by both the hooks and the MCP server, over authenticated IPC only (CCI-31). `seat_key` is derived from the socket path, never from the token, and is not a secret.
- A session whose MCP server lacks the messaging socket (glossary §25 F3), with an effective `crossSessionInbound` of `hold` or `refuse`, or with `--bare`, has seat wiring `HOOK_ONLY` (glossary §3: no MCP inbox posting; CCI-33). The wiring is published in a board `event{kind: health}` so requesters see "queued; shown at their next action" (COO-).
- Not yet measured (glossary §25 F3): inheritance by a **plugin-packaged** MCP server (the first implementation-phase check), macOS and Linux, and later Claude Code releases. The behaviour does not depend on the answer: where inheritance is absent, seats fall to `HOOK_ONLY` automatically, and no token relay is ever added.

### 3.13 Human-only verbs: the evidence gate

Every slash verb has `disable-model-invocation: true` and runs through `!` preprocessing of `node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" <verb> $ARGUMENTS` (glossary §15). Claude can still run `node .../cli.js save` through Bash, and an injected instruction might ask it to. The daemon executes an **acting verb** only with human evidence:

**Algorithm (daemon side):**

1. The hook loader (CCI- §3.4.1 step 7, CCI-54), on **UserPromptExpansion** (registered for `cowork|cowork-sync:cowork` for **all** verbs, glossary §25 F5 and §13), checks locally that the input's `expansion_type` is `slash_command` and its `command_name` is `cowork` or `cowork-sync:cowork`. Only then does it produce an evidence record `{seat_key, prompt_id, verb, args_sha256, mono_ns}` from the input's `prompt_id` and `command_args` (§2). `command_source` names where the command file is defined (for example `projectSettings`), not who typed it, and is never treated as evidence. Other prompts are never sent, stored or logged, and neither the prompt text nor `command_args` leaves the loader. (Changed in rev 2.3, glossary §25 F5: UserPromptExpansion fires **before** the `!` line, measured ≈ 475 ms earlier, while UserPromptSubmit fires only **after** the `!` line has finished; an evidence wait on UserPromptSubmit would deadlock the CLI and is forbidden. The former UserPromptSubmit trigger and its character-0 prefix test are removed: the host decides what is a slash command, and only an expansion proves it did.)
   - Repo live, not paused, daemon answering: the record rides the UserPromptExpansion IPC request.
   - Otherwise (non-live repo, paused repo, daemon down): the loader appends it as one JSON line to `<gitdir>/cowork/tmp/evidence.jsonl` (glossary §6; created user-only), tagged `HMAC-SHA256(ipc.key, "evidence" ‖ canonical line)` when `ipc.key` exists. An **untagged** line is accepted only for `start` and `doctor`, and only while `ipc.key` does not yet exist (glossary §6; first-ever `/cowork start`). A tagged line whose tag does not verify is discarded and recorded as the security event `SEC_EVIDENCE_TAG_INVALID`.
2. The daemon (or, before a daemon exists, the CLI's start path) mints or accepts an evidence record **unless** the seat's current turn is wake-originated (glossary §3 turn origin `wake`; S5), the expansion's `prompt` contains a cowork nonce `cws-[0-9a-f]{16}` (the glossary §25 F2 turn-origin rule applied to the expansion, which arrives before the doorbell's UserPromptSubmit), or the hook input marks the prompt as coming from another session or a non-human origin. A UserPromptSubmit never mints evidence (glossary §25 F5).
3. The CLI sends `{verb, args_sha256, tty, ancestry_has_claude}`.
   - `tty` = `process.stdin.isTTY && process.stdout.isTTY`.
   - `ancestry_has_claude` = the CLI found a claude ancestor, or env `CLAUDECODE` is set.
4. The daemon accepts if **either**:
   - (a) `tty` is true and `ancestry_has_claude` is false, meaning a human ran it in their own terminal; **or**
   - (b) an unused evidence record exists with the same `verb` and `args_sha256`, minted from a UserPromptExpansion ≤ 60 s earlier (Δmono via `mono_ns`; glossary §15 "within 60 s", §25 F5) from a seat of this repo. It is marked used (single use); a consumed or expired `evidence.jsonl` line is removed from the file.
   If neither holds, the CLI waits up to 3 s for (b) (polling the daemon or the file; glossary §25 F5), because the `!` line can start while the UserPromptExpansion IPC request is still in flight. Then it refuses with `SEC_REFUSE_NOT_HUMAN`.
5. Confirmation flows use the preview id `--confirm=<id>` (6-hex digest, glossary §15; formula LIF-02): `save`, `recover`, `start --publish` with pre-existing local work, `start --fresh`, `stop --discard-holds`, `uninstall --purge --discard-holds`, `review <id> --accept` (digest of record rev, team blob and disk blob, §3.15 item 3), and (rev 2.5, F10) `revert <cs_id>|last` (digest of the target, the oids of its commits, every result path's disk blob and result blob, and the kept and skipped lists; the write uses the digested disk blobs as expected values, F10 Algorithm REV step 8). The confirming invocation needs its own fresh evidence. A stale id is refused with `PREVIEW_STALE` and a fresh preview (08-lifecycle §2.7).
6. For `pause` and the marker step of `resume` typed in Claude Code, the loader additionally creates or removes the `paused` marker natively on the same UserPromptExpansion (glossary §13, LIF-16), which works with no daemon. That event is itself human evidence for those two verbs.
7. Every accepted acting verb renews the 60-min human lease on the daemon (glossary §15, CCI-50).
8. `/cowork pause` and `/cowork stop` are the only supported ways to stop coordination (glossary §24 default 8). Deleting `<gitdir>/cowork/live` by hand or from a shell command is not one: the daemon re-creates an unexplained-missing marker, records a security event and raises `LIVE_MARKER_RESTORED` (CCI-53), so a Bash `rm` cannot turn the gate off silently.

Read-only verbs (`status`, `queue`, `show`, `doctor`, `log`) need no evidence. (rev 2.5, F04, F10, F12, F14) The same holds for every read-only verb and flag glossary rev 2.5 adds: `since` (F04), `wrap` (F12), `status --flow` (F14) and `show <cs_id>|last --undo` (F10). None of them consumes evidence or renews the human lease (step 7 is for acting verbs only), and none changes a ref, hold record, claim, config or working-tree file (10-product INV-UX-READONLY; the daemon's local F04 `meta.since` marks excepted, §3.11): `wrap` prints its commands for the human to type, and `show --undo` only previews what an acting `/cowork revert` would write.

**SPIKE-0 dependency** (item g, TST-27). Measured (glossary §25 F5; spike 02, 3 runs, `claude -p`, Windows): UserPromptExpansion fires before the `!` line with `prompt_id`, `command_name` and `command_args`; UserPromptSubmit fires only after the `!` line has finished; the `!` line does not pass through PreToolUse(Bash). That settles the original question (UserPromptSubmit cannot carry the evidence) and is why route (b) now uses UserPromptExpansion. Still to measure before route (b) ships: (i) 50 interactive CLI and 50 VS Code trials in which the UserPromptExpansion for `/cowork …` reaches the daemon before the `!` CLI's evidence check (≤ 3 s wait); (ii) that text delivered through the inbox socket (a doorbell or any other session's message) is never expanded as a slash command. If (i) fails, or (ii) shows inbox text can be expanded, route (b) is removed. Acting verbs then work only from a terminal (route (a)); the slash command prints the exact terminal command to run (`node "<plugin root>/dist/cli.js" <verb> …`), and `pause` plus the marker step of `resume` stay available through the loader's native UserPromptExpansion handling (step 6). README and `/cowork doctor` state this.

The claude-ancestor check is hardening, not a boundary (§3.1). The CCI- PreToolUse(Bash|PowerShell) handler also denies command lines that invoke `dist/cli.js` with an acting verb (`SHELL_COWORK_CLI`). That deny is advisory.

### 3.14 Managed policy and delivery detection

Behaviour decides. A static read is advisory, except that a definite hook-disabling policy is enough to freeze.

1. **Behavioural, per seat (CCI-33 computes seat wiring and flags, glossary §3):** hooks observed from the `seat_key`; MCP paired within 3 s (glossary §20 "MCP pairing 3 s"); messaging env present; `permission_mode`; effective `crossSessionInbound`. Any hook from a `seat_key` proves hooks run. The seat is `NO_HOOKS` (CCI-35, 06-claude §3.11.6) when it calls a cowork MCP tool and no hook from its `seat_key` arrives within 10 s (glossary §20 "NO_HOOKS window 10 s"), or when it produces ≥ 3 unmatched edit-class Pre/Post pairs within 10 min (glossary §11, §20). A single unmatched pair only marks the seat `DEGRADED` (seat-scoped, glossary §11).
2. **Static, advisory, at start, SessionStart and doctor:** read only the documented managed-settings locations (`C:\Program Files\ClaudeCode\managed-settings.json`, `/Library/Application Support/ClaudeCode/managed-settings.json`, `/etc/claude-code/managed-settings.json`, plus their `managed-settings.d/` directories) and the user, project and local settings files. Report each hit by setting name and file. No other policy source is assumed.
3. **Mapping:**

| Finding | Effect |
|---|---|

4. **Lifting `NOHOOKS`:** every live seat in the checkout shows hooks again (or has ended), and no static hit remains (glossary §8: "hooks observed again / policy lifted").
5. File changes that no paired seat's hooks reported are human-class edits. The hard boundary B1 still applies to them (K6 human_in_claim).

### 3.15 Execution surfaces, quarantine and review

**Programs cowork may run from the repository:** exactly two kinds. (i) The clean/smudge filter drivers configured in the user's git config (DAT-). (ii) `checks.save` after human approval (CFG-04). `checks.checkpoint` is never executed by cowork; it only matches commands Claude ran (HLD-). Never run: git hooks (empty hooksPath, also in save and doctor worktrees), fsmonitor hook commands, `ext::` transports, custom merge drivers, diff drivers and textconv programs, submodule operations, or LFS (filter=lfs paths are commit-with-git only, DAT-).

**Quarantine set:** exactly glossary §16 (scope class `QUARANTINED`, glossary §3). Behaviour (glossary §16, S8):

1. *Outgoing.* MASK sets `S_pub[p] := A[p]` for every quarantined path, and `P` is built only from `MASK(R)` (glossary §3, INV-MASK), so a quarantined path never differs from `A` in `S_pub` or in `P`; ENG-41(h) asserts it again before every push. The local edit stays on disk, untouched. Quarantined paths are path-class masks, not hold records (glossary §9, HLD-01). Only LIVE paths enter a mirrored hold record (glossary §9): when a change-set that also edits a quarantined path is withheld (K2, K3, K6, K7, B1 PIN, `wake-scope`), the record contains only the CS's LIVE paths, so the quarantined bytes never reach a `held/` entry; a record that would have to include a quarantined path is `local_only` (content-free board stub, glossary §7). The quarantined edit stays on disk under the mask (S8, INV-SECRET). Status lists the path as `quarantine: commit with git`. No claims are taken on quarantined paths (REG-). The CCI- gate passes local edits with one additionalContext line per seat per path saying so.
2. *Incoming.* Changes to quarantined paths reach a peer only through a branch move (a base-move commit, LIF-18) or a non-conforming peer. For each such path p with `¬DISK_EQ(p, X[p])` for the incoming team version X[p], the apply does not write the path. It creates or updates a **review item**: an `INCOMING` hold record with guard `quarantine-review` (glossary §9), a DECISION owned by the local human. p keeps `A[p]` and is a pending path with an INCOMING record, so LA_C can still advance past it (glossary §3 LA_C). The review item MUST NOT hold back the rest of the incoming change: glossary §21 INV-GROUP names incoming quarantined paths (guard `quarantine-review`) as not applicable, so the review item is its own INCOMING record from the start and never defers the other paths of its group (ENG-31, HLD-53, HLD-54; it is not a `DEFERRED` reason). Its board mirror carries no `held/` entries for the quarantined path (glossary §9, only LIVE paths enter a mirrored record; the team version is already on the remote through the branch): the record is `local_only` by the LIVE-only rule, so its board op is the glossary §7 content-free stub (HLD-54, HLD-03; §8 Q7 closed). The path appears in `status.json.pending.not_converged` and in adopt-blocking reasons (glossary §12: an INCOMING path blocks adopt).
3. *Review* (preview/confirm, glossary §15). `/cowork show <id>` (or `/cowork show <path>`, glossary §25.2 item 7) displays the change, rendered in memory from stored blobs; filtered paths in stored form only (UX-12). `/cowork review <id> --accept` (acting verb, SEC-25) first prints the same rendering plus a preview id: the 6-hex digest (LIF-02 formula) of the record's `rev`, the team blob and the **disk blob** (the clean blob of the current disk content, or `ABSENT`). Nothing is written. `/cowork review <id> --accept --confirm=<id6>` (fresh evidence) recomputes the digest from current state; if it differs, it refuses with `PREVIEW_STALE` and prints the fresh preview, so a team version the human never saw is never written. On a match it writes the team version through `writeLocal(path, expectedCleanBlob, newBlob|DELETE)` (ENG-37) with `expectedCleanBlob` = the disk blob digested in the confirmed preview id (`writeLocal` checks it with `DISK_EQ`; a disk change between recompute and write fails the CAS and is reported as `PREVIEW_STALE` with a fresh preview). Before the write, if the digested disk blob differs from `A[p]` (a local edit exists), that local version is recorded as a `PATCH` hold record with `local_only=true` (quarantined content may be sensitive, e.g. `.envrc`), so nothing is lost (INV-NOLOSS). That record is `OFF_DISK` (its bytes leave the disk with this write) and therefore masks nothing: 05-holds MASK step 2 applies only to `ON_DISK` records (INV-HLD-OFFDISK). The write releases the record's `quarantine-review` guard, the one carve-out of HLD-58; the INCOMING record then ends `SUBSUMED` once its path counts as applied (HLD-54). Acceptance applies to this PC only and records a board `event{kind: health, reason_code: SEC_REVIEW_ACCEPTED}` with codes only.
4. *Tools.* No MCP tool may write, restore or accept a quarantined path. `cowork_resolve(id, "restore")` on a record whose paths include a quarantined path refuses with `QUARANTINE_HUMAN_ONLY` (owned by CCI, 06-claude §3.16.3; 07 `R.refused` #12). No claim exists on a quarantined path (item 1), so no request or handoff can carry one.
5. *New symlink (120000) and gitlink (160000) entries* are quarantined when they first appear (glossary §16). Existing ones are `UNMANAGED` (glossary §3, DAT-).

README states that tests Claude runs execute teammates' live code. Live code itself is shared by design. Quarantine protects the *configuration of the tools* (hooks, Claude settings, CI, editor tasks), not the code under test.

It never holds secrets, tokens, the IPC key or environment *values*; `env.passthrough` stores variable *names*. *(rev 2.5, F04)* It also holds the two catch-up switches `since.recap` and `since.claudePointer` (booleans, default true; glossary §29.5, 10-product §3.12). ### 3.18 Runtime integrity and local artefacts

- At daemon spawn, the runtime is copied to `CLAUDE_PLUGIN_DATA/runtime/<version>/` (glossary §6). Every copied file is verified against the plugin's committed `dist/SHA256SUMS` (glossary §6 canonical `dist/` list, REL-02). The daemon runs only from the verified copy. A mismatch refuses with `SEC_REFUSE_RUNTIME_INTEGRITY`. No runtime downloads, `npx` or postinstall exist (REL-03, CCI-02).
- `<gitdir>/cowork/` and `tmp/` are created user-only (POSIX 0700). `tmp/` is never a store (glossary §6). `tmp/evidence.jsonl` holds only evidence records (no prompt text). `tmp/deny-<id>.bin` pre-records (CCI-18) hold working-tree-form plaintext. They are created 0600 and deleted as soon as the blob is written through the clean path (or on start if left over). They are never logged.
- `tmp/stage/<path>` staged copies (glossary §26.1 W1) also hold **working-tree-form plaintext**, before any clean filter, so they are as sensitive as the user's files. The snapshot reads the user file with one short read (open share-all, read, close; glossary §26.1 W1, W3), writes the copy user-only (0600 / user-only ACL), hashes it with `--path=<p>` and deletes it when that hash (or, for a ready-pair capture, publish, apply or hold record, the object write) completes — objects are written only for those four (glossary §26.1 W6), and a hook-driven request for named paths gets ids and in-memory bytes without `-w`; a leftover `tmp/stage/` is emptied at daemon start. `<path>` is built only from a repo-relative path that passes the syntactic part of `validPath` (SEC-35), and the copy is created inside the daemon-created `tmp/stage/` tree without following symlinks in any component, so a crafted path or a planted link can never make the daemon write outside `tmp/stage/`. Staged copies are never logged, never a store and never pushed.
- `log/*.jsonl` lines never contain file content, diff text, tool_input, prompt text, notes, tokens, keys or environment values (SEC-38).

## 4. Rules

### Git runner and environment

- **SEC-01** cowork-sync MUST make network connections only via `runGit` network-class calls, to the destinations in the egress list (§3.2). The build MUST fail (TST- lint, esbuild metafile) if any `dist/*.js` imports `http`, `https`, `http2`, `tls`, `dgram` or `dns`, or contains a URL literal outside the documentation allowlist. No telemetry, crash report, update check or analytics endpoint may exist. _Covers: board-plaintext-and-permanence, supply-chain-versions_
- **SEC-02** Every git process MUST be started by `runGit` with the glossary §18 arguments (which since rev 2 include `-c submodule.recurse=false` on every call and `--no-ext-diff --no-textconv` on every diff-family command, the family being `diff`, `diff-tree`, `diff-index`, `diff-files`, `log -p`, `show`, `blame`, §2) plus the remaining network-safety arg `--no-recurse-submodules` on every fetch. _Covers: synced-execution-surfaces, fetch-head-hijack-and-auto-maintenance_
- **SEC-03** `runGit` MUST set `GIT_AUTHOR_NAME`/`GIT_COMMITTER_NAME` to the display name, `GIT_AUTHOR_EMAIL`/`GIT_COMMITTER_EMAIL` to `<peer_id>@cowork.invalid`, and `GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE` with a `+0000` offset on every live code and board commit. The user's `user.email` and local timezone never reach a cowork ref. _Covers: board-plaintext-and-permanence_
- **SEC-04** `runGit` MUST classify results only by exit code and structured output (`--porcelain`, `-z`, curl trace HTTP status lines). A push rejection MUST be classified by outcome (glossary §26.2 item 2; §3.9): fetch; leased ref moved → lease loss, retry in the next window; ref unchanged and our op ids absent → transient, retry in the next window with backoff; the third consecutive rejection of the same publish with the ref unchanged → NON-RETRYABLE. Rejection text (`cannot lock ref …`, `(failed)`, `fatal error in commit_refs`, `GH013`) MUST NOT select among these outcomes. Message text MAY only (a) choose the explanation shown or (b) make handling stricter (for example `local_only`, SEC-17). It MUST NOT cause a retry, a publish or a lifted pause. (Changed in rev 2.3: the former structural "board unchanged → NON-RETRYABLE after one attempt" reading is replaced by the outcome rule.) A fetch that fails twice in a row while `ls-remote <pinned URL>` succeeds (for example an fsck failure) MUST surface code `SEC_FETCH_REJECTED_OBJECT` with sanitized stderr in doctor, under the ordinary `OFFLINE` publish pause. _Covers: path-quoting-and-git-locale, push-rejection-poisons-chain, hung-network-git-after-sleep_
- **SEC-05** The daemon and every git, filter and check process it starts MUST receive DAEMON_ENV (§3.4), built from the allowlist and never-list and fixed at spawn; the daemon itself MUST be spawned with that explicit environment object, never with the spawning hook's inherited environment (which carries the messaging token, glossary §26.2 item 6). Every git command that may run a filter MUST run with cwd = the repository root (glossary §25 F12), and DAEMON_ENV MUST keep the PATH entries the configured filter drivers need, resolved at start and shown in doctor (glossary §25 F12). `runGit` MUST append the BatchMode options to the effective ssh command (`-batch` for the plink variants, nothing for `simple`) and never replace it. `/cowork start` and doctor MUST run `git ls-remote --exit-code <pinned URL> refs/heads/<b>` and the DAT- filter preflight in a child built by the same builder; the preflight MUST run in the real work tree and compare only through DISK_EQ-safe forms (§3.4; glossary §25 F12, §26.2 item 3). Failure refuses start with `SEC_REFUSE_ENV_AUTH` or the DAT- code, naming the missing tool or variable and the `env.passthrough` line that would fix it. _Covers: secret-filter-fails-open-in-daemon-env, offline-auth-claims, filter-passthrough-leak_
- **SEC-06** Names on the never-list MUST be dropped even when listed in `env.passthrough`. Doctor MUST warn about any such entry. _Covers: secret-filter-fails-open-in-daemon-env_

### Secrets and what leaves the machine

- **SEC-07** Before every push attempt (live code, board, displaced ref; including each retry after a lease loss or a transient rejection, glossary §26.2 item 2) and again after every rejection (§3.9), the daemon MUST run `scanSecrets` (D1 + D2 + D3, §3.6) on every blob the push would add: blobs changed in `diff-tree -r -z --no-renames TIP OUT`, new `held/` blobs and the new `ops.jsonl`. A hit MUST abort that push attempt before any network call, without spending a governor attempt. The CS(s) owning the path become a `PIN` hold with `local_only=true` and guard `{name: "secret-scan", class: DECISION, owner: "human"}`, keeping INV-GROUP (HLD- registry semantics). A hit in a `held/` blob makes that hold record `local_only` instead of mirrored. The human (status, OS notification) and the owning seat's Claude MUST be told the path, line number and detector name only, never the matched text (Claude: `NOT_SHARED` with reason `secret-scan`, 07 `T-LOCAL_ONLY`). Only LIVE paths of the CS enter the record (glossary §9). _Covers: splice-text-from-worktree-leaks-secret, peer-normalization-secret-leak, secret-filter-passthrough, filter-passthrough-leak, board-plaintext-and-permanence_
- **SEC-08** Every free-text field before publication (notes from `cowork_note`, `cowork_request`, `cowork_respond`; the save commit summary) MUST pass `scanSecrets` with `ctx.kind` `note` or `commit_message`. A hit refuses the call: an MCP-tool note with `NOTE_SECRET_HIT` (COO-19, tool result), a save summary with `SEC_SUMMARY_SECRET_HIT` (CLI). The text is never silently trimmed. (Changed in rev 2.3: the former `SEC_NOTE_REFUSED_SECRET` is removed, dropped in favour of `NOTE_SECRET_HIT`, glossary §25.2 item 3.) (rev 2.5, F12) The suggested summary draft of 10-product §3.20 (shown by `/cowork wrap` and in the `/cowork save` preview; displayed, never published or written) MUST pass `scanSecrets` with `ctx.kind` `commit_message` before display, its headline and each bullet separately. A hit is not a refusal: it drops that bullet, or replaces the headline with the placeholder-free `UI_DRAFT_HEADLINE_PLAIN`, and is counted in `UI_DRAFT_DROPPED` (never the text), so nothing is left out silently. The summary the human then types is scanned and refused as above. _Covers: board-plaintext-and-permanence_
- **SEC-09** Every board op MUST be serialized by one serializer that validates the glossary §7 schema with per-field maximum lengths and rejects (security event `SEC_BOARD_FIELD_REJECTED`) any string matching an absolute path, a transcript path, this machine's OS user name or host name (all fields except `display`), or a `scanSecrets` hit. Code content MUST appear only as blob ids from the pinned clean path; `hash-object --stdin` without `--path`, raw tool_input and prompt text are forbidden (TST- lint). _Covers: board-plaintext-and-permanence, splice-text-from-worktree-leaks-secret_
- **SEC-10** README (every language, anchor `safety-and-permanence`), the first-run screen of `/cowork start`, and doctor MUST state that everything under `refs/cowork/*` is readable by everyone with repo read access, is kept by the host practically permanently including after resets, and that the remedy for a leaked secret is rotation. README anchor `what-leaves-your-machine` MUST reproduce the §3.2 egress list. _Covers: board-plaintext-and-permanence_

### Local IPC and token custody

- **SEC-20** The IPC key MUST be 32 random bytes in `CLAUDE_PLUGIN_DATA/ipc.key`, created user-only (POSIX 0600 with owner check; Windows `icacls /inheritance:r /grant:r *<SID>:F`) and verified by SID through SDDL, never by account name. Any ACE other than the user SID, `S-1-5-18` or `S-1-5-32-544` MUST refuse start (`SEC_REFUSE_IPC_ACL`). A cowork process whose environment lacks `CLAUDE_PLUGIN_DATA` (measured absent for a project MCP server, glossary §25 F3) MUST derive the data directory from the plugin id and MUST apply the same owner and ACL verification before reading the key; it MUST NOT fall back to any other key location. _Covers: ipc-pipe-exposure_
- **SEC-21** The endpoint name MUST be derived from `HMAC-SHA256(key, "endpoint:" ‖ root)` per §3.11, where `root` is the canonical repo root form of the common gitdir (glossary §24 default 12: `fs.realpathSync.native`, lower-case drive letter, `/`, NFC, lower-cased on Windows and macOS), computed identically by the daemon, loader, core and MCP server. POSIX sockets MUST live in a lstat-verified 0700 directory owned by the uid. A full socket path over 100 bytes for every candidate directory MUST refuse start (`SEC_REFUSE_SOCKET_PATH`). On `EADDRINUSE` the daemon MUST run the handshake as a client: a pass means reuse, a failure means refuse with `SEC_REFUSE_IPC_SQUATTER` plus a security event and one OS notification. _Covers: ipc-pipe-exposure_
- **SEC-22** Every connection MUST complete the mutual HMAC handshake of §3.11 before any other byte: the server sends nothing before `hello`, and the client sends no session data before verifying `srv`. Proofs MUST be compared with `crypto.timingSafeEqual`. Frames MUST be newline-delimited JSON ≤ 1 MiB and schema-validated; an unknown type or invalid frame closes the connection. Every failed handshake MUST be logged as `SEC_IPC_HANDSHAKE_FAILED`; five or more in 60 s MUST raise at most one OS notification per 30 min (10 `NT_SECURITY`). _Covers: ipc-pipe-exposure_
- **SEC-23** No IPC request may execute a command supplied in the request, touch a path outside the main-worktree realpath, or return tokens, the key or environment values. Every 30 s the daemon MUST check that `ipc.key` still exists with the same hash, that the plugin is enabled and that its `runtime/<version>/` copy is intact (CCI-53). If any check fails, it runs the LIF-36 removal sequence and exits. _Covers: ipc-pipe-exposure, uninstall-deletes-state-daemon-orphaned, orphan-daemon-uninstall_
- **SEC-24** `CLAUDE_CODE_MESSAGING_TOKEN` MUST be read only by `dist/mcp.js` from its own environment and held only in memory (glossary §26.2 item 6: the host also puts it in every hook's environment, so this is a rule about cowork's code, not about where the variable exists). `mcp.js` MUST write it only in the `{"type":"auth","token":T}` frame on its own session's inbox socket (glossary §25 F1). It MUST NOT appear in IPC frames, files, logs or hook output. The hook loader, `core.js`, the CLI and the daemon MUST NOT read it; the daemon and every child of the CLI MUST get an environment from the §3.4 builder, which drops `CLAUDE_*`. The daemon MUST have no code path that opens an inbox socket. Pairing uses `SHA-256(CLAUDE_CODE_MESSAGING_SOCKET)` over authenticated IPC only. A TST- lint MUST fail on any reference to `CLAUDE_CODE_MESSAGING_TOKEN` outside `mcp.js`. A seat whose MCP server lacks the messaging socket (glossary §25 F3), or with effective `crossSessionInbound` of hold or refuse, or `--bare`, MUST be `HOOK_ONLY` and published as such in a board `health` event. _Covers: inbox-delivery-disabled-by-mode-or-settings, ipc-pipe-exposure_

### Human-only verbs

- **SEC-25** The daemon MUST execute an acting verb (§2) only with human evidence per §3.13: (a) the CLI reports a TTY on stdin and stdout and no claude ancestor and no `CLAUDECODE` env; or (b) an unused evidence record with identical `verb` and `args_sha256` (SHA-256 of `args_norm`), minted ≤ 60 s earlier (Δmono) from a **UserPromptExpansion** of a seat of this repo with `expansion_type` `slash_command`, `command_name` `cowork` or `cowork-sync:cowork`, and the `prompt_id` and normalised `command_args` the record carries (glossary §25 F5), consumed on use. The CLI MUST wait up to 3 s for (b) before refusing with `SEC_REFUSE_NOT_HUMAN`. Evidence MUST NOT be minted from a UserPromptSubmit (it fires only after the `!` line has finished; waiting on it would deadlock, glossary §25 F5), for wake-originated turns, for an expansion whose `prompt` carries a cowork nonce (glossary §25 F2), or for prompts marked as originating from another session. If the SPIKE-0 interactive trials (TST-) show the expansion does not reach the daemon before the `!` CLI's 3 s wait, or show that inbox-delivered text can be expanded as a slash command, route (b) MUST be removed (terminal-only, §3.13). (Changed in rev 2.3: the source was UserPromptSubmit with a character-0 prefix test.) _Covers: model-invocable-save_
- **SEC-26** The hook loader MUST forward evidence to the daemon only from a UserPromptExpansion that qualifies under SEC-25, and then only as `{prompt_id, verb, args_sha256}` where `args_sha256 = SHA-256(args_norm)` (§2 evidence record; the glossary §25 F5 field `command_args` is carried in this hashed form). ### Untrusted strings

- **SEC-34** Every string originating from the board, a peer, a commit message, a path or a host error MUST pass `sanitize(text, channel)` before display or logging. `sanitize` MUST:
  - apply NFC;
  - strip C0/C1 controls (keeping `\n` only in channel `claude`), ANSI CSI and OSC sequences (including OSC 8 and OSC 52), bidi controls U+061C, U+202A–U+202E, U+2066–U+2069, zero-width and format characters U+200B–U+200F, U+2060–U+2064, U+FEFF, and Unicode tag characters U+E0000–U+E007F;
  - replace `<` and `>` with U+FF1C and U+FF1E;
  - remove leading `/` command tokens at the start of any line, and replace URLs with `[link removed]`;
  - in the `note`, name, label and path placeholders (glossary §19 caps), replace every line break (`\n`, `\r`, U+0085, U+2028, U+2029) with one space, and replace every run of three or more dash-like characters (U+002D, U+2010–U+2015, U+2212, U+FE58, U+FE63, U+FF0D) with one `—`, so that teammate text can never close the COO- `T-NOTE` block early or start a line that looks like a cowork-sync line outside it (07-coordination §3.16 template delimiters are `---` lines);
  - truncate each placeholder to its glossary §19 cap (names 20 rendered / 64 raw, label 80, path 80, note 280), never truncating a whole rendered template.

  Teammate free text MUST appear only inside the COO- data-not-instructions block and never in a deny reason (`permissionDecisionReason` or stderr).

  (rev 2.5, F12) **Paste-safe pass.** The suggested summary draft of 10-product §3.20 exists to be copied by the human into `/cowork save "<summary>"`, whose `!` line hands `$ARGUMENTS` to a shell; `sanitize` does not neutralise shell syntax, and display names and labels are teammate-controlled (`validLabel` admits `$`, `(` and `)`). Every draft placeholder (the `wrap` draft section, the save preview's draft and `--json` `data.draft`) MUST therefore, after `sanitize` and its type cap, have `"`, `` ` ``, `$`, `\` and `!` replaced by their full-width forms U+FF02, U+FF40, U+FF04, U+FF3C and U+FF01, so a pasted draft line holds nothing a POSIX shell or PowerShell expands inside double quotes. No `UI_DRAFT_*` template in any of the six catalogs MAY contain one of these five characters (I18N-07 lint). The draft MUST never fill a `{cmd}` placeholder (FEAT-F12-10). The pass applies to the draft only; other output keeps the plain `sanitize` result.

  _Covers: teammate-text-as-instructions, phrasing-blame-and-peer-text-injection_
- **SEC-35** The fold (PRO-) and all renderers MUST use these deterministic validators. A record failing `validPath` or `validId` is a deterministic no-op, logged as `SEC_RECORD_INVALID`; names and labels are cleaned at render instead.
  - `validPath(p, tree)`: syntactic part: repo-relative POSIX, NFC, no `..` segment, no leading `/`, no drive letter, no `:`, no `\`, no NUL, ≤ 4,096 bytes. The syntactic part is a separate, tree-independent predicate `validPathSyntax(p)` that MUST be evaluable on the path string alone; 03-data uses it alone to classify tracked paths as `UNMANAGED` (`portability`), and the staged-copy path (§3.18) uses it alone. Tree part (never local disk), by op type: `claim` — present in the tree of the op's `anchor` (or of a tombstone anchor); `hold` of a non-`local_only` record — present under `held/<hold_id>/<stage>/` for at least one stage in the board tree that carries the op (so a PATCH for a path TIP deleted still passes through its `h0`/`h1` entry); `hold` stub of a `local_only` record — syntactic part only (a stub carries no bytes and is never a write source); `request` — one of the `paths` of the folded hold record `req_id`.
  - A tracked path (in `EPOCH_BASE` or arriving with a branch move) that fails the syntactic part is a board-unrepresentable path (§2): DAT- MUST give it scope class `UNMANAGED` with not-shared reason `portability` at start and at every `EPOCH_BASE` change, so no claim or hold op ever names it and no hold-op rejection loop can start (PRO-24 `HOLD_MIRROR_REJECTED` remains the backstop).
  - `validId`: the glossary §2/§7 formats (op id `<32 hex>/<epoch>/<seq>`, ULID, `cs_id` forms, 6-hex preview ids).
  - `validName`: `[\p{L}\p{M}\p{N}_ .'-]{1,64}`; otherwise rendered as `peer-<first 6 of peer_id>`.
  - `validLabel`: `[\p{L}\p{M}\p{N}_.:#<>,$@\[\]()-]{1,200}` (identifier-like, no whitespace; REG- `label-convention/1` names such as `Outer.Inner.m` and the normalized `disc` `(int,string)` pass, and a rare label with whitespace, such as some C# operator names, is shown as `?`), applied to each label field; otherwise rendered as `?`. Labels reach deny reasons, PostToolUse block reasons and Stop blocks as `{sym}` without the data-not-instructions framing (06-claude §3.6.5), so a board label MUST NOT be able to read as a sentence.
  - Renderers apply `validLabel` to the label returned by REG- `verifyLabel` (REG-34): a received label that does not re-derive from its claim's anchor blob and ranges is rendered as `?`, and the mismatch is written to `log/security.jsonl` with ids only (op id, `claim_id`, anchor oid, path) and no label text; the line uses the existing code `SEC_RECORD_INVALID` with field `label` and validator `verifyLabel` (no new message code). Unlike a `validPath`/`validId` failure, the record still folds; only its label is replaced at render.

  _Covers: teammate-text-as-instructions, ref-rewind-silent-revert_

## 5. Invariants

**Glossary invariants enforced here:** INV-SECRET as worded in glossary §21 rev 2.1 — no blob from an unfiltered or failed-filter path, no `local_only` path, no secret-scanner hit, no quarantined path's local bytes (S8) and no restore-marker blob ever reaches a remote ref (SEC-05, SEC-07, SEC-08, SEC-09, SEC-17, SEC-31, SEC-37 for staged plaintext copies, SEC-38; DAT- for filters and restore markers; HLD- for the LIVE-only record rule of glossary §9), INV-OID (egress list E4 is the only deletion), INV-CLOCK (SEC-18, SEC-19, SEC-25 Δmono windows), INV-MASK (SEC-31 quarantine membership), INV-NOLOSS (SEC-07 secret holds are registry records; SEC-33 preserves the local version before review accept), INV-GROUP (SEC-32: an incoming quarantined path is not applicable and never defers its group), INV-NOSILENT (every refusal, freeze and secret hold has a status code and a seat-visible template).

**Chapter-local invariants:**

| Id | Statement |
|---|---|
| **INV-EGRESS** | The only network connections cowork makes are the egress list E1–E7, made through git. `dist/*.js` contains no HTTP, TLS, DNS or UDP client module and no non-documentation URL. |
| **INV-NOEXEC** | No repository-controlled program runs during sync, save or doctor except the user-configured clean/smudge filters and a human-approved `checks.save`. |
| **INV-URL** | Every fetch and push targets the pinned URL. A config change that would redirect them produces zero transfers to any target until a human lifts `CONFIG(url)` after doctor passes. |
| **INV-IPC** | An unauthenticated client receives 0 bytes, and a client sends 0 session bytes to an unauthenticated server. |
| **INV-TOKEN** | No cowork process other than `dist/mcp.js` reads, stores, logs or forwards `CLAUDE_CODE_MESSAGING_TOKEN`; `mcp.js` holds it only in memory and writes it only in the auth frame on its own session's inbox socket. (Changed in rev 2.3, glossary §26.2 item 6: the host places the token in every hook's environment, so the former "exists only in the MCP server's memory" could not hold.) |
| **INV-HUMANONLY** | Every acting verb takes effect only with SEC-25 evidence, and each evidence record authorises at most one invocation. |
| **INV-QUARANTINE** | No quarantined path is ever in `paths(diff(A, S_pub))` or in a mirrored hold record, and no incoming quarantined change is written to disk without that PC's human `/cowork review <id> --accept --confirm=<id6>` whose preview id digests the written team blob. |
| **INV-CONFIG-SOURCE** | Every config value used by a decision was read from a blob at this peer's `EPOCH_BASE`, or is the last valid such value, or is a built-in default. |
| **INV-SANITIZE** | No string from the board, a peer, a commit message or a host error is displayed or logged without `sanitize`. No path from the board is used for a disk write without `validPath` and a validated live tree. |
