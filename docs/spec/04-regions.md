This chapter turns bytes into regions and regions into verdicts. It never turns a region back into bytes. Everything defined here is a set of pure, deterministic functions that the daemon, the hook-facing gate, the board fold and T0 call. Every output is a verdict: line ranges, labels, booleans, claim ids, CS ids or path lists.

Principles used throughout (cited as [Pn]):

- **P1** No region logic can produce, drop or move a byte.
- **P2** Every uncertain case degrades to a larger claim or to the conflict path, never to "no conflict".
- **P3** One parser, one line mapper, one touch predicate, one claim shape.
- **P4** Unsupported files get whole-file or block claims instead of clever handling.
- **P5** No clock anywhere in region identity or in the fold (glossary INV-CLOCK).
- **P6** Every rule cites the region harness evidence (sweep/region, rc_* experiments) or a failure finding.

## 1. Scope

### 1.1 v1 in scope

- Symbol-level region tables for **Python, JavaScript, TypeScript, TSX and C#**, built by one pinned web-tree-sitter 0.27.x WASM runtime with cowork's own query files (upstream `tags.scm` misses C# constructors, properties, structs and records).
- Pseudo-symbols: class/type residue, module-level `const:NAME` assignments, top-level gap blocks, and the never-claimed `<imports>` region.
- Grammarless text: whole file when ≤ 300 lines, blank-line blocks when longer (glossary §20). Non-UTF-8 text is split on raw `0x0A` bytes.
- Whole-file claims for binary paths, `.ipynb`, paths with a (non-LFS) `filter=` or `working-tree-encoding` attribute, and any blob containing conflict-marker lines. Symlinks, submodules and LFS paths are never `LIVE` and take no claim (REG-32).
- Line-tracked claims: an anchor live code commit plus stored-form 1-based inclusive line ranges, moved between versions by one bundled Myers line mapper with EOL/BOM-insensitive line equality. Deleted claimed ranges become tombstones.
- One touch predicate used by PreToolUse prediction, the B1 publish gate, the post-merge placement check and holder-side breach detection; one range-overlap function used by the board fold.
- The group-name addition rule for C# and TypeScript overload sets, including C# partial types found by `git grep` on the private index.
- The API set `regionTable`, `hunks`, `mapRanges`, `touch` (with its containment form `contained`), `predict`, `confirm`, `computeClaims`, `gate`, `placementCheck`, `claimPrecheck`, `foldOverlap`, `breach`, `regionTripwire`, `interfaceCheck`, `verifyLabel`, `editCheck` (section 3.1), all taking `(base, ours, out)`-style tree arguments.
- The relative region tripwires and the interface/caller/callee/import checks that T0 (HLD-50) consumes.
- *(added in rev 2.4; glossary §27.1)* The **edit check** behind S1 (rev 2.4): `editCheck(A, R, TIP, cs)`, one entry point that runs the four structural checks of glossary §27.1 on the CS's candidate capture by calling `regionTripwire` and `interfaceCheck` (plus a size comparison), within ≤ 0.5 s, and returns pass/fail only. A pass lets 05-holds/01-engine keep the candidate as the CS's ready pair; a fail creates nothing (3.20, REG-36). *(rev 2.5, F14, F12; D1)* Each failed entry names its check (none for the non-check reasons `no_snapshot`, `merge_conflict`, `no_merge`) and, for checks 1–3, the row of the merged tree where the failure starts; 05-holds keeps the last failing result in daemon memory as `last_check`, which only the output of a `/cowork status --flow` or `/cowork wrap` run displays, slash or terminal, and which is never pushed (3.20; glossary §29.1 D1).
- *(added in rev 2.1)* The own-claim containment verdict behind part (b) of the S5 **wake work set** ("regions inside this seat's own claims"), consumed by the wake-turn gate check (CCI-38) and by the `wake-scope` guard at PostToolUse/TXN close (glossary S5, §9; REG-33).
- *(added in rev 2.1)* Receiver-side label verification: a claim label received from another peer is rendered only after this daemon re-derives it from the claim's anchor blob and ranges, otherwise as `?` (REG-34; owner follow-up 3 of the 09-security pass-1 fix).
- Claims exist only on paths of scope class `LIVE` (glossary §3 "scope class"; REG-32). Every other class is reset to `A[p]` by MASK and never published live, so it takes no claim.
- *(added in rev 2.3; glossary §26 W1, W3, W6)* The read contract for region inputs: stored blobs are read only by oids the engine has written into the object store, and working bytes arrive only as a `diskSnapshotId` taken from one short, stable read by the daemon. The region module never opens a user's working file, never runs git on one and never reads a snapshot-tick oid through `cat-file` (section 2 "diskSnapshotId", 3.1, REG-35).

### 1.3 Deferred (glossary §22; MUST NOT be implemented or described as v1 behaviour)

- Sub-block claims inside long units (§22 "Sub-block claims, rename aliases, file:line attribution"): v1 claims the whole unit at any length.
- Rename aliases (§22): a rename is a removal plus an addition; the caller check (REG-27) catches references to the removed name.
- Fork detector / possible-fork note (§22 "Fork detector"): replaced by the standing RULES text (COO-) and the dependency bundle (HLD-).
- Notebook cell-level claims (§22): whole-file claims for `.ipynb`.
- Claude-facing templates in zh-CN, ja, fr, es (§22): this chapter's Claude-facing codes ship in `en` and `ko` only (1.2).
- Not in §22 but out of v1 by this chapter: type-aware caller resolution (LSP), statement-level claims below the blank-line block, YAML key-path checks, C# `using`/namespace import resolution, compiler-backed C# partial-type index, human-held claims (humans take no claims in v1, COO-09). Each is covered in v1 by a coarser rule cited in the relevant section.

## 3. Design

### 3.1 Module boundary and API

The region module is a library loaded by the daemon. Parsing, mapping and the interface check run only in the daemon's `worker_threads` pool; the main thread reads cached tables and line arrays. It imports no filesystem write API and no git command that writes objects or refs (REG-02 lint). It reads blobs through the daemon's `cat-file --batch` reader and the private index (ENG-), and attributes at `EPOCH_BASE` through `runGit` with `attr.tree` (glossary §18). *(rev 2.3; glossary §26 W6)* Through `cat-file` it reads only oids that are in the object store: blobs of the live chain and the board (anchors, TIP, `A[p]`), ready-pair captures, publish trees (P, OUT), the trees an apply merges, and hold-record blobs (§26 W6: objects are written only for ready-pair captures, publishes, applies and hold records). Every other working content (the current disk at `predict` and `confirm`, a seat's pre-image or view blob when its object was not written) reaches the module only as a `diskSnapshotId` (section 2) and is read from its in-memory bytes. The module never opens a user's working file and never runs git on one (§26 W1).

Signatures (tree arguments are tree oids or in-memory tree views; `p` is a repo-relative POSIX NFC path; ranges are `[[lo,hi],…]`):

```

    blobRef = stored blob oid | diskSnapshotId (working bytes held by the daemon; section 2,
              rev 2.3: its oid is not read through cat-file, glossary §26 W6)

                   errorCount, labelCounts:{labelKey: n}}

    1-based; a pure insertion after base line k has aLo = k+1, aHi = k;
    a pure deletion has bHi = bLo-1.

mapRanges(fromBlob, toBlob, ranges, mode: fold|local) -> ranges | TOMBSTONE | WHOLE_FILE

touch(hunk, claim, claimRangesInBase | WHOLE_FILE, postTable | NO_TABLE, ctx)
    -> {touch: bool, reason: base-overlap | insert-inside | boundary-in-extent |
        boundary-in-error | boundary-no-table | group-name | degraded-whole-file | none}

    -> bool     (added rev 2.1: containment form of `touch`, 3.6; S5 wake work set part (b))

    not stable (rev 2.3, glossary §26 W1/W3; Algorithm PREDICT step 1)
    -> {status: located | locate_failed | undecided, diskLines:[[lo,hi]], hunksInBase:[Hunk],
        touches:[{claim_id, reason}], moved?:{fromLabel, toLabel | TOMBSTONE}, fallbackUsed,
        ownTouches:[{claim_id, suspect: bool, granted: bool}],
        ownContained: bool}

    `contained` in this seat's wake-turn own-claim set (3.6 "Containment form"); false on
    locate_failed, undecided or fallbackUsed (a whole-file prediction is contained only in an
    own `granularity: file` claim on p)

confirm(seat, cs_id, p, preBlob, postBlob, A[p], claimView)
    preBlob, postBlob = blobRefs; postBlob is a diskSnapshotId from a stable read
    (rev 2.3, glossary §26 W1/W2; Algorithm CONFIRM step 1)
    -> {hunksInBase:[Hunk], touches:[{claim_id, holder, reason}], drafts:[ClaimDraft],
        notOwnContained:[Hunk]}
    notOwnContained added rev 2.1: the hunks not `contained` in this seat's wake-turn own-claim
    set (3.6 "Containment form"); computed only for a CS of a wake turn; input of the
    `wake-scope` guard (glossary S5, §9)

verifyLabel(claimOp) -> label | "?"     (added rev 2.1, REG-34; display only)

computeClaims(seat, p, drafts, anchorTip) -> {publish:[claimOp], localOnly:[ClaimDraft]}

    -> {blocked:[{cs_id, claim_id, holder, path, reason}], admitted:[{cs_id, claim_id, path}]}
    R = the rebased ready trees of the ready groups (glossary §3 "ready pair"); base A = A_cap,
    equal at publish time by the HLD-41 rebase (HLD-42, ENG- pipeline step 1 assert)

placementCheck(base, ours, theirs, out, gateResult?, claimView?) -> [{path, reason}]
    publish: (A, P, TIP, OUT); apply: (A, S_disk, TIP, M_disk);
    base move (ENG- §3.13 case iii): (tree(B), tree(TIP), tree(Hr), newtree)
    `identityCheck` (the name some chapters, e.g. ENG-29, still use) is an alias of this function;
    it is the same function (sub-check (a) only on apply and base move, (a)+(b) on publish)

claimPrecheck(pendingClaimOps, foldState@leasedTip) -> [{claim_id, cs_id, overlaps: claim_id}]

foldOverlap(C1, C2, readBlob) -> bool         (pure; used by the PRO- fold)

breach(commits (LA_C, TIP], ownHeldClaims) -> [{claim_id, holder, commit, path, base_move: bool}]

regionTripwire(theirs[p], ours[p], out[p]) -> [violation]

interfaceCheck(base, ours, out, cs) -> {breaking:[…], incompatibleCallers:[…], orphanCalls:[…],
                                       unresolvedImports:[…], notes:[…], incomplete: bool,
                                       symbolDelta:{added[], signatureChanged[]},
                                       referencedNames:{identifiers[], imports[]}}
    symbolDelta / referencedNames: added rev 2 for HLD-48/49 (05-holds §8 Q2 default), computed
    from the same worker parse and cache; verdict data only (REG-02)

editCheck(A, R, TIP, cs) -> {pass: bool, failed:[{check?: 1|2|3|4, path, reason, line?}],
                             incomplete: bool, elapsedMs}
    added rev 2.4 (glossary §27.1; section 3.20, REG-36). A = A_cap of the candidate capture,
    R = the candidate ready tree taken at this edit checkpoint, TIP = the board tip of A's apply;
    cs = {cs_id, paths (the CS's LIVE paths), merged: M (per path of cs.paths, the
    `merge-tree --merge-base=A R TIP` result as a blobRef, supplied by 01-engine, or
    `absent` / `conflicted`)}. Calls regionTripwire and interfaceCheck; verdict only, no claim
    input, no record, no message; pass = all four checks pass and incomplete = false
    rev 2.5 (F14): `line` = the 1-based stored-form row of M' (M[p] on the checked paths, TIP
    elsewhere) where the first offending node, call or reference of a check 1-3 entry starts;
    `path` = the file of M' holding that row (3.20 "Failed entries"); display data only.
    rev 2.5 (F12): an entry whose reason is `no_snapshot`, `merge_conflict` or `no_merge`
    carries no `check`. The caller keeps the last failing result in daemon memory as
    05-holds' `last_check`, which is not a record or message (3.20; D1)
```

### 3.2 Coordinates and text handling

1. A file's lines are split on byte `0x0A` only. Never on U+2028/2029, never with `splitlines`.
2. Tree-sitter results are read only through `startPosition.row` / `endPosition.row`. One line-table helper converts rows of a single in-memory Buffer; `startIndex`, `endIndex` and any byte, character or UTF-16 offset are forbidden anywhere else (CI lint).
3. Text decoding is read-only: `TextDecoder('utf-8', {fatal: true, ignoreBOM: true})`. A decode failure marks the blob `decodable: false`. The module never encodes text back to bytes.
4. BOM stripping, CRLF→LF and folding of U+2018/2019/201C/201D to ASCII quotes are allowed only inside `predict` to locate `old_string`, and the result is converted to line numbers at once. None of these changes the count of `0x0A` bytes, so line numbers in the normalized view equal disk rows.
5. Disk rows and stored rows of the same version have equal counts: canon (DAT-05) changes only line endings and a leading BOM. The mapper's equality (3.4) makes the two forms produce zero hunks.
6. *(added in rev 2.3; glossary §26.2 item 3)* The mapper's EOL/BOM-insensitive equality decides hunks and images only. Whether a path's disk content equals a blob is never decided by the region module: that test is always glossary §3 DISK_EQ, and never `hash-object --path` of a working file compared with a blob id (it misreports `i/crlf` files, §26.2 item 3). A region verdict of "zero hunks" therefore never stands in for a disk-equality answer.

Why: VERIFIED offset-units-form-drift (splice offsets in the wrong unit system corrupted files); VERIFIED daemon-text-handling-corrupts-cp949-bom (string round-trips corrupt cp949 and strip BOMs); VERIFIED rc_touch R1 (identical rows and labels for the BOM+CRLF working bytes and the LF stored bytes, 432 units).

### 3.3 Region tables

**Runtime.** `web-tree-sitter` 0.27.x and the grammars `tree-sitter-python`, `-javascript`, `-typescript`, `-tsx`, `-c_sharp` (pinned versions, `.wasm`) plus cowork's query files ship in `dist/` and are copied to `CLAUDE_PLUGIN_DATA/runtime/<version>/` (glossary §6). Language selection is by extension: `.py .pyi` → python; `.js .mjs .cjs .jsx` → javascript; `.ts .mts .cts` → typescript; `.tsx` → tsx; `.cs` → c_sharp. No other parser (Python `ast`, ctags, regex) may supply ranges that are published or used by `gate`, `placementCheck`, `breach` or the fold. The regex fallback of REG-28 serves the PreToolUse decision only.

**Path classes** (first match wins; applied only to paths of scope class `LIVE`, REG-32):

| # | Condition (attributes read at `EPOCH_BASE`, DAT-13) | Table | Claim granularity |
|---|---|---|---|
| 1 | Blob has a conflict-marker line: `^(<{7} \|={7}$\|>{7} \|\|{7} )` after stripping one trailing CR (the ENG-41(e) detector) | `NO_TABLE{conflict_markers}` | `file` |
| 2 | Binary (DAT-04): NUL in the first 8,000 bytes, or `-text`/`binary` attribute | `NO_TABLE{binary}` | `file` |

| 4 | Pinned grammar and `decodable` | symbol table | `symbol` / `block` (3.3 units) |
| 5 | Otherwise (no grammar, or grammar but not UTF-8), ≤ 300 lines | `NO_TABLE{grammarless_small}` | `file` |
| 6 | Otherwise, > 300 lines | block table | `block` (blank-line blocks; raw `0x0A` split when not UTF-8) |

Row 3 is defensive: `120000`/`160000` entries and `filter=lfs` paths are never `LIVE` (existing entries and LFS are `UNMANAGED`, new symlink/submodule entries are `QUARANTINED`, glossary §3/§16), so in practice only `.ipynb`, non-LFS `filter=` paths (DAT-20) and `working-tree-encoding` paths reach it. *(rev 2.3)* Because every filtered or re-encoded path stops at row 3, the paths that get a table (rows 4 and 6) differ between working bytes and stored form only by canon, which is what lets a `diskSnapshotId` stand in for a stored blob (section 2; glossary §26 W1).

Markdown has no pinned grammar and follows rows 5/6 (changed per glossary §20: the source catalog's ATX-heading sections are dropped; `*.md` concurrency is handled by the `merge.insertionMerge` default in DAT-).

**Units per language** (query files implement exactly this list; anything else is gap-block territory):

| Language | Leaf units | Kind |
|---|---|---|
| Python | module-level `def`/`async def`; `class` (as residue); methods, recursing into nested classes; module-level assignment with a single identifier target (`NAME = …`, `NAME: T = …`) | `function`, `class`, `method`, `const` |
| JS/TS/TSX | `function`/generator declarations; `class` (as residue); `method_definition` incl. `get`/`set` (distinct units, `disc = get|set`); `const`/`let`/`var` with a single declarator bound to an arrow function, function expression or class; methods and function-valued pairs of object literals bound at top level (`qualname = obj.name`); TS `interface`, `type` alias, `enum` declarations; units inside IIFE/UMD wrappers (a top-level call whose callee or argument is a function expression is descended into, and its body's declarations are treated as top level) | `function`, `class`, `method`, `const`, `type` |
| C# | `class`/`struct`/`record`/`interface`/`enum` (as residue; namespaces, block or file-scoped, are descended into, nested types recurse); methods, constructors, destructors, properties, indexers, events, field declarations, operators and conversion operators, each overload its own unit | `type`, `method`, `ctor`, `dtor`, `property`, `indexer`, `event`, `field`, `operator` |

Nested functions, lambdas, callbacks, local functions and inner closures fold into their named ancestor. Python class-level assignments and JS/TS class fields are residue.

**Extent convention `extent-convention/1`.**

1. Start row: the first row of the outermost of: Python `decorated_definition`; the first C# `attribute_list` of the member; the first TS overload `function_signature` with the same name immediately preceding the implementation; a JS/TS `export_statement` that wraps the declaration; otherwise the declaration node.
2. Extend upward over contiguous comment lines (grammar `comment` nodes, incl. C# `///`) with **no blank line** between the comment and the start row; a comment line that is the last line of the unit above belongs to that unit. Consequently a comment-only insertion directly above a held unit (no blank line) lies inside its post-image extent and touches it (glossary §23 decided default; `touch` step 4).
3. End row: `endPosition.row`, minus 1 when `endPosition.column == 0`.
4. Residue of a class/type = its extent minus the extents of its member leaf units (multi-range).

**Labels `label-convention/1`.** `kind` per the table; `qualname` = dotted enclosing names (`Outer.Inner.m`; C# includes the namespace); `simple` = the declared name; `type` = the enclosing type qualname or empty; `disc` = `get`/`set`/`setter`/`deleter` for accessors (Python `@x.setter`/`@x.deleter`, JS/TS `get`/`set`), the normalized parameter type list for C# overloads (`(int,string)`), `overload` for TS signature sets, and a branch ordinal for same-name definitions in sibling branches of a top-level `if`/`#if` (Python platform branches). A label is never identity (REG-14).

**`sigSlice`** per unit is the input of REG-26 (3.10).

**Error spans.** Every `ERROR` and `MISSING` node's row span is recorded in `errorSpans`; `errorCount` is their number; `labelCounts` counts each label key.

**Cache.** Tables are cached by blob oid (and by `diskSnapshotId` for working bytes) in a 300 MB LRU (glossary §20 "Parse"). *(rev 2.3)* The line array and table of a `diskSnapshotId` that a claim draft references as its `srcBlob` are pinned until that draft is emitted or discarded (3.5 Algorithm CLAIM step 4), because no object exists to re-read them from (glossary §26 W6); pinned entries count toward the 300 MB. At most 8 parse trees per worker are kept live for incremental re-parse. A parse is ≤ 400 ms (glossary §20); over budget, the table is `NO_TABLE{budget}` for that blob (P2 consequences in 3.6, 3.7).

**Last-good table** of a path: the newest cached table of that path whose top-level unit covering the lines in question has no `ERROR`/`MISSING` span. Used only by REG-18.

### 3.4 The one line mapper (FoldMapper/1)

1. **Equality.** Two lines are equal when their bytes are equal after removing one trailing `\r` from each and, for line 1 only, a leading U+FEFF (`EF BB BF`).
2. **Diff.** Common prefix and suffix trimming, then the Myers O(ND) algorithm with the standard greedy forward snake and leftmost tie-break, over the remaining lines. Output: hunks in the `Hunk` shape. `git diff` output never feeds claim mapping, the fold, `touch` or `gate` (VERIFIED: git placed a 9-line same-tail insertion after line 5339 while the bundled Myers placed it after 5341; both exact, but different).
3. **Image of `[lo,hi]` from X to Y:** the union of (a) the images of unchanged lines in `[lo,hi]`; (b) the whole b-side of any hunk whose a-side intersects `[lo,hi]`; (c) the b-side of any pure insertion after base line k with `lo ≤ k < hi`. An insertion with `k == hi` or `k == lo−1` is not included (boundary insertions are decided by `touch` case 3). The union is normalized to sorted, merged closed intervals. If every line of `[lo,hi]` is deleted and (b)/(c) add nothing, the image is **TOMBSTONE**.
4. **Direct mapping only.** A range is always mapped by one direct diff between the two blobs, never composed through intermediate versions, so the result is path-independent.
5. **Caps.** If D > 5,000 the result is **WHOLE_FILE** in every mode. In `mode: local` only, a single mapping that exceeds 200 ms wall time also returns WHOLE_FILE (glossary §20 "Region mapper"). `mode: fold` has no time cap.
6. **Frozen.** FoldMapper/1 is part of `proto = 1`. Any change to steps 1–5 is a protocol change (v2). A golden-fixture test pins its output (T-REG-20).

Measured (VERIFIED rc_touch R3, Node 24): 1.3 ms at D = 60 and 30–37 ms at D = 2,000 on 5,960 lines; an exact-equality diff of the CRLF vs LF forms produced 5,960 changed lines and took 536 ms, so the EOL-insensitive equality is also the fast path. VERIFIED fwd_results.json: exact mapping in 4/4 insertion variants including the same-tail case.

### 3.5 Claims: shape, computing, anchoring, tombstones

**Op shape** is glossary §7 `claim` verbatim: `claim_id, path, anchor, base_blob, ranges, tombstones[{anchor, ranges}], granularity: symbol|block|file, label, regionSpec, cs_id, holder{peer, seat, agent}, reserved_for_req?`. Nothing else about code. `anchor = live_code(the board commit that carries the op)`; `base_blob = anchor:path`. Code and claim therefore form one CAS unit (the board push). **Absent-path form** (referred to by PRO-17): when `path` does not exist in the anchor tree — the old-location op of a cross-file move or of a deleted file, whose every range has become a tombstone (REG-09, REG-10) — the op carries `base_blob: null`, `ranges: []` and a non-empty `tombstones` list, each tombstone keeping its own anchor. Any other op with `base_blob: null` is invalid.

**Algorithm CLAIM (per seat, per path, per confirmed edit):**

1. `confirm` (REG-29) yields the tool's hunks in `A[p]` coordinates.
2. Choose units (REG-15) in the post-image table: the leaf units containing the post-image lines of those hunks; for pure deletions, the leaf unit(s) of the post-image containing the deletion point, else the base unit containing the deleted lines. If error spans of the post-image cover those lines, use the last-good table instead (3.14, REG-18).
3. Drop any unit whose lines lie inside a foreign claim admitted for this seat's CS by a go-first grant (the holder keeps that claim; PRO-19, COO-17).
4. Each remaining unit becomes a **draft** `{claim_id, srcBlob = the post-image blobRef, srcRanges = the unit's ranges in srcBlob}` (*rev 2.3:* the post-image is a `diskSnapshotId` whose object was not written, glossary §26 W6; its line array stays pinned in the region cache until the draft is emitted or discarded, 3.3 "Cache", and EMIT step 2 maps from those bytes, never through `cat-file`; no object is written for a draft): reuse the claim_id of this seat's existing claim (HELD or TENTATIVE) whose image intersects the unit, otherwise a new claim_id. The draft is TENTATIVE + confirmed. Creating or changing a draft on a unit present in TIP makes board ops pending, so the governor schedules a board-only push (PRO-31, ENG-42, PRO- governor) and the claim becomes visible within seconds (S1, unchanged by glossary §27.1) instead of waiting for the CS's code; that push is an ordinary governed attempt, subject to every governor limit including the sliding team guard (*rev 2.4, glossary §27.2:* no attempt while ≥ B landed board commits were observed in the last 60 s Δmono, B = `protocol.json.budget`, 12 by default, 6 while the automatic throttle fallback is in force; the governor itself is 02-protocol's). *(rev 2.4)* A code push that publishes a capture taken at a passing edit checkpoint (3.20) carries any pending draft op like every other push (PRO-31), so a new unit's local-only draft (step 3 of EMIT) is emitted as soon as the edit that created it passes the edit check and lands; the draft rule itself is unchanged. While a FREEZE reason is set, or VERSION or another publish pause forbids claim ops (glossary §8: claim ops are not among the ops allowed while frozen or under the regionSpec-only VERSION pause; PRO-45), the draft stays TENTATIVE and local, and its op waits in the outbox (PRO-31).
5. Local overlap check: a draft that overlaps (by `foldOverlap` semantics in post-image coordinates) a confirmed TENTATIVE claim of another local seat that is earlier in claim order is not recorded; the touching hunks are reported as touches (the CS is blocked at B1, REG-21).

**Algorithm EMIT (at each push carrying board ops; `computeClaims`):** for each draft and each HELD claim of local seats on a path whose code changes in this push or that needs re-anchoring:

1. Let `T = tree(live_code(new board commit))[p]`, the anchor blob.
2. Image of the draft: one direct REG-07 `fold`-mode mapping of `srcRanges` from `srcBlob` to `T` (for a HELD claim: of its ranges from its anchor blob to `T`). Never composed through `A[p]` or other intermediates (3.4 point 4), and never with the local time cap, because the result is published.
3. If the image is TOMBSTONE or the unit is absent in `T` (new unit, or the new location of a moved unit not yet published), the draft stays **local-only** (blocks only this daemon's other seats) and is retried at the next push. It MUST be emitted in the first board commit whose live code contains the unit.
4. Otherwise snap to `T`'s table: ranges = the extents in `T` of the leaf units that contain any image line (if error spans of `T` cover those lines, the last-good table per 3.14). For `granularity: file` the ranges are `[[1, lineCount(T)]]`.
5. Run `claimPrecheck` (REG-22). A failing op is not pushed; its CS is blocked. A failing drift re-anchor (below, case b) is simply not pushed: the claim stays valid at its current anchor and the re-anchor is retried at the next push.

**Re-anchor** (same claim_id, new anchor) happens (a) whenever this daemon's push changes a path on which a local seat holds a claim: the claim is recomputed by EMIT steps 2–4 from the image of its old ranges plus the seat's newly published changes; and (b) when `D(anchor blob, TIP[p]) > D_reanchor` (1,000) for a HELD claim, by image only (no snap), riding the next push that is allowed to carry claim ops (none while a FREEZE reason, VERSION or another publish pause is set: glossary §8, PRO-31, PRO-45). Case (a) rides in the same board commit as the own code change that caused it (PRO-31). Drift is therefore bounded by one holder push or 1,000 lines, which keeps fold and gate mappings far below the 5,000 cap.

**Tombstones.** A claimed range all of whose lines this seat's own CS deleted (delete or move-away) is not re-anchored: it is moved into `tombstones` with its last anchor and stays until the claim is released or a save includes the deletion. A peer whose base still has those lines is therefore still blocked there. A move inside a file or across files publishes the new-location claim and the old-location tombstone in the same op batch, so no published copy of the code is ever unclaimed (VERIFIED results_all.json S2: move-splice duplicates without this).

**Readers** map every claim (and tombstone) from its anchor blob to the blob they are deciding against with REG-07, by line content. A claim is never looked up by name, so a rename, a same-name insertion above, a deleted neighbour or a lagging board cannot detach it (VERIFIED line-tracked variants byte-correct in S1, S3 py/js, S4, S6a, S9).

**Reserved claims** (`reserved_for_req`, written by the releasing holder's daemon after its `answer{release}`, PRO §3.6 / PRO-19) are ordinary HELD claims of the requester seat for every function in this chapter: they block every seat but their holder (PRO-17).

### 3.6 The one touch predicate

Input: a hunk `h` of `diff(base[p], post[p])` (base = the decision base: `A[p]`, which equals `A_cap[p]` of a ready pair at publish time), a claim `c` mapped into base coordinates as `[lo,hi]` ranges (or WHOLE_FILE), the post-image table, and context (`regionSpec` of `c`, group-name data).

1. If `c.regionSpec ≠` this daemon's regionSpec, or the mapping returned WHOLE_FILE, or `c.granularity == file`: **touch** (`degraded-whole-file`).
2. `h` deletes or modifies any base line in a claimed range: **touch** (`base-overlap`).
3. `h` is a pure insertion after base line k with `lo ≤ k < hi` for some claimed range: **touch** (`insert-inside`).
4. `h` is a pure insertion with `k == hi` or `k == lo−1`: **touch** iff any of (an attached comment inserted directly above a held unit is inside its extent by `extent-convention/1` step 2, so it touches — glossary §23 decided default)
   - the inserted post-image lines lie inside the post-image extent of the leaf unit containing `c`'s image (for `block` claims: inside the blank-line block or gap block containing `c`'s image) (`boundary-in-extent`);
   - an `ERROR`/`MISSING` span of the post-image covers an inserted line (`boundary-in-error`);
   - the post-image has `NO_TABLE` (`boundary-no-table`).
5. A group-name hit (REG-17): **touch** (`group-name`).
6. Otherwise: no touch.

The predicate takes no input from the hold registry, from the caller's own claims, or from labels except in step 5. Claims never exempt anything (HLD-06). A touch verdict is consumed per change-set: one touching hunk blocks every CS the hunk is attributed to.

**Containment form** *(added in rev 2.1; glossary §1 S5, §24 "S5")*. Part (b) of the wake work set ("regions inside this seat's own claims", 07-coordination §2) needs the opposite question: does a hunk lie entirely inside the seat's own claims? It is answered only by `contained(h, …)`, which reuses `touch`'s inputs (the same REG-07 `local`-mode mapping into `A[p]`, the same post-image table and the same step-4 extent test) and never consults the hold registry or labels.

- **Own-claim set O** of a wake turn on p: this seat's HELD non-STALE and confirmed TENTATIVE claims on p as of the Pre or TXN open that the check belongs to (06-claude §3.8.2a), minus every claim first confirmed during the current wake turn (turn origin, 06-claude §3.12.2; *rev 2.3:* the wake turn begins at the UserPromptSubmit that carries a cowork nonce with a new `prompt_id`, and a doorbell delivered mid-turn neither starts a wake turn nor resets the CS, glossary §25 F2). A wake turn therefore cannot widen its own scope by claiming: a write the backstop PINned still drafts claims (Algorithm CLAIM), and without this exclusion the next edit in the same unit would pass. Tombstones are not in O.
- `h` is **contained** iff one of: (1) some claim of O has `granularity: file`; (2) `h` deletes or modifies base lines and every one of them lies in the union U of the mapped ranges of O; (3) `h` is a pure insertion after base line k with `lo ≤ k < hi` for a range of U; (4) `h` is a pure insertion with `k == hi` or `k == lo−1` for a range of U and its inserted lines lie inside the post-image extent of the leaf unit containing that claim's image (`touch` step 4, first bullet).
- Everything else is **not contained** (P2 counterpart: an uncertain answer narrows what a wake turn may publish, never widens it): a claim of O whose mapping returned WHOLE_FILE contributes nothing to U; a boundary insertion decided only by an `ERROR`/`MISSING` span or by `NO_TABLE` is not contained; a group-name hit never makes a hunk contained; a path not of scope class `LIVE` has no claims and is never contained (quarantined paths are never in the wake work set).
- Consumers: `predict.ownContained` for CCI- gate row 3 (the advisory gate, CCI-38), and `confirm.notOwnContained` for the hard backstop (06-claude §3.12.3 and §3.8.2a: any hunk of a wake-turn CS on a `LIVE` path outside the whole wake work set PINs the whole CS with guard `wake-scope`, glossary §9, so it is never published). Part (a) (paths of requests the seat accepted) is a path-level test owned by 07-coordination/06-claude; a hunk is in the wake work set iff its path is in part (a) or `contained` is true.

### 3.7 Foreignness and the B1 publish gate

**Foreign claim.** For a hunk attributed to the seat set `S(h)` (CCI- attribution; overlapping TXN windows attribute to several seats, a write with no attribution is the human pseudo-seat), claim `c` with holder seat `(peer, seat)` is **foreign** unless every seat in `S(h)` is `c`'s holder seat. Exception (consolidation cross-check fix to source-catalog rule CS-04, "call `gate` verbatim, with seat-level foreignness"; applied in HLD-45): for hunks attributed only to this peer's `human`, claims held by any seat of this same daemon are not foreign. Another seat on the same PC is foreign. Agents of one seat are the same seat (CCI-30). STALE claims are non-blocking and are not in the claim view (glossary §3, S4). Attribution is CCI-27's table (06-claude §3.8.3).

**Algorithm GATE (`gate(A, R, attribution, claimView@leasedTip)`):** `R` is the rebased ready tree of each ready group (glossary §3 "ready pair"; `A_cap == A` at publish by HLD-41/HLD-42).

1. For every path p of a ready group with `R[p] ≠ A[p]`: compute `H = hunks(A[p], R[p])` (REG-07, on stored blobs: `R` is a ready-pair capture, for which the engine writes objects, glossary §26 W6) and `regionTable(R[p])`.
2. For every claim `c` in the claim view on p that is foreign to some hunk: map `c` (ranges and tombstones) from its anchor (or the local post-image for confirmed TENTATIVE sibling claims) into `A[p]` with REG-07 `local` mode.
3. For each hunk `h` and each foreign `c`: if `touch(h, c, …)`:
   - if `c` has an active grant (PRO-19) and every CS attributed to `h` is the grant's `cs_id` of the grantee seat: record `admitted`;
   - else: for every CS attributed to `h`, record `blocked{cs_id, claim_id, holder, path, reason}`.
   - A confirmed TENTATIVE sibling claim blocks only hunks of seats that are later in claim order than it.
4. Return `{blocked, admitted}`. `gate` never returns hunks to remove and never consults the hold registry. HLD- holds every blocked CS (with its publication group) as one PIN (HLD-45; only the CS's `LIVE` paths enter the record and its board mirror, glossary §9 rev 2.1); COO- creates the K3/K6 event.

GATE runs on every candidate before every push and is recomputed from scratch after every push rejection, against the claim view of the tip fetched after it (new leased tip, new claim view, new OUT). *(rev 2.3)* Every rejection is followed by a fetch and is classified by its outcome, not its text (glossary §26.2 item 2): a moved board ref (lease loss) and an unmoved ref (transient) both lead to a fresh GATE before the next attempt, and a publish that ends `NONRETRYABLE` after three unchanged-ref rejections is PINned whole by the engine (glossary §8), not by this chapter. Because it runs in the daemon on the published delta, it covers Bash/PowerShell writes, failed-open hooks, seats whose wiring is `HOOK_ONLY`, `NO_MCP` or `NO_HOOKS` or that are flagged `DEGRADED` (glossary §3 "seat wiring / flags"), and human editors; hook denies are early warnings only. Human CSs are gated the same way (never denied, but held and flagged, K6).

**Relation to P (INV-FENCE).** The glossary states INV-FENCE as "publish gate B1 on P". B1 gates `R`, before P is composed (HLD-45, ENG- pipeline step 2); this is the same fence because `P[p]` is either `A[p]` or `MASK(R[p])` (glossary §3 "P") and MASK only resets lines to `A[p]`, so P changes no line against A that R does not change. The placement fence sub-check (b) of 3.8 re-checks the merged OUT against the same claim view as the second line of defence.

**Grants.** A grant admits only in `gate` (B1), only for the grantee's granted `cs_id`, and only while it is active in the claim view. It ends exactly at the PRO §3.6 termination conditions (PRO-19), among them the grantee's (peer, epoch) being presumed absent: a holder that granted go-first may presume the grantee absent 30 min after folding the grant with no op from it (glossary §1 S4, §20 "Presume absent", §24 "S4"). After that the claim is the holder's again and the grantee's hunks are foreign touches. A grant never admits at `predict`: a requester's new Edit inside the granted claim is still a foreign touch (COO-17: the granted change lands through the SHADOW write). The holder seat's own edits inside a granted claim are paused until the grant ends (`T-GRANT_PAUSE`; *rev 2.4:* confirmed by the user on 2026-10-02 and binding, glossary §27; formerly a glossary §23 proposed default pending sign-off); `predict` reports them in `ownTouches` with `granted: true` and the PreToolUse deny is CCI- gate row 13b (COO-17). `gate` does not block the holder's own hunks.

Running the touch test in `A` coordinates on the local delta, before trusting the merge, is what prevents the same-tail misplacement (VERIFIED premerge_results.json: `merge-tree` moved `return round(total, 2)` into `compute_tax` with exit 0).

### 3.8 The post-merge placement check

One check, two sub-checks, one outcome. Run after every merge that produces a tree this peer will push or write, and after every re-merge:

- publish: `placementCheck(A, P, TIP, OUT, gateResult, claimView)` (P and OUT as in glossary §3; ENG- builds OUT from P);
- apply: `placementCheck(A, S_disk, TIP, M_disk)` (sub-check (a) only; the `S_disk` and `M_disk` blobs of the merged paths are objects the apply writes, glossary §26 W6, so they are read as stored blobs);
- base move: `placementCheck(tree(B), tree(TIP), tree(Hr), newtree)` (sub-check (a) only; ENG- §3.13 case iii).

`identityCheck` (ENG-29) is an alias of `placementCheck`.

(a) **Identity.** For every path with a symbol table where `ours[p] ≠ base[p]` and `theirs[p] ≠ base[p]` (claimed or not): for each hunk of `hunks(base[p], ours[p])`, the label of the leaf unit containing its post-image lines in `ours[p]` must equal the label of the leaf unit containing their REG-07 image in `out[p]`. A mismatch, or an image that is TOMBSTONE or WHOLE_FILE, fails the path. The comparison is within one peer and one parser, so labels are comparable here.

(b) **Fence.** For every path where `out[p] ≠ theirs[p]` and the claim view has a foreign claim `c` on p: map `c` into `theirs[p]`; if a hunk of `hunks(theirs[p], out[p])` touches `c` and the gate result has no `admitted` entry for `c` on p, fail the path.

Every failed path goes to the ONE conflict function (DAT-41, Algorithm D8) exactly like a `merge-tree` exit-1 path (on a base move: ENG-48 instead blocks the base move with a base-move hold record): TIP's entry goes on disk and in OUT, the local blob becomes the CONFLICTED hold (K4). Nothing is pushed or written for that path from the merge result. As for every K4 `TAKE_TIP`, the rest of the change-set still publishes (glossary §24 technical default 3; 05-holds INV-HLD-ATOMIC-PUB exception for a K4 displacement); a placement failure never pins the group by itself. The check reuses T0's parse of OUT.

Why: VERIFIED region-gap inspection: `merge-tree` and `merge-file` exited 0 with B's edit landing in `compute_tax`; the identity check flagged `symbol_in_SNAP=compute_total` vs `symbol_in_OUT=compute_tax`. Sub-check (b) covers block- and whole-file-claimed paths that have no symbol table.

### 3.9 Fold overlap (called by the PRO- fold)

`foldOverlap(C1, C2, readBlob)` decides whether claim op C2 conflicts with an active claim C1 of a different holder seat on the same path:

1. If either has `granularity: file`: **overlap**.
2. Map C1's ranges and each tombstone's ranges from their anchors to C2's anchor blob with REG-07 `fold` mode (blobs are read as stored objects; both are reachable through the board's last-parent links).
3. If any mapping returns WHOLE_FILE: **overlap**.
4. If any mapped C1 range intersects any C2 range as closed intervals: **overlap**.
5. Otherwise: no overlap.

A C2 in the absent-path form (3.5) has no ranges, so step 4 cannot fire for it; its tombstones are not tested as C2 ranges.

The PRO- fold (PRO-17) calls this for every claim op against every active (HELD, not STALE, not released) claim of a different holder seat on the same path; overlap makes the op an invalid deterministic no-op (glossary §7 "Fold"); the later of two overlapping claims is always the invalid one (PRO-17). A claim op carrying an existing claim_id of the same seat replaces that claim's anchor, ranges and tombstones (re-anchor) and is validated the same way. The fold uses only op fields and FoldMapper/1: no parse, no regionSpec, no labels, no git diff, no clock, no time cap. Since overlap is decided by ranges, two peers whose region tables differ still fold identically.

### 3.10 Interface classifier and caller/callee/import checks (region part of T0)

**Signature slices.**

| Language | Slice |
|---|---|
| Python function/method | parameter list (positional-only, positional, keyword-only, `*args`, `**kwargs`, names, presence of defaults), decorators, return annotation |
| Python class | bases, set of method names, class-level assignment names |
| Python module | `__all__`, UPPER_CASE module names |
| JS/TS | formal parameters (count, rest, defaults, destructured names), export status and exported name, class member names |
| C# | for non-private members: modifiers, return type, parameter list (types, `ref`/`out`/`in`/`params`, defaults); property and field types; the overload set per (type, simple name) |
| JSON (`*.json`) | key paths (`JSON.parse` of both blobs) |

**Classes** (net over the whole CS, comparing `base[p]` with `ours[p]` per unit, never per edit):

- **breaking:** a unit or export removed; a positional parameter removed, reordered or renamed; a new required parameter; `*args`/`**kwargs` removed; a C# parameter-list change that leaves no overload accepting the old calls. A rename is a removal of the old name plus an addition (aliases are deferred, §22).
- **compatible:** body-only change; an appended parameter with a default; a new optional keyword-only parameter; an added overload.
- **note:** a decorator change; a default-value change; any JSON key-path removal or rename (glossary §10 K7 lists no config-key check, so JSON key changes are notes in v1; T1 is the backstop).

**Callers of breaking changes (on `out`).** For each breaking change: `git -c attr.tree=<EPOCH_BASE> grep -z -n -w -F -e <name> <out tree oid> -- <paths with a symbol table>` through `runGit` (`LC_ALL=C`, `core.quotepath=off`). Drop hits inside the definition itself, in comments and in strings (except UPPER_CASE names). Parse hit files from the oid cache and classify each call:

- **definite:** a bare-name call that resolves to the defining module (same file; Python `from m import name` or `import m` + `m.name(…)` where m resolves to the defining file; a JS/TS named import from a relative specifier resolving to the defining file); `self.`/`this.` calls inside the same class; C# calls inside the same type (including its partials) or `TypeName.Member(…)` with the simple type name;
- **possible:** an attribute call on an unknown receiver.

A definite call not written by this CS whose arity or keywords are incompatible with the new signature is an `incompatibleCallers` entry (T0 failure, K7 "caller arity").

**Callees of new calls.** For every call node this CS added or changed in `ours`, resolve the callee by the same rules in `out` and check arity/keywords against its `out` signature; a definite incompatible call is an `orphanCalls` entry (K7). This catches the orphan call when a teammate's breaking change landed first.

**Import names.** Python `from <local module> import n` and JS/TS relative named imports (`import {n} from './m'`) in files this CS changed, plus every importer (found by the same grep) of a module whose exported names this CS removed: a name absent from the resolved module in `out` is an `unresolvedImports` entry (K7 "import name"). Python module resolution: dotted path → `a/b.py` or `a/b/__init__.py`, from the repo root and, for relative imports, the importer's package. JS/TS: the specifier with `.ts .tsx .js .jsx .mjs .cjs`, then `/index.*`.

**Arity compatibility.** Python: required positional parameters satisfied, no surplus positional without `*args`, every keyword exists unless `**kwargs`; a call using `*x`/`**x` splats is compatible (note). JS/TS: argument count ≥ required count and ≤ maximum count when there is no rest parameter. C#: some overload in `out` has a parameter-count range covering the argument count and all named arguments; types are not checked in v1.

**Note-only cases.** Possible hits, more than 50 hits for one name, and the stoplist names `get set run main init __init__ update load save close` produce a count or note only and never hold a CS. Without type information, Python method changes mostly have only possible callers; T1 at checkpoint and save is the backstop (HLD-).

**Budget.** grep + filtering ≤ 150 ms on 611 files (research: `git grep -w -F` 73–80 ms); the whole region part of T0 ≤ 0.5 s on the 1.3 MB file (glossary §20). Over 4× budget the check stops and returns `incomplete: true`; incomplete is never a pass (HLD- retries it at the next loop). *(rev 2.4)* When `editCheck` calls this function (3.20) the caller-site search is split as described there (TIP's stored tree for paths outside the CS, in-memory merged blobs for the CS's paths) and the call stops at the edit check's own 0.5 s deadline (1×, not 4×), returning `incomplete: true`.

### 3.11 PreToolUse prediction and PostToolUse authority

**Algorithm PREDICT** (`predict`, answered from memory within the gate budget):

0. If `p` is not of scope class `LIVE` (glossary §3), `predict` is not called: CCI- gate row 5 answers G2 `NOT_SHARED` and no claim is recorded (REG-32).
1. Take the target file's current bytes from `diskBytes`. *(rev 2.3; glossary §26 W1, W3)* The caller (06-claude) obtains them with fs, never git and never a memory mapping, as one short read (open share-all, read the whole file, close; no handle outlives that read call) with size and mtime equal before and after, re-read once if they differed. If the caller passes `unstable` (the re-read differed too), `predict` answers `status: undecided` at once: the gate answers G2 and CONFIRM decides, exactly as for an undecided boundary insertion (step 7); torn bytes never yield a located prediction. If `p` is in path class 1–3 or is `.ipynb`/NotebookEdit: predicted hunks = whole file (every foreign claim on p touches); go to 7.
2. Build the normalized view V0 = disk with leading BOM stripped, CRLF→LF, U+2018/2019 → `'`, U+201C/201D → `"`. Normalize each `old_string`/`new_string` the same way.
3. Edit/MultiEdit: apply each edit in order to the view: locate the normalized `old_string`; `replace_all` → all non-overlapping matches; otherwise a unique match, or every candidate when ambiguous (conservative). No match → `status: locate_failed` (the gate answers G2 and PostToolUse decides; a locate failure is never turned into a whole-file claim). Write: the view becomes the normalized `content`.
4. Predicted post-image V1. Tool lines = the b-side lines and deletion points of `hunks(V0, V1)` (disk rows).
5. `hunksInBase` = the hunks of `hunks(norm(A[p]), V1)` that intersect the tool lines (A[p] from the cached line array, quote-folded the same way).
6. Moved-code check: if the seat has a view blob for p (06-claude local definition; CCI- gate row 10), map the matched lines from that blob to the current disk with REG-07; if the leaf-unit label differs or the image is TOMBSTONE, set `moved`. Why this check is needed: the host applies an Edit after an external change whenever `old_string` still matches, adding only the note "the file had been modified on disk since you last read it" (MEASURED, glossary §25 F7), so nothing but this check notices that the matched text now sits in a different unit.
7. Run `touch` for every foreign claim in the claim view (HELD foreign claims, and confirmed TENTATIVE claims of sibling seats on this daemon that are earlier in local order — glossary §10 K1, REG-21) mapped into `A[p]`. Grants do not admit here (3.7 "Grants"). Also run `touch` against this seat's own claims and list every hit in `ownTouches` with its SUSPECT flag (PRO-37) and whether it has an active grant; CCI- gate rows 12 (SUSPECT) and 13b (GRANT PAUSE, `T-GRANT_PAUSE`, COO-17) consume it. Step 4 of `touch` needs the post-image table: request an incremental re-parse of V1 from the worker's live tree of the disk blob and wait at most `T_predict` (10 ms). If it is not available, the hunk's step-4 verdict is `undecided`: it does not cause G1, the reply records `status: undecided`, and PostToolUse decides.
8. If the region table of the disk blob is not cached, use the **fallback region**: from the nearest preceding column-0 line that starts a definition (`^(async\s+)?def |^class ` for Python; `^(export\s+)?(default\s+)?(async\s+)?(function|class) |^(export\s+)?(const|let|var) \w+\s*=` for JS/TS; for C#, the nearest preceding line at the indentation of a member declaration matching `^\s*(public|private|protected|internal|static|override|virtual|async|partial)\b`) to the line before the next such line. The fallback serves the G1/G2 decision only and is never published or stored (`fallbackUsed: true`).

Outputs feed the CCI- ordered gate (CCI-13: G1 `MOVED` for `moved` at row 10, G1 K1 for a foreign touch at row 13, G2/G3 otherwise) and record predicted TENTATIVE claims (discarded at fence release unless confirmed).

**Algorithm CONFIRM** (`confirm`, at PostToolUse of an edit-class tool and at Bash/PowerShell/Monitor TXN close, in a worker):

1. Pre-image = the blob captured under the fence/TXN (CCI-25, CCI-27); post-image = the current disk content of p as a `diskSnapshotId`. *(rev 2.3; glossary §26 W1, W2, §20 "Shrink guard")* The post-image MUST come from one stable read as in PREDICT step 1. A post-image that is empty, or more than 50 % shorter than the pre-image, is used only when a second stable read returns the same bytes (the glossary §20 shrink guard's "2 stable snapshots"; the tool call is the attribution); spike 04 captured a transient 0-byte file in 1 of 480 staged reads (§26 W2), which CONFIRM would otherwise read as "every line deleted" and turn into a false K2 against every foreign claim on p. When no stable or no confirmed post-image is available, CONFIRM for p is not computed from those bytes: it is re-run on the next stable read of p for the same `cs_id`, and its result rides the seat's next hook (06-claude §3.8.1 "a later result rides the seat's next hook"). If the CS reaches its boundary first, the last such read is the ready-pair capture itself: the deferred `confirm` runs with `R[p]` of that capture as post-image (glossary §3 "ready pair"; a stored object, §26 W6; the snapshot behind it already applies the §20 quiet period and shrink guard), so the deferral always ends at the latest at the CS boundary. Until then p has no drafts and no K2 verdict; this is a deferral, not a "no conflict" answer, because B1 (REG-20) still gates every hunk that is published (P2).
2. Tool lines = b-side lines and deletion points of `hunks(pre, post)` (EOL/BOM-only differences produce no hunks).
3. `hunksInBase` = hunks of `hunks(A[p], post)` intersecting the tool lines.
4. `touches` = `touch` of each hunk against each foreign claim of the claim view of the fold recorded at PreToolUse/TXN open (glossary §10 K2, CCI-26); a touch is a K2 situation handled by CCI-26/HLD-46 (record + whole-CS PIN, no disk write). Claims folded after that point are B1's (K3, REG-20).
5. `drafts` = Algorithm CLAIM. Only these become confirmed claims.

### 3.13 Imports and shared insertion points

`<imports>` is the first maximal run of top-level nodes that starts with an import-class node and continues while the next top-level node is import-class or a comment, including blank lines inside it, ending at the last import-class node. Import-class: Python `import`/`from … import` (incl. `__future__`); JS/TS `import`, `export … from`, and top-level `const|let|var x = require(…)`; C# `using` directives and `extern alias`. It is never claimed and never blocks. A pure insertion outside every unit's post-image extent (between units, at end of file, at the end of a class after its last member) claims only the new unit, and only once published. Concurrent changes at these points are textual: clean merges pass; conflicts go to the DAT-42 insertion-concat fast path or the conflict function (DAT-41); T0 checks the result. Two claims that touch without overlapping are never an overlap. Blank-line-only hunks claim nothing. VERIFIED e7/e7b (adjacent lines and shared insertion points conflict textually without any claim overlap); VERIFIED DH6 (ordered concat parses where `--union` fails).

### 3.14 Error trees

1. A new claim range or label is never derived from a tree whose `ERROR`/`MISSING` spans cover the touched lines. The claim uses the path's last-good table, mapped forward with REG-07. If the touched lines map into no last-good unit, the claim is the span strictly between the nearest last-good units above and below (`granularity: block`). With no last-good table: `granularity: file`.
2. Existing claims are never re-derived from an erroring tree; they keep mapping by REG-07, which needs no parse.
3. `touch` step 4 answers touch when an error span covers an inserted line.
4. Conflict-marker blobs have no table (path class 1).

### 3.15 Relative region tripwires

Run per path with a symbol table on every outgoing blob after every merge and re-merge, and on every insertion-concat output (DAT-42, D9 tripwire); *(rev 2.4)* also called by `editCheck` on the merged candidate `M[p]` with `theirs = TIP[p]`, `ours = R[p]` (3.20; there forms (a) and (c) count as check 1 — a blob that does not decode cannot be shown free of new error nodes — and form (b) as the label part of check 4; a violation is only a failed edit check, not a T0 failure):

(a) `errorCount(out) ≤ errorCount(theirs)` (0 for a new path);
(b) for every label key: `count(out) ≤ max(count(theirs), count(ours))` (concat: `ours` = LOCAL);
(c) `out` decodes as UTF-8 if `theirs` did.

A violation is a T0 failure (glossary §10 K7, rev 2: "new ERROR/MISSING parse nodes relative to TIP" and "label count above max(TIP, local)" are exactly forms (a) and (b)); the CS is held by HLD-50 as a PIN, the path is not pushed, output is never repaired. ### 3.16 Holder-side breach detection (input to K5)

At apply, `breach` walks the live code commits in `(LA_C, TIP]` on the first-parent chain. For each commit C with first parent `C^1` (written `C^1`, not P, to avoid the glossary's publish composition P) and each path p changed by C on which a local seat holds a HELD claim: map the claim into `C^1[p]`, compute `hunks(C^1[p], C[p])`, and report every touching hunk where C's CS attribution for p (`Cowork-CS-Paths`, else `Cowork-Seat`) contains no CS of the holder seat, C's `Cowork-Seat` is not the holder seat. ### 3.17 Keying of requests and shadows; display

Nothing that refers to a claim is keyed by a symbol name, ordinal or code hash:

- A denied-edit **SHADOW** (K1 PATCH record) is found by the shadow key `(seat_id, foreign claim_id, path)` (HLD-47, CCI-18), where claim_id is the earliest (board order) foreign claim intersected. Chained denials on one claim compose on one shadow even after renames or line shifts. The record's own identity is its ULID `id` (glossary §9, HLD-02).
- A **request** is identified by `(req_id, to_holder.seat)` with `req_id == hold_id` of the PATCH/PIN record that carries the attempted change (glossary §3 "request"); one PIN may produce one request per holder seat. It names claims only through `claim_ids` (glossary §7 `request`).
- A `note` op that targets a claim names it by `claim_id` (glossary §7 `note`). The target is chosen by glossary §24 technical default 10 (07-coordination §3.6 "Notes"): the seat's newest non-terminal request, else its newest HELD claim (newest = latest board position), else `null`; never by a name in the note text.
- CLI and tool arguments that name a claim (`cowork_release(claim_id | "all")`, `/cowork release <claim_id>`, `cowork_show(id)` when the id is a claim id) resolve to claim_ids.

Displays render code by reading blobs by oid — a claim's anchor blob, a hold record's registry blobs, or its board mirror entries `held/<hold_id>/<stage>/<repo path>` (glossary §3) — and selecting the claim's mapped lines with REG-05/REG-07; that text is shown, never written. The region module returns raw labels and paths; a label taken from another peer's claim op is handed to renderers only through `verifyLabel` (REG-34: the re-derived label, else `?`), so a forged or skewed board label never reaches `{sym}` in a deny reason, PostToolUse block or Stop block (06-claude §3.6.5, SEC-35 `validLabel` is applied on top); truncation to the glossary §19 placeholder caps (label 80, path 80, `{sym}` = `path::label` 80 total with middle ellipsis keeping the label) is `sanitize()`'s, applied by the renderers (07-coordination for Claude-facing text, 10-product for human-facing text, LIF-27 for `Cowork-Symbol` save trailers). Applying a request is a whole-blob 3-way merge owned by HLD-/COO-; no region-scoped apply exists.

**Label verification (`verifyLabel`, REG-34; added in rev 2.1).** Board labels are not authenticated (a forged op can carry any label that passes SEC-35 `validLabel`), so a receiver re-derives every label it renders:

1. Scope: every folded `claim` op not computed by this daemon itself (other peers' claims and this peer's claims from an earlier epoch). Claims of this daemon's current seats are verified by construction.
2. After the fold admits or re-anchors the op, the daemon schedules, in a worker and outside the fold and the gate decision, `regionTable(base_blob, path)` with its own runtime (the anchor blob is reachable through the board's last-parent link; the table is cached by oid, 3.3).
3. For `granularity: symbol`: the label is **verified** iff the leaf unit of that table whose ranges contain the first line of the op's first range has a label equal to the op's `label` in all five fields. A drift re-anchor by image (3.5 case b) keeps the unit's first line inside the unit, so it verifies as well.
4. For `granularity: block | file`, the absent-path form, `NO_TABLE` (any reason, incl. budget), an error span covering that line, a missing blob, or a check not yet finished: the label is not verified.
5. Renderers (07-coordination, 10-product; LIF-27 save attribution is unaffected because it uses this daemon's own tables) receive the verified label or `?`. The result is cached per `(claim_id, anchor)` and recomputed after every re-anchor. A mismatch writes one `log/security.jsonl` line with `claim_id`, holder peer and anchor (ids only, never the label text; 09-security).

Verification is display-only: it never changes the fold, `foldOverlap`, `touch`, `gate`, the group-name rule (glossary §7 keeps the op label as its input; a label can only add a conflict there, REG-14) or any other verdict. Under regionSpec skew a peer's labels may legitimately fail to verify; they then render as `?` next to `REGION_SPEC_MISMATCH`.

### 3.20 The edit check (`editCheck`) *(added in rev 2.4; glossary §27.1)*

S1 (rev 2.4, glossary §27.1) publishes a Claude change-set at every **edit checkpoint** whose **edit check** passes, besides turn end, green checkpoint and `cowork_checkpoint`. `editCheck(A, R, TIP, cs)` is the single entry point of that check. It answers one question, "may the candidate capture taken at this checkpoint become the CS's ready pair?", and nothing else. It is built from the T0 machinery of this chapter (`regionTripwire`, 3.15; `interfaceCheck`, 3.10) so that there is still one parser, one tripwire and one interface classifier (P3).

**Caller and trigger.** 06-claude raises the edit checkpoint after PostToolUse of Edit/Write/MultiEdit/NotebookEdit of a Claude seat, or at a Bash/PowerShell TXN close attributed to a Claude seat, once CONFIRM (3.11) has run for that tool use. 05-holds/01-engine take the candidate capture under their ordinary capture rules (stable read, quiet period, shrink guard; glossary §20, §26 W1–W3) and call `editCheck`. A human CS never calls it (it still publishes after 20 s without edits or `/cowork done`, glossary §27.1), *(rev 2.5, F10; added at merge)* except the read-only prediction of a `/cowork revert` preview (05-holds Algorithm REV step 6, verb-mode preview only), which calls this entry point and `gate` (REG-20) on the result buffers of `revertInverse()` held in memory, with `TIP`'s blobs elsewhere. That verdict is display data only (`UI_REVERT_WOULD_BREAK`, `UI_REVERT_WOULD_HOLD`): it never decides a capture, writes no record and no `last_check`, and the revert change-set the human then confirms is checked at publish like any human CS (T0 with HLD-50's attribution, B1).

**Inputs.**

- `A` = `A_cap` of the candidate (the CS's apply base; captures are rebased at every apply, HLD-41). `R` = the candidate ready tree taken at this checkpoint. `TIP` = the live code tree of the newest board tip this daemon has fetched, the tree the next publish would merge onto.
- Checked paths = the CS's paths of scope class `LIVE` (REG-32) with `R[p] ≠ A[p]`. Other paths are not published by this CS and are not checked.
- `R[p]` is read as a stored blob when the engine wrote it, else as a `diskSnapshotId` (REG-35; a candidate is not an object until it is captured, glossary §26 W6). A checked path whose candidate content is unavailable (unstable read, CONFIRM deferred, 3.11 step 1) fails the check with `reason: no_snapshot`.
- `cs.merged` = `M[p]` per checked path, the `merge-tree --merge-base=A R TIP` result restricted to the CS's paths (glossary §27.1), supplied by 01-engine (ENG-46): when `TIP[p] = A[p]`, `M[p]` is `R[p]` itself and no merge runs (the module asserts this equality); otherwise the engine's 3-way merge result as a blobRef, or `conflicted` (fails, `reason: merge_conflict`), or `absent` (fails, `reason: no_merge`; the first checkpoint after the apply that rebases the CS checks again with `TIP[p] = A[p]`). `M'` = the tree that equals `TIP` outside the checked paths and `M[p]` on them; a deletion in `M[p]` is the path's absence in `M'`.
- *(rev 2.5, F12)* A failed entry whose reason is `no_snapshot`, `merge_conflict` or `no_merge` carries no `check` number: it says the candidate could not be checked, not that a check failed, and it reaches 05-holds' `last_check` as such, never as a check 1–4 failure (FEAT-F12-06).

**The four checks** (numbered as glossary §27.1; the check number is reported in `failed[].check`):

1. **No new parse errors.** For every checked path that has a symbol table in `TIP[p]` or `M[p]` (path class 4): `regionTripwire(TIP[p], R[p], M[p])` form (a), `errorCount(M[p]) ≤ errorCount(TIP[p])` (0 for a path absent from `TIP`), and form (c): a grammar path whose `TIP[p]` decodes as UTF-8 and whose `M[p]` does not fails (no tree can show it free of new error nodes). `M[p]` with conflict-marker lines (path class 1) fails.
2. **No unhandled breaking interface change.** `interfaceCheck(A, R, M', cs)` (3.10, merged tree `M'` as `out`). Any `incompatibleCallers` entry for a breaking change other than a removal (a positional parameter removed, reordered or renamed, a new required parameter, `*args`/`**kwargs` removed, a C# parameter-list change leaving no overload for the old calls) fails. Callers this CS updated are not entries (3.10: "a definite call not written by this CS"). Any `orphanCalls` entry also fails here: a call this CS added or changed whose definite callee in `M'` has an incompatible signature is a caller in the merged tree that is not updated, in the other direction (the same K7 "caller arity" class T0 would hold at publish).
3. **No reference to a name the merged tree does not define.** From the same `interfaceCheck` result: any `unresolvedImports` entry (a local import name absent from the resolved module in `M'`), and any `incompatibleCallers` entry for a removal (a unit or export this CS removed or renamed, a rename being a removal plus an addition, 3.10) fails.
4. **No count growth and no large shrink.** For every checked path with a symbol table in `M[p]`: `regionTripwire` form (b), `count(M[p]) ≤ max(count(TIP[p]), count(R[p]))` for every label key. For every checked path: if `TIP[p]` is non-empty, `M[p]` MUST NOT be absent, empty or smaller than 50 % of `TIP[p]`'s stored-form byte size. Unlike T0's shrink guard (HLD-50 item 3) there is no attribution exemption: an intended large deletion simply waits for turn end, a green checkpoint or `cowork_checkpoint`, where T0 decides with attribution.

Paths without a symbol table on either side (no grammar, `NO_TABLE{binary | special | grammarless_small}`, block tables, `.ipynb`) pass checks 1–3 trivially and are subject to check 4's size part only (glossary §27.1 "Unsupported languages"). JSON key-path changes stay notes (3.10) and never fail. Possible-only hits, more than 50 hits and stoplist names stay notes and never fail, exactly as in T0. A grammar path whose table is `NO_TABLE{budget}`, or a blob read that misses the object store (REG-35), makes the result `incomplete`.

**Failed entries** *(rev 2.5, F14; FEAT-F14-07)*. Every failed entry of checks 1–3 carries `line`, the 1-based stored-form row of `M'` (`M[p]` on the checked paths, `TIP` elsewhere, because an un-updated caller of check 2 can sit outside the CS) where the first offending node, call or reference of that entry starts, and its `path` names the file of `M'` that holds that row:

- check 1: the first `ERROR`/`MISSING` span of `M[p]` in row order that does not intersect the REG-07 image of any span of `TIP[p]` (else the first span of `M[p]`), so a parse error TIP already had is not the row reported; for conflict markers, the first marker line; an `M[p]` that does not decode (form (c)) has no node and carries no `line`;
- check 2: the row of the definite call of the `incompatibleCallers` or `orphanCalls` entry, i.e. the 3.10 hit row (`git grep -n` on TIP's tree outside the checked paths, the in-memory row of `M[p]` on them; "Caller search without a stored merged tree" below);
- check 3: the row of the unresolved import name (`unresolvedImports`) or of the call to the removed name.

Check-4 entries and the non-check reasons carry no `line`. `line` is display data for 05-holds' `last_check` (10-product §3.5.1): it never changes `pass`, is computed only for a failing result, and, like the rest of the result, is never written to a record, log, board op, file or `status.json` (REG-01: a row, never a byte offset).

**Caller search without a stored merged tree.** 3.10 greps `<out tree oid>`, but `M'` is usually not a stored tree (candidate blobs are `diskSnapshotId`s, glossary §26 W6). `editCheck` runs the same search in two parts whose union equals a grep of `M'`, because `M'` equals `TIP` outside the checked paths by definition: (i) the 3.10 `git grep` through `runGit` on TIP's live tree oid, with one `:(exclude,literal)<p>` pathspec per checked path; (ii) the same fixed-string, whole-word predicate (word constituents `[A-Za-z0-9_]`, byte-wise, as `git grep -w -F`) and the same hit filtering over the in-memory line arrays of `M[p]` for the checked paths. Module resolution for imports and callees reads `M[p]` on checked paths and `TIP` elsewhere. No object, index entry or ref is written (REG-02, REG-35).

**Budget and scheduling.** Worker pool only (REG-31). Total wall time ≤ 0.5 s per call on the 1.3 MB file (glossary §27.1), measured from the start of the worker job; at 0.5 s the job is abandoned and returns `incomplete: true` (1×, not the 4× of T0: a missed pass costs only delay, never correctness). Caches are shared with CONFIRM and T0: `R[p]`'s table is the one CONFIRM parsed for the same `diskSnapshotId` (3.3), TIP's tables are cached by oid, and `M[p] = R[p]` needs no further parse; the basis is VERIFIED x10 (AST plus symbol table 397 ms on 1.3 MB) and the grep research (73–80 ms on 611 files). Per CS at most one `editCheck` runs and at most one waits; a newer checkpoint replaces the waiting one (the newest content is checked next) but never cancels the running one, so a steady stream of edits still reaches passing captures. A result stays valid if an apply rebased the CS while it ran: the capture is then rebased like any other (HLD-41), and the publish-time checks below decide.

**Result and what it controls** (the consumers' rules are 05-holds' and 01-engine's, stated here for orientation). `pass` = every check passed and `incomplete` is false. Pass → the candidate becomes the CS's ready pair, replacing an older one (newest passing capture wins), and the governor publishes it as part of P. Fail or incomplete → no capture, no record, no event, no message (3.19); the CS keeps its last passing capture, whose publication is never blocked by a newer failing edit (glossary §27.1). *(rev 2.5, F14, F12; D1, replacing rev 2.4's "nothing: … no status text")* The `failed` list is kept in daemon memory only, as 05-holds' `last_check` (HLD-67 step 4; its shape is 10-product §3.5.1), and is shown in full only in the output of a `/cowork status --flow` run (10-product §3.5.1, F14) or `/cowork wrap` run (10-product §3.20.4, FEAT-F12-06), as a slash command (whose output the seat's Claude reads) or in a terminal, and is never pushed (glossary §29.1 D1). That latest result per open CS is not a record, event, message or status text: it is never in `status.json`, a seat carrier (06-claude §3.14.1), a human mirror (10-product §3.12) or a notification, it is lost at daemon restart, and the reasons `no_snapshot`, `merge_conflict` and `no_merge` reach it as such, never as a check number. Turn end, green checkpoint and `cowork_checkpoint` are unchanged: they publish without a passing edit check only if T0 passes, and a still-failing CS becomes a K7 PIN there.

**What it is not.** It is not a gate: it takes no claim view, and foreign-claim touches remain K2 at CONFIRM (3.11) and B1 at publish (REG-20). It is not T0: a passing edit check authorizes no push; every publish of the capture still runs `gate` (REG-20), `placementCheck` (REG-24) and T0 (HLD-50) on the real P and OUT at the leased tip, which may differ from `M'` (INV-REG-EDITCHECK). It is not a timer: it runs only at edit checkpoints, so 05-holds' "no time-capped WIP publishes" stays (glossary §27.1). A wake-turn CS is checked like any Claude CS; a `wake-scope` PIN (REG-33) holds it regardless of the result.

Expected Claude-edit latency with this check: ≈ edit check (≤ 0.5 s) + governor window (G = 5 s, S = 1.5 s at B = 12, glossary §27.2) + receiver fetch/apply ≈ 10–30 s (MODEL, glossary §27.1; measured in the soak, TST-).

Why: glossary §27 (the user's answer "must be faster" to the 30 s – 3 min Claude-edit latency); VERIFIED x10 (T0's region part fits 0.5 s); VERIFIED X7 and x2/x3 (half-done states that break callers or imports pass `py_compile` but are exactly what checks 2–3 catch, so publishing at structural checkpoints instead of on a timer keeps them unpublished).

**Chapter-local invariants**

- **INV-REG-COORD** No IPC message, board op, region API value or log record carries a byte, character or UTF-16 offset of file content.
- **INV-REG-NOWRITE** Dropping every region verdict except the blocked-CS list and the placement failures leaves every pushed blob byte-identical; every pushed blob equals `TIP[p]`, `P[p]` or the OUT entry for that path (merge output, conflict-function whole-path replacement or concat blob; glossary §3 "OUT").
- **INV-REG-FENCE** For any live commit C landed on the remote and any claim c active at the board tip C was leased on, the lines of c mapped into C differ from the previous live tip only by hunks attributed to c's holder seat, to the holder peer's `human` (REG-19 exception), to a CS admitted by a go-first grant on c, or by a base-move commit (`Cowork-Base`), whose changes raise the K5 input via REG-25.
- **INV-REG-MAP** A claim's mapped range always equals the true extent of the lines it was taken on, across any sequence of peer insertions and deletions above, inside and below it, and across stored and working forms.
- **INV-REG-FOLD** All peers that folded the same board tip agree on the validity of every claim op, whatever their machine speed or region tables.
- **INV-REG-TRIPWIRE** No pushed blob has more `ERROR`/`MISSING` nodes than TIP's blob of that path, more occurrences of any label key than `max(TIP, ours)`, or invalid UTF-8 where TIP was valid.
- **INV-REG-NOLABEL** No claim is ever found, matched, released or cleared by its label.
- **INV-REG-PARTITION** The leaf units, `<imports>` and gap blocks of one table are pairwise line-disjoint; the claims one table can produce never overlap each other.
- **INV-REG-NOVALID-OVERLAP** No two active claims of different holder seats in a fold state overlap under `foldOverlap`.
- **INV-REG-READ** *(added in rev 2.3; glossary §26 W1, W6)* No region function opens a user's working file, runs git on one, or reads through `cat-file` an oid that only a snapshot tick computed; every working content it sees is a `diskSnapshotId` from one stable short read (REG-35).
- **INV-REG-EDITCHECK** *(added in rev 2.4; glossary §27.1)* Removing `editCheck` (every call failing) changes only when a Claude CS is captured and published, never what is pushed: every pushed blob still passed `gate`, `placementCheck` and T0 on its real P/OUT, and a failed edit check leaves no record, event or message behind (REG-36). *(rev 2.5, F12)* The daemon's in-memory latest result per open CS (`last_check`, 10-product) is not a record, event, message or status text: it is never in `status.json`, a seat carrier, a mirror or a notification, and is rendered only in the output of a `/cowork wrap` (FEAT-F12-06) or `status --flow` (F14) run, slash or terminal. *(rev 2.5, F10)* A revert preview's prediction (3.20 "Caller and trigger") is likewise display data and changes neither when nor what is published.
