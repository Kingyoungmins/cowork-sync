# 05 — Holds, change-sets and publication timing

**Status:** normative · conforms to glossary REVISION 2.4 (§23, §24 with its twelve owner-decided technical defaults, §25 rev 2.2 spike facts F1–F13 and pass-2 owner decisions, §26 rev 2.3 Windows contention facts W1–W6 and synthesis decisions, §27 rev 2.4 user review answers and spec approval of 2026-10-02 (S1 revised: publish at every passing edit checkpoint; U3 revised: push budget 12 per minute with automatic fallback to 6); where they differ the newest section wins) · **rev 2.5 (2026-10-08, proposals F10, F12, F14; glossary §29):** own change-set revert (Algorithm REV, HLD-68), the in-memory `last_check` of a failing edit check (HLD-67 step 4); owner decisions D1 (`last_check` shown in full in the output of every `status --flow` and `wrap` run, slash or terminal, and never pushed) and D2 (a confirmed revert's written blob, carried forward by a clean HLD-41 rebase, is shrink attribution, HLD-50) are **final** since the owner decided them on 2026-10-08 (glossary §29.1) · **Depends on:** 00-glossary (+ 01-engine ENG-, 02-protocol PRO-, 03-data DAT-, 04-regions REG-, 06-claude CCI-, 07-coordination COO-, 08-lifecycle LIF-, 09-security SEC-)

This chapter decides which local bytes may leave this PC and which incoming bytes may land on it. It works in whole change-sets. Every version it withholds or displaces goes into exactly one store, the hold registry (glossary §9). The registry is mirrored to the remote board, so a displaced version never lives on only one disk unless it is secret-bearing (`local_only`).

It owns:
- the hold registry (record lifecycle, the closed guard table of glossary §9, board mirror, compaction);
- the operator family REBASE / MASK / PARK / RESTORE;
- the one revert detector;
- the mass-change breaker that sets FREEZE `MASS`;
- change-set (CS) identity, boundaries, ready trees and publication groups;
- publication timing (S1 as revised in glossary §27.1), including the edit check that gates an edit-checkpoint capture (HLD-67);
- sender-side whole-CS holds (the PIN side of K2, K3, K6 and K7, and the S5 `wake-scope` PIN) and the K1 SHADOW record;
- receiver-side change-set closures (INV-GROUP);
- the escalation ladder, including the S6 24 h auto-park;
- the durability preconditions used by stop and uninstall;
- the INV-NOLOSS harness extension;
- Algorithm REV, the reverse 3-way merge that takes one of this peer's own shared change-sets out of the live tree (HLD-68). *(added in rev 2.5, F10.)*

## 1. Scope

### v1 in scope

- One hold registry at `refs/cowork-local/<enc(b)>/holds` with the kinds `PATCH`, `PIN` and `INCOMING`, the residences `ON_DISK` and `OFF_DISK`, the states and offer values of glossary §9, mirrored as `hold` ops plus `held/<hold_id>/<stage>/<repo path>` blobs (glossary §3 board commit, §7).
- The operator family REBASE, MASK, PARK and RESTORE, built only on `git merge-file -p --object-id` (git ≥ 2.43).
- Content capture from the working tree only through the staged-copy read (one short read of the user's file into `<gitdir>/cowork/tmp/stage/<path>`, then git on the copy; glossary §26.1 W1), and object writes by this chapter only for record content and ready-pair captures, never on a detection tick and never for a hook request; `S_disk` blobs are written only when ENG- materializes for a capture, an apply or a hold record (glossary §26.1 W6; 01-engine §3.8; HLD-03, HLD-40).
- A two-tree loop: `S_disk` is the only apply input; `S_pub = MASK(S_disk)` is the detection and status tree; the publish composition P (glossary §3, built from `MASK(R)` of ready pairs) is the only publish input; INV-MASK (over `S_pub` and P) is asserted on every loop.
- One bidirectional per-line revert detector, fed by the provenance journal `prov/<enc(b)>.jsonl`.
- The mass-change breaker, which sets FREEZE `MASS` (glossary §8).
- A guard contract with PREDICATE and DECISION guards that compose with AND.
- CS identity, boundaries and triggers; publication groups; capture-at-trigger ready pairs that are rebased at every apply; `Cowork-CS` and `Cowork-CS-Paths` trailers (glossary §5).
- The edit checkpoint of glossary §27.1: after every Claude edit (edit-class PostToolUse, or a Bash/PowerShell transaction close) the daemon runs the edit check (four structural checks, ≤ 0.5 s on a 1.3 MB file) on a capture of the CS; a pass makes that capture the CS's ready pair, a fail captures nothing and says nothing (HLD-67). *(added in rev 2.4.)* A fail pushes nothing to any carrier; the daemon keeps its result in memory (`last_check`, §2) for a `/cowork status --flow` or `/cowork wrap` run (read-only verbs; shown in full as a slash command, which the seat's Claude then reads, or in a terminal). *(added in rev 2.5, F14, F12; owner decision D1, final 2026-10-08, glossary §29.1.)*
- Whole-CS PIN records for K2, K3, K6 and K7, and for writes of a wake-originated turn outside the wake work set (guard `wake-scope`, S5, HLD-66); the K1 SHADOW PATCH record; dependency bundling. Only LIVE paths enter a mirrored record (glossary §9, rev 2.1; HLD-03).
- Receiver change-set closures and INCOMING records.
- The branch-escape check for held changes that leave through a human git commit.
- Human `/cowork resolve <id> --publish|--discard|--park|--restore|--handoff` semantics, `/cowork done`, and the MCP `cowork_checkpoint` and `cowork_resolve(id,"restore")` handlers.
- The escalation ladder (glossary §20 "Hold escalation") and the S6 24 h auto-park, including records that carry restore markers (the markers park, §3.4 item 3; glossary §9 rev 2.1).
- Durability preconditions for `/cowork stop`, `/cowork uninstall [--purge]` and start re-attach.
- Own change-set revert (Algorithm REV, HLD-68): the computation behind the human acting verb `/cowork revert <cs_id>|last` (preview/confirm, SEC-25 evidence; verb, texts and refusal codes are 10-product's) and behind the undo view of `/cowork show <cs_id> --undo` and `cowork_show(<cs_id>)` (06-claude, 07-coordination `T-SHOW_UNDO.*`). The result is one ordinary human-class CS; nothing new reaches the board (no op, op field, trailer key or ref). *(added in rev 2.5, F10.)*

## 3. Design

### 3.1 Why one registry

Each of the following failed in the failure sweep:
- several holding stores, which led to ghost duplicates (one-change-two-stores, VERIFIED x1: the conflict stage-2 oid equals the revert hold's H1);
- positional keys (line-range-hold-misses-and-corrupts and hunk-identity-key-unstable, both VERIFIED critical);
- `.patch` files replayed with `git apply` (positional-patch-quarantine-misapplies, VERIFIED: lands in the wrong function with exit 0);
- local-only refs (park-refs-in-worktree-namespace-vanish, VERIFIED: deleted by `git worktree remove`, pruned by `gc --prune=now`).

The design therefore has:
- **one store**: an append-only commit chain in the common ref namespace, mirrored to the board;
- **one representation**: the ORIGINAL stored-form blob pair, or the three conflict stages;
- **one primitive**: `merge-file`.

Presence is computed, never matched. VERIFIED exp_j_fuzz: rebased mask 160/160 correct, while a static mask was wrong in 19/19 team-revert trials. VERIFIED exp_r_rebase: single-step rebase from the original pair equals iterative rebasing in 347/347 trials.

### 3.2 The record

The record schema is glossary §9, verbatim. In this chapter:

- `kind`
  - `PATCH`: a sub-path change. H1 is the held version of the path; MASK removes only the H0→H1 change.
  - `PIN`: whole paths pinned to `A[p]` in the outgoing tree. Always used for a whole CS or bundle, and for binary paths.
  - `INCOMING`: a receiver closure not yet applied.
- `residence`
  - `ON_DISK`: the held bytes are on disk and are masked out of `S_pub`.
  - `OFF_DISK`: the disk has the team version; the bytes live only in the registry and on the board.
- `state`: valid combinations are in Table 1.
- `offer`: independent of state (HLD-09).
- `displaced_by`: an op id or null (Table 2).
- `rev`, `age_anchor`, `blobs`: glossary §9 (§2 above gives this chapter's content of `age_anchor`).
- Paths: only LIVE paths enter a mirrored record (glossary §9 rev 2.1); a record that would have to include a non-LIVE path is `local_only` (HLD-03).

**Table 1: residence × state**

| residence | allowed non-terminal states | meaning |
|---|---|---|
| ON_DISK | ACTIVE | held bytes on disk; masked if the guard set is non-empty |
| ON_DISK | CONFLICTED | REBASE or MASK conflicted; the **whole path** is withheld (`S_pub[p] := A[p]`); or a conflict-policy displacement is waiting for a lease before its TIP write; or a base-move conflict (ENG-48, HLD-56) on bytes still on disk |
| OFF_DISK | PARKED | displaced by PARK (stop, `--park`, S6 timer), or born off disk (a SHADOW: its bytes were never written; a returned SHADOW stays here; a marker companion, §3.4 item 3) |

### 3.4 Operators (all `git merge-file -p --object-id`, through `runGit`, class `attr`)

Notation: `mf(cur, base, other)` is `git merge-file -p --object-id <cur> <base> <other>` with MERGE_FLAGS (glossary §18), and returns (blob, rc). `A` is ENG's per-path base `A[p]`, **never** `tree(LA_C)[p]` (pending-path-base-misset-reverts, VERIFIED). Every "disk equals blob" test in this chapter is `DISK_EQ` (glossary §3, ENG-11), never `hash-object --path` of a working file compared with a blob id (it misreports `i/crlf` files; glossary §26.2 item 3). Every read of a user's working file is the staged-copy read of HLD-03 (glossary §26.1 W1).

Operator inputs are blob objects (`--object-id`). Detection ticks write no objects (glossary §26.1 W6: objects are written only for ready-pair captures, publishes, applies and hold records), so the objects these operators read come only from those occasions: team blobs (`A[p]`, TIP; applies and fetches), ready-pair captures (`R`, HLD-40), record content (`H0`, `H1`, stages; HLD-03), and `S_disk` as ENG- materializes it (01-engine §3.5 step 3, §3.8 "When an iteration materializes": a ready-pair capture, an admitted apply, or a hold record created from disk bytes). An edit checkpoint (HLD-67) is a ready-pair capture occasion whether its edit check then passes or fails: the candidate is materialized before the check runs (§8 Q14 on the object growth this adds). *(added in rev 2.4.)* MASK step 5, HLD-19, HLD-21 and R1 read `S_disk[p]` of a held path from the last materialized `S_disk`; this chapter writes no per-tick blob for a held path, so a held path that an editor keeps saving costs no object until the next materializing iteration (§8 Q12, resolved). Between materializations `S_pub` stays the MASK of the last materialized `S_disk`. That is safe: `S_pub` is for detection and status only (HLD-20), and P is composed only from ready pairs (HLD-42), each captured in a materializing iteration after D2 and MASK ran on that `S_disk` (01-engine §3.5 step 4, ENG-14). Every record created or refreshed from disk bytes (HLD-46, HLD-47, HLD-66, the Table 4 collision capture) writes those bytes as record content through the staged-copy read (HLD-03); a PARK (its held-side refresh and its writer CAS), the markers park and a RESTORE, which also read `S_disk[p]`, run in an iteration that materializes their paths first, so their `S_disk[p]` is the current disk. Both are W6's "hold records" occasion (01-engine §3.8 (c)). A hook request for named paths (for example a PostToolUse refresh of HLD-21) gets ids or in-memory bytes without `-w` and writes no object (glossary §26.1 W6). A path without a record is tracked by id only until a capture, an apply or a record materializes it.

1. **REBASE(r, p)**: `H1'[p] = mf(A[p], H0[p], H1[p])`, always single-step from the ORIGINAL pair, with `H0'[p] = A[p]`. The result is cached by `(r.id, r.rev, A[p])`. rc ≠ 0 means conflict.
2. **MASK(X)** (glossary §3; X is `S_disk` for `S_pub`, or a ready tree `R` for P), per path p, in this order:
   1. p's scope class is `QUARANTINED`, `SAVE_ONLY` or `UNMANAGED` → `A[p]`.
   2. p is a path of a non-terminal ON_DISK `local_only` record, or of an ON_DISK record carrying a whole-path guard (§2) → `A[p]` (absent if `A[p]` is absent). An OFF_DISK `local_only` record (a marker companion, the local copy a collision `--publish` or a `review --accept` keeps) masks nothing (INV-HLD-OFFDISK).
   3. p is covered by an ON_DISK PIN with a non-empty guard set → `A[p]`.
   4. p is covered by an ON_DISK CONFLICTED record, or by an OFF_DISK record carrying `claim-breach` → `A[p]`.
   5. Otherwise, for each ON_DISK ACTIVE PATCH with a non-empty guard set on p, in ULID order: `x := mf(x, H1'[p], H0'[p])`, starting from `x = X[p]`. rc ≠ 0 → the record becomes CONFLICTED and the path takes `A[p]`.
   6. Otherwise `x`.

   OFF_DISK records never change `S_pub` or P, except a `claim-breach` path pin.
3. **PARK(r)**: for each p of r, a target is computed:
   - PATCH ACTIVE with no whole-path guard (§2): the step-5 MASK result for r alone;
   - PIN, CONFLICTED, or a record carrying a whole-path guard (its path is masked by step 2, not step 5): `A[p]`.

   Before any write, every byte of `S_disk[p]` that differs from the target must be inside r:
   - PATCH ACTIVE with no whole-path guard: true by construction;
   - PIN, CONFLICTED, or a record carrying a whole-path guard other than `markers`: refresh the held side (`H1[p]`, or `s2[p]` for a record with stages) `:= S_disk[p]` (new rev) first;
   - a record carrying `markers`: the markers park below, never a refresh.

   Then `writeLocal(p, S_disk[p], target)` (ENG-37). Residence becomes OFF_DISK and state becomes PARKED, except that a CONFLICTED record stays CONFLICTED with residence OFF_DISK.

   **Markers park** (a record r carrying `markers`; glossary §9 rev 2.1: S6 applies to records of restore markers, and restore markers never reach any remote ref, neither live blobs nor `held/` blobs). r's disk file holds restore-marker rows and possibly a half-done resolution that is in no blob, so r's held side is never refreshed from disk (that would copy marker rows into a `held/` blob). Instead, in one registry commit:
   1. for every path p of r, `M[p]` := the clean blob of the disk file, through the pinned clean path (HLD-03);
   2. one **marker companion** r′ is created over r's paths: PATCH, `h0[p] = A[p]`, `h1[p] = M[p]`, `origin = r.origin`, born OFF_DISK PARKED, `displaced_by` null, with no guard (its PARKED state is its displacement, HLD-17; this is the only `hold()` call without a guard, HLD-05), and `local_only = true` (HLD-03), so every op it emits is a content-free stub and M never reaches a remote ref;
   3. `writeLocal(p, M[p], A[p])` for every path p (ENG-37; `writeLocalGroup` when r has several paths), all or none (HLD-16);
   4. r's guard `markers` releases (the disk has no restore-marker row any more); r keeps its mirrored blobs unchanged; residence becomes OFF_DISK and state PARKED (a CONFLICTED r stays CONFLICTED).

   r′ is a separate change (the in-progress resolution), so HLD-07 never merges it into r; `/cowork show` lists it as the in-progress resolution of r (same origin and paths). `/cowork resolve <r′> --restore` (or `cowork_resolve(r′,"restore")` under HLD-59) writes M back with its rows and guard `markers` (item 4); `--discard` of r′ drops only the half-done resolution, and r stays restorable from its own blobs. A marker companion ends GONE as soon as its `markers` guard releases on disk: what is on disk then is the actor's ordinary edit and publishes through every gate (R1). Human `--park`, S6 (HLD-61) and stop (HLD-63) all use the markers park for a record carrying `markers`. *(changed in rev 2.1: rev 2 refused `--park`, postponed S6 and left the record ON_DISK at stop; glossary §9 now applies S6 to these records.)*
4. **RESTORE(r)** (glossary §23 decided default; DAT-45): the bytes to restore are `held = H1` (or `s2` for a conflict record), on the base `b = H0` (or `s1`).
   - Text path: compute `git merge-file -p --diff3 --object-id -L cowork:disk -L cowork:base -L cowork:held <disk[p]> <b[p]> <held[p]>`, where `disk[p]` is the clean blob of the current disk content, taken through the staged-copy read and written as record content (HLD-03; glossary §26.1 W1, W6).
     - Clean (rc 0): write it with `writeLocal(p, disk[p], result)`. If the written result contains a restore-marker row (the restore of a marker companion), the record gains guard `markers` exactly as below.
     - Conflicted (rc > 0): write the result, with its `cowork:`-labelled restore markers, on the owner's disk through the same `writeLocal` call, and add guard `markers` to the record. While `markers` holds, MASK keeps `S_pub[p] := A[p]` and P never carries the path; the seat or human is told `RESTORE_MARKERS(id, path, rows[])` naming the marked rows (DAT-45's code; template COO-). When the rows are gone, the path publishes as an ordinary observed edit (DAT-45). Restore markers never reach any remote ref (glossary §9 and INV-SECRET, rev 2.1): DAT-46 and ENG-41(e) enforce it for live blobs; this chapter enforces it for `held/` blobs (a record carrying `markers` is never refreshed from disk, and a marker companion is `local_only`, item 3).
   - Binary path (human `--restore` only, DAT-45): write `held[p]` whole when `DISK_EQ(p, b[p])` or `DISK_EQ(p, A[p])`; otherwise write nothing and refuse with `HOLD_RESTORE_CONFLICT`. `/cowork show <id>` renders base, disk and held from the oids.
   - Deletions and recreations follow DAT- §3.9 cases 2–3.
   - `merge-file --theirs` (allowed by glossary §9 only inside RESTORE) is not used in v1.
5. **taintOnlyH1(p, tainted hunks)**: `H1 = A[p]` with only the tainted -U0 hunks of `diff(A[p], S_disk[p])` applied. This is the **only** function allowed to apply -U0 hunks. Its output is only ever a record's H1, never an outgoing, working-tree or saved blob. The outgoing effect is always produced by MASK through `merge-file` (glossary §9 lint allow-list entry).

### 3.6 Algorithms

**Algorithm D2 (revert detector, on every newly materialized `S_disk` (01-engine §3.5 step 4), before that iteration's merge or capture; glossary §26.1 W6):**
1. For each path p whose snapshot blob changed since the previous snapshot entry (the private-index entry, which ENG- round-trips to `M_disk[p]` after an apply, so applied changes are not local deltas), compute `Δ = diff -U0 (prev[p], S_disk[p])`. Which paths changed is known from the detection ticks since the last materialization (ids only, no object written; 01-engine §3.8 step 5, glossary §26.1 W1, W6); `prev[p]` (the private-index entry before this materialization) and `S_disk[p]` are both objects, so D2 writes no object of its own except `hold()` content (HLD-03). A detection tick that materializes nothing has no new `S_disk` and runs no D2; a delta made between materializations is classified at the next materializing iteration, before any byte of it is merged, captured or recorded (01-engine §3.5).
2. Drop observed deltas (HLD-26).
3. For each remaining hunk h:
   - h is tainted if a removed non-trivial line's SHA-1 appears in the journal as `add` by a writer ≠ this peer;
   - or if an added non-trivial line's SHA-1 appears as `del` by a writer ≠ this peer;
   - always within the retention window.
   - ws-equal pairs are exempt.
   - A hunk that REBASE-matches a RESOLVED_PUBLISH record on p is exempt (HLD-29).
4. If any hunk of p is tainted, compute `H1 = taintOnlyH1(p, the hunks of diff(A[p], S_disk[p]) that contain a tainted line)` and call `hold([p], PATCH, revert, H0=A[p], H1, origin)`. The dedup rule (HLD-07) attaches it to an existing record when H1 matches.
5. A binary path, or a deletion, with taint becomes a PIN with guard `revert` instead.

**Algorithm P (publish, inside ENG step 6):**
1. `G := groups()` (HLD-38). For each group: ready? (HLD-39).
2. For each ready group g, run REG `gate()` over every hunk of `diff(A[p], R[p])` for p ∈ paths(g), on the board fold of the exact tip the push will lease. A blocking result means `hold(LIVE paths of g, PIN, claim:<claim_id>, …)` for the whole group (HLD-45; glossary §9 LIVE-only rule).
3. `P := compose()` (HLD-42). If `P == A` on every path and there are no board ops, no push.
4. ENG- computes OUT (glossary §3: `merge-tree --write-tree --merge-base=A P TIP` plus the conflict function's whole-path replacements and concat blobs; ENG-39) and routes conflicts and REG identity-check failures (REG-24) to DAT-.
5. T0(OUT) (HLD-50). A failure holds the failing group as a PIN with guard `t0` and restarts at step 3 without it; when the failing group's capture is an edit-checkpoint capture of a still-open CS, the capture is dropped instead (no PIN, no message; HLD-67, rev 2.4) and step 3 restarts without it. The drop records `last_check{kind: stale}` for that CS (§2; HLD-67). *(added in rev 2.5, F14; owner decision D1.)*
6. ENG- pushes. On CAS loss, ENG- refetches and step 1 runs again from scratch (no verdict is reused, ENG-40).
7. On push ok, ENG- updates A per its confirmed-push rule (ENG-44). Groups whose content landed are marked published; their CSs are removed from the open table after the next record evaluation.

**Algorithm R1 (record evaluation after each apply step, ON_DISK records, first match wins):**
1. **CONFLICTED** if REBASE of any path conflicts, or MASK of any path conflicts. For a PIN, REBASE(H1) conflicting is CONFLICTED too.
2. **SUBSUMED** if for every p, `H1'[p] == A[p]`. A record that was released by an explicit `--publish`, `--restore` or `cowork_resolve(id,"restore")` becomes **RESOLVED_PUBLISH** instead (HLD-29).
3. **GONE** if:
   - PATCH: `MASK_r(S_disk)[p] == S_disk[p]` for every p (the held change is no longer on disk);
   - PIN: `S_disk[p] == A[p]` for every p.
4. Otherwise **ACTIVE**.

A record carrying `markers` (after a conflicted RESTORE, HLD-17) skips steps 1–3 while `markers` holds: it stays ACTIVE with its path withheld whole (whole-path guard). When `markers` releases on disk, the record has no displacement guard left, its disk content publishes as the actor's observed change, and it ends RESOLVED_PUBLISH once that publish reaches A (HLD-29); a marker companion ends GONE at once instead (§3.4 item 3).

OFF_DISK records are checked only when `A[p]` changes, by one REBASE from the original pair. `H1' == A` on every path means SUBSUMED; otherwise nothing changes. They are never GONE-evaluated (INV-HLD-OFFDISK). INCOMING records are evaluated by HLD-54.

**Algorithm REV (own change-set revert, HLD-68; on a CLI or MCP request, in a daemon worker, never in a hook):** *(added in rev 2.5, F10.)* Input: a target `t` and a mode, `verb` (`/cowork revert`: preview, then the confirmed write) or `view` (`/cowork show <cs_id> --undo` and `cowork_show(<cs_id>)`: the same computation, no write). All git work goes through `runGit` (glossary §18) and stays in memory except the confirmed write: `merge-file -p` prints to stdout, and nothing in steps 1–7 writes an object (glossary §26.1 W6; §8 Q17). Bounds (glossary §20 row "Revert"): the window is the provenance journal's 14 days (HLD-25); ≤ 2,000 paths per revert and ≤ 500 `merge-file` runs per computation (paths unchanged since the CS need none, step 4(a)), computed within ≤ 30 s; past any bound → `RF_REVERT_TOO_BIG`.
1. **Resolve and locate.** `t` is a full `cs_id` (glossary §3), a unique prefix of ≥ 6 characters among the CSs inside the window, the qualified form `<cs_id>@<epoch8>` (the first 8 characters of the epoch in `Cowork-Writer`), or `last`: the newest **closed** CS of this peer, by board order of its newest commit, or by local close order for a CS not yet in the live chain. Open CSs are ignored, and closure comes from the CS table, never from the trailer state (a CS fully published by edit checkpoints has only `state=checkpoint` trailers, §8 Q16). A revert CS is a CS too, so `last` after a shared revert previews its redo.
   - `C(t)` = the journal entries (HLD-25) whose `cs_ids` contain `t`, in first-parent order, restricted to one `(peer, epoch)` (HLD-33): the epoch named by `@<epoch8>`, else the only epoch under which `t` occurs in the window. The epoch is read from each commit's `Cowork-Writer` trailer (the journal's `writer` keeps only the `peer_id`). The same `cs_id` under another epoch is another CS, so an unqualified `t` found under two epochs, or a prefix that matches several CSs, → `AMBIGUOUS_ID` (≤ 5 candidates, qualified where needed).
   - `C(t)` empty: one `rev-list --first-parent -F --grep='Cowork-CS: <t> '` over the live chain decides `RF_REVERT_TOO_OLD` (found) or `RF_SHOW_UNKNOWN_ID`; `last` with no qualifying CS → `RF_REVERT_NO_LAST`.
   - Any `c ∈ C(t)` with a writer ≠ this peer → `RF_REVERT_NOT_OWN` (in view mode: the summary only, `T-SHOW_UNDO.notown`, never an undo view). `t` in the open-CS table → `RF_REVERT_OPEN`. `t` in a ready pair, or in the `cs_ids` of a non-terminal record → `RF_REVERT_NOT_SHARED`; `last` refuses the same way and never skips to an older CS.
   - Verb mode while any FREEZE reason is set (glossary §8) → `RF_REVERT_FROZEN` (stricter than glossary §8, which still allows a human resolve while frozen). A publish pause (`OFFLINE`, `AUTH`, `VERSION`, `NONRETRYABLE`) refuses nothing: the revert CS waits like any CS.
2. **Paths** of `t` in each `c ∈ C(t)`: its `Cowork-CS-Paths`, or, without one (> 256 paths), every path of `diff(parent(c), c)` (HLD-37: a CS without a path list covers every path of its commit). A path is `MIXED` if in some `c ∈ C(t)` that changes it another `Cowork-CS` of `c` also covers it (by its list, or by having none). **Rename pairs:** the two paths that `diff -M` of some `c ∈ C(t)` against its first parent (`runGit`, `--no-ext-diff --no-textconv`, glossary §18) pairs as one rename are one unit in steps 3–7: when either side is skipped for any reason, the other is skipped as `RENAME_PAIR`, so a partial revert never leaves both the old and the new file.
3. **Path guards.** p not `LIVE` now (glossary §3 scope classes) → `NOT_LIVE`. Verb mode only: p in an open or unpublished CS, under a non-terminal record, `A[p] ≠ TIP[p]`, or `¬DISK_EQ(p, A[p])` → `BUSY`. So in verb mode every remaining path has `S_disk[p] = A[p] = TIP[p]`.
4. **Reverse 3-way**, per remaining path p: `ours := S_disk[p]` (the current disk; in view mode the newest materialized blob of p, used only when `DISK_EQ(p, it)` holds — otherwise p is not computed and the view lists it as one line "changed on this PC since; ask again shortly", so view mode writes no file or object, §8 Q17); then for each `c ∈ C(t)` that changes p, newest first, with `before = parent(c)[p]` and `after = c[p]`:
   - (a) `ours == after` (nobody touched p since) → `ours := before`: a file the CS created is deleted, a file it deleted is restored; no process;
   - (b) else, if a side is ABSENT, p is binary (DAT-04) or the file mode differs → `FILE_CHANGED_LATER`: skip the whole path;
   - (c) else `(out, rc) := mf(ours, after, before)`; rc 0 → `ours := out`; rc > 0 → `ours :=` the same run with `--ours` (the one `--ours` use, HLD-12), and each conflict region becomes a kept hunk (`CHANGED_LATER`). Conflict markers are never written anywhere.
5. **Taint backstop.** On `diff(S_disk[p], ours)`, Algorithm D2's step 3 predicate (same journal), restricted to lines outside the CS's own journaled sets (the union over `C(t)` of `paths[p].add` for removed lines and `.del` for re-added ones): any such non-trivial line journaled `add` (removed here) or `del` (re-added here) by a writer ≠ this peer → the whole path is skipped as `TEAMMATE_LINE`. Steps 4(a)–4(c) only remove lines the CS added and re-add lines it removed, so this never fires on a correct run; it guards the merge, costs no process, and gives the observed revert write the protection D2 gives an unobserved delta (HLD-68).
6. **Predict** (verb-mode preview only): REG `gate()` (REG-20) of the result hunks on the current claim view → `UI_REVERT_WOULD_HOLD` (a B1 K6 at publish); 04-regions' edit-check entry point (HLD-67 checks 1–3 and the label-count part of check 4, the checks T0 shares) → `UI_REVERT_WOULD_BREAK` (a T0 K7 at publish). Because `BUSY` guarantees `A[p] = TIP[p]` and `DISK_EQ(p, A[p])` on every result path, the merged tree `merge-tree --merge-base=A R_rev TIP` is TIP with the result blobs on those paths, so the check is fed the result buffers and TIP's blobs directly; no tree or object is written. 04-regions admits this one read-only caller (3.20 "Caller and trigger", REG-35, REG-36): the buffers stay in memory, the verdict is display only, and no capture, record or `last_check` follows from it. The shrink part of check 4 and T0's shrink guard are not predicted: they do not fire on the blob the revert writes (HLD-50 item 3).
7. **Result** `R_rev` = the paths with `ours ≠ S_disk[p]`; empty → `RF_REVERT_NOTHING`. In view mode `R_rev` is rendered as the undo view (unified diffs only for in-file text changes; every created, deleted, binary, mode-changed or filtered path as one `T-SHOW_UNDO.human` line, never a diff; the kept hunks and skipped paths one line each, a path that step 4 did not compute in view mode as the skip reason `CHANGED_NOW`; 06-claude, FEAT-F10-10) and nothing further happens.
8. **Write** (verb mode, on a matching `--confirm=<id>`): recompute steps 1–7. The preview id is the LIF-02 digest over `t`, the oids of `C(t)`, and per path `(S_disk[p], R_rev[p])` plus the kept and skipped lists; a mismatch → `PREVIEW_STALE` (a fresh preview; nothing written). `hash-object -w` each result blob (§8 Q17), then one `writeLocalGroup` (ENG-37; all or none; `expected` = the digested disk blob, target = the result or `DELETE`, with human evidence). `MISMATCH` → `PREVIEW_STALE`; `LOCKED`, `DEFERRED`, `COLLISION`, `PHANTOM` or `FROZEN` → `RF_REVERT_WRITE_FAILED`; in every outcome other than `WRITTEN` nothing is written. On `WRITTEN`:
   - open a new human-class CS `<peer_id>/human/<n>` (HLD-33) whose members are exactly these paths, and close it at once (HLD-40 "human close"; its capture records `R[p]` = the written blobs);
   - mark these writes revert-attributed for T0's shrink guard (HLD-50 item 3) as `{cs, path → written oid}` (the result blob's oid, or ABSENT for a deletion) while that CS is **pending**: its ready pair is in `journal/ready/` or its `cs_id` is in a non-terminal record (the §8 Q18 restart condition, so memory and restart agree). The mark is dropped when the CS publishes, when that record becomes terminal (RESOLVED_DISCARD, SUBSUMED) or when the CS leaves `journal/ready/` without publishing. The mark exempts only content equal to its current oid, and a hold keeps it, so a K6 PIN that auto-publishes on release (HLD-52) does not then fail T0's shrink guard (§8 Q18); *(pending condition: merge round 2)*
   - the mark follows a clean teammate rebase *(owner decision D2, 2026-10-08: §8 Q18 option (a); trigger and line contents restated in merge round 3)*: when an apply writes p as a clean merge or a `CONCAT` blob and HLD-41 rebases the group's ready pair for p — whether the plain `merge-file` rebase returned rc 0 or HLD-41's first bullet decided it — with no member file effect on p after the capture (`S_disk[p] == R[p]` before that apply), **and that pair's `R[p]` immediately before the rebase equals the mark's current oid for p** (a clean HLD-41 rebase, as HLD-41 defines it), the mark's oid for p becomes the new `R[p]` (the marked blob with the teammate's change merged in). The daemon then appends `{cs, of: t, t_local_ms, written}` to `cs/<enc(b)>.reverts.jsonl`, one line per apply: `of` and `t_local_ms` repeat the original line's values, and `written` is the mark's current map, every path of it, with the oid of every path this apply rebased replaced (so no line drops an earlier move of another path). The line is appended and fsynced before the state update that stores the rebased pair (ENG-36), so a crash between the two leaves a journaled pair that still matches an earlier line: the restart rule of §8 Q18 (per path, the newest line of that `cs` whose oid matches the journaled content) re-derives the mark that pair carries, never one the journal does not hold, and the restart's completion of the interrupted apply (ENG-53, deciding the rebase as ENG-36 does) is itself a clean HLD-41 rebase when the apply was, so it moves the mark again. The "revert of" label reads `of`, which every line of a `cs` carries alike, so extra lines do not change it. When `R[p]` before the rebase is any other blob (for example another member's later capture of p, 11-testing TC-F10-17 (d)), in any other HLD-41 case (a displaced local side, readiness cancelled, `A[p]` changed without a write of p, a member effect after the capture) and after any later effect, the mark is unchanged, so that content gets the ordinary guard;
   - append `{cs, of: t, t_local_ms, written: {path → oid | ABSENT}}` to `cs/<enc(b)>.reverts.jsonl` (glossary §6; display, plus the re-derivation of the mark at start, §8 Q18; kept 14 days) and report `REVERT_REPORT`.

### 3.7 Publication timing (S1, revised in glossary §27.1)

Confirmed claims (glossary §3 `claim`) leave at once, as board-only pushes in the next governor window, so they are visible within seconds (U4, S1; PRO-). Code leaves only as whole publication groups, from a passing capture (§2) taken at one of these triggers:
- a Claude CS (glossary §27.1, rev 2.4), at the first of:
  - (a) every **edit checkpoint** whose **edit check** passes (HLD-67): after every Claude edit (edit-class PostToolUse, or a Bash/PowerShell transaction close), on a capture of the CS's current content;
  - (b) turn end (Stop, StopFailure, SubagentStop; and the other closes of HLD-34);
  - (c) a green checkpoint (a passing `checks.checkpoint` command);
  - (d) `cowork_checkpoint`;
- a human CS after 20 s without edits on its paths, or at `/cowork done` (unchanged);
- the human-class revert CS of a confirmed `/cowork revert` at its write, which closes it at once (Algorithm REV step 8, HLD-68). *(added in rev 2.5, F10.)*

*(changed in rev 2.4: rev 2.3 published a Claude CS only at turn end or a green checkpoint; the user answered "must be faster" to its 30 s – 3 min latency, glossary §27.)*

A passing edit check replaces the CS's ready pair (newest passing capture wins). A failing one captures nothing, keeps the last passing capture, never blocks that capture's publication, and creates no record and no pushed message (glossary §27.1; HLD-67); the daemon keeps its result only in memory (`last_check`, §2), shown only when `/cowork status --flow` or `/cowork wrap` runs, as a slash command or in a terminal (*changed in rev 2.5, F14, F12: "no message"; owner decision D1*). At turn end the normal path applies: a still-failing CS becomes a K7 PIN as before (HLD-50).

**No time-capped WIP publish (unchanged; glossary §9, §27.1).** An edit checkpoint is a structural checkpoint, not a timer: nothing publishes because time has passed, and an edit whose merged result breaks parsing, callers, references or file size (the four checks of HLD-67) is not published. What an edit checkpoint can publish is a *structurally consistent* intermediate state of a turn (for example a new helper before its first caller). The user accepted that for speed (glossary §27); the rev 2.3 claim "half-done exposure 0 %" is therefore not carried over, and the measure is now the I12 exposure of states that break a peer's parse, build or tests (§7).

The tree published is the one captured AT the trigger (ready pairs), rebased at every later apply. This matters because VERIFIED sweep/holdcat X1 showed that an unrebased capture drops a peer's fix with merge-tree rc 0 while every engine assert passes.

**Latency model (rev 2.4; MODEL, measured in the soak):** expected Claude-edit latency ≈ edit check (≤ 0.5 s) + governor window + receiver fetch/apply ≈ **10–30 s** (glossary §27.1), from these parts:
- edit check ≤ 0.5 s on a 1.3 MB file (HLD-67; the T0 budget, glossary §20 "T0 checks"), after a capture bounded at 150 ms (HLD-40, CCI-36);
- governor window at the U3 budget of glossary §27.2: B = 12 attempts per minute team-wide, G = 5 s, S = 1.5 s; worst normal publish wait for 4 peers G + 3·S = 9.5 s (+1 cycle per collision); under the automatic 30-min throttle fallback (B = 6, G = 10 s, S = 3 s) it is 19 s;
- receiver: the next fetch (loop period 2.5 s active, glossary §20) and apply coalescing (≤ 1 apply per 10 s per worktree; ≤ 1 per 2 min into files fully read by a mid-turn seat, which is the one case that can exceed the model).

Soak acceptance (glossary §27.2): ≤ B attempts in any 60 s window, zero HTTP 429, publish p95 ≤ 40 s, fallback engaged within one window of an injected throttle signal. More publishes per turn do not mean more pushes than the budget: the governor coalesces every ready group of the peer into one push (HLD-44), and a newer passing capture that arrives before the window simply replaces the older one.

**rev 2.3 baseline (kept as history; triggers (b)–(d) only, B = 6):** measured with checkpoints and no WIP cap (x12_sim_fixed, 3 seeds): half-done exposure 0 %; edit→publish p50 30–36 s, p90 96–111 s; 2.0–2.9 pushes/min. With Stop as the only trigger: p50 165–195 s. A time-debounced sub-turn unit (one that publishes whatever is on disk after a quiet period) would publish half-changes in 65 % of turns (debounce-splits-every-multifile-turn, VERIFIED x11 over 1,901 turns); the edit check is what separates an edit checkpoint from that unit.

### 3.8 Sender-side holds: why whole-CS PIN

Per-hunk withdrawal publishes trees no one ran. VERIFIED results:
- hunk-withdrawal-publishes-signature-without-callers: TypeError and CS7036 on peers;
- intra-file-withdrawal-mangles-file: duplicated or deleted functions with 0 py_compile failures;
- cas-remerge-breaks-cs-invariant.

A whole-CS PIN loses nothing (the author's disk is untouched), publishes nothing half-done, and needs no splice operator. The few designed cases where part of a CS stays behind (path-class masks, revert hunks, a K4 displacement) are listed in INV-HLD-ATOMIC-PUB; a path withheld whole by a record pins the rest of its group (HLD-42). The same PIN is used for:
- K2: a post-hoc foreign-symbol hit; per the cross-check fix there is no disk write;
- K3: a race loss in B1;
- K6: a human hunk in a foreign claim;
- K7: T0 failure or dependency.

### 3.9 Receiver side: why closures

Applying a CS partially breaks the receiver's running code:
- receiver-path-deferral-materializes-half-cs, VERIFIED x5a/x5b: TypeError and ImportError;
- dev-servers-restart-and-crash-on-split-apply, VERIFIED.

The receiver therefore defers whole CS closures, reading membership from the code commit's trailers. Membership must ride the code commit, because board and code are not pushed atomically (cs-manifest-must-ride-code-commit). ENG-'s two-phase verifying writer writes a closure all-or-none (INV-GROUP).

## 4. Rules

### A. Registry

- **HLD-01** Every reason this PC's disk or outgoing tree differs from (TIP + this peer's ready, unheld publication groups) MUST be a record in the one hold registry. The only exceptions are path-class masks (scope classes `QUARANTINED`, `SAVE_ONLY`, `UNMANAGED`, see §3.3) and the per-loop transient exclusions of HLD-32 (glossary §9).
  - The registry is the commit chain at `refs/cowork-local/<enc(b)>/holds`. Each transition is a new commit whose first parent is the previous registry commit, with tree `records/<id>.json` plus the referenced blobs.
  - Nothing is overwritten.
  - The ref is updated only by CAS `update-ref --create-reflog <ref> <new> <old>` through `runGit(class: refupdate)` (which carries `core.logAllRefUpdates=always` and the fsync options).
  - The daemon calls `crashpoint("registry.cas")` immediately before and immediately after that CAS `update-ref` (two call sites, one name; glossary §25.2 item 10, 11-testing §3.6). *(added in rev 2.3.)*
  - It is never under `refs/worktree/*`.
  - It is re-attached on daemon start before the first snapshot is published.

  _Covers: park-refs-in-worktree-namespace-vanish, local-only-holds-break-nothing-lost, no-history-undo, one-change-two-stores_
- **HLD-02** A record's identity MUST be its ULID `id`. Its content MUST be the ORIGINAL stored-form pair (`H0` = A[p] when made, except SHADOW per HLD-47; `H1` = the held version) or the stages `s1,s2,s3 = (A, LOCAL, TIP)` for a conflict record. Content hashes MAY be used only for display and dedup. Line ranges, patch-ids and pre/post-image hashes MUST NOT appear in the record or decide masking, release or matching. _Covers: line-range-hold-misses-and-corrupts, hunk-identity-key-unstable_
- **HLD-03** Blob content MUST enter the registry only through the pinned clean path: a private-index add, or `hash-object -w --path=<p>` with `attr.tree=<EPOCH_BASE>` and `filter.<d>.required=true` for every discovered driver (glossary §18). It MUST NOT come from `--stdin` without `--path`, from JS strings, or from raw tool input.
  - **Staged-copy read** (glossary §26.1 W1; on every OS, one code path): git never runs on a user's working file. To capture p, the daemon makes one short read (open share-all, read the whole file, close; glossary §26.1 W3), compares size and mtime before and after (one re-read if they differ), writes the bytes to `<gitdir>/cowork/tmp/stage/<path>`, and adds or hashes **the copy** with `--path=<p>`, so attributes and filters apply as for p (filters run with cwd = the repository root, glossary §25 F12). A read that is still unstable after the re-read captures nothing this loop: the path is a transient exclusion (`unstable`, HLD-32) and the capture is retried at a later loop. A captured 0-byte or > 50 % shrunk file is subject to the shrink guard (glossary §20, §26.1 W2; HLD-32). Every "through the clean path" and every `clean(disk[p])` in this chapter (HLD-46, HLD-66, the markers park, RESTORE, Table 4 collision capture) is this read; HLD-47 hashes the bytes of the CCI-18 deny pre-record the same way (written to the stage path, added with `--path=<p>`). *(added in rev 2.3.)*
  - **Object writes** (glossary §26.1 W6: objects only for ready-pair captures, publishes, applies and hold records): this chapter uses `-w` only for record content (`H0`, `H1`, stages) and for ready-pair captures (HLD-40). `S_disk[p]`, held path or not, is written only by ENG-'s materialization (01-engine §3.8 "When an iteration materializes"), never at a detection tick, which computes ids without `-w`; a hook request for named paths gets ids or in-memory bytes without `-w` (§3.4). *(added in rev 2.3; changed in rev 2.3: a held path's `S_disk[p]` is no longer written per changed snapshot.)*
  - A record is `local_only = true` (recomputed at every rev) while its guards include `filter-failure` or `secret-scan`, while its path matches a U10 secret-like pattern, while it would have to include a path whose scope class is not LIVE (glossary §9 rev 2.1), and always for a marker companion (its held blob contains restore-marker rows, §3.4 item 3). Its `hold` op is a content-free stub with no `held/` entries and no blob oids (glossary §7, PRO-21).
  - **Only LIVE paths enter a mirrored record** (glossary §9 rev 2.1). A record created from a CS (K2, K3, K6, K7, the B1 PIN, `wake-scope`) takes only the CS's LIVE paths; its non-LIVE paths stay on disk under their mask (MASK steps 1–2) and never reach a remote ref (S8, INV-SECRET).
  - A `filter-failure` record stores no `h1` (glossary §9: the bytes cannot be hashed safely and stay only on disk).

  _Covers: splice-text-from-worktree-leaks-secret, board-plaintext-and-permanence, synced-execution-surfaces_
- **HLD-04** Every record, single- or multi-path, MUST store per-path blob maps (glossary §9 `blobs`) and, unless `local_only`, mirror them as tree entries `held/<hold_id>/<stage>/<repo path>` with stage ∈ `h0, h1, s1, s2, s3` and no entry for an ABSENT side (glossary §3 board commit). The single call without a guard is the marker companion of the markers park (§3.4 item 3). A guard name a reading daemon does not know MUST be treated as a DECISION guard that this daemon never releases or transitions. _Covers: version-skew-board-and-guards_
- **HLD-06** Claim state MUST NOT be an input to the revert detector, MASK, REBASE, PARK, RESTORE or record evaluation. A claim never exempts, releases, narrows or re-keys a record. The only claim-dependent guard is `claim`, and its predicate is REG `gate()`, which never reads the registry. _Covers: claim-launders-held-revert_
- **HLD-07** One change MUST have one id.
  - When `hold()` is called for a path set and an H1 that equals, or REBASE-converges to, the current `H1'` of a non-terminal record on the same paths, the guard is added to that record (new rev) instead of creating a record.
  - A text conflict (K4) on a path already held transitions the EXISTING record to CONFLICTED with stages attached.
  - Guards compose with AND: each `(record, guard)` pair is released separately, and a record masks while any guard remains.

  _Covers: one-change-two-stores, single-guard-release-publishes-multiguard-hunk_
- **HLD-08** After every apply step, ON_DISK records MUST be evaluated with Algorithm R1 (CONFLICTED > SUBSUMED > GONE > ACTIVE).
  - OFF_DISK records MUST NOT be rebased per loop, masked or GONE-evaluated, and MUST NOT withhold a path. The one exception is a record carrying `claim-breach`, which pins its path until resolved.
  - A record is born OFF_DISK whenever the daemon itself displaces or never wrote the bytes:
    - the K4 local side, once ENG- verified the TIP write (until then it is ON_DISK CONFLICTED);
    - claim-breach;
    - SHADOW;
    - PARK.
  - This follows VERIFIED sweep/holdcat X2: a conflict record evaluated with the on-disk order rebases with rc 1 and would withhold its path forever.

  _Covers: stale-hold-resurrects-team-revert, absorbed-hold-evades-history-detectors, conflict-tree-applied-or-auto-resolved, permanent-hold-never-converges_
- **HLD-09** `offer` MUST move only along these transitions:
  - `none|returned → pending_leftover`: at SHADOW birth, or at a K2/K3/K6 PIN creation while the causer's CS is open;
  - `pending_leftover → offered`: at a promoter of the causer seat (Stop, StopFailure, SubagentStop for that agent, SessionEnd, the next human-origin prompt (§2; a UserPromptSubmit carrying a cowork nonce is a doorbell and promotes nothing, glossary §25 F2), 10 min without a hook, seat-lease loss), at `--handoff`, at `cowork_request(rid,"handoff")`, or for K6 at +10 min (HLD-60). A record that carries `wake-scope` is not promoted while that guard holds (HLD-66);
  - `offered → accepted`: on a folded `answer{verb: accept|grant}`. In a human-origin turn the holder's Claude presents the request to its human and answers `accept` only on the human's word; a wake turn follows S5 (U5 as reworded in rev 2.1; COO-);
  - `offered → returned`: on `decline`, `release`, the holder's PC presumed absent (`presume_absent` of its (peer, epoch), S4), holder seat end, or a `request_status{status: returned}` written by the requester (withdrawal; glossary §7);
  - `accepted → returned` (go-first grant only): the grant ends before the requester's change lands: a grant lapse the requester writes as `request_status{status: returned}`, or the holder's `presume_absent` of the grantee's (peer, epoch) 30 min after folding the grant with no op from it (timer restarted at every later op of that PC; see 02 §3.7 step 4, PRO-53) (S4 rev 2.1, glossary §20). *(changed in rev 2.1: the grant lapse was listed under `offered → returned`.)*

  An acknowledgment (`request_status`) without an answer leaves `offer = offered`. The requester's daemon files exactly one automatic re-attempt (`attempt+1`) 30 min after the acknowledgment (timer restarted at every later op of that PC; see 02 §3.7 step 4, PRO-52), which re-arms the presume-absent timer (S4 rev 2.1, glossary §7 `request`, §20; PRO-/COO-); a re-attempt changes the `request` op only (including its `est_minutes`, glossary §25.2 item 5), never the record.

  The `request` op (glossary §7; identity `(req_id, to_holder.seat)` with `req_id == hold_id`, one per distinct holder seat, glossary §3) is published by COO- when `offer` becomes `offered`; before that, holders see the `hold` op as a notice (glossary §10 K1). Only the owner's daemon writes the `hold` op that records an offer change, after folding the holder's `answer` op (a go-first `accept` is written as `grant`, glossary §7). `declines` increments on each folded `decline` of the same `(requester, claim_id, H1)`. At 2, the item goes to the requester's human (COO-). _Covers: handoff-patch-rot-and-orphaned-returns_
- **HLD-10** Registry transitions MUST be mirrored as the single `hold` op (glossary §7) with `rev`/`prev_rev`, and blobs at `held/<hold_id>/<stage>/<repo path>` (HLD-04) unless `local_only`.
  - A record emits an op only on: creation, a residence/state/offer/guard-set change, or a PIN H1 refresh at member close.
  - It never emits one per loop, because readers compute age locally.
  - Ops ride the next governed push of any kind. Hold mirrors are allowed board-only ops while any FREEZE reason is set and under the regionSpec-only `VERSION` pause (glossary §8). They wait (queued, never dropped) while `INCIDENT` (no push), `CONFIG(url|public)` (no network call), the proto `VERSION` pause (zero pushes), `NONRETRYABLE` (no push until human `/cowork resume`; set only by outcome, glossary §26.2 item 2) or `OFFLINE`/`AUTH` is in effect. A rejected push that is not (yet) NONRETRYABLE keeps the queued ops for the next window.
  - INCOMING records and publish-side `unreadable`/`unstable` records emit their creation op only once the condition has persisted 60 s. A record released before that emits nothing.
  - PRO-'s fold (PRO-21) applies a `hold` op only if `prev_rev` equals the folded rev AND the writing peer equals the record's `owner`. Otherwise it is a deterministic no-op and the writer is told.
  - A `hold` op the fold rejects for any reason other than a `prev_rev` race (a SEC-35 validator, a missing or forbidden `held/` subtree, the stub rule) is not re-issued automatically (PRO-24): the record stays in the local registry with its bytes, unmirrored, shown as `HOLD_MIRROR_REJECTED` (glossary §9 rev 2.1, INV-NOSILENT), and its next op is written only at its next transition. Such a record is not durable (HLD-62). `HOLD_MIRROR_REJECTED` is told to the human in status and to Claude at the next hook of the record's origin seat, or of the peer's next seat when that seat is gone (glossary §25.2 item 9; template COO-). *(changed in rev 2.3: it was human-only.)*

  _Covers: local-only-holds-break-nothing-lost, board-plaintext-and-permanence_
- **HLD-11** Compaction (a fold rule, PRO-27) MUST drop only terminal records older than 2 checkpoints from `state.json` and `held/`. Non-terminal records (including PARKED and offered ones) are never compacted, and board history keeps everything (glossary §7).

### B. Operators and the two trees

- **HLD-13** All record arithmetic MUST use `git merge-file -p --object-id` via `runGit` (git ≥ 2.43; there is no file-based fallback). The base is ENG-'s `A[p]`, never `tree(LA_C)[p]`. _Covers: pending-path-base-misset-reverts, stale-hold-resurrects-team-revert_
- **HLD-14** REBASE MUST be single-step from the original pair (§3.4 item 1) and cached by `(id, rev, A[p])`.
- **HLD-15** MASK MUST follow §3.4 item 2 exactly. A MASK conflict makes the record CONFLICTED and withholds the whole path. VERIFIED d2: an adjacent-line edit cannot be separated (rc 1).
- **HLD-16** PARK MUST capture first (H1 refresh for PIN and CONFLICTED), then write through `writeLocal(p, S_disk[p], target)` (ENG-37).
  - A CAS failure retries next loop with a new snapshot. A record is never half-parked: either every path of the record is written, or the record's residence does not change.
  - PARK MUST NOT be applied to a `local_only` record or an INCOMING record. A record carrying `markers` MUST be parked only by the markers park (§3.4 item 3), which never refreshes its held side from disk.
  - While any FREEZE reason is set, only human-typed commands (§2; glossary §25 F5) may PARK (glossary §8 allows human `/cowork resolve` while frozen; otherwise `writeLocal` returns `FROZEN`, ENG-37).
  - Every PARK, markers-park and RESTORE write goes through ENG-'s two-phase verifying writer (rename target → `.old`, rename `.new` → target), the only writer form (glossary §26.1 W4). A file held open without delete sharing (an Excel-like holder) refuses it and `writeLocal` returns `LOCKED` (ENG-37): nothing is written, the record's residence does not change, an S6 park stays postponed and retries at a later loop (HLD-61), and a human command changes nothing and reports the lock. On a file system without hard links the writer's copy fallback is weaker; `/cowork start` warns and doctor shows it (glossary §26.2 item 7). *(added in rev 2.3.)*
- **HLD-17** RESTORE MUST follow §3.4 item 4. A restore write is an observed change of the commanding actor (HLD-29). After RESTORE:
  - the record's residence becomes ON_DISK;
  - the guard that caused the displacement (`conflict`, `claim-breach`, `base-move`, or the PARKED state) is released;
  - every other guard stays;
  - a restore whose written result contains restore-marker rows (a conflicted text restore, or the restore of a marker companion) adds guard `markers` (PREDICATE, whole-path) and the path stays withheld until the rows are gone (glossary §23 decided default, DAT-45); the acting seat or human is told `RESTORE_MARKERS(id, path, rows[])` (DAT-45), while `HOLD_RESTORE_CONFLICT` is only the binary refusal (glossary §25.2 item 3); the rows never reach any remote ref (§3.4 items 3–4, INV-SECRET);
  - the restored content then passes B1 (REG `gate()`, REG-20) and T0 as part of the actor's CS.
- **HLD-18** `taintOnlyH1` MUST be the only code path that applies -U0 hunks. Its output MUST be used only as a record's H1.
- **HLD-19** After every MASK the daemon MUST assert INV-MASK:
  - re-applying every ON_DISK PATCH (`mf(cur=S_pub, base=H0', other=H1')` in reverse ULID order) reproduces `S_disk` on the path, except for whole-path-withheld paths;
  - `diff(A, S_pub)` contains no line of any ON_DISK `revert` record's H0'→H1' change;
  - for P (HLD-42): no path of scope class `QUARANTINED`, `SAVE_ONLY` or `UNMANAGED`, no path of a `local_only` record, no path withheld whole and no held range differs from `A` (glossary §21 INV-MASK over `S_pub` and P).

  On failure:
  - no code push this loop (board-only pushes continue);
  - doctor error `HOLD_MASK_INVALID`;
  - a loud notice to the human and to every live seat's Claude (`HOLD_MASK_INVALID`, both audiences, §2);
  - `S_disk` is NEVER pushed as a fallback.

  _Covers: masked-tree-as-apply-base-starves, absorbed-hold-evades-history-detectors, hunk-identity-key-unstable_
- **HLD-20** `S_disk` MUST be the only tree used as an apply input (`M_disk` from ENG-; ENG-14). `S_pub` MUST be used only for detection and status, and P only as the publish-side input of the outgoing merge (ENG-39). Nothing merged or written locally is recorded as applied. A changes only by ENG-'s verified-write and confirmed-push rules. VERIFIED masked-tree-as-apply-base-starves (d1): with BASE = S_pub, `read-tree` exits 128 and blocks every path. _Covers: masked-tree-as-apply-base-starves, naive-push-reverts-unapplied-paths_

### E. Mass-change breaker

- **HLD-30** The daemon MUST set FREEZE `MASS` (glossary §8) when either:
  - the union of paths with unobserved deltas first seen within any 30 s local-monotonic window exceeds max(10 files, 2 % of tracked files); or
  - an unobserved deletion removes a file containing a non-trivial line the journal lists as added by another writer.

  On entry the daemon:
  - keeps the pre-freeze snapshot tree as `journal/keep/snap_pre_freeze` in the state ref (glossary §4; reachable under `gc --prune=now`, ENG-04);
  - posts one `event{kind: freeze, reason_code: MASS}`;
  - notifies the human (status, systemMessage, OS notification ≤ 1 per 30 min per reason class) and each live seat (next hook).

  index.lock and logs/HEAD are NOT triggers (changed per cross-check: a commit-message editor legitimately holds index.lock). VERIFIED breaker-freezes-publish-not-apply (exp_k_stash): freezing only publish lets the apply break `stash pop`. That is why the FREEZE stops both directions. _Covers: breaker-freezes-publish-not-apply, human-git-mass-revert, formatter-whole-file-rewrites, e-formatter-and-write-livelock, git-ops-publish-team-revert_

That oid is the written oid, or the oid a clean HLD-41 rebase carried it to (Algorithm REV step 8), and the mark still exempts only content equal to that oid (HLD-50 item 3). Matching per path, not taking the newest line whole, keeps a restart from moving one path's mark back when a later line rebased another path, and from adopting a line whose state update a crash prevented (the line is fsynced before that update, Algorithm REV step 8). This is the same condition under which the in-memory mark lives (Algorithm REV step 8), so a revert whose PIN was discarded (RESOLVED_DISCARD) or subsumed has no mark either side of a restart *(aligned in merge round 2)*. The file is then load-bearing until its CS publishes; if it is lost before that, the revert falls back to the ordinary shrink guard. Alternative: a flag next to the journaled ready pair in the state ref (HLD-36), which survives with the CS itself (01-engine's schema). Snapshot side (now stated in 01-engine ENG-25, merge round 2; HLD-32): Algorithm REV step 8 closes the revert CS at once and HLD-40 captures in that loop. If the snapshot-side shrink exclusion (a > 50 % shrink or a shrink to 0 bytes needs 2 stable snapshots plus attribution; "the previous blob is kept") excludes a revert-shrunk path in that loop, `R[p]` is the pre-write blob (`A[p]`), P equals A on that path, and the revert publishes nothing for it with no later trigger to capture again. **Default:** the observed revert write (HLD-26) counts as attribution there only for a snapshot whose blob equals the mark's current oid (a torn read or a later edit of that path gets the ordinary ENG-25 exclusion), and a closed CS whose capture hit a shrink exclusion is captured again at the next completed snapshot (as HLD-41's all-closed case); the same check applies to a `/cowork done` right after a human truncation. **Teammate apply before the push** *(merge round 2; decided by the owner 2026-10-08)*: when a teammate's change to another part of a reverted file lands between the confirmed write and the push, a clean HLD-41 rebase (an apply that wrote p as a clean merge or `CONCAT` with `S_disk[p] == R[p]` before it, whether the plain rebase returned rc 0 or HLD-41's first bullet decided it) moves the revert CS's pair to the merged blob, which is not the written oid. **Decision (D2 with option (a)):** the mark follows that rebase. When a clean HLD-41 rebase (an apply that wrote p as a clean merge or `CONCAT` with `S_disk[p] == R[p]` before it) rebases the revert CS's pair on p, **and that pair's `R[p]` before the rebase equals the mark's current oid for p**, the mark's oid for p becomes the new `R[p]`, and the daemon appends a `reverts.jsonl` line carrying it, so the restart rule above (per path, the newest matching line) re-derives the same mark; any other HLD-41 case (a displaced local side, `A[p]` changed without a write of p, a member effect after the capture), an `R[p]` before the rebase other than the mark's oid (another member's later capture of p, 11-testing TC-F10-17 (d)) or a later effect leaves the mark unchanged *(precondition and wording: merge round 3)*. The confirmed revert therefore still publishes, with the teammate's change merged in (TC-F10-10's variant), and the mark is still dropped when the revert is discarded or published. *Not taken (option (b), the merge-round-2 default):* the mark stays on the written oid, T0's ordinary shrink guard applies to the rebased content, and a file still more than half smaller than TIP makes the revert a K7 PIN with guard `t0` (a PREDICATE guard, `HOLD_GUARDS_REMAIN`) that can only be discarded and reverted again.
