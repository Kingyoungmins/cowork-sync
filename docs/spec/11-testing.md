This chapter defines how cowork-sync proves "no sync issues": the production seams that make the daemon testable, the deterministic multi-peer simulator, the fault and crash catalogues, the oracles for every glossary invariant, the mutation gate, the lint suite, the CI matrix, the real-host and real-Claude-Code tests, the SPIKE-0 acceptance list that MUST run before implementation continues, and the release process. It owns the rule prefixes `TST-` and `REL-`. Behaviour under test is defined by the owning chapters; this chapter defines only how it is proven and when a build may ship.

### 3.2 Production seams (ports)

Every side effect of the daemon, worker, CLI, MCP server and hook loader goes through one of these ports. Release builds bind the real implementations; the lint suite (TST-12) forbids bypassing them.

| Port | Interface | Real binding | SIM binding |
|---|---|---|---|
| `Clock` | `monoMs(): number`, `wallMs(): number`, `sleep(ms)` | `performance.now()`-based monotonic, `Date.now()` | per-peer virtual time; injectable wall offset (±600 s), drift, suspend gaps (Δwall − Δmono > 5 s) |
| `Scheduler` | `schedule(task, atMono)`, `yieldPoint(name)` | Node timers / event loop | seeded queue; one step at a time; `yieldPoint` lets the harness interleave another peer's step or a concurrent write |
| `Random` | `bytes(n)` | `crypto.randomBytes` | seeded PRNG (peer_id, epoch, seat_id, ULIDs, IPC nonces, preview ids) |
| `Fs` | read/write/rename/link/unlink/stat/lock-probe, all on `Buffer`s | `fs` | real disk + fault hooks: fail rename/link/write with EACCES/EPERM/EBUSY/ENOSPC, emulate locks, delay |
| `GitRunner` | `runGit(args, {class})` (glossary §18) | the single git runner | the same runner, optionally wrapped by the transport shim; never mocked |
| `Ipc` | listen/connect with the HMAC handshake (09-security) | named pipe / Unix socket | the same, real |
| `Notifier` | OS notification, status write, trace event | OS adapters | recorder (counts per reason class) |
| `InboxPoster` | used only by `mcp.js` to post a doorbell | the session inbox socket | Inbox stub with the measured host wire behaviour (glossary §25 F1, F2): accepts only `{"type":"auth","token":T}` followed by `{"type":"user","message":{"role":"user","content":…}}` lines, silently drops any other frame (`type:"message"`, plain text), closes ≈ 2 ms after a missing or wrong auth line, and never writes a byte back; delivers an accepted frame by making FakeHost fire UserPromptSubmit with the raw text (mid-turn: after the current tool result, in the same turn; idle: a new turn with a new `prompt_id`); can withhold delivery (hold), refuse by closing within 100 ms, and refuse bursts |
| `crashpoint(name)` | `void` | no-op | throws `KilledAt(name)` or lets STRESS kill the process |

Test-only additions are exactly those of glossary §18 (`GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE` from the peer's virtual wall clock through the `GitRunner` port, so commit oids are reproducible) and glossary §4 (the test ref prefix). Release builds compile these branches out (`TEST_SEAM_IN_RELEASE`, L-DIST).

### 3.3 SIM harness

**Setup (per run).**
1. Create a temp root; `git init --bare remote.git`; install server-side hooks on it: `pre-receive` (policy reject, size limit, sleep to make results ambiguous, CAS emulation is native), `post-receive` (appends `(ref, old, new)` to `remote-log.jsonl` and signals the harness for ambiguous-push faults), `reference-transaction` (logs deletions).
2. Seed the branch `main` with the fixture set of §3.7 and push it.
3. Create N = 3 or 4 peers: `git clone`, set `core.autocrlf=true` on Windows-profile peers, configure the counting clean/smudge secret filter, write the canary into the filtered file.
4. For each peer, start an in-process daemon instance bound to SIM ports, with its own `CLAUDE_PLUGIN_DATA` directory and IPC key; run `/cowork start` through the real CLI entry (`dist/cli.js start`) with a test TTY.
5. For each peer create 0–3 **fake seats**. A fake seat is a FakeHost process that: spawns the real `dist/mcp.js` over stdio with the env Claude Code would give it (including `CLAUDE_CODE_MESSAGING_SOCKET/TOKEN` pointing at the Inbox stub); for every scripted tool call runs the real `dist/hook.js <Event>` with the hook JSON on stdin and the glossary §13 timeouts; honours exit 2 (the tool call does not happen) and `additionalContext`; performs the edit on disk only if allowed; then runs PostToolUse / PostToolUseFailure / Stop etc. FakeHost implements the measured host behaviours: exit-2 deny honoured; exit 1 (and any exit other than 0 and 2) = host fail-open; a hook past its `timeout` = host fail-open after the timeout; ENOENT = host fail-open (glossary §25 F6). For a typed `/cowork <verb>` it fires UserPromptExpansion (with `prompt_id`, `command_name`, `command_args`, `command_source`) before the `!` line runs and UserPromptSubmit only after the `!` line has finished, and the `!` line never passes through PreToolUse(Bash) (glossary §25 F5). The messaging socket and token are in every hook's env and in the MCP server's env, as the host does (glossary §26.2 item 6); `CLAUDE_PLUGIN_DATA` is given to the MCP server in some runs and withheld in others, because its presence for a plugin MCP server is not yet measured (glossary §25 F3). The real host is checked separately by TST-19.

**Run.**
1. The generator (fast-check, dev dependency) draws operations from the catalogue §3.5 with the per-category weights of `test/sim/weights.json`, each with resolved parameters, and appends them to the op-log.
2. The scheduler executes one step at a time: either one daemon loop step of one peer (snapshot, fetch+fold, apply group, publish attempt, timers), or one operation. At every `yieldPoint` the scheduler may run a concurrent operation (e.g. a human write between phase 1 and phase 2 of a writer group).
3. After every step: run the "after every op" oracles (§3.4). Collect trace events.
4. At random points (p = 0.02 per step) inject a crash at the next crashpoint of a random peer (§3.6), then restart that daemon from its persisted state.
5. After the operation budget: quiescence. The harness heals every partition and clears pending injected rejections first (the forced heal). Run loops until K = 20 loops per peer have passed, then 40 further loops, and run the quiescence oracles. *(Plan 2 merge, ruling R-32 as amended in Task 19:)* K is counted per peer from its first successful fetch of the remote board tip after the forced heal (02-protocol §3.11 "a peer observing T\*"), not from the tip's last change; the count restarts at every tip change.

**Failure.** The run stops at the first oracle violation, writes the op-log, the trace, `remote-log.jsonl` and a `git bundle` of every peer and the remote, then shrinks (TST-09).

**Host emulation.** Partitions: rename `remote.git` (fetch fails fast) or point the pinned URL at the blackhole server (`lifecycle/blackhole.js`: accepts TCP and never answers). Ambiguous push (a): the `post-receive` hook signals the harness, which kills the pushing git client after the server ref update. Ambiguous push (b): the transport shim reports failure although the ref landed. Throttling (the throttle signals of glossary §27.2): the shim delays pushes beyond 10 s RTT, or reports HTTP 429 or a 5xx status for a push (taken from the emulated `GIT_TRACE_CURL` line), or `pre-receive` produces a streak of 2 transient rejections. Auth failure windows: a test credential helper returns failure for a window. Transient host failures (glossary §25 F11): `pre-receive` rejects with `[remote rejected] … (failed)` or prints `remote: fatal error in commit_refs`, leaving the ref unchanged, for 1–3 consecutive attempts of one publish. GitHub lease-loss text (glossary §25 F9): the shim rewrites a server-side lease loss to `[remote rejected] (cannot lock ref '<ref>': is at <X> but expected <Y>)`. Latency profile `github-seoul` (glossary §25 F10): push RTT p50 1.8 s / p95 2.8 s, fetch p50 1.2 s / p95 1.6 s.

**Why real git.** harness-mock-blind-mixed-os (VERIFIED): mocked git passes while real teams break on case collisions, EOL, file locks, attribute source and partial apply; e2/e4/e6/e9/e14 show behaviours a mock would not reproduce.

### 3.4 Oracles

One oracle set. The glossary invariants are THE definitions; the catalog variants (engine/holds/coordination INV-NOLOSS, INV-CONVERGE with K = 10 or 5, INV-CI-B1, INV-REG-FENCE, INV-CN-PREEMPT) are not separate oracles (changed per glossary §21: one NOLOSS, one fence, K = 20).

**Glossary invariants**

| Invariant | Check | When | Must be failed by mutant |
|---|---|---|---|
| INV-FF | For every entry of `remote-log.jsonl` on `refs/cowork/<enc(b)>/{board,code}`: `old` is on `git rev-list --first-parent new`, unless the entry was produced by a harness rewrite fault or a human `/cowork recover`. Every daemon push argument list contains no `+` refspec and no `--force` (trace). | after every op | M07 |
| INV-FIRSTPARENT | For every `merge` trace event: LA_C is on TIP's first-parent chain and LA_B on the board tip's. Fault "rewrite keeping the old chain as second parent" raises `INCIDENT` on every peer within 2 polls with zero applies and zero pushes. | after every op | M07 |
| INV-BASE | Every `merge-tree` / `merge-file` trace event carries `--merge-base` equal to the journaled A for its paths; `A_set(p)` events occur only after a verified write or a confirmed push of p. | after every op | M05, M06 |
| INV-PUSHED-IS-MERGE | For every landed live code commit C with lease value TIP: `tree(C)` equals `merge-tree --write-tree --merge-base=A P TIP` (P = the publish composition of glossary §3, recomputed from the journal's ready pairs and A) plus the conflict function's whole-path replacements and concat blobs (03-data); a raw snapshot, `S_disk` or `S_pub` is never the pushed input (ENG-39); `paths(diff(TIP, C)) ⊆ paths(diff(A, P))`. | after every push | M06, M20 |

### 3.19 Release process

1. **Versions.** Plugin semver `X.Y.Z` in `.claude-plugin/plugin.json`. `proto` is the integer 1 for all of v1. `regionSpec` is a version string of the bundled grammars, queries and mapper (04-regions); it changes only in a minor release, under a changelog heading "Region spec", with a release note that a team must update together (a peer whose regionSpec differs from `teamRegionSpec` is in the VERSION publish pause until every peer of R announces the same value, glossary §3/§8).
2. **Build.** The dev toolchain lives in `tools/build/` with its own `package.json` and lockfile (dev dependencies: esbuild at an exact version, typescript, fast-check, eslint); the plugin root has no `package.json` dependencies and no lockfile. `npm run build` with `SOURCE_DATE_EPOCH` = tag commit time produces `dist/`; `dist/SHA256SUMS` lists every file in `dist/`.
3. **Tag.** A signed annotated tag `vX.Y.Z` (SSH or GPG; GitHub shows Verified) on a commit whose committed `dist/` was produced by step 2.
4. **Release job.** CI checks out the tag, rebuilds `dist/` with the pinned toolchain, and fails `DIST_NOT_REPRODUCIBLE` on any byte difference; verifies `SHA256SUMS`; creates a GitHub release with `SHA256SUMS` and a build-provenance attestation; checks the REL-06 gate.
5. **Channels.** `marketplace.json` has two entries: `cowork-sync` (stable) and `cowork-sync-next`, each with `ref` = a signed tag and `sha` = that tag's commit. A passing tag is pinned into `cowork-sync-next` by a PR.
6. **Promotion.** After REL-07 holds, a PR re-pins `cowork-sync` to the same sha.
7. **Rollback.** Tags are never moved or deleted. A rollback republishes the previous code under a higher patch version through the full process (gates may be shortened to the PR matrix plus fold-compat for a rollback, see REL-11) and re-pins the affected channel.

## 8. Open questions (blocking; each with a proposed default)

1. **regionSpec mismatch semantics.** *(Decided in glossary rev 2 §3/§8; no longer open.)* A peer whose regionSpec differs from `teamRegionSpec` is in the VERSION publish pause (code pushes paused, board-only ops allowed, applying continues); every peer gates claims written under a different regionSpec as whole-file; `teamRegionSpec` switches only when every peer of R announces the same value. §3.17 run 2 and TST-24 assert it.
2. **Which runner pool and GitHub plan host the test repository** (rulesets on custom refs are plan-dependent). **Default:** a GitHub organization owned by the maintainers on the free plan; ruleset probes recorded as "not available" where the plan lacks them; no paid feature is a gate.
3. **"Real team" evidence for promotion without telemetry.** **Default:** a maintainer statement in the promotion PR plus at least one voluntarily shared doctor bundle summary (counts only) from that team.
4. **Interactive checklist automation.** ConPTY/VS Code automation is v2; v1 relies on a human. **Default:** the release PR template contains the TST-20 and REL-08 checklists with per-item evidence links (transcript excerpts with file content removed); a release without them fails REL-06.
5. **SPIKE-0 (f) duration.** A 14-day GCM run cannot gate the start of implementation. **Default:** SPIKE-0 accepts a 24 h run plus forced revocation; the 14-day continuation is a REL-06 pre-release item for the first stable release. The forced sign-out needs the user (glossary §26.3); the overnight `ls-remote` watcher of the spike session (at most about 15 h, no revocation) is supporting evidence only.
6. **`host.pushBudgetPerMin` outside 6–24** (glossary §27.2 gives the range, not the handling; owner 02-protocol). **Default:** at genesis an out-of-range or non-integer value is an invalid `.cowork/config.json` (handled like F-CFG-4: `/cowork start` refuses with the config error and creates no board); it is never clamped silently. TC-PRO-01 asserts whatever 02-protocol adopts.
7. **Edit check that cannot finish within 0.5 s** (glossary §27.1 gives the budget, not the overrun behaviour; owners 04-regions, 05-holds). **Default:** an overrun, a parse past the 400 ms parse cap, or a region mapper in WHOLE_FILE mode counts as a **fail** for that checkpoint (no capture, no record, no message); the CS keeps its last passing capture and the next edit checkpoint or turn end decides, so an overrun never publishes an unchecked state. TC-REG-09 asserts it; the overrun count is reported by the perf gates.
