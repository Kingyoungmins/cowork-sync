# 02 — Board protocol, governor, liveness and convergence

**Status:** normative · **Depends on:** 00-glossary (§1–§26: revision 2, §24 "Revision 2.1", §25 "Revision 2.2" (spike-0 facts F1–F13 and pass-2 owner decisions) §26 "Revision 2.3" (Windows contention W1–W6 and synthesis decisions) and §27 "Revision 2.4" (user-approved 2026-10-02: S1 edit checkpoints, U3 push budget 12 with automatic fallback to 6), and §29 "Revision 2.5" (2026-10-08; its only change here is F14's read-only governor query `wait_detail()`, §3.8; the protocol is unchanged, `proto` stays 1); where they differ, the newest section wins), 01-engine (ENG-: fetch, publish, writer, incidents, status writer), 03-data (DAT-: preflight, scope classes), 04-regions (REG-: mapper, fold-overlap, regionSpec), 05-holds (HLD-: hold registry, PIN/PATCH, escalation), 06-claude (CCI-: gate, seats, MCP), 07-coordination (COO-: K-flows, templates, wake), 08-lifecycle (LIF-: start, stop, save, VERSION UX), 09-security (SEC-: git runner, ref trust, secrets, validators), 10-product (UX-: doctor, status rendering), 11-testing (TST-: simulator, SPIKE-0)

This chapter defines what is written on the board and how every daemon reads it back: the board commit format, op identity and ordering, the deterministic fold, checkpoints and compaction, the claim lifecycle, liveness on contest (request_status, SUSPECT, presume_absent), the team push governor, version gating, the start-time host probe with the fallback namespace, and the convergence argument. It does not define how code trees are built, merged or written (01-engine), how a conflict is shown (07-coordination) or how a region is computed (04-regions). It defines the shared state those chapters read.

## 1. Scope

### 1.1 v1 in scope

- One fast-forward-only board chain per live branch (`refs/cowork/<enc(b)>/board`) as the only authority; the code mirror is a lease value only (glossary §3, §4).
- Board commit format: parents, message, tree layout (`ops.jsonl`, `protocol.json`, `checkpoint/state.json`, `held/`), size caps (glossary §20 "Board caps").
- Op identity (`<peer_id>/<epoch>/<seq>`), seq allocation, writer ids, total order by board position, and the content hash `H()` used for `cid`.
- The fold: a pure, total, deterministic function from the board's first-parent chain to the shared state. It includes validity and effect rules for every op type in glossary §7, rejection reporting to the writer, and incremental persistence.
- Checkpoints at first-parent heights divisible by 256, checkpoint verification, joiner replay of at most 255 commits, and compaction of terminal records after 2 checkpoints.
- The claim lifecycle state machine (TENTATIVE → HELD → released, or STALE), with grants and reservations as fold states. There is no TTL, no renewal, no dormancy and no auto-grant.
- Liveness proven only when contested: the holder daemon's `request_status`, the requester's "not responding" display at 120 s, `presume_absent` after **30 min** (S4, PC-level), exactly one automatic re-attempt 30 min after an acknowledgment without answer (S4), the granting holder's presumption of a silent grantee (S4), and the holder's own SUSPECT self-guard (60 s, suspend gap > 5 s).
- The team push governor: LRU rank over the fold's ranked set R (glossary §3), windows anchored on the local observation of the board tip, B = 12 / G = 5 s / S = 1.5 s by default (glossary §27.2; `protocol.json.budget` seeded at genesis from `host.pushBudgetPerMin`, 6–24), the automatic per-peer fallback to B = 6 / G = 10 s / S = 3 s for 30 min on a host-throttling signal and its team-wide propagation through a `health` event (PRO-55), a per-peer cap, the sliding team guard (glossary §27.2: no attempt while ≥ B_eff landed board commits were observed in the last 60 s), attempt counting, coalescing, throttle back-off, the classification of push rejections by outcome (landed / lease loss / transient / NONRETRYABLE after 3 consecutive transients, glossary §26.2 item 2), and which ops may be pushed in which state.
- Version gating: fixed `proto = 1`, `teamRegionSpec` computed by the fold, and the two forms of the VERSION publish pause (glossary §8: proto mismatch → zero pushes; regionSpec mismatch → board-only ops only).
- The start-time host capability probe, the `caps` op, and the `refs/heads/cowork/…` fallback namespace with its refusals.
- The convergence argument behind INV-CONVERGE (K = 20) and the protocol obligations that make the board quiet.

## 3. Design

### 3.1 Board commit format

**Shape.** A board commit X has parents `[previous board commit, live code commit]`. The genesis board commit B0 has the single parent `[L0]`. `live_code(X)` is X's last parent. When a publish carries no code change, the last parent repeats the previous `live_code`. Board commits are never merged with each other. A CAS loser rebuilds its commit on the new tip (01-engine). Commit-level shape checks and rewrite incidents belong to 01-engine (INV-FF, INV-FIRSTPARENT).

**Message.** The subject is `[skip ci] ***NO_CI*** cowork board`. After a blank line come the trailers, in this order: `skip-checks: true`, `Cowork-Proto: 1`, `Cowork-Writer: <peer_id>/<epoch>/<seq>`, then one `Cowork-CS: <cs_id> state=closed|checkpoint seq=<n> origin=prompt|wake|human checks=pass|fail|skipped paths=<n>` per change-set published in this commit, and `Cowork-CS-Paths: <cs_id> <base64url(zlib(NUL-joined sorted paths))>` when that CS has ≤ 256 paths (glossary §5). `Cowork-Seat` trailers belong to live code commits only (glossary §5). The author and committer are `<display name> <peer_id@cowork.invalid>`, set explicitly through `GIT_AUTHOR_*`/`GIT_COMMITTER_*` with timezone `+0000` (glossary §5, §18; SEC-03). Commit dates are wall-clock times used for display only; test builds may take them from the virtual clock (glossary §18). Commits are never signed (`-c commit.gpgSign=false`, glossary §18). The commit shape is built by 01-engine (ENG-12).

**Tree.** It has exactly these entries and nothing else:

| Path | Content |
|---|---|
| `ops.jsonl` | Only the ops introduced by this commit. It is replaced in every commit, never appended. |
| `protocol.json` | Written once at genesis and carried byte-identical (the same blob oid) by every v1 writer. |
| `checkpoint/state.json` | The full fold state at heights divisible by 256, otherwise the previous entry carried unchanged. |
| `held/<hold_id>/<stage>/<repo path>` | For each mirrored, non-terminal (or not-yet-compacted) hold: one blob entry per stage `h0`, `h1`, `s1`, `s2`, `s3` and per path of the record. A side that is ABSENT has no entry. |

The `held/` layout makes each displaced version readable with plain git: `git show refs/cowork-remote/<enc(b)>/board:held/<id>/h1/src/foo.py`. Paths under `held/<id>/<stage>/` are the record's repo-relative POSIX NFC paths. The board tree is never checked out, so Windows-invalid names cannot hurt there. This is the glossary §3 layout `held/<hold_id>/<stage>/<repo path>` (stage ∈ `h0, h1, s1, s2, s3`; no entry for an ABSENT side). A `local_only` record has no `held/` entries at all (glossary §7 content-free stub).

**`ops.jsonl` encoding.** UTF-8 without BOM, LF line ends, one JSON object per line, no blank lines. At most 1,000 lines and 64 KiB per file, and at most 16 KiB per line. Ops appear in strictly increasing seq order.

**`protocol.json` (v1).** UTF-8 JSON with no BOM:

```
{ "proto": 1, "regionSpec": "<regionSpec id of the genesis writer>",
  "budget": 12, "G_s": 5, "S_s": 1.5 }
```

These are the default values (glossary §27.2, rev 2.4; rev 2–2.3 wrote `budget: 6, G_s: 10, S_s: 3`). **Budget seeding** (PRO-04). The genesis writer (and only it) takes `budget` from the team config at EPOCH_BASE, `.cowork/config.json` `host.pushBudgetPerMin` (glossary §27.2; not yet listed in the glossary §17 config block), as an integer in 6–24; when the key is absent, `budget = 12` (chapter default for an invalid value, §8 question 7: an integer outside 6–24 is clamped to the nearest bound, any other value is ignored and gives 12; doctor shows the seeded `budget`). It derives the other two fields with the formula both §27.2 parameter sets satisfy (B = 12 → 5 s / 1.5 s, B = 6 → 10 s / 3 s): `G_s = ⌈60,000 / budget⌉ / 1,000` and `S_s = ⌈18,000 / budget⌉ / 1,000`, i.e. `60 / budget` and `18 / budget` seconds rounded **up** (the stricter side) to whole milliseconds and written as the shortest JSON number, so every genesis writer produces the same bytes for the same budget (B = 24 → `2.5`, `0.75`; B = 7 → `8.572`, `2.572`). `protocol.json` is not part of the fold state, so its non-integer numbers do not conflict with the fold's integers-only rule (§3.3). After genesis a config change of `host.pushBudgetPerMin` has no effect on that board (v1 writers never change this file; the board's value stays the team's).

Each daemon uses the stricter of these values and the local constants of its governor mode (§2, PRO-55; normal `B_local = 24, G_local = 2.5 s, S_local = 0.75 s`, fallback `B_local = 6, G_local = 10 s, S_local = 3 s`): `B_eff = min(B_local, budget)`, `S_eff = max(S_local, S_s)`, `G_base = max(G_local, G_s, 60 / B_eff)`. With the default board this gives B_eff = 12, G_base = 5 s, S_eff = 1.5 s in normal mode and B_eff = 6, G_base = 10 s, S_eff = 3 s in fallback, whatever the board's budget within 6–24. A missing or malformed field (not a positive finite number) reads as its fallback value (`budget` 6, `G_s` 10, `S_s` 3), the stricter side. v1 writers never change this file. Version gating reads `proto` (PRO-47). The team regionSpec is derived by the fold and is not read from this file after genesis (PRO-48).

**Content restrictions** (glossary §7, §9, INV-SECRET; serializer and validators in 09-security SEC-08, SEC-09, SEC-35). Code content appears only as blob ids produced by the pinned clean path. Under `held/` only LIVE paths of a mirrored record appear (glossary §9 rev 2.1): never a quarantined path's local bytes (S8), a restore-marker blob, a `local_only` path or any other non-LIVE path; a record that would need one is `local_only` and is mirrored only as the content-free stub. This is a writer-side check made before the push (PRO-21): a fold rejection would come too late, because the blobs are already on the remote when the fold sees the op. Board text fields are limited to: notes (≤ 280 chars: the `text` of a `note` op from `cowork_note`, and the `note?` of `request`/`answer` ops from the `note` argument of `cowork_request`/`cowork_respond`, each after the local secret scan), display names (≤ 64 raw chars), labels (≤ 80 chars), message codes from the glossary §19 registry (`reason_code`), and enumerated values. Ops carry no wall-clock field. Rendered template text never appears on the board.

**Caps** (glossary §20 "Board caps"). The fold state holds at most 5,000 records. The board tree size is the sum of the sizes of `ops.jsonl`, `protocol.json`, `checkpoint/state.json` and every tree object under `held/`; held blobs are code content and are not counted. That size is at most 5 MB. Each `ops.jsonl` holds at most 1,000 ops and 64 KiB. A writer never builds a commit that breaks a cap. Outbox ops that do not fit wait for the next window, oldest seq first (01-engine ENG-42 decides which whole change-sets are dropped from a code publish when caps force a split). When the record cap is reached, the writer withholds record-creating ops (new claim, request, hold creation, note, conflict event) and sets `BOARD_FULL`. Ops that end records (release, answer, request_status, seat_end, leave, terminal hold transitions) are always allowed, because they are what compaction needs.

### 3.2 Identity and ordering

1. `peer_id` (128-bit random) is created once per clone/worktree at `<gitdir>/cowork/peer`. `epoch` is a new random 128-bit value whenever this peer's local state is (re)initialised: first start, lost-state rebuild (01-engine), or the re-anchor mode of `/cowork recover` (01-engine §3.7 step 2a, which keeps the old chain under `incident-<n>-own`, glossary §4, and emits `LOST_STATE`). A daemon restart with an intact state ref keeps its epoch. `seat_id` is random, minted by the seat's MCP server at `hello`, or by the daemon when no MCP `hello` arrives within 3 s (a `NO_MCP` seat); the first bound id is kept for the life of the Claude Code process (glossary §2; 06-claude CCI-31, CCI-47).
2. **Seq allocation.** Seqs are allocated per `(peer_id, epoch)` from a counter whose high-water mark is persisted in the state ref before any push that uses them (01-engine journal). A new epoch's counter starts at 1. An op receives its seq when it is first placed into a publish intent. It keeps that op id across rebuilds until it lands or the daemon drops it (for example, a claim revalidated away after a CAS loss). Each publish intent then allocates one more seq for its writer id, so the writer seq is larger than every op seq in the commit. The code commit and the board commit of one intent carry the same `Cowork-Writer` value. Because one daemon has at most one publish intent at a time, landed seqs of a `(peer, epoch)` increase strictly in board order. Gaps are allowed.
   **Re-numbering** (PRO-09). An op that already has a seq can be left out of an intent that lands: it is not allowed in the current state (PRO-45), its change-set was dropped by a caps split (01-engine ENG-42), or it is waiting behind a `join` (PRO-36). After that landing the fold's `last_seq` of this `(peer, epoch)` is at or above the op's seq, so the op would fold as a no-op (PRO-16). Therefore, when a publish intent of this `(peer, epoch)` lands, every outbox op whose seq is below the landed writer seq and that was not in that intent MUST get a new seq from the counter before it is placed into an intent again; ops keep their relative order. The same holds when the daemon builds an intent and finds an outbox op whose seq is ≤ the folded `last_seq` of its own epoch at the leased tip. This is safe: an intent that did not land can never land after a later intent of the same writer landed (single-ref CAS; an ambiguous push is resolved before the next intent is built, step 5). The old op id never appeared on the board, so nothing on the board refers to it; local references to it (for example a pending event's own-id `cid`) are recomputed with the new id.
3. **Order.** The only order is board position. "Earlier claim", "conflict causer" (the later one, U4), FIFO queues and governor rank are all functions of board position. A wall-clock reading never feeds a decision, and no timer compares readings from two machines (INV-CLOCK). Every timer is a Δ from a local anchor taken through one helper. A CI lint forbids `Date.now()` comparisons outside it. Observers wait on Δmono, which does not count suspend, so an observer errs toward waiting longer. A peer judging its own staleness uses `max(Δwall, Δmono)`, so it errs toward "I may be stale".
4. **Content hash.** `H(x, y)` is the glossary §3 function: `base32c(sha256(x ‖ 0x00 ‖ y))[0:8]` (Crockford alphabet) over the UTF-8 bytes of x and y. The conflict id is `cid = H(winner op id, loser op id)` (glossary §10). For the non-conflict event kinds (`freeze`, `unfreeze`, `incident`, `nonretryable`, `health`), `cid = H(<the event op's own id>, kind)`. The conflict kinds are `K1..K7` and `breach`. Display forms (`C<cid>`, the request display id `R` + `base32c(sha256(hold_id))[0:8]`, and the `AMBIGUOUS_ID` refusal on a display-id collision) are glossary §3; their rendering belongs to 07-coordination and 10-product. The fold keys events by the full `cid` value it was given and never re-derives it.
5. **Ambiguous push.** A push without an explicit per-ref `ok` or reject is UNKNOWN. After fetching, it counts as landed iff its writer id, or any of its op ids, appears on the board's first-parent chain after the lease value. A push is never resolved by content or by stderr text, and is never blindly re-sent. The mechanics belong to 01-engine (ENG-44).
6. **Mirror.** No decision reads `refs/cowork/<enc(b)>/code` or `refs/cowork-remote/<enc(b)>/code`. They are read only as the lease value of the mirror refspec. A CI lint enforces this.

*Why:* commit-position keys duplicated or lost events, and a board merged as text gave one symbol two holders (op-identity-cursors-board-merge). Wall-clock leases broke under skew and suspend (lease-expiry-clocks-heartbeats, DOCUMENTED). The governor model's two clock-offset bugs became the lint's regression tests.

### 3.3 The fold

**Inputs**, per board commit X in first-parent order from genesis or from a checkpoint:
- the `Cowork-Writer` and `Cowork-CS` trailers of X;
- `live_code(X)` (X's last parent oid);
- `protocol.json` of X;
- `ops.jsonl` of X;
- which `held/<hold_id>/` subtrees exist in X's tree;
- blobs reachable from live code commits, read only through the 04-regions mapper.

The fold reads nothing else: no clock, no network, no local seat state, no parse, no labels, no `git diff`, no time-based cap. It is **total**: every byte string has a defined result, and malformed input becomes a no-op, never an exception. Path and id fields are checked with 09-security's deterministic validators (`validPath`, `validId`, SEC-35); a failing op is a no-op.

**Fold state** (serialised as RFC 8785 canonical JSON; integers only; keys sorted by code point):

```
{ v: 1, height,
  proto, teamRegionSpec, caps: {custom_refs, lease, delete, push_options, two_parent_ok} | null,
  peers: { <peer_id>: { epoch, status: active|left|absent, retired_epochs: [..],
                        display, plugin_version, plugin_sha, regionSpec, config_fingerprint,
                        coauthor_optin, last_seq, last_height } },
  seats:  { "<peer>/<epoch>/<seat>": { status: live|ended, permission_mode, ended_height? } },
  claims: { <claim_id>: { path, anchor, base_blob, ranges, tombstones, granularity, label, regionSpec,
                          cs_id, holder: {peer, epoch, seat, agent}, op_id,
                          state: HELD|STALE|RELEASED, release_reason?, terminal_height?,
                          reserved_for_req?, grant?: {req_id, grantee: {peer, epoch, seat}, cs_id, since_height} } },
  requests: { "<req_id>|<to_holder.seat>": { req_id, kind, ckind, from: {peer, epoch, seat, agent},
                          to_holder: {peer, epoch, seat},
                          claim_ids, path, cs_id, attempt, est_minutes?, origin, note?,
                          last_request_op, status, answer?: {verb, by, reason_code, note?},
                          closed_reason?, terminal_height? } },
  holds:  { <hold_id>: { <latest hold op fields>, owner, terminal_height? } },
  events: { <cid>: { kind, refs, reason_code, op_id, height } },
  notes:  { <op_id>: { target, text, from: {peer, epoch}, height } },
  last_save: { save_commit, saved_live, chain_base, height } | null,
  record_count }
```

**Per-commit algorithm** (PRO-15). For board commit X at height h:

1. Parse the `Cowork-Writer` trailer into `w = (peer, epoch, seq_c)`. If it is missing or malformed, every op of X is a no-op; go to step 5.
2. Read `protocol.json`. If `proto` ≠ 1, set the local VERSION flag (PRO-47); folding continues.
3. For each line i of `ops.jsonl` (only the first 1,000 lines and 64 KiB; any line over 16 KiB is a no-op):
   a. Parse the JSON. Unknown `type` → no-op. Missing required fields, values out of range, or a path/id failing the SEC-35 validators → no-op. A `reason_code` that does not match `^[A-Z][A-Z0-9_]{2,47}$` (glossary §19) → no-op. Unknown fields are ignored.
   b. Generic validity (PRO-16): the op id's `(peer, epoch)` equals `(w.peer, w.epoch)`; its seq is greater than `peers[peer].last_seq` (if `w.epoch` is the recorded epoch) and greater than the previous op's seq in X, and less than `seq_c`. The writer's epoch is active, or the op is a `join`. The epoch is not in `retired_epochs`.
   c. Type-specific validity and effects (table below). Invalid → deterministic no-op, recorded as an own-op rejection if `w.peer` is this peer.
4. Apply the `Cowork-CS` trailers of X as landing facts for grants (PRO-19).
5. Set `peers[w.peer].last_height := h`, and `last_seq := seq_c` when `w.epoch` is the peer's recorded epoch. This applies even when every op was a no-op, because the commit consumed a window.
6. Re-evaluate `teamRegionSpec` (PRO-48).
7. If `h mod 256 == 0`, compact (PRO-27). The resulting state is the checkpoint value for h, which is compared with X's `checkpoint/state.json` (PRO-28).

**Validity and effects per op type** (in addition to step 3b):

| Op | Valid iff | Effect |
|---|---|---|
| `join` | The epoch is not retired. | If `peer` has another recorded epoch: that epoch is retired; its seats end; its claims become RELEASED (reason `superseded`); open requests addressed to it close as `returned`. When the join records a new epoch for the peer (an unknown peer, or a new epoch of a known one): set `peers[peer].epoch := w.epoch`, `status := active` and `last_seq := the join op's seq`, so later ops of the same commit are checked against the new epoch's counter (step 3b). If `(peer, epoch)` was `left` or `absent`: it becomes active again, `last_seq` is kept, and its STALE claims become RELEASED. Record `display, plugin_version, plugin_sha, proto, regionSpec, config_fingerprint, coauthor_optin`. |
| `leave` | The writer is active. | Status `left`. Its seats end; its claims are RELEASED (`stop`); open requests addressed to it close `returned`; grants whose grantee is one of its seats end. |
| `seat_start` | The seat `(peer, epoch, seat_id)` is not live. | The seat is live, with `permission_mode` recorded. |
| `seat_end` | The seat is live. | The seat ends. Its claims are RELEASED (`seat_end`); open requests addressed to it close `returned`; grants to it end. |
| `claim` | See PRO-17. | New `claim_id`: HELD. Same `claim_id` and same holder `(peer, seat)`, record HELD: re-anchor (replace anchor, base_blob, ranges, tombstones, cs_id, label; this also clears `reserved_for_req`). Same `claim_id` and same holder `(peer, seat)`, record RELEASED or STALE: the record becomes HELD again as a new claim: every field is replaced from the op, `holder.epoch` is the writer's epoch, and `release_reason`, `terminal_height`, `grant` and `reserved_for_req` are cleared. This is the same result as when compaction has already dropped the old record and the op takes the "new" branch. |
| `release` | Each listed `claim_id` is HELD or STALE and its holder `(peer, epoch)` is the writer. Others are skipped individually; if none qualify, the op is a no-op. `reason` is one of `explicit|answer|save|seat_end|stop|reservation_transfer` (`superseded` is fold-derived only and never valid in an op). | The listed claims become RELEASED with `reason`. |
| `request` | See PRO-18 and §3.6. | Create the request under its request key `"<req_id>|<to_holder.seat>"`, or update it on `attempt + 1`. Status `pending`. |
| `request_status` | The request key `"<req_id>|<to_holder.seat>"` names an open request. Writer = its `to_holder` active epoch with `status` ∈ {asked, queued_until_turn_end, awaiting_human, undeliverable, returned}; or writer = its `from` peer (active epoch) with `status = returned` (withdrawal or grant lapse, glossary §7). | Record the status. `returned` closes that request (`returned`). |
| `answer` | The request key names an open request; writer = its `to_holder` active epoch; verb allowed for its kind (PRO-18). | Per §3.6, PRO-18 and PRO-19. |
| `note` | The writer is active; `text` is 1–280 chars; `target` is null, a `req_id` with at least one open request whose `from` or `to_holder` peer is the writer, or a HELD/STALE `claim_id`; the record cap is not reached. | Create a note record (terminal at creation). |
| `presume_absent` | See PRO-35. | Per PRO-36. |
| `hold` | See PRO-21. | Store the latest record; set `terminal_height` when the state becomes terminal. |
| `event` | `kind` is in the glossary §7 enum; `reason_code` is a registry code (step 3a); for conflict kinds (`K1..K7`, `breach`), `cid` is not yet present. | Record it (terminal at creation). |
| `caps` | The writer is active. | `caps :=` the op's probe results. |
| `save` | The writer is active. | `last_save :=` the op. Each `released_claim_ids` entry held by one of the writer's own seats becomes RELEASED (`save`); other entries are skipped. |

**Determinism.** Two daemons that folded the same tip hold byte-identical canonical fold states and identical own-op rejection sets for each writer (INV-PRO-FOLD). The fold is incremental. Each daemon persists `(last folded board oid, fold state)` with its state (01-engine) and folds only new first-parent commits. After `/cowork recover` (01-engine) restores a different chain, or re-anchors this late peer onto the team's already-recovered chain (01-engine §3.7 step 2a), the daemon discards its fold state and refolds from the newest checkpoint on that chain at or below their last common first-parent ancestor. In re-anchor mode the peer also starts a new epoch (§3.2 step 1): its unlanded outbox ops are rebuilt from local state under the new epoch (old-epoch op ids can never fold valid): hold mirrors are re-issued from the registry against the folded `rev`, and ops that name seats or claims of the old epoch are dropped. Its `join` retires the old epoch (claims `superseded`), and it re-claims only through ordinary claim ops of the new epoch for its restart records.

### 3.4 Checkpoints and compaction

- The writer of a commit at a height divisible by 256 writes `checkpoint/state.json` = the canonical fold state after folding that commit, including compaction (PRO-26). The writer knows the height when it builds; a CAS loser rebuilds and recomputes.
- **Compaction** (PRO-27) is a fold rule, so it holds the same whether a peer folded from genesis or from a checkpoint. At each height h with `h mod 256 == 0`, drop every terminal record whose `terminal_height ≤ h − 512`. Ended seats are dropped once no non-terminal claim or request references them. This is the glossary §7 rule "compaction drops only terminal records older than 2 checkpoints" (05-holds HLD-11). The writer of that commit also removes the `held/<hold_id>/` subtrees of the dropped holds. Non-terminal records are never dropped. History is never rewritten: every compacted record and blob stays reachable through earlier board commits (INV-NOLOSS).
- **Verification** (PRO-28). Every daemon that folds a checkpoint height compares its canonical state with the committed `state.json`, byte for byte. On a mismatch it first refolds from its previous verified checkpoint (or genesis), to rule out corruption of its own incremental state. If the refold matches, it continues. If it still differs, it enters the VERSION publish pause with `message_params.cause = "checkpoint_mismatch"` (glossary §7) in its board-only form (code pushes paused, the glossary §8 board-only ops still allowed, so the peer keeps acknowledging and answering and is not presumed absent; §8 open question 2) and raises a P2 alert (status, OS notification, every live seat at its next hook) that names the checkpoint writer's `plugin_version` and its own. It lifts the pause when a later checkpoint matches its fold again, or after a plugin update followed by a matching refold.
- **Join** (PRO-29). A joiner starts from the newest checkpoint at or below the tip (`256·⌊ht(tip)/256⌋`) and replays at most 255 commits. It verifies the next checkpoint it reaches.

*Why:* an FF-only board with per-commit op batches means no peer ever rewrites another peer's records, so version skew cannot drop unknown records (version-skew-board-loss, version-skew-board-and-guards). Compaction keyed to heights, not wall time, keeps it a P5-safe fold rule, which fixes the naive compaction race (board-growth-compaction).

### 3.5 Claim lifecycle

| From | Event | To | Decided by |
|---|---|---|---|
| — | PreToolUse prediction (06-claude) | TENTATIVE (predicted, local) | daemon |
| TENTATIVE (predicted) | PostToolUse / TXN close confirms the region changed | TENTATIVE (confirmed; claim op in outbox) | daemon |
| TENTATIVE (predicted) | PostToolUseFailure, PermissionDenied, or no change | dropped | daemon |
| TENTATIVE (confirmed) | its `claim` op folds valid | HELD | fold |
| TENTATIVE (confirmed) | its `claim` op folds invalid (overlap with an earlier claim) | dropped; the covering CS is PIN-held as K3 (05-holds HLD-45, 07-coordination COO-06) | fold → holds |
| HELD | `release` (`explicit`, `answer`, `save`, `stop`, `reservation_transfer`), `seat_end`, `leave`, epoch superseded, `answer{release}` | RELEASED (terminal) | fold |
| HELD | applied `presume_absent` on the holder's epoch | STALE (visible, non-blocking) | fold |
| STALE | `join` by the same `(peer, epoch)`, `leave`, or epoch superseded | RELEASED | fold |
| HELD (own) | self-guard trigger | HELD + SUSPECT (local overlay) | daemon |
| HELD + SUSPECT | a fresh fetch+fold still shows the claim HELD under this epoch | HELD | daemon |
| HELD | `answer{grant}` | HELD + grant | fold |
| HELD + grant | the grant ends (PRO-19) | HELD | fold |
| — | reservation `claim` op written by the releasing holder | HELD (`reserved_for_req`) | fold |
| HELD (reserved) | requester's CS closes without changing it → `release{reservation_transfer}` | RELEASED | requester daemon |
| HELD (reserved) | requester re-claims the same `claim_id` | HELD (ordinary) | fold |
| RELEASED or STALE (not yet compacted) | a valid `claim` op of the same holder `(peer, seat)` with the same `claim_id` (for example a re-claim after the PRO-36 return) | HELD (as a new claim; §3.3 `claim` row) | fold |

RELEASED is terminal for every purpose (compaction, request closing, the derived "free" flag) until such a re-claim folds. The re-claim passes the full overlap test of PRO-17, and its result is the same whether or not compaction has already dropped the old record.

There is no TTL, no renewal, no dormancy and no automatic grant (U5, U6). Only `confirmed` TENTATIVE claims (glossary §3) are published; they go out at the next governed window, as board-only ops if their change-set has not closed yet (U4, S1: "claims are visible within seconds"). A claim's `anchor` is always `live_code` of the board commit that carries it, so its ranges are recomputed on every rebuild of a publish intent (04-regions REG-11, REG-22). Re-anchoring after this peer's own code change rides in the same board commit as that code, so it costs no extra push. While any FREEZE reason or either form of the VERSION pause is set, confirmed claims stay TENTATIVE and are not published (glossary §8). The local gate decides against the claim view (glossary §3): folded HELD non-STALE claims, this daemon's confirmed TENTATIVE claims of other local seats in local order, and active go-first grants (04-regions REG-21, 06-claude). Other peers never see TENTATIVE claims.

**Save release** (PRO-32). After folding a `save` op with `saved_live = Lk`, each daemon releases its own seats' HELD claims c, with `release{reason: save}`, at the first moment all of these hold: (a) the change-set named in c's `cs_id` landed at a board commit whose `live_code` is Lk or a first-parent ancestor of Lk; (b) the holder seat has no open or ready change-set touching c's path; (c) the holder seat is not mid-turn (otherwise, at its next Stop). The saver's own `save` op lists the claims released this way on the saver's peer. A daemon never releases another peer's claims.

*Why:* starvation is handled by asking an idle holder at once (07-coordination) and by liveness on contest for machines that are truly gone. Dormancy and auto-grant are ruled out by U5/U6 (zombie-claims-idle-holder, claims-held-all-day-starvation). Release at seat end is safe because a seat ends only on MCP stdin EOF or when the claude pid disappears (checked every 5 s), both of which mean the Claude Code process exited (06-claude CCI-32, VERIFIED).

### 3.6 Requests, answers, grants and reservations (op semantics)

The flows (who files, who is asked, what text appears) belong to 07-coordination. This section fixes only what the ops mean in the fold.

- **Identity** (glossary §3). A request is identified by `(req_id, to_holder.seat)`, with `req_id == hold_id` of the PATCH/PIN record that carries the attempted change. One PIN that intersects claims of several holder seats produces one request per holder seat, all sharing `req_id`. `request_status` and `answer` ops name the request by both fields; a `note` op targets a `req_id` (all requests sharing it).
- **When it is published** (owned by 07-coordination COO-11, 05-holds HLD-09). The requester daemon writes the `request` op when the record's `offer` becomes `offered` (U5). Before that, the holder sees the record's `hold` op only as a notice.
- **request** (PRO-18). Valid iff all of these hold:
  - the writer is `from.peer`, with an active epoch, and the `from` seat is live;
  - a non-terminal, non-`local_only` `hold` record with `hold_id == req_id` and `owner == writer` was folded earlier (in an earlier commit, or on an earlier line of this one); its bytes are in `held/<req_id>/`;
  - `to_holder` names a live seat of an active epoch;
  - `ckind` ∈ {claim_visible, claim_posthoc, claim_race, human_in_claim, dependency} (glossary §7; there is no `text` ckind). For the four claim kinds, `claim_ids` is non-empty and every listed claim is HELD by the `to_holder` seat. For `dependency`, `claim_ids` may be empty;
  - `kind = go_first` only with a non-empty `claim_ids`;
  - `note`, when present, is ≤ 280 chars.

  The first valid op for a request key creates the request, with `to_holder.epoch` taken from the fold. A later op with the same request key, the same writer and a higher `attempt` updates `attempt`, `claim_ids`, `cs_id`, `est_minutes` (glossary §25.2 item 5; an absent field clears it) and `note`, sets status `pending`, and re-arms liveness (PRO-35). The request op carries no blob fields (glossary §7); the bytes are in `held/<req_id>/`.
- **answer verbs.** Handoff: `accept | decline | later | release`. Go-first: `grant | decline | later | release`. The MCP `cowork_respond(verb: "accept")` is written as `grant` on a go-first request and as `accept` on a handoff (glossary §7; 07-coordination COO-14). `by` ∈ {claude, human, daemon}. Human answers (glossary §7): the holder's human answers through `/cowork release`, which writes the `release` op and one `answer{verb: release, by: human}` per open request on those claims (COO-14), or through their own Claude. The requester's human acts through `/cowork resolve <id> --handoff|--park|--discard|--restore` (05-holds HLD-58); in the fold these appear as `hold` transitions (a terminal state closes the requests of that `req_id`) or as a requester-written `request_status{returned}` (withdrawal), never as an `answer`.
  - `decline` closes the request (`declined`). The requester's record goes back to it (U5).
  - `later` changes only the status. No re-ask follows (07-coordination), and no automatic re-attempt either (any folded `answer` cancels PRO-52).
  - `accept` sets status `accepted`. The request closes when its hold record becomes terminal, or with `returned`. The holder daemon publishes `request_status{returned}` when an accepted handoff is still unapplied at the moment the holder releases the claim; when the holder seat ends, the `seat_end` op already closes it `returned` in the fold, and no extra op is written.
  - How the holder's Claude reached its decision is not visible to the fold: under U5 (rev 2.1) it answers `accept` in a human-origin turn only on its human's word, and in a wake turn S5 applies (the accepted work joins the wake work set; writes outside it are PINned with guard `wake-scope`). Both are written `by: claude`; 07-coordination owns the rule.
  - `release` releases every listed claim still HELD by the `to_holder` seat (reason `answer`) and closes the request (`released`). The holder daemon MAY first write an explicit `release{reason: answer}` for the same claims (07-coordination §3.10); the answer then finds them already RELEASED, which is not an error. In the same board commit, **after** the answer line, the holder daemon MAY write one reservation `claim` op per released claim (PRO-19). The fold order within that batch is therefore `release` (optional) → `answer` → reservation `claim`.
  - `grant` creates a grant (PRO-19).
- **Closed requests.** A request is closed on: `declined`, `released`, `returned` (from either side, or derived from seat end, leave, epoch supersede or `presume_absent`), `landed` (grant consumed), or when its hold record becomes terminal (which closes every request sharing that `req_id`). `closed_reason` and `terminal_height` are recorded.
- **Derived flag.** An open request whose claims are all RELEASED or STALE is shown as "free" (07-coordination `T5.release` / `T5.free.head`). It stays open until the requester's record closes it.
- **note** (glossary §7). A `note` op carries `cowork_note(text)` from a seat of the writer's peer. It never changes a claim, request or hold. Renderers show it only inside 07-coordination's `T-NOTE` block (COO-29).

**Grants and reservations** (PRO-19, resolves cross-check interface mismatch 10):
- `answer{grant}` is valid only if no listed claim already has a grant. For every listed claim, the effect is `grant = {req_id, grantee: request.from seat, cs_id: request.cs_id, since_height: h}`. The 04-regions publish gate (REG-20) takes the fold's grants as input. For the grantee only, it admits hunks of the change-set `cs_id` inside the granted claims. Every other seat still sees the claim as blocking. 06-claude's gate denies the holder seat's own edits to a granted claim with `T-GRANT_PAUSE` until the grant ends (glossary §23 default, confirmed by the user and binding since glossary §27, rev 2.4; 07-coordination COO-17).
- A grant ends at the first of these: (a) a later board commit written by the grantee's peer with a `Cowork-CS: <cs_id> state=closed` trailer (the request closes `landed`); (b) `request_status{returned}` from the grantee's peer (grant lapse, glossary §7), published when the grantee's change-set closed without the granted change or when the grant is void (07-coordination §3.9); (c) the grantee seat ends, its epoch leaves, is superseded or is presumed absent — including by the granting holder itself when the grantee's PC stays silent for 30 min after the grant (S4 rev 2.1, PRO-53); (d) the claim is released. After that, the claim is the holder's again. No timer is involved, except the PRO-53 30-min presumption in (c) (glossary S4, §20), and even that one ends the grant only through a folded `presume_absent` op.
- A **reservation** claim op is valid iff:
  - it carries `reserved_for_req = r` (a `req_id`);
  - an `answer{release}` by the same writer on a request q with `q.req_id = r` was folded earlier in the same board commit (q's key is `"r|<q.to_holder.seat>"`);
  - the writer is q's `to_holder` peer;
  - the holder is q's `from` seat (still live), with its epoch taken from q;
  - its ranges pass the ordinary overlap test against the remaining active claims.

  It blocks every seat except its holder (07-coordination §3.10). The holder's own later claim op with the same `claim_id` re-anchors it and clears the reservation. The holder's peer releases an unused reservation with `release{reason: reservation_transfer}` at the holder seat's next change-set close.

### 3.7 Liveness: proven only on contest

1. **No liveness traffic.** No op exists for heartbeats, renewals or "alive" (INV-PRO-QUIET). A quiet, uncontested team makes zero liveness pushes.
2. **Acknowledgment** (PRO-33). For every request op it folds that is addressed to one of its seats (each new `attempt` included), the holder's daemon puts one `request_status` in its outbox, published in its next governed window. The status follows the holder seat's activity (glossary §3 seat activity; classification owned by 06-claude, mapping by 07-coordination §3.7 and COO-12/COO-13): `MID_TURN` → `queued_until_turn_end`; `IDLE` and doorbell-eligible → `asked` (once the doorbell is confirmed: delivery is confirmed only when a UserPromptSubmit of the holder seat carries the doorbell's nonce; a post that was only `sent` — line written, connection not closed within 100 ms — is not a confirmation, glossary §25 F1/F2); `AWAITING_PERMISSION` → `awaiting_human`; `IDLE` and not eligible → `undeliverable`; `ENDED` → none (the seat's `seat_end` op closes the request `returned` in the fold, 07-coordination §3.7). A later change of that state publishes one more `request_status`. Wake eligibility honours S5: sessions in auto/acceptEdits/dontAsk/bypassPermissions mode are woken too, within the glossary §20 caps. The daemon, not Claude, owns this obligation, so an idle or absent human never makes a live machine look absent.
3. **Not responding** (PRO-34). The requester's daemon starts a Δmono timer when it folds its own request op. After 120 s with no folded op from the holder's active epoch, the request shows NOT_RESPONDING in status and in 07-coordination's outputs (`T5.noresp`, 07-coordination §3.11). Nothing is published.
4. **presume_absent** (PRO-35). The same timer, at **30 min** Δmono (S4). The requester daemon then:
   1. fetches and folds;
   2. if the request is still open, the holder's epoch is still active, and no op from it was folded after the request op, publishes `presume_absent{peer, epoch, last_seq_seen = peers[peer].last_seq}` in its next window.

   The fold applies the op iff all of these hold:
   - the writer is active and ≠ the target peer;
   - the target `(peer, epoch)` is active;
   - `peers[peer].last_seq == last_seq_seen`;
   - a relationship from the writer to the target exists: (i) an open request from the writer peer to that `(peer, epoch)`, or (ii) a HELD claim of a seat of the writer's active epoch whose grant has a grantee seat of that `(peer, epoch)` (PRO-53).

   Any target op that lands earlier makes it a no-op, so an acknowledgment that wins the race always wins. Every new request op (a re-attempt) re-arms the timer. Each request op yields at most one `presume_absent`.

   **Automatic re-attempt after a silent acknowledgment** (PRO-52; S4 rev 2.1, glossary §20 "Presume absent"). The 30-minute test above proves absence only for a machine that was already gone when the request op was folded, because a running holder daemon always acknowledges within one window (step 2). For a holder PC that acknowledged and then went away, the requester daemon files **at most one** automatic re-attempt per request key, and exactly one whenever the conditions below hold:
   1. It arms a Δmono timer when it folds the first `request_status` of the current attempt from the holder's active epoch (the acknowledgment), and restarts it at every later folded op of that `(peer, epoch)` (a later `request_status` after a seat-state change is an acknowledgment too). The timer therefore measures 30 min of silence after the latest acknowledgment.
   2. When it fires, the daemon fetches and folds, and files the re-attempt only if all of these still hold: the request is open; no `answer` of any verb has been folded for this request key (a `later` is an answer, so it cancels the re-attempt); no op from the holder's `(peer, epoch)` was folded since the timer's last restart; no automatic re-attempt was filed before for this key (a fact persisted in the state ref with the outbox, so a daemon restart cannot file a second one); and the request op would be valid under PRO-18 (the `from` seat is still live; when the previous attempt listed claims, the op lists those still HELD by the `to_holder` seat). If the `from` seat has ended, or the previous attempt listed claims and none is still HELD (the request is then shown "free"), nothing is filed and the age notifications stay the cue. A `dependency` request with empty `claim_ids` is re-attempted with empty `claim_ids`.
   3. The op is a `request` with the same `req_id`, `to_holder`, `kind`, `ckind`, `cs_id` and `origin` as the previous attempt (`origin` has no daemon value, glossary §7), `attempt + 1`, `claim_ids` as in step 2, the previous attempt's `est_minutes` carried verbatim when present (display only), and the previous attempt's `note` carried verbatim (it was already secret-scanned and published). Both are carried because a higher attempt updates `est_minutes` and `note` (glossary §25.2 item 5), so an absent field would clear them. The status line `REQUEST_REATTEMPTED` is shown (§2.1).
   4. While it waits in the outbox (a FREEZE reason or a VERSION pause allows no `request` op, PRO-45), the conditions of step 2 are re-checked at every intent build; if one fails, the op is dropped, never published. It updates an existing record, so `BOARD_FULL` never withholds it.

   The holder daemon then acknowledges the new attempt like any other (step 2; under glossary §19 rev 2.1 the holder seat may get one Stop block for this attempt). If the holder PC is alive, that acknowledgment is an op and no `presume_absent` follows; this is the last automatic action, and the claim stays HELD until a human or Claude acts, with the 30-minute age notifications (`T-AGE.req` / `T-AGE.hold`, 07-coordination §3.11) as the cue. If the PC is gone, the re-attempt re-arms the 30-minute test and `presume_absent` follows 30 min later. Further attempts come only from the requester side (a Claude `cowork_request` call, or a human `/cowork resolve --handoff` after the record returned; 07-coordination §3.6).

   **What "activity" means here** (S4 rev 2.1: "a holder whose PC (daemon epoch) publishes no op"; glossary §20 "Presume absent"). The test counts any folded op from the holder's `(peer, epoch)`, including the daemon's own `request_status`; because step 5 of §3.3 advances `last_seq` for every board commit of a writer, "no op" means "no board commit written by that epoch". It is a test of the holder's PC, not of the holding seat or its human: an idle or absent human on a running PC is handled by asking, the one automatic re-attempt, the age notifications and release, never by `presume_absent`.

   **Silent grantee** (PRO-53; S4 rev 2.1). A holder that granted go-first has no request to the grantee, so (i) cannot apply. Its daemon arms a Δmono timer when it folds its own `answer{grant}` and restarts it at every later folded op of the grantee's `(peer, epoch)`. The grantee normally publishes at least one such op right after the grant (the `hold` op mirroring `offered → accepted`, PRO-21, 05-holds HLD-09), so a test that only looked at "any op since the grant" would never fire for a grantee that mirrored the offer and then went away. This chapter therefore reads glossary §20 "30 min after folding the grant with no op from it" as 30 min of silence from the grantee's PC counted from the grant or its latest op after the grant. When the timer fires and the grant is still active, the daemon fetches, folds, re-checks, and publishes `presume_absent{peer, epoch, last_seq_seen}` for the grantee's PC under relationship (ii); at most one per (grant, `last_seq_seen`). A live grantee seldom stays silent that long while its grant is active, because its change-set closes at the latest at the 10-min seat fallback close (glossary §20) and the landing or lapse ends the grant first. Applying it ends the grant (PRO-19 (c)), lifts `T-GRANT_PAUSE`, and shows `GRANTEE_PRESUMED_ABSENT` on the holder side (§2.1).
5. **Effect** (PRO-36). The target epoch becomes `absent`. Its claims become STALE (visible, non-blocking) and its seats end. Open requests addressed to it close `returned`, which 07-coordination renders as `T5.free.head` with `{FREEREASON}` #3 (07-coordination §3.11, COO-12). Grants to its seats end. Its reservations become STALE. Nothing is deleted. Its unpublished bytes stay on its disk and in its hold registry (S4, INV-NOLOSS).
6. **Return of an absent peer.** A daemon that folds an applied `presume_absent` naming its own active epoch must, before any other op, put a `join` (same epoch) in its outbox, followed by `seat_start` for its live seats. Every outbox op that has not landed is re-numbered to come after them (§3.2 step 2), because an op placed before the `join` would fold while the epoch is still absent. The `join` turns its STALE claims RELEASED. It then re-claims through ordinary claim ops for regions where it still has unpublished change-sets. Re-claims that now overlap a teammate's earlier claim fold invalid (in practice 04-regions REG-22 `claimPrecheck` withholds them before the push), and those change-sets are PIN-held as K3 (05-holds HLD-45, 07-coordination COO-06), bytes preserved. Its code is always judged by the publish gate against the fold of the leased tip, which already contains the `presume_absent`, so a zombie push cannot land inside a teammate's claim (INV-FENCE).
7. **Self-guard / SUSPECT** (PRO-37). Each daemon marks all its own HELD claims SUSPECT when either holds:
   - its last successful fetch or push is older than 60 s by `max(Δwall, Δmono)`;
   - the suspend gap `Δwall − Δmono` between two loop ticks exceeds 5 s.

   On a suspend gap it also starts a fetch at once. A gate query on a SUSPECT claim makes the daemon fetch and fold now and wait at most 5 s. A peer never runs two fetches at once (glossary §25 F10): when a fetch is already in flight, "at once" and "now" mean that fetch if it started after the SUSPECT mark was set, otherwise the next fetch, started right after it ends; the 5 s bound is unchanged (measured fetch p95 1.43–1.57 s, §25 F10). If the fresh fold shows the claim HELD under this peer's active epoch, SUSPECT clears and the gate continues. Otherwise the answer is G1 deny (glossary §11) with code `SUSPECT_LOST` (06-claude CCI-17), rendered by 07-coordination ("cannot confirm you still hold …"). The 06-claude loader `extend` frame (total ≤ 7 s, glossary §13, §20) covers this wait; the 45 s fetch watchdog does not lengthen it. Any successful fetch and fold that shows the claims still HELD clears SUSPECT for all of them.
8. **Ghosts** (glossary §3, `K_evict` = 200 first-parent heights). A ghost keeps its claims, which stay blocking until contested. It is excluded from R, and so from governor ranking and regionSpec unanimity (PRO-39, PRO-48), and it does not count in other PCs' wake share. The per-PC wake share is `max(2, floor(12 / max(1, |R ∪ {self}|)))` per 60 min (glossary §20 rev 2.1; 07-coordination §3.12): every PC counts itself, so a PC that is itself a ghost, or a team whose R is empty, never divides by zero. It re-enters R with its next board commit.

*Why:* every periodic cadence spends budget in proportion to time × peers (lease-expiry-clocks-heartbeats, claims-held-all-day-starvation). Tying the proof to a request makes the cost proportional to contests; the one automatic re-attempt per request key and at most one grantee `presume_absent` per (grant, observed `last_seq`) (S4 rev 2.1) keep it bounded. The self-guard (60 s) expires far ahead of any observer (30 min), using `max(Δwall, Δmono)` (sleep-offline-stale-and-suspect-claims). The fold-level seq check removes the race between take-over and acknowledgment without clocks.

### 3.8 The push governor

**Algorithm** (PRO-39 … PRO-44). Each daemon, per live branch:

```
on fetch completing with board tip T:
    if T != anchor_tip: anchor_tip := T; anchor := now_mono()
on own push result "ok" (board ref): anchor_tip := Bnew; anchor := now_mono()
observed landings := Δmono instants of the observed landings (§2): each new first-parent board commit a
                     fetch reveals counts at that fetch's completion; this peer's own landed push at its "ok"

rank(self) := 1 + |{ p in R : key(p) < key(self) }|,  key(p) = (last_height(p), peer_id(p)),
              where a peer with no landed board commit has last_height = -1;
              if self not in R: rank := 1     // ghost, new joiner, returning peer: "a peer with none first"

mode := fallback if now − last_signal < 30 min or now − last_throttle_event_folded < 30 min, else normal
                                          // PRO-55, glossary §27.2; both instants are this daemon's Δmono
(B_local, G_local, S_local) := mode == normal ? (24, 2.5 s, 0.75 s) : (6, 10 s, 3 s)
B_eff := min(B_local, budget);  S_eff := max(S_local, S_s);  G_base := max(G_local, G_s, 60 s / B_eff)
                                          // §3.1; default board: 12 / 1.5 s / 5 s normal, 6 / 3 s / 10 s fallback
G_eff := min(60 s, G_base · 2^k)          // k = throttle level, starts at 0; fallback raises G_base, k still multiplies it

preempted(self) := number of tip changes observed (anchor resets not caused by its own "ok")
                   while pending(self) and state_allows(self) held, since its own last attempt
                   (or since pending became true, whichever is later)
aged(self) := preempted(self) ≥ 2

wait(self) := if aged(self): G_base                        // aging: rank 1, throttle ignored for the shared window
              else:          G_eff + (rank − 1) · S_eff

may_attempt(now) :=
      pending(self)                          // P ≠ A on some path (a ready, unheld publication group), or allowed outbox ops (PRO-45)
  and state_allows(self)                     // PRO-45
  and no attempt in flight
  and now − anchor ≥ wait(self)
  and now − own_last_attempt ≥ G_eff         // throttle also spaces this peer's own attempts
  and |{attempts with now − t < 60 s}| < B_eff        // per-peer cap (own attempts)
  and |{observed landings with now − t < 60 s}| < B_eff  // sliding team guard (glossary §27.2; 12 by default, 6 in fallback);
                                                         // aging never bypasses it

wait_detail() := { ms, term }                // (rev 2.5, F14; FEAT-F14-13) read-only (10 §3.5.1):
                                             // reading it MUST change no governor state (anchor, rank, preempted,
                                             // throttle level, attempt counts)
      ms   := Δmono until may_attempt could hold         // a lower bound: any tip change resets anchor
      term := the first blocking term, in this order: window (now − anchor ≥ wait(self)),
              own_spacing (now − own_last_attempt ≥ G_eff), peer_cap (per-peer cap), team_guard (sliding team guard),
              in_flight (an attempt in flight), backoff (the ENG-44 transient backoff: 01-engine §3.6, 30 s doubling
              to 5 min, glossary §20)
              // this order is a display priority for 10 §3.5.1, not may_attempt's evaluation order
              // (which tests "no attempt in flight" third); F14 §4's "in that order" is read this way (rev 2.5, merge note)

attempt:
    build one publish intent against anchor_tip with EVERYTHING pending (code delta + outbox ops, caps permitting)
    push (01-engine ENG-43), record the attempt time
    ok          -> anchor := receipt time (above); clear landed ops from the outbox; rejects := 0
    anything else (rejected, ambiguous, killed) -> fetch and fold, then classify by OUTCOME, never by text
                   (glossary §26.2 item 2; PRO-54; mechanics 01-engine ENG-44/ENG-45; the mirror line is ignored):
      own writer id or op ids on the board's first-parent chain after the lease value
                  -> landed (§3.2 step 5, PRO-12): handled as ok
      leased ref moved (T' != lease value), own ids absent
                  -> lease loss: refold, re-merge, re-run every guard against the new tip
                     (01-engine ENG-40, ENG-44), wait for the NEW window; rejects := 0
      leased ref unchanged (T' == lease value), own ids absent, a per-ref rejection line was returned
                  -> transient rejection: rejects := rejects + 1; k := k + 1 (backoff); retry in a later window;
                     when rejects reaches 3: NONRETRYABLE (01-engine ENG-45: the whole rejected publish is
                     PINned; publishing stops until human /cowork resume)
      leased ref unchanged, own ids absent, no per-ref status line (transport failure, watchdog kill)
                  -> retryable network failure: throttle rule below; retry in a later window; rejects unchanged
    the rejection text (e.g. "(stale info)", "cannot lock ref … is at … but expected …", "(failed)",
    "fatal error in commit_refs", glossary §25 F9/F11) never selects a class; it only chooses the explanation shown
throttle: an attempt that took > 10 s Δmono, was killed by the watchdog, or ended with no per-ref status line
          in --porcelain output -> k := k + 1 (until G_eff = 60 s);
          a transient rejection -> k := k + 1 (above), never lowered by its fast per-ref status;
          at most one increment per attempt;
          any other attempt that returned per-ref status within 10 s -> k := max(0, k − 1)
fallback (PRO-55, glossary §27.2): on each throttle signal (§2: HTTP 429 or any 5xx on a push or fetch; a push
          attempt with RTT > 10 s Δmono or watchdog-killed; rejects reaching 2):
              last_signal := now                      // (re)starts this peer's 30-min fallback
              if the signal came from a push attempt, or from a fetch while pending(self) held without this event,
                 and no HOST_THROTTLED health event was folded or put in the outbox by this peer in the last 15 min:
                  outbox += event{kind: health, reason_code: HOST_THROTTLED}   // rides the next governed window
          on folding event{kind: health, reason_code: HOST_THROTTLED} from any writer (own included):
              last_throttle_event_folded := fold completion instant       // never re-posted by a follower
          an unpublished HOST_THROTTLED event is dropped from the outbox once this peer's mode is normal again
```

**Properties.**
- R and rank depend only on the folded tip, so every peer that folded the same tip computes the same ranking.
- Timing uses only each peer's own Δmono since its own observation, so no clock is ever compared.
- A peer that just landed becomes last. A CAS loser keeps its earlier key and therefore rises, which gives an intrinsic back-off.
- No starvation. Every window is anchored on the latest tip change, so a window that always opens later than the busy peers' windows would never open. Two rules prevent this. (1) A peer outside R (a ghost, a new joiner, a peer returning after `presume_absent`) takes rank 1, so its `join`, its acknowledgments and its re-claims are not stuck behind the ranked peers. (2) Aging: a peer whose pending work was pre-empted by two tip changes of other writers since its own last attempt uses `G_base` as rank 1 for the shared window, whatever its throttle level k. The throttle still spaces its own attempts by G_eff, and its next attempt lets k go down (PRO-44). A tie at rank 1 is an ordinary CAS collision.
- Landed publishes are spaced by at least G_base as each peer observes them, which bounds the sustained team rate at 60 / G_base = B_eff per minute: 12 by default, 6 in fallback (glossary §27.2). The sliding team guard (glossary §20 rev 2.1, §27.2) keeps U3 per 60 s, not only on average: no peer starts an attempt while it has observed ≥ B_eff (12 by default, 6 in fallback) landings in the last 60 s Δmono, whatever its rank, aging or throttle state. The per-peer cap of B_eff attempts per 60 s Δmono bounds a single runaway peer. The guard delays but never starves: observed landings age out after 60 s, and it adds no landed commits of others, so INV-PRO-NOSTARVE's count is unchanged.
- Worst normal wait is `G + (|R| − 1)·S` = 5 + 3·1.5 = 9.5 s for 4 peers by default (19 s in fallback), plus one cycle per collision (≈ 20 s under full contention by default, ≈ 40 s in fallback; MODEL, to be re-measured by T-PRO-20). At G = 5 s the measured push RTT (p50 ≈ 1.8 s), fetch (p50 ≈ 1.2 s) and the 2.5 s fetch period (glossary §25 F10) are no longer small against G: a peer observes a landing up to one fetch period plus one fetch late, so the observed spacing can be shorter than G_base by that much (INV-PRO-GOV) and the guard, not G alone, keeps the per-60 s count.
- **Fallback is local, follows the stricter side, and spreads once** (PRO-55, glossary §27.2). A throttle signal moves only the observing peer into fallback at once; its one `HOST_THROTTLED` health event (at most one per 15 min per peer, none from a peer that only folded a teammate's event, and none for a fetch signal while the peer has nothing else to push) makes every peer that folds it apply fallback for 30 min of its own Δmono from that fold. Each peer therefore runs at the stricter of its own state and the team's latest event; no clock is compared and no peer ever returns to normal earlier than 30 min after its own last reason. Fallback only lowers B_eff and raises G_base and S_eff, so it can delay attempts but never adds one; the throttle level k still multiplies the fallback G_base (G_eff ≤ 60 s). Restart: governor mode is not persisted (Δmono does not survive a restart), so the first fetch of a run treats a `HOST_THROTTLED` health event in the last 180 first-parent heights of the folded chain (30 min at the fallback rate of 6 per minute) as folded at that fetch's completion; the daemon thus restarts in fallback when the team was throttled recently, and otherwise in normal mode.

**Counting.** Every push attempt goes through the one governed push function and counts, whatever its result (landed, rejected or ambiguous). That covers publishes, board-only pushes, save (two attempts, branch then board, inside one window, 08-lifecycle LIF-25/LIF-26, 01-engine ENG-49), base moves, displaced-ref copies (01-engine ENG-21, at most 3 per branch), the recover push (ENG-22) and probe pushes (01-engine ENG-46 is the engine side of this rule). Fetch polling (2.5 s active / 10 s idle, glossary §20, 01-engine ENG-13) is not governed: 4 peers make about 1.6 reads/s, ≈ 11 % of GitHub's 15 git reads/s per repository. A peer never runs two fetches at once: the next fetch starts ≥ 2.5 s after the previous one started, or right after it ends if it took longer (glossary §25 F10), so a slow fetch lowers the read rate instead of stacking reads. Fetch requests are not budgeted, but an HTTP 429 or 5xx on a fetch is a throttle signal (PRO-55). Budget (glossary §27.2, rev 2.4; U3 revised): B = 12 attempts/min team-wide by default, configurable per team in 6–24 at genesis (§3.1), with the automatic 30-min fallback to 6. Basis: spike 01 measured 0 failures and no throttling text at 6, 12 and 24 pushes/min with concurrent pushes to separate refs, and transient `(failed)` rejections only at 48/min with heavy overlap (glossary §25 F11); cowork's governed pushes are serialised on one board ref, so they overlap less than the spike's. Rev 2–2.3 kept B = 6 and recorded this headroom without using it; rev 2.4 uses half of the measured 24/min and keeps the old values as the fallback. **Edit-checkpoint publishes** (glossary §27.1, S1 rev 2.4: a Claude change-set publishes at every edit whose edit check passes) are ordinary pending work: they go through the one governed push function, count like any attempt and coalesce, because a newer passing capture of a change-set replaces its older ready pair before the window opens. A Claude editing fast therefore adds at most one publish per window of its peer, never one push per edit; this is why S1 rev 2.4 raises the publish rate only up to B_eff and needs no change to attempt counting.

**No priorities.** Everything pending rides the one push of a window: the code delta, claims, releases, request_status, answers, hold mirrors and events. Outbox overflow beyond the per-commit caps leaves in seq order in the following windows. Acknowledgments reach the board within ≈ 20 s at full contention by default (≈ 40 s in fallback), plus the measured push and fetch latency (push p50 ≈ 1.8 s, fetch p50 ≈ 1.2 s, together ≈ 1.5 s more per window, glossary §25 F10; at G = 5 s this latency is a visible share of each window, and the rev 2–2.3 remark that G dominates no longer holds), far inside the 120 s display threshold and the 30 min presume_absent. The resulting Claude-edit latency (edit check ≤ 0.5 s + governor window + receiver fetch/apply ≈ 10–30 s, glossary §27.1) is a MODEL figure, measured in the soak (T-PRO-20).

**What may be pushed in which state** (PRO-45):

| State | Code publish | Board-only ops allowed |
|---|---|---|
| ok / degraded | yes | all |
| FREEZE (any reason set, none of them INCIDENT or CONFIG(url\|public)) | base moves only (R3, 01-engine ENG-47/ENG-48) | exactly the glossary §8 list: freeze-class events (`event` of kind `freeze` / `unfreeze`) and `health` events, answer-class ops (`answer`, `request_status`), release-class ops (`release`, `seat_end`, `leave`) and hold mirrors (`hold`, including those caused by a human `/cowork resolve`). | FREEZE with INCIDENT | no | none: INCIDENT forbids every push on the branch (glossary §8) except (a) the one governed, `ABSENT`-leased copy of `LA_B` to `displaced/<oid12>` made at detection (01-engine ENG-21; ≤ 3 displaced refs per branch, glossary §20) and (b) the pushes of the human-typed `/cowork recover` (01-engine ENG-22) |

| NONRETRYABLE (entered after 3 consecutive transient rejections with the leased ref unchanged, PRO-54, glossary §26.2 item 2) | no | none until human `/cowork resume`; the whole rejected publish is already PINned (glossary §8; 01-engine ENG-45) |
| VERSION, proto form (board `proto` ≠ 1) | no | none: zero pushes of any kind (glossary §8) |

When several rows apply, the most restrictive wins. `request` (including the PRO-52 automatic re-attempt) and `presume_absent` are allowed only in the ok / degraded row. `/cowork stop` during the regionSpec form proceeds with the board-only ops above and skips its code publish; during the proto form it refuses (glossary §24 technical default 6; 08-lifecycle). Ops not allowed in the current state stay in the outbox. They leave when the state allows; if an intent of this peer landed in the meantime, they are re-numbered first (§3.2 step 2, PRO-09). A `HOST_THROTTLED` health event (PRO-55) may leave in the ok / degraded and FREEZE rows (it is a `health` event), not in the VERSION rows; one that is still unpublished when this peer's governor mode returns to normal is dropped, never published late. Governor mode is orthogonal to this table: it changes only the numbers of the governor (B_eff, G_base, S_eff), never what may be pushed.

*Why:* MODEL results reproduce the measured baselines (cas-storm-starvation-governor, e6c 2.5× attempts VERIFIED; push-herd-governor-undercount, sweep/e5 VERIFIED). Attempts are budgeted rather than successes because rejected attempts also consume the host's budget. Throttling and push rejections are classified by observation, not message text (glossary §18; §26.2 item 2). The measured rejection strings (`cannot lock ref …` for a lost lease race, §25 F9; `(failed)` and `fatal error in commit_refs` under overlapping pushes at 48/min, §25 F11) differ per host and per cause, so text could only mislead; the outcome after a fetch (ids present, ref moved, ref unchanged) is what decides. Three consecutive transient rejections against an unchanged ref (§26.2 item 2) keep a truly refusing host from being retried forever while a short host-side failure burst, like the F11 one, is retried. The automatic fallback (glossary §27.2) is what makes B = 12 safe to ship on hosts other than the measured GitHub path: a host that throttles at 12 per minute moves the team back to the rev 2–2.3 rate within one window of the first signal. Its HTTP-status signals are read from git's transport error output (01-engine owns the parsing), which is message text; glossary §18 allows text to "make handling stricter", and fallback only lowers the rate: it never selects a rejection class, never causes a retry, a publish or a lift (the 30-min expiry is a timer, not a text reading). A misread status can therefore only slow the team for 30 min.

### 3.9 Version gating

- `proto` is fixed at 1 (glossary §22: protocol raise is v2). Every board and live commit carries `Cowork-Proto: 1`. A board whose tip `protocol.json.proto` ≠ 1 puts this peer in the proto form of the VERSION publish pause: zero pushes of any kind. Fetch, fold (unknown ops are no-ops) and apply continue (glossary §8; 01-engine ENG-55).
- **teamRegionSpec** (glossary §3; PRO-48). It starts as the genesis `protocol.json.regionSpec`. At step 6 of each folded commit, if every peer in R has the same latest announced `regionSpec` X′ ≠ the current value, `teamRegionSpec` becomes X′. This is deterministic and needs no new op. A peer whose own regionSpec ≠ `teamRegionSpec` is in the regionSpec form of the VERSION pause: code pushes paused, the glossary §8 board-only ops allowed (`message_params: {reason: "regionSpec", waiting_for: [display names in R whose regionSpec differs]}`). A peer that is not paused, while some peer in the live set announced a different regionSpec, shows `VERSION_SKEW` in status.
- **Claims under another regionSpec.** Every peer's gate and publish gate treat a claim whose `regionSpec` differs from its own as a whole-file claim (glossary §8; 04-regions REG-04). The fold itself does not: its overlap test uses ranges only and ignores regionSpec (04-regions REG-23), so every peer folds the same verdict whatever its own regionSpec. The fold reads regionSpec only to compute `teamRegionSpec`.
- **Re-announcement.** A daemon puts a `join` (same epoch) in its outbox whenever its `plugin_version`, `plugin_sha`, `regionSpec` or `config_fingerprint` differs from the values in its latest folded `join`, for example after an upgrade restart. `join` is allowed in the regionSpec form of the VERSION pause, which is how a team that upgraded one by one gets unblocked. The 04-regions mapper itself is pinned for proto 1: a mapper change requires a protocol raise (v2, glossary §22).
- **Plugin upgrade handshake, drain and restart** belong to 08-lifecycle (LIF-37) and 06-claude (CCI-52). Downgrade detection on the state ref belongs to 08-lifecycle (LIF-37). The start-time version check compares the board's `proto` and this peer's regionSpec against the folded `teamRegionSpec`, not against `protocol.json.regionSpec`, which is the genesis value only.

### 3.10 Host probe and fallback namespace

**When** (PRO-49). At genesis, meaning the first `/cowork start` on a branch with no board; it is the last preflight step (08-lifecycle §3.3 step 2.11). A joiner reuses the folded team `caps` and skips probing; its own first push (the `join`) proves its write access. If that push is non-retryable, 01-engine (ENG-45) handles it, and 08-lifecycle refuses start with the host's message. There is no human-invoked re-probe in v1: `/cowork doctor` is read-only (glossary §15) and only reports the folded `caps` (10-product `DR_HOST_CAPS`, UX-14).

**Steps.** Every probe push is a governed attempt (§3.8, bounded by the per-peer cap). Results are classified by exit code, `--porcelain` per-ref status and a re-fetch of the probe ref, never by text (glossary §18). Let `Q` be the probe ref of the namespace being probed: `refs/cowork/probe-<peer_id>`, or `refs/heads/cowork/probe-<peer_id>` when probing the fallback namespace (glossary §4). (`Q` replaces the letter P used here in revision 1, because P now names the publish composition, glossary §3.) A rejection is read by outcome (glossary §26.2 item 2): in steps 1, 2 and 5, where a rejection means "the host refuses this", a rejection with Q unchanged on re-fetch is first treated as transient and the step is repeated in a later governed window; the step counts as rejected only after 3 consecutive rejections with Q unchanged. Step 3 expects a rejection and step 4 reads the client's exit, so neither is repeated.

1. `Q1 = commit-tree <empty tree> -p Hr`, with the skip markers of glossary §5. Push `Q1:Q` with lease ABSENT. Status `ok` → `custom_refs = true`. Rejected → `custom_refs = false`; stop and go to the refusal table.
2. `Q2 = commit-tree <empty tree> -p Q1 -p Hr`. Push with lease `Q:Q1`. `ok` → `two_parent_ok = true`. Rejected while Q is still Q1 → `two_parent_ok = false`.
3. Push `Q3 = commit-tree <empty tree> -p Q1` with `--force-with-lease=Q:<X>`, where X is an existing commit oid that is not Q's current value (X = Q1 if step 2 landed, else X = Hr). The push must be rejected and Q must be unchanged on re-fetch: then `lease = true`. Otherwise `lease = false`.
4. Push `Q4 = commit-tree <empty tree> -p <current Q>` with a correct lease and `-o ci.skip`. Exit non-zero with Q unchanged → `push_options = false`. `ok` → `push_options = true`.
5. Delete Q with a correct lease. `ok` → `delete = true`. Rejected → `delete = false`, and Q is left in place and listed by doctor. Deleting the probe ref of the active namespace is the only remote deletion cowork performs (INV-OID, glossary §4, §21).

The results are published as one `caps` op in the genesis board commit. Live pushes use `-o ci.skip` only when `caps.push_options` is true.

**Measured on GitHub** (glossary §25 F8, F9). Custom refs push and fetch, two-parent commits are accepted, `--force-with-lease` create/update/delete behave as the probe expects, push options are advertised, and of 100 simultaneous leased pushes from two clones exactly one won every round (0 double wins, 0 ambiguous). A plain `git fetch` does not bring custom refs, so the explicit refspecs of glossary §4 are required. GitHub Actions `on: push` did not run for pushes to `refs/cowork/*`; the skip markers stay because other hosts may behave differently. These were measured from one PC on one network; the cross-network lease race is still to be run (glossary §26.3).

**Refusals and fallback** (PRO-50):
- `custom_refs = false`, and the team config at EPOCH_BASE does not set `host.fallbackNamespace: true` (glossary §17) → `START_REFUSED_CUSTOM_REFS`, which names the opt-in and states that it creates `refs/heads/cowork/…` branches visible to CI.
- `custom_refs = false` and opted in → re-run the probe in `refs/heads/cowork/` (its probe ref is then the active-namespace probe ref that INV-OID allows deleting). The opt-in shows the human the confirmation of 09-security SEC-16, listing every CI configuration file present at EPOCH_BASE (`.github/workflows/**`, `azure-pipelines*.yml`, `.gitlab-ci.yml`, `bitbucket-pipelines.yml`). If `two_parent_ok = false` there → `START_REFUSED_FALLBACK_LINEAR`.
- `lease = false` in either namespace → `START_REFUSED_NO_LEASE`.
- `--atomic` is never probed and never used (glossary §26.2 item 1: one rule for every host, P3). The board-authority / lagging-mirror rule already makes the board+mirror pair safe without it (PRO-13, glossary §4). GitHub advertises `atomic` (§25 F8); that support is recorded for v2 only.

In the fallback namespace the refs are `refs/heads/cowork/<enc(b)>/{board,code}`, with identical semantics. Every commit already carries the skip markers. Save commits never carry them, and no branch commit has a live commit as an ancestor (01-engine ENG-12), so a marker never suppresses CI on a real branch.

### 3.11 Convergence

**Definition** (INV-CONVERGE, glossary §21). The team has converged at board tip T\* iff every live peer i has folded T\* (so all hold identical fold states), and for every synced path p (scope class `LIVE`) not in i's `not_converged` list: `S_disk_i[p] == A_i[p] == tree(live_code(T*))[p]` (stored-form blob oids). Working-tree bytes are identical among peers with equal `config_fingerprint`. Across different checkout configurations only the stored form is promised. A differing `config_fingerprint` is never a join refusal: 03-data §3 (filter preflight, DAT-16) refuses a join only on a failing filter round trip (`START_FILTER`; the real-work-tree check of glossary §25 F12 as corrected by §26.2 item 3), and differing `core.autocrlf`/`eol` settings are displayed only, because canon makes published blobs identical.

**Assumptions**, each mapped to the rule that provides it:

| Id | Assumption | Provided by |
|---|---|---|
| A1 | Quiet: after t₀ there are no working-tree edits, Claude tool calls, human verbs or answers, and only finitely many daemon restarts. | (environment) |
| A2 | Every synced path can eventually be applied and every ready publication group can eventually be published; a path that cannot (lock, fence, ping-pong breaker, ON_DISK hold, a path that is not *applicable* under INV-GROUP — unmaterialisable, locally colliding, or an incoming quarantined path awaiting `/cowork review <id> --accept` (guard `quarantine-review`), each with its own INCOMING record — or a path of a ready publication group that cannot be published because of a publish pause (`VERSION`, `NONRETRYABLE`, `OFFLINE`/`AUTH`) or a FREEZE reason) is listed in `not_converged`, with the pause or FREEZE reason shown in status. | 01-engine ENG-31/ENG-32 (writer, defer, write groups) and its status writer (`pending.not_converged`), 05-holds HLD-01/HLD-54 (registry, INCOMING), PRO-45 (what a paused peer may push), INV-GROUP, INV-NOSILENT |
| A3 | Round trip: `clean(smudge(x)) == x` for synced paths, checked at start; breaking paths are excluded loudly. The start check runs in the real work tree with cwd = the repository root: for each filtered path p, `git cat-file --filters HEAD:p \| git hash-object --path=p --stdin` equals `HEAD:p`'s blob id (both sides converted by the same path); disk-versus-blob comparisons use only DISK_EQ, never `hash-object --path` of a working file against a blob (glossary §25 F12, §26.2 item 3). | 03-data DAT-16 (filter preflight), 01-engine ENG-34 (per-write round trip) |
| A4 | Governor progress: every round with at least one attempt lands at least one commit, unless the host is non-retryable. Rounds whose only attempts are transient host rejections or network failures land nothing and are retried with backoff; a transient that repeats 3 times against an unchanged ref becomes NONRETRYABLE (glossary §26.2 item 2), and a lasting network failure becomes the OFFLINE pause, so either way the affected paths end up in `not_converged` (A2). | PRO-40, PRO-43, PRO-54, single-ref CAS (01-engine ENG-43, ENG-44); lease arbitration measured on GitHub: exactly one winner in 100 of 100 simultaneous leased pushes (glossary §25 F9) |
| A5 | Pushed trees are merges against the explicit base: `merge-tree --write-tree --merge-base=A P TIP` (plus the conflict function's whole-path replacements and concat blobs), and after landing `A[p] :=` the pushed blob on the written paths. | INV-BASE, INV-PUSHED-IS-MERGE, INV-MASK (01-engine ENG-06, ENG-29, ENG-44) |
| A6 | Every timer-driven daemon op fires at most once per (subject, reason). | PRO-38, PRO-52 (one re-attempt per request key), PRO-53 (one `presume_absent` per (grant, `last_seq_seen`)), PRO-55 (one `HOST_THROTTLED` health event per peer per 15 min, only with other pending work or on a push) |

**Argument.**
1. *One state.* The board is a single CAS-serialised fast-forward chain (INV-FF), so it has a total order, and the fold is deterministic (INV-PRO-FOLD). The same tip therefore gives the same state on every peer.
2. *Finitely many board commits.* Every op type has a cause:
   - `claim`: confirmed tool edits (none after t₀), plus re-anchors and reservations that ride other commits;
   - `request`: denies and holds created before t₀, attempt increments caused by actions, and at most one automatic re-attempt per request key (PRO-52);
   - `request_status`: one per folded request op, plus one per local seat-state change, and seat states change finitely often under A1;
   - `answer`: an action, or at most one daemon auto-answer per request op (07-coordination COO-17);
   - `presume_absent`: at most one per request op, plus at most one per (grant, `last_seq_seen`), and the grantee's ops are finite under A1 (PRO-53);
   - `hold`: transitions, of which the timer-driven ones (glossary §20 "Hold escalation": revert-taint board event at +10 min, INCOMING health stub at 60 s, K6 human-held record offered at +10 min; the 24 h S6 auto-park) fire once per record (A6; 05-holds HLD-60, HLD-61);
   - `note`: an action;
   - `event`: once per cid, or per (subject, reason); a `HOST_THROTTLED` health event only after an own throttle signal on a push attempt, or on a fetch while this peer had other pending work, and at most one per 15 min per peer (PRO-55). Once a peer's other pending work is gone (the end of this argument), a fetch that keeps returning 429/5xx only keeps its local mode in fallback and posts nothing, so the count stays finite;
   - `join`, `leave`, `seat_*`: process starts and ends (A1), plus at most one re-announcing `join` per changed value;
   - `caps`: once, at genesis; `save`: human-typed;
   - code: change-sets captured before t₀, base moves caused by branch moves (finite), and K3 PIN conversions after CAS losses (one per change-set).

   No heartbeat, renewal or periodic op exists (PRO-38). So the total pending work after t₀ is finite. By A4 each round lands at least one commit, so the tip becomes fixed at some T\*. The code mirror keeps lagging by one publish, and nothing pushes to heal it.
3. *Fixed point.* After its last landed push, or once its remaining ready groups are blocked by a publish pause or FREEZE (their paths are then in `not_converged`, A2), peer i has `diff(A_i, P_i) = ∅` on every path outside `not_converged`, and so `diff(A_i, S_disk_i) = ∅` on every such path outside MASK (A5, INV-MASK). At T\* it applies `merge(A_i, S_disk_i, live_code(T*))`, which equals `live_code(T*)` on applyable paths (A2). It re-snapshots, and A3 gives `S_disk_i == A_i == T*`. No ready change-set and no outbox op that its state allows remain, so the governor's `pending` is false and peer i makes zero pushes.
4. *Holds.* An OFF_DISK hold is not on disk, and its bytes are on the board or in the local registry. An ON_DISK hold makes its paths differ from A. Those paths are in `not_converged`, visible in `status.json` and to the affected seat (INV-NOSILENT). S6 bounds the on-disk divergence of a non-`local_only` ON_DISK record that is mirrored on the board to 24 h: it is then PARKed, so disk returns to the team version and the bytes stay in the registry (05-holds HLD-61). S6 waits for durability (glossary §25.2 item 1): a record that is not mirrored (offline, `HOLD_MIRROR_REJECTED`) is never auto-parked; it stays on disk, visible and in `not_converged` until it is mirrored (and then follows S6) or a human resolves it. `local_only` (secret-bearing) records are never auto-parked and stay in `not_converged` until a human resolves them.
5. *Bound.* A peer that observes T\* (counted from its first successful fetch of T\*; *Plan 2 merge, R-32*: in SIM, the first such fetch after the forced heal, 11-testing §3.3) reaches the fixed point within K = 20 loops: one fetch and apply, at most 4 loops of apply coalescing at 2.5 s, at most 3 writer re-merge retries, 2 stable snapshots for the shrink guard and the 1 s deletion confirmation. The loop runs at the active period while work is pending. Snapshots read each stat-dirty file once into a staged copy and hash that copy without writing objects (glossary §26.1 W1, W6); the before/after stat check skips a tick only when the file changed during the read, which A1 excludes after t₀, so the staged read adds no loops to the bound.

**Convergence ≠ correctness.** A team can converge on a revert. Correctness is INV-NOLOSS, proven by the 05-holds/11-testing harness (11-testing INV-NOLOSS oracle). This argument only shows that the board goes quiet and the disks match it.

## 4. Rules

### Board format

- **PRO-01** Every board commit MUST have parents `[previous board commit, live code commit]`, or `[L0]` for genesis. Its subject MUST begin `[skip ci] ***NO_CI***`. Its trailers MUST be `skip-checks: true`, `Cowork-Proto: 1`, `Cowork-Writer: <peer_id>/<epoch>/<seq>`, plus the glossary §5 `Cowork-CS`/`Cowork-CS-Paths` trailers for each change-set it publishes. Its author and committer MUST be `<display> <peer_id@cowork.invalid>`, set explicitly through `GIT_AUTHOR_*`/`GIT_COMMITTER_*` with timezone `+0000`, it MUST NOT be signed, and it MUST NOT be merged with another board commit. _Covers: non-atomic-pair-and-fence, host-policy-and-ci, op-identity-cursors-board-merge_
- **PRO-02** The board tree MUST contain exactly `ops.jsonl`, `protocol.json`, `checkpoint/state.json` and `held/<hold_id>/<stage>/<repo path>` blob entries (stage ∈ {h0, h1, s1, s2, s3}, no entry for an ABSENT side), never a code path outside `held/`, and under `held/` only LIVE paths of mirrored records (PRO-21). _Covers: board-plaintext-and-permanence, non-atomic-pair-and-fence_
- **PRO-03** `ops.jsonl` MUST hold only the ops introduced by its commit: UTF-8 without BOM, LF, one JSON object per line, strictly increasing seq, ≤ 1,000 lines, ≤ 64 KiB total and ≤ 16 KiB per line. _Covers: version-skew-board-loss, board-growth-compaction_
- **PRO-04** (revised in rev 2.4, glossary §27.2) `protocol.json` MUST be `{proto: 1, regionSpec, budget, G_s, S_s}`, written at genesis and carried as the same blob by every v1 writer. The genesis writer MUST seed `budget` from the team config `host.pushBudgetPerMin` (integer 6–24; default 12 when absent; §3.1 for invalid values) and MUST derive `G_s = ⌈60,000 / budget⌉ / 1,000` and `S_s = ⌈18,000 / budget⌉ / 1,000` (default board: `budget: 12, G_s: 5, S_s: 1.5`); a later config change MUST NOT change an existing board's file. Daemons MUST use the stricter of board values and the local constants of their governor mode (§2, PRO-55): `B_eff = min(B_local, budget)`, `G_base = max(G_local, G_s, 60/B_eff)`, `S_eff = max(S_local, S_s)`, reading a missing or malformed field as its fallback value. _Covers: cas-storm-starvation-governor, version-skew-board-and-guards_
- **PRO-05** Board ops MUST carry code content only as blob ids from the pinned clean path, free text only as notes of ≤ 280 chars (`note` op text from `cowork_note`; `note?` on `request`/`answer` from the `note` argument of `cowork_request`/`cowork_respond`) after the local secret scan, `reason_code` only as a glossary §19 registry code, and no wall-clock field and no rendered template text. No board commit may carry a quarantined path's local bytes, a restore-marker blob, or a `local_only` or secret-scanner-hit blob (INV-SECRET, S8; glossary §21 rev 2.1). _Covers: board-plaintext-and-permanence (with SEC-08, SEC-09)_
- **PRO-06** A writer MUST NOT build a board commit that breaks the caps (5,000 folded records; 5 MB board tree as defined in §3.1; 1,000 ops and 64 KiB per `ops.jsonl`). Overflowing outbox ops MUST leave in seq order in later windows. At the record cap the writer MUST withhold record-creating ops, keep ending ops flowing, and set `BOARD_FULL` in status with one `event{kind: health, reason_code: BOARD_FULL}`. _Covers: board-growth-compaction_
- **PRO-07** The genesis board commit B0 MUST have the parent `[L0]`, `protocol.json`, `ops.jsonl` = the starter's `join` followed by its `caps`, and `checkpoint/state.json` = the fold state at height 0. It MUST be pushed with ABSENT leases on board and mirror; the loser of a simultaneous genesis refetches and joins (01-engine ENG-51). _Covers: op-identity-cursors-board-merge, host-policy-and-ci_

### Identity and ordering

- **PRO-08** `peer_id`, `epoch` and `seat_id` MUST be generated as in §3.2 step 1 (glossary §2: `seat_id` minted by the MCP server at `hello`, or by the daemon for a `NO_MCP` seat after 3 s, first bound id kept for the process life). The seq high-water mark MUST be persisted in the state ref before any push that uses it, and a seq MUST NOT be reused within an epoch. _Covers: op-identity-cursors-board-merge, ambiguous-push-and-crash-stale-base_
- **PRO-09** An op MUST receive its seq when first placed into a publish intent and keep that id across rebuilds until it lands or is dropped. When an intent of this `(peer, epoch)` lands, every outbox op whose seq is below the landed writer seq and that was not in that intent MUST be re-numbered (new seq from the counter, relative order kept) before its next placement; an op found with a seq ≤ the folded `last_seq` of its own epoch when an intent is built MUST be re-numbered too (§3.2 step 2). Every publish intent MUST allocate a writer seq larger than all its op seqs, and the code commit and board commit of one intent MUST carry the same `Cowork-Writer`. _Covers: op-identity-cursors-board-merge, ambiguous-push-and-crash-stale-base_
- **PRO-10** Every order-dependent decision (earlier claim, conflict causer, FIFO, governor rank, request precedence) MUST use board position only. No decision may compare wall-clock values from different machines (INV-CLOCK); timers MUST be Δ from a local anchor taken through the single anchor helper, enforced by a CI lint. _Covers: lease-expiry-clocks-heartbeats, sleep-offline-stale-and-suspect-claims, warning-fanout-single-warner_
- **PRO-11** `cid` MUST be `H(winner op id, loser op id)` for conflict kinds and `H(event op id, kind)` otherwise, with `H(x, y)` = `base32c(sha256(x ‖ 0x00 ‖ y))[0:8]` in the Crockford alphabet (glossary §3). _Covers: warning-fanout-single-warner_
- **PRO-12** An ambiguous push MUST be resolved only by whether its writer id or op ids appear on the board's first-parent chain after its lease value (mechanics: 01-engine ENG-44). It MUST NOT be resolved by tree content or message text. _Covers: ambiguous-push-and-crash-stale-base_
- **PRO-13** No daemon decision may read `refs/cowork/<enc(b)>/code` or its fetched copy. The mirror value is used only as the mirror refspec's lease (CI lint). _Covers: non-atomic-pair-and-fence_

### Fold

- **PRO-14** The fold MUST be a pure, total, deterministic function of the board first-parent chain, using only the inputs listed in §3.3. It MUST NOT use clocks, network, local seat state, parsing, labels, `git diff` or time-based caps, and it MUST turn malformed input (including fields failing the 09-security SEC-35 validators) into no-ops, never exceptions. _Covers: op-identity-cursors-board-merge, version-skew-board-and-guards_
- **PRO-15** Each board commit MUST be folded by the 7-step algorithm of §3.3, in commit order and then line order. _Covers: op-identity-cursors-board-merge_
- **PRO-16** An op MUST be a no-op unless all of these hold: its id's `(peer, epoch)` equals the commit's writer; its seq exceeds the writer's folded `last_seq` and the previous op's seq in the commit and is below the writer seq; the writer's epoch is active (or the op is a `join` from a non-retired epoch); and it passes its type schema. An op whose id is already folded is thereby a no-op. Unknown op types MUST fold as no-ops and unknown fields MUST be ignored. _Covers: op-identity-cursors-board-merge, version-skew-board-loss_
- **PRO-17** A `claim` op MUST be valid only if all of these hold:
  - the holder is a live seat of the writer's active epoch, or the reservation case of PRO-19 applies;
  - `anchor == live_code` of the carrying commit;
  - `base_blob` equals the anchor's blob of `path` (or, for a path absent from the anchor tree, the 04-regions §3.5 absent-path form `base_blob: null`, `ranges: []`, at least one tombstone; REG-08);
  - ranges are well-formed (stored-form, 1-based inclusive, glossary §7);
  - the `claim_id` is 16 lowercase base32 characters (glossary §3) and is new, or belongs to a claim record (HELD, STALE or RELEASED) of the same holder `(peer, seat)`: a HELD record is re-anchored, a STALE or RELEASED one becomes HELD again (§3.3 `claim` row);
  - the record cap is not reached for a new id;
  - the 04-regions fold-overlap test (`foldOverlap`, REG-23: FoldMapper/1 in `fold` mode with the deterministic D cap, no regionSpec input) finds no intersection with any HELD claim of a different seat on the same path. STALE claims never block; reservations block every seat but their holder; grants do not change blocking.

  The later of two overlapping claims is always the invalid one. _Covers: race-loser-hunk-lands, op-identity-cursors-board-merge, non-atomic-pair-and-fence_
- **PRO-18** `request`, `request_status`, `answer` and `note` ops MUST be validated and applied as in §3.3 and §3.6. A request MUST be keyed by its identity `(req_id, to_holder.seat)` (glossary §3), and `request_status`/`answer` MUST name both fields. `ckind` MUST be one of `claim_visible|claim_posthoc|claim_race|human_in_claim|dependency`. Answer verbs are `accept|decline|later|release` for handoff and `grant|decline|later|release` for go_first. Request ops MUST NOT carry blob fields and MUST reference a non-terminal, non-`local_only` hold record of the writer. A `note` op MUST NOT change any claim, request or hold. _Covers: deadlock-and-return-to-sender-pingpong, go-first-unbounded-and-slower-than-job, zombie-claims-idle-holder_
- **PRO-19** Grants and reservations MUST be fold states with exactly the creation, admission and termination rules of §3.6. The publish gate input (04-regions REG-20) MUST include them. Neither may involve a timer, except the PRO-53 presumed-absent end of a grant (glossary S4, §20 "Presume absent"), which reaches the grant only through an applied `presume_absent` op (end condition (c)). _Covers: go-first-unbounded-and-slower-than-job, claims-held-all-day-starvation_
- **PRO-20** `join`, `leave`, `seat_start` and `seat_end` MUST have the effects in the §3.3 table. A `join` from a new epoch of a known peer MUST retire the old epoch (seats end, claims RELEASED `superseded`, addressed requests `returned`). `seat_start` MUST be published no later than, and in the same board commit as, the seat's first claim or request; a seat with no board footprint publishes neither `seat_start` nor `seat_end`. _Covers: zombie-claims-idle-holder, op-identity-cursors-board-merge_
- **PRO-21** A `hold` op MUST be valid only if: the writer is the record's owner; `prev_rev` equals the folded `rev` (null on create) and `rev > prev_rev`; `local_only = true` implies a content-free stub (no `held/<hold_id>/` subtree and no blob oids, glossary §7); and a non-terminal, non-`local_only` record has its `held/<hold_id>/` subtree in the carrying commit's tree. The writer MUST put only LIVE paths into a mirrored `hold` op and its `held/` subtree, and MUST mirror a record that would need any non-LIVE path only as the `local_only` content-free stub (glossary §9 rev 2.1). This is checked by the writer before the push (serializer, 09-security SEC-09), never left to the fold, because a fold rejection comes after the blobs reached the remote. An offer change caused by an answer MUST be mirrored by the owner in a later `hold` op. _Covers: board-plaintext-and-permanence, permanent-hold-never-converges (with HLD-10)_
- **PRO-22** An `event` op of a conflict kind whose `cid` is already folded MUST be a no-op (backstop for INV-ONE-EVENT; the creating daemon is defined in 07-coordination COO-01). _Covers: warning-fanout-single-warner_
- **PRO-23** `save` MUST release only `released_claim_ids` held by the writer's own seats. `caps` MUST replace the team caps. _Covers: host-policy-and-ci_
- **PRO-24** A daemon MUST detect its own ops that folded as no-ops and act on them, never by re-sending the identical op:
  - an op rejected only by the generic checks of step 3b (seq ≤ `last_seq`, or its epoch not active) is not a type-specific rejection: it MUST NOT become K3 or any other conflict; it is re-numbered and stays in the outbox (PRO-09; an op of an absent epoch waits behind the PRO-36 `join`);
  - claim rejected by the PRO-17 overlap test → the covering change-set to 05-holds as K3 (HLD-45, COO-06);
  - claim rejected for any other reason (anchor, `base_blob`, ranges, a SEC-35 validator) → not K3; the claim stays TENTATIVE (local) and MUST NOT be re-published automatically, and the daemon shows `CLAIM_REJECTED` in status once per (claim_id, reason) (PRO-38);
  - hold op rejected because the folded `rev` differs from the op's `prev_rev` → re-issue once from the folded rev;
  - hold op rejected for any other reason (a SEC-35 validator, a missing or forbidden `held/` subtree, the `local_only` stub rule) → MUST NOT be re-issued automatically: the rejection is deterministic and would repeat in every window. The record stays in the local registry with its bytes (INV-NOLOSS), the daemon shows `HOLD_MIRROR_REJECTED` with the hold id in status once (PRO-38) and tells the affected seat's Claude once at its next hook (§2.1 carrier, INV-NOSILENT), and the next hold op for that record is written only after the record changes (a new rev from a local transition or a human `/cowork resolve`);
  - rejected request, status, answer or note → re-evaluate against the fold and tell the seat through 07-coordination;
  - rejected `presume_absent` → nothing, because the target PC published an op first (or the request or grant ended).

  Every re-issue under this rule counts under PRO-38 as a daemon-initiated op of (subject, reason), so a rejection can never drive an unbounded series of pushes.

  _Covers: op-identity-cursors-board-merge, race-loser-hunk-lands_
- **PRO-25** Fold state MUST be persisted incrementally with the last folded board oid. After `/cowork recover` restores a different chain, or re-anchors this peer onto the team's recovered chain (01-engine §3.7 step 2a), a daemon MUST discard its fold state and refold from the newest checkpoint at or below the last common first-parent ancestor. In re-anchor mode it MUST start a new epoch, rebuild its unlanded outbox ops under the new epoch as in §3.3 "Determinism", and re-claim only through ordinary claim ops of the new epoch. _Covers: ref-rewind-silent-revert (with ENG-22)_

### Checkpoints and compaction

- **PRO-26** The writer of a board commit at a height divisible by 256 MUST write `checkpoint/state.json` as the RFC 8785 canonical JSON of the fold state after folding and compacting that commit. All other commits MUST carry the previous entry unchanged. _Covers: board-growth-compaction_
- **PRO-27** At each height h ≡ 0 (mod 256), the fold MUST drop terminal records with `terminal_height ≤ h − 512`, and ended seats no longer referenced. The writer MUST remove the dropped holds' `held/` subtrees in that commit. Non-terminal records MUST never be dropped and history MUST never be rewritten. _Covers: board-growth-compaction, version-skew-board-loss_
- **PRO-28** On a checkpoint mismatch a daemon MUST first refold from its previous verified checkpoint. If the mismatch persists, it MUST enter the VERSION publish pause with `cause = checkpoint_mismatch`, raise a P2 alert to the human and every live seat, and lift the pause only on a later matching checkpoint or after a plugin update and a matching refold. _Covers: version-skew-board-and-guards_
- **PRO-29** A joiner MUST start its fold at the newest checkpoint at or below the tip, replay at most 255 commits, and verify the next checkpoint it folds. _Covers: board-growth-compaction_

### Claim lifecycle

- **PRO-30** Claims MUST follow the §3.5 state machine. A HELD claim MUST leave HELD only through the listed events. Claims MUST NOT carry a TTL, renewal, dormancy or automatic grant. _Covers: zombie-claims-idle-holder, claims-held-all-day-starvation, lease-expiry-clocks-heartbeats_
- **PRO-31** A confirmed TENTATIVE claim MUST enter the outbox and ride the next governed window, as a board-only op if its change-set is still open. A re-anchor MUST ride in the same board commit as the own code change that caused it. Claim ranges MUST be recomputed for every rebuild of a publish intent. Only `confirmed` TENTATIVE claims MAY be published. While a FREEZE reason or either form of the VERSION pause is set, claims MUST stay TENTATIVE. _Covers: race-loser-hunk-lands, offline-split-brain, offline-auth-claims_
- **PRO-32** After folding a `save`, each daemon MUST release, with reason `save`, exactly those of its own seats' claims that meet the three conditions of §3.5. It MUST release them at the holder seat's next Stop when that seat is mid-turn, and MUST NOT release another peer's claims. _Covers: claims-held-all-day-starvation_

### Liveness

- **PRO-33** For every folded request op (each attempt) addressed to one of its seats, the holder daemon MUST publish one `request_status` (naming `req_id` and `to_holder.seat`) in its next governed window, with the status mapped from the seat activity as in §3.7 step 2 (`ENDED` → no op: the `seat_end` op closes the request `returned`), plus one per later change of the seat state. It MUST publish `request_status{returned}` for an accepted handoff that is still unapplied when the claim is released. _Covers: zombie-claims-idle-holder, lease-expiry-clocks-heartbeats_
- **PRO-34** The requester daemon MUST show a request as NOT_RESPONDING (message code `REQUEST_NOT_RESPONDING`, §2.1) after 120 s Δmono from folding the request op without a folded op from the holder's active epoch. It MUST NOT publish anything for this. _Covers: offline-split-brain_
- **PRO-35** After 30 min Δmono from folding a request op with no folded op from the holder's active epoch since then, the requester daemon MUST fetch and fold, re-check, and only then publish `presume_absent{peer, epoch, last_seq_seen}`. The fold MUST apply it only under the four conditions of §3.7 step 4, the last being relationship (i) (an open request from the writer to the target) or (ii) (a grant on the writer's HELD claim to a seat of the target, PRO-53). Each request op arms at most one `presume_absent`. The test is PC-level (S4 rev 2.1): any board commit of the target `(peer, epoch)` counts as activity. _Covers: lease-expiry-clocks-heartbeats, zombie-claims-idle-holder, offline-split-brain_
- **PRO-36** An applied `presume_absent` MUST make the target epoch absent: claims STALE, seats ended, addressed requests closed `returned`, grants to it ended, nothing deleted. A daemon that folds its own epoch as absent MUST put a `join` (same epoch) and its `seat_start` ops first in its outbox, MUST re-number every unlanded outbox op so that it comes after them (PRO-09), and re-claim only through ordinary claim ops. _Covers: sleep-offline-stale-and-suspect-claims, offline-split-brain_
- **PRO-37** A daemon MUST mark its own HELD claims SUSPECT when its last successful fetch or push is older than 60 s by `max(Δwall, Δmono)`, or when the suspend gap exceeds 5 s. A gate query on a SUSPECT claim MUST trigger a fetch and fold and wait ≤ 5 s. The claim is confirmed only if the fresh fold shows it HELD under this peer's active epoch; otherwise the gate answers G1. _Covers: sleep-offline-stale-and-suspect-claims, offline-auth-claims_
- **PRO-38** No daemon may publish a heartbeat, renewal or "alive" op. Every daemon-initiated op not caused by a local human/Claude action or by a newly folded op MUST be emitted at most once per (subject, reason). _Covers: lease-expiry-clocks-heartbeats, phantom-delta-pingpong-convergence, permanent-hold-never-converges_
- **PRO-52** (added in rev 2.1, S4) When the holder's active epoch acknowledged the current attempt of a request with `request_status` and then 30 min Δmono pass with no further folded op from that `(peer, epoch)` and no folded `answer` for the request key, the requester daemon MUST fetch, fold and re-check, and then file the automatic re-attempt of §3.7 step 4: at most one per request key, ever, and exactly one when the conditions hold. The timer restarts at every folded op of that `(peer, epoch)`. The op MUST carry the same `req_id`, `to_holder`, `kind`, `ckind`, `cs_id`, `origin`, `est_minutes` (when present) and `note` as the previous attempt, `attempt + 1`, and, when the previous attempt listed claims, only those still HELD by the `to_holder` seat. It MUST NOT file one when the `from` seat has ended or when the previous attempt listed claims and none is still HELD, MUST re-check the conditions at every intent build while the op waits, and MUST drop it, unpublished, when one fails. The fact that a key's automatic re-attempt was filed MUST be persisted with the outbox. _Covers: zombie-claims-idle-holder, lease-expiry-clocks-heartbeats_
- **PRO-53** (added in rev 2.1, S4) A holder daemon whose `answer{grant}` folded MUST (glossary §20 permits it; v1 always uses the permission), after 30 min Δmono of silence from the grantee's `(peer, epoch)`, counted from folding the grant or from the grantee's latest folded op after it, if the grant is still active, fetch, fold, re-check and publish `presume_absent{peer, epoch, last_seq_seen}` for the grantee's PC (relationship (ii) of §3.7 step 4), at most once per (grant, `last_seq_seen`). The applied op ends the grant (PRO-19 (c)) through the PRO-36 effects. _Covers: go-first-unbounded-and-slower-than-job, zombie-claims-idle-holder_

### Governor

- **PRO-39** R MUST be the glossary §3 ranked set: the live set minus ghosts (no board commit in the last `K_evict` = 200 first-parent heights), and rank MUST be the 1-based position by `(last_height ascending, a peer with none first; peer_id ascending)`. A peer outside R (ghost, new joiner, peer returning after `presume_absent`) MUST use rank 1; a tie with the ranked rank-1 peer is an ordinary CAS collision. _Covers: cas-storm-starvation-governor, push-herd-governor-undercount_
- **PRO-40** A peer MUST start a push attempt only when it has pending work allowed by its state, no attempt is in flight, `Δmono since anchor ≥ wait(self)` (§3.8: `G_eff + (rank − 1)·S_eff`, or `G_base` once aged), `Δmono since its own last attempt ≥ G_eff`, it made fewer than `B_eff` attempts in the last 60 s Δmono, and it observed fewer than `B_eff` landings (§2) in the last 60 s Δmono (sliding team guard, glossary §20 rev 2.1 and §27.2: B_eff = 12 by default, 6 in fallback; aging never bypasses it). The anchor MUST be the local observation of the current board tip, or the receipt of its own `ok`. A peer whose allowed pending work was pre-empted by two tip changes of other writers since its own last attempt MUST be treated as aged (rank 1, `G_base`, whatever its throttle level). _Covers: cas-storm-starvation-governor, push-herd-governor-undercount_
- **PRO-41** Every push of every kind (publish, board-only, save ×2, base move, displaced copy, recover, probe) MUST go through the one governed push function and count as an attempt, whatever its result. Fetch MUST NOT be governed. _Covers: push-herd-governor-undercount_
- **PRO-42** A peer MUST push only when its publish composition P differs from A on some path (a ready, unheld publication group with a non-empty diff, glossary §3) or it has allowed outbox ops. It MUST put everything pending into the one push of a window, with no priority classes. _Covers: push-herd-governor-undercount, cas-storm-starvation-governor_
- **PRO-43** After a CAS loss (a lease loss in the PRO-54 classification: the leased ref moved and its own ids are absent) a peer MUST fetch, refold, re-merge and re-run every guard against the new tip (01-engine ENG-40, ENG-44), then wait for its newly computed window. It MUST NOT retry immediately. _Covers: cas-storm-starvation-governor, race-loser-hunk-lands_
- **PRO-44** An attempt that took > 10 s Δmono, was watchdog-killed, returned no per-ref status, or was classified as a transient rejection (PRO-54) MUST raise the throttle level (G_eff doubles, capped at 60 s). Any other attempt with per-ref status within 10 s MUST lower it by one level (rev 2.3: a transient rejection is the "backoff" of glossary §26.2 item 2 and never lowers it). The throttle level MUST NOT keep a peer from ever attempting: aging (PRO-40) bounds its wait for the shared window. The current G_eff MUST be shown in status. The throttle level is independent of the governor mode (PRO-55): a slow (> 10 s) attempt raises k and is also a throttle signal, and in fallback k multiplies the fallback G_base (rev 2.4). _Covers: cas-storm-starvation-governor_
- **PRO-45** Board and code pushes MUST be restricted per state exactly as in the §3.8 table. Ops not allowed in the current state MUST stay in the outbox, keeping their ids until an intent of this peer lands without them, after which PRO-09 re-numbers them. _Covers: offline-split-brain, version-skew-board-and-guards_
- **PRO-46** (revised in rev 2.4, glossary §27.2) The governor parameters MUST be the glossary §27.2 values: by default B = 12, G = 5 s, S = 1.5 s, per-peer cap B_eff (12) per 60 s Δmono, sliding team guard: no attempt while ≥ B_eff (12) observed landings in the last 60 s Δmono; in fallback (PRO-55) B = 6, G = 10 s, S = 3 s with the cap and the guard at 6; throttle cap 60 s in both modes. A team board seeded with another `budget` in 6–24 scales these through PRO-04. The worst normal wait is `G + (|R| − 1)·S` (9.5 s for 4 peers by default, 19 s in fallback). _Covers: cas-storm-starvation-governor_
- **PRO-54** (added in rev 2.3, glossary §26.2 item 2) Every governed push that does not return `ok` for its leased ref MUST be classified by outcome after a fetch and fold, never by message text: (a) its writer id or any of its op ids is on the board's first-parent chain after the lease value → landed (PRO-12); else (b) the leased ref moved → lease loss (PRO-43); else (c) the leased ref is unchanged and a per-ref rejection line was returned → transient rejection: retry in a later governed window with backoff (PRO-44); else (d) no per-ref status → retryable network failure (PRO-44). A counter of consecutive transient rejections MUST reset at every landing of this peer and at every move of the leased ref; when it reaches 3, the peer MUST enter `NONRETRYABLE` (the whole rejected publish is PINned, 01-engine ENG-45; publishing stops until human `/cowork resume`). The host's rejection text (glossary §25 F9 `cannot lock ref … is at … but expected …`, F11 `(failed)` / `fatal error in commit_refs`, or any other) MAY only choose the explanation shown to the human. A single rejection MUST NOT set `NONRETRYABLE`. The counter and the `NONRETRYABLE` consequence apply to publishes and board-only pushes, whose leased ref is the board ref (glossary §26.2 item 2 speaks of "the same publish"). For the other governed pushes (save, 08-lifecycle LIF-25/LIF-26; base move, 01-engine ENG-47/ENG-48; displaced copy, ENG-21; recover, ENG-22) the outcome reading (a)–(d) and the no-text rule apply to the ref that push leases, and the owning rule decides what a transient rejection leads to. Probe pushes follow §3.10 and PRO-49: there the third consecutive transient rejection is the step's "rejected" result, not `NONRETRYABLE`. When the counter reaches 2 it is also a throttle signal (PRO-55, glossary §27.2). _Covers: push-rejection-poisons-chain, host-policy-and-ci, cas-storm-starvation-governor_
- **PRO-55** (added in rev 2.4, glossary §27.2) Each daemon MUST keep a local governor mode, `normal` or `fallback`, never written to the board or the fold state.
  - **Signals.** A throttle signal (§2) is: an HTTP status 429 or any 5xx on a push or fetch to the pinned remote; a push attempt with RTT > 10 s Δmono or killed by the watchdog; the PRO-54 transient-rejection counter reaching 2. On each one the daemon MUST set `last_signal := now` (Δmono). A remote reached over ssh has only the RTT and streak signals.
  - **Mode.** The mode MUST be `fallback` while `now − last_signal < 30 min` or `now − last_throttle_event_folded < 30 min` (both this daemon's Δmono), else `normal`; fallback MUST take effect for the next window decision after the signal, i.e. within one window. Normal mode MUST use the local constants `B_local = 24, G_local = 2.5 s, S_local = 0.75 s`, fallback `B_local = 6, G_local = 10 s, S_local = 3 s`, combined with `protocol.json` by PRO-04. The mode MUST NOT change what may be pushed (PRO-45) and MUST NOT lower the throttle level k. Status MUST show `HOST_THROTTLED` with its source and the minutes left while the mode is fallback.
  - **Team event.** On an own throttle signal that came from a push attempt, or from a fetch while the peer had other pending work, the daemon MUST put one `event{kind: health, reason_code: HOST_THROTTLED}` (cid `H(<event op id>, health)`, §3.2 step 4) in its outbox unless a `HOST_THROTTLED` health event was folded, or put in its outbox, by this daemon in the last 15 min Δmono. It rides the next governed window like any op (PRO-42; allowed in the ok / degraded and FREEZE rows of PRO-45) and MUST be dropped unpublished if the mode is `normal` again before it leaves. A daemon that is in fallback only because it folded a teammate's event MUST NOT post one.
  - **Following.** On folding `event{kind: health, reason_code: HOST_THROTTLED}` from any writer, the daemon MUST set `last_throttle_event_folded :=` that fold's completion instant (Δmono), so each peer applies the stricter of its own state and the latest folded team event, for 30 min of its own observation. The fold itself only records the event (§3.3 `event` row); following is local behaviour and reads no clock from the board. The first fetch of a run (start, join, restart) MUST treat such an event in the last 180 first-parent heights of the folded chain as folded at that fetch's completion; other history revealed by that fetch does not count.
  _Covers: cas-storm-starvation-governor, push-herd-governor-undercount, host-policy-and-ci_

### Version and host

- **PRO-47** A daemon MUST treat a board tip whose `protocol.json.proto` ≠ 1 as the proto form of the VERSION publish pause (zero pushes of any kind, glossary §8), and keep fetching, folding (unknown ops as no-ops) and applying. _Covers: version-skew-board-and-guards, version-skew-board-loss_
- **PRO-48** `teamRegionSpec` MUST start as the genesis value and MUST switch to X′ exactly when every peer in R has announced X′ in its latest `join`. A peer whose regionSpec differs from it MUST be in the regionSpec form of the VERSION pause (code pushes paused, glossary §8 board-only ops allowed). The fold MUST NOT use regionSpec for anything else (claim overlap ignores it, REG-23). A daemon MUST re-announce `join` (same epoch) whenever its `plugin_version`, `plugin_sha`, `regionSpec` or `config_fingerprint` differs from its latest folded `join`. _Covers: version-skew-board-and-guards_
- **PRO-49** The host probe MUST run at genesis only, with the five governed steps of §3.10, classified by exit code, porcelain status and re-fetch only; a rejection in steps 1, 2 or 5 MUST count as the host's refusal only after 3 consecutive rejections with the probe ref unchanged (glossary §26.2 item 2; §3.10). Its results MUST be published as one `caps` op. Joiners MUST reuse the folded team caps. The only remote deletion MUST be the probe ref of the namespace being probed (INV-OID). _Covers: host-policy-and-ci, non-atomic-pair-and-fence_
- **PRO-50** Start MUST refuse with `START_REFUSED_CUSTOM_REFS`, `START_REFUSED_NO_LEASE` or `START_REFUSED_FALLBACK_LINEAR` as in §3.10. The fallback namespace MUST be used only with `host.fallbackNamespace: true` at EPOCH_BASE, after the SEC-16 confirmation and a passing probe in that namespace. `--atomic` MUST NOT be used, on any host, including hosts that advertise it (glossary §26.2 item 1; v2 candidate). _Covers: host-policy-and-ci_

### Convergence

- **PRO-51** Every peer MUST reach the fixed point of §3.11 within K = 20 loops after observing the final board tip T\* of a quiet period, on every synced (`LIVE`) path not in `not_converged`, and then make zero pushes. Every protocol mechanism MUST preserve assumptions A4 and A6. _Covers: phantom-delta-pingpong-convergence, permanent-hold-never-converges_

## 5. Invariants

**Glossary invariants enforced here:** INV-FF (the board half: FF-only board; the fold assumes it), INV-FENCE (this chapter supplies the fold at the leased tip, including grants and reservations, that publish gate B1 runs on P), INV-PUSHED-IS-MERGE and INV-MASK (assumed by §3.11 A5 over P; enforced by 01-engine and 05-holds), INV-GROUP (assumed by §3.11 A2 over applicable paths; unmaterialisable, locally colliding and incoming quarantined paths are not applicable, rev 2.1), INV-ONE-EVENT (fold dedupe backstop, PRO-22), INV-CONVERGE (§3.11, PRO-51), INV-CLOCK (PRO-10), INV-OID (only the probe ref of the active namespace is deleted, PRO-49), INV-NOSILENT (BOARD_FULL, VERSION, REQUEST_NOT_RESPONDING, SUSPECT, HOLD_MIRROR_REJECTED, CLAIM_REJECTED, REQUEST_REATTEMPTED and GRANTEE_PRESUMED_ABSENT are surfaced), INV-SECRET (board content, PRO-05; only LIVE paths under `held/`, so no quarantined bytes, restore markers or `local_only` blobs, PRO-21), INV-NOLOSS (compaction never drops a non-terminal record and history is never rewritten, PRO-27; `presume_absent` deletes nothing, PRO-36).

**Chapter-local invariants:**

| Id | Statement |
|---|---|
| **INV-PRO-FOLD** | Any two daemons that folded the same board tip hold byte-identical canonical fold states and identical own-op rejection sets, whatever their wall clocks, mapper timing, start point (genesis or any checkpoint whose `state.json` equals the genesis fold at its height; a joiner trusts the nearest checkpoint, glossary §24 technical default 9, and a wrong checkpoint is detected later by PRO-28) or plugin build of the same proto and regionSpec. |
| **INV-PRO-TOTAL** | For any content of `ops.jsonl`, trailers and `protocol.json`, the fold terminates without an exception, within bounded time per commit (≤ 1,000 ops). |
| **INV-PRO-QUIET** | Under assumption A1 the number of board commits after t₀ is finite. No op type is emitted periodically; the only timer-driven liveness ops are bounded per subject (one automatic re-attempt per request key, one `presume_absent` per request op or per (grant, `last_seq_seen`), and grantee ops are finite under A1). `HOST_THROTTLED` health events need an own throttle signal on a push or on a fetch with other pending work, and are spaced ≥ 15 min per peer (PRO-55). |
| **INV-PRO-GOV** | Each peer makes at most B_eff attempts per 60 s Δmono, and starts none while it has observed ≥ B_eff landings in the last 60 s Δmono (sliding team guard), where B_eff is the value of its current governor mode (12 by default, 6 in fallback, PRO-55; glossary §27.2). Landed board commits, as observed by any one peer that keeps a pending publish, are spaced by at least G_base minus one poll period. A peer is in fallback for at least 30 min Δmono after its own last throttle signal and after its folding of any `HOST_THROTTLED` health event. |
| **INV-PRO-NOSTARVE** | A peer with pending work, a working host and a state that allows publishing lands within at most max(\|R\|, 2) landed commits of other peers plus its own collisions, counted from the moment G_eff has passed since its own last attempt, whether or not it is in R and whatever its throttle level (outside-R rank 1 and aging, PRO-39, PRO-40). |

Every target op landing before it makes it a no-op. A requester files at most one automatic re-attempt per request key (PRO-52). |
| **INV-PRO-COMPACT** | Compaction never drops a non-terminal record. The fold from genesis equals the fold from any checkpoint at every later height. |
| **INV-PRO-WRITER** | Every folded op's `(peer, epoch)` equals its commit's writer. Only the reservation claim op names a holder on another peer, and only under PRO-19. |

6. **Should a receiving daemon re-derive a claim's label?** (09-security pass-1 follow-up.) 7. **Details of the rev 2.4 governor that glossary §27.2 leaves to this chapter** (added in rev 2.4). §27.2 fixes the numbers, the signal list, the 30-min fallback, the `health` event and the stricter-of rule; these points are chapter defaults that implementers follow unless the glossary later says otherwise:
   - *G and S for a budget other than 6 or 12:* `G_s = 60 / budget`, `S_s = 18 / budget` seconds, rounded up to whole milliseconds (§3.1, PRO-04); both §27.2 parameter sets satisfy it.
   - *Invalid `host.pushBudgetPerMin`:* an integer outside 6–24 is clamped to the nearest bound; any other value gives 12; doctor shows the seeded value. The key is not yet in the glossary §17 config block or `config.v1.json` (owner: 08-lifecycle / 09-security schema).
   - *Fetch statuses:* HTTP 429 and 5xx on a fetch are throttle signals too (§27.2 does not restrict the list to pushes), but a fetch signal posts the health event only while the peer has other pending work (INV-PRO-QUIET).
   - *Event code and spacing:* the `health{throttle}` event is `event{kind: health, reason_code: HOST_THROTTLED}` (§2.1, flagged for the glossary §19 registry; human template owned by 10-product), posted at most once per 15 min per peer and never by a peer that only follows.
   - *Restart:* governor mode is not persisted; the first fetch of a run counts a `HOST_THROTTLED` event in the last 180 first-parent heights (PRO-55).
   - *Mode and throttle level:* independent; fallback raises G_base and k still multiplies it (PRO-44).
