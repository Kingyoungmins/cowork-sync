### 1.1 v1 in scope

- Seats (one per Claude Code process), the seat states of glossary §3, subagent handling, refusal of worktree-isolated work while live.

- Daemon spawn through one routine whose in-session caller is the hook path (glossary §25 F4), environment allowlist, lease-based lifetime, newest-version-wins handshake, plugin-disable and key-loss detection.
- The hook side of human-only `/cowork` verbs: `!` preprocessing, UserPromptExpansion evidence forwarding (glossary §25 F5), native `pause`/`resume` in the loader.
- Short, share-all reads of user files with git run only on bytes in hand or on a staged copy, never on the working file, and no object written except for hold records (glossary §26 W1–W3, W6; §3.7.6).

## 3. Design

### 3.1 Where safety lives

cowork-sync has exactly two hard boundaries, both inside the daemon: the **publish gate B1** (INV-FENCE: no hunk inside a foreign claim earlier in board order is ever published from P, re-run after every CAS re-merge; REG-20 `gate()` against the claim view, owned by ENG-/HLD-/REG-) and the **verifying writer** (a working-tree path is written only if `DISK_EQ(p, expected blob)` holds, skipping the defer set; ENG-37/ENG-31). Every Claude Code hook is **advisory**: it gives early denies, attribution and feedback. A hook failure can only cause a pause, a hold or a lost note, never a publish. No hook ever pushes.

Why: VERIFIED run1 (Claude Code 2.1.270) — a missing executable (ENOENT), an uncaught throw (exit 1), a host hook timeout and an `mcp_tool` hook returning `isError` all let the Write through; 2.1.284 shows the model nothing for a non-blocking hook error. Managed policy (`disableAllHooks`, `allowManagedHooksOnly`) and `--bare` remove hooks entirely (gate-fails-open-on-every-hook-failure, fail-open-enforcement, mcp-gate-fails-open, policy-fail-open).

Within that frame, S3 makes the gate **fail closed**: whatever the loader can control (exceptions, bundle load errors, daemon unreachable, deadline) becomes exit 2. Only host-level failures it cannot control (node missing on PATH, a host hook timeout) fail open; they are detected and surfaced (§3.11) and B1 still holds.

Every claim-safety test asserts on the remote live code ref with `git cat-file`, never on whether the local Edit happened (TST-).

The `dist/` contents are exactly the canonical list of glossary §6.

`commands/cowork.md` frontmatter: `description`, `argument-hint: "<verb> [args]"`, `disable-model-invocation: true`. Its body is exactly one `!` line running `node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" $ARGUMENTS` (the verb is the first token of `$ARGUMENTS`) followed by one sentence telling the human the result is above. No `skills/` directory exists. No `package.json` with dependencies and no lockfile is shipped, so Claude Code never runs a dependency install. No document or command uses `npx`; humans and commands reach the CLI only as `node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" <verb>` (supply-chain-versions, auto-mode-classifier-blocks-cowork-commands).

**Build lints** (CI fails the build): any hook that is not `{"type":"command","command":"node",...}` exec form; any `mcp_tool`, `http`, `prompt` or `agent` hook; the string `permissionDecision` anywhere in `dist/` (no hook emits any permission decision); a command file without `disable-model-invocation: true`; `npx` or `git push` in `commands/`; `dist/hook.js` over 150 lines or requiring anything other than Node built-ins and `./core.js`; any code outside `dist/mcp.js` that reads `CLAUDE_CODE_MESSAGING_TOKEN` or opens the inbox socket (the host places the token in every hook's environment, glossary §26.2 item 6, so this lint, not the environment, is the boundary); any daemon spawn outside `spawnDaemon()` of §3.17.2, and any spawn call in `dist/mcp.js`; a `child_process` spawn of `git` outside the SEC- git runner.

**Install scope.** User scope only. `/cowork start` reads `enabledPlugins` across the settings layers and refuses with `REFUSE_PROJECT_SCOPE` when `cowork-sync` is enabled only in project or local settings (project settings live in `.claude/**`, which is quarantined, and would differ per PC).

**Floors.** Claude Code ≥ 2.1.270 (oldest build with VERIFIED behaviour; exec-form hooks need ≥ 2.1.139), Node ≥ 20, git ≥ 2.43 (glossary §18). The Claude Code version is read by the MCP server from `initialize` `clientInfo.version`. Hooks carry no version, so a seat without MCP (`NO_MCP`) is unversioned; doctor shows `CC_VERSION_UNKNOWN` as WARN for it.

### 3.4 The loader and the hook ↔ daemon protocol

#### 3.4.1 Loader algorithm (`dist/hook.js`)

1. **First statements:** install `process.on('uncaughtException')` and `process.on('unhandledRejection')`. For a gating event they write the loader's fixed G4 text with cause `hook error` to stderr and exit 2; for every other event they exit 0 with no output.
2. Read stdin fully and parse JSON. A parse failure is an internal failure (step 1 mapping).
3. **Resolve the target repo without spawning git.** For an edit-class PreToolUse, from `tool_input.file_path` (or `notebook_path`); a relative path is resolved against `cwd`. For every other event, from `cwd`. Normalize (**canonical root form**): `fs.realpathSync.native` (the on-disk case and long names, not the spelling given in `file_path`/`cwd`; for a path that does not exist yet, such as a Write of a new file, the nearest existing ancestor is resolved and the remaining components appended), lower-case drive letter, `\` → `/`, NFC. Walk up to the first `.git` entry:
   - `.git` is a **file** (linked worktree, nested `.claude/worktrees/**`, submodule): never live. If the common gitdir it points to is live, emit the `WT_NOTE` note (variant `WT_SUBMODULE` when the gitdir path lies under `modules/`) on SessionStart and edit-class PreToolUse only, exit 0. Otherwise exit 0 silently.
   - `.git` is a **directory**: the repo is *live* iff `<gitdir>/cowork/live` exists and names this worktree's realpath; it is *paused* iff `<gitdir>/cowork/paused` also exists. The marker comparison is between canonical root forms and, on Windows and macOS, is **case-insensitive** (the same rule as DAT-34 canonPath), so a `file_path` or `cwd` spelled in a different case never makes a live repo look non-live (which would be a silent fail-open: no gate, no record, no G4).
   - **One canonical form for every consumer** (glossary §24 default 12; 03-data and 09-security use the same form): the loader, core, the MCP server (§3.16.2 step 3) and the daemon derive the live-marker test, the gitdir and the SEC-21 endpoint input (`realpath(common gitdir)`) from this same canonical root form; for the endpoint input on Windows and macOS the string is additionally lower-cased (locale-independent), so two spellings of one clone always reach one endpoint and never bind a second daemon.
   - No `.git` found: exit 0 silently.
4. **UserPromptExpansion** (`cowork` or `cowork-sync:cowork`, every verb). MEASURED (glossary §25 F5, spike 02): it fires **before** the command's `!` line runs, with `prompt_id`, `command_name`, `command_args` and `command_source`. The verb is the first token of `command_args`.
   - **Markers:** if the verb is `pause`, create `<gitdir>/cowork/paused` (idempotent); if `resume`, remove it. This works even when `core.js` cannot load (LIF- pause/resume).
   - **Human evidence** (glossary §25 F5): if the verb is an acting verb (glossary §15), produce the evidence record `{seat_key, prompt_id, command_name, verb, args_sha256, mono_ns}`. This is glossary §25 F5's `{prompt_id, command_name, command_args, t}` with `command_args` carried as the SHA-256 of its SEC-25 normal form (so no argument text, such as a save summary, is ever sent or stored) and `t` as the loader's monotonic receive time. If the repo is live, not paused and the daemon answers within the loader deadline, the record rides the UserPromptExpansion IPC request sent by core (steps 8–9; the daemon may refuse to mint it for a wake-classified expansion, §3.12.2). Otherwise the loader appends it, HMAC-tagged with `ipc.key` when the key exists, as one JSON line to `<gitdir>/cowork/tmp/evidence.jsonl` (created user-only; glossary §6); this write uses Node built-ins only, so it works when `core.js` cannot load. SEC-25 decides acceptance: the `!`-run CLI accepts an acting verb only with matching evidence ≤ 60 s old and waits ≤ 3 s for it; untagged evidence is accepted only for `start` and `doctor` before `ipc.key` exists (glossary §6).
   - Never block the expansion: exit 0 with no output in every case. The `!` line of the command then runs the CLI, which informs the daemon.
5. **Not live:** exit 0, no IPC, no output — except the UserPromptExpansion marker handling and evidence line (step 4). The non-live fast path costs ≤ 80 ms p95 end to end on Windows, measured over ≥ 200 calls (glossary §26.2 item 4, which replaces the 45 ms of glossary §13).
6. **Paused:** no IPC. On SessionStart and UserPromptSubmit print exactly one line of additionalContext: "cowork-sync is paused for this repo by the user; edits are not coordinated." (glossary §13). All other events: exit 0 silently (plus the step 4 marker handling and evidence line).
7. **No evidence from UserPromptSubmit** *(changed in rev 2.3: evidence moved to UserPromptExpansion, step 4)*. UserPromptSubmit fires only after the `!` line has finished (glossary §25 F5), so it never produces human evidence, and no cowork process waits on a UserPromptSubmit for evidence: such a wait would deadlock the `!` CLI and is forbidden (glossary §25 F5). The prompt text is never sent or stored; UserPromptSubmit sends only the wake nonces it contains (§3.4.3).
8. `require('./core.js')` inside try/catch. On failure: gating event → stderr "cowork-sync hook failed to load (version X); edits paused for this repo. Human: type /cowork pause to continue without coordination, or /cowork doctor", exit 2; non-gating → exit 0.
9. Hand control to core (§3.4.2).

The loader embeds only three texts: the G4 text, the paused line and the load-failure line. They are Claude-facing, so they exist in `en` and `ko` only (glossary §19, §22), generated at build time from the COO- templates in `dist/i18n/claude.{en,ko}.json`. The loader takes the human language from `CLAUDE_PLUGIN_DATA/user.json` `language`, else the OS locale, else `en` (it cannot read the team config; glossary §17 loader precedence), and renders in `L_c` (`ko` if that language is `ko`, else `en`; glossary §17).

#### 3.4.2 Core algorithm (per hook process)

1. Read `<gitdir>/cowork/status.json` (no IPC). If its heartbeat is older than 3 loop periods or the file is missing, the daemon is treated as down: spawn it (§3.17.2) before connecting.
2. Connect to the daemon endpoint and complete the SEC- mutual HMAC handshake (endpoint naming and key handling: SEC-). On refusal, retry with 50 ms spacing until the loader deadline (§3.4.4).
3. Send exactly one request frame (§3.4.3).
4. Read frames until one complete `reply` line. An `extend` frame (SUSPECT only) raises this process's deadline (§3.6.3). Exit on the first complete `reply` line; never wait for the pipe `end` event (it costs ≈ +60 ms on Windows, VERIFIED e11).
5. Write the output for the event (§3.4.5), flush stdout and stderr, then send `printed{batch_id}` on the same connection and exit.
6. Deadline expiry or any connection failure: gating event → G4 (§3.6.4); non-gating → exit 0 with no output, except that the first non-gating hook of a seat after the daemon became unreachable prints the `DAEMON_DOWN` systemMessage once (tracked in `<gitdir>/cowork/tmp/seen-<first 8 hex of seat_key>`).

The loader never leaves a child attached to its stdio. The only child it may spawn is the daemon, detached with stdio `ignore` (an orphan holding a hook's stdout keeps that hook running for hours; issues #43123, #96945).

#### 3.4.3 Frames

Hook → daemon, one per hook process:

```
hook { event, seat_key, claude_pid, session_id, prompt_id?, agent_id?, agent_type?,
       permission_mode, repo_root, plugin_version, hook_proto, payload }
printed { batch_id }
```

`payload` by event:

| Event | Payload fields |
|---|---|
| SessionStart | `source`, `transcript_path` (daemon memory only), `messaging_present` (whether `CLAUDE_CODE_MESSAGING_SOCKET` is set; the token is never read, §3.16.4), `static_policy_hits[]` (§3.11.4) |
| UserPromptSubmit | `nonces[]` (every `cws-[0-9a-f]{16}` token found in the prompt; no other prompt text; never evidence, §3.4.1 step 7) |
| UserPromptExpansion | `command_name`, `verb`, `command_source`, `evidence?` (§3.4.1 step 4; `prompt_id` rides the frame header) |
| PreToolUse edit-class | `tool_name`, `tool_use_id`, `path` (repo-relative POSIX NFC), `tool_input` edit fields (`old_string`, `new_string`, `replace_all`, `content`, `edits[]`, NotebookEdit fields) |
| PreToolUse Bash/PowerShell/Monitor | `tool_name`, `tool_use_id`, `command`, `run_in_background` |
| PostToolUse | `tool_name`, `tool_use_id`, `path?`, `read{offset, limit, full, enoent, size}` for Read, `exit_status?` when `tool_response` exposes it |
| PostToolUseFailure, PermissionDenied | `tool_name`, `tool_use_id` |
| PostToolBatch | `tool_use_ids[]` |
| Stop, SubagentStop | `stop_hook_active`, `background_tasks_running` (count), `ids_in_last_message[]` (cowork ids matched in the last assistant message when the host provides it) |
| StopFailure, SessionEnd | `reason?` |
| SubagentStart | `agent_id`, `agent_type`, `cwd` |
| Notification | `type` |

Daemon → hook:

```
extend { deadline_ms }                                   // SUSPECT only, ≤ 7000, at most once
reply  { batch_id, decision, text, system?, events[], cursor }
```

`decision ∈ {deny, block, context, none}`; `text` is the Claude-facing text (stderr reason, block reason or additionalContext); `system` is the optional human systemMessage; `events[]` are the event ids carried by this output; `cursor` is the seat's pull cursor after this output. The frames are exactly the loader protocol of glossary §13 (`hook`, optional `extend`, `reply` with `system?`, `printed`).

MCP server ↔ daemon frames are the glossary §13 set; their fields here:

```
hello      { seat_id, seat_key, claude_pid, cc_version, plugin_version, hook_proto, messaging_present }
heartbeat  {}                                            // every 15 s
seat_end   {}                                            // on stdin EOF
ring       { event_ids, text, nonce }                    // daemon → MCP server
ring_result{ nonce, sent | refused | error }             // MCP server → daemon (glossary §25 F1)
```

Privacy of frames (INV-SECRET support): no frame carries the messaging token, prompt text, OS user names or transcript content. `tool_input` lives only in daemon memory and, for a denied edit, only as the post-image inside `<gitdir>/cowork/tmp/deny-<id>.bin` until it becomes a clean-path blob (§3.6.6).

#### 3.4.4 Deadlines

Measured from loader process start: **1.5 s** for every event except SessionStart (**3 s**); the SUSPECT `extend` frame may raise one gating request's deadline to at most **7.0 s** (≥ 3 s under the 10 s host timeout). On expiry, gating events take G4 and others exit 0.

*(added in rev 2.4, glossary §27.1)* The edit check never raises a hook deadline and no hook reply waits for it: at an edit checkpoint the PostToolUse (or PostToolUseFailure) reply waits only for the candidate capture, bounded at 150 ms (§2 local numbers), and the check runs after the reply (§3.8.4); `extend` stays SUSPECT-only. A PostToolUse whose candidate capture misses the bound replies on time and skips that edit checkpoint.

| Event | Allowed outputs |
|---|---|

| PostToolUse | exit 0 with empty stdout, `{"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":…}}`, or `{"decision":"block","reason":…}` (K2 only); optional `systemMessage`. |
| PostToolUseFailure | exit 0; optional additionalContext. |
| SessionStart, SubagentStart, UserPromptSubmit | exit 0; optional additionalContext; optional `systemMessage`. Never `decision:block`. |

| SubagentStop, StopFailure, SessionEnd, PostToolBatch, PermissionDenied, Notification, UserPromptExpansion | exit 0, no stdout. |

No output of any hook contains `permissionDecision`. Interactive sessions may also receive `terminalSequence` OSC 9 with the same text as a `systemMessage` (UX- notifications). The human-facing mirror of a G1 (exit 2 carries no JSON) rides the seat's next exit-0 output as a `systemMessage` (COO- mirror rule).

### 3.5 The PreToolUse gate (edit-class)

#### 3.5.1 Daemon-side constraints

The daemon answers gate requests **only from memory**: the claim and region cache, the board fold, held-region data from the hold registry, and trees parsed in the worker pool cached by blob oid (300 MB LRU, glossary §20). It never waits on git, the network or a parse. If the current file's tree is not parsed yet, REG-'s conservative fallback region is used and the PostToolUse diff remains authoritative. The single permitted wait is for the verifying writer's in-flight write group on the same path, ≤ 250 ms (glossary §20). Budgets (the one hook timing table of glossary §26.2 item 4, each measured over ≥ 200 calls): daemon handling ≤ 15 ms p95; live gating hook ≤ 100 ms p95 end to end on Windows (glossary §20 gate latency, §25 F6); the event loop is never blocked > 20 ms (measured with `monitorEventLoopDelay`; excess shown in status). Why: VERIFIED e12 — a main-thread parse of the 1.3 MB file blocks 337–368 ms; VERIFIED e11 — p50 30.8 / p95 42.8 ms end to end; MEASURED spike 02 (glossary §25 F6) — a near-no-op command hook costs 62–66 ms end to end on Windows, ≈ 40 ms of it process creation and ≈ 3 ms the script, so the earlier 60 ms bound was infeasible (hook-latency-event-loop-stall).

#### 3.5.2 Ordered evaluation (first match wins)

G2/G3 additionalContext carries at most one note (NOT_SHARED, the first OFFLINE notice of the episode, or the newest pull event about the target file) within the 800-char "other reasons" cap of glossary §19.

#### 3.5.3 Locating and predicting an edit

Claude Code's Edit matches after normalizing CRLF, BOM and curly quotes (VERIFIED sweep/edit), so raw matching misses (edit-normalization-breaks-symbol-mapping). The daemon locates on a **normalized view** of the current disk bytes: BOM stripped, CRLF → LF, U+2018/U+2019 → `'`, U+201C/U+201D → `"`; matches are mapped back to raw byte offsets and then to stored-form 1-based line rows (DAT- canon, REG- coordinates).

- `Edit`: every match when `replace_all` is true, else the first unique match.
- `MultiEdit`: the edits are applied in order on the normalized view; each edit's ranges are mapped back.
- `Write` to an existing path: the whole new content is diffed against the pre-image on the normalized view.
- `Write` to a new path: the whole file (REG- grammarless/new-file rule).
- `NotebookEdit`: whole file (glossary §22: notebook cell claims are v2; this replaces the cell-id mapping of research catalog item CCI-09 in `docs/research/consolidation/cat_claude.md`, which is not this chapter's rule CCI-09).

The located ranges go to REG- `predict(seat, toolName, toolInput, diskBytes, lastReadBlob?, A[p], claimView)` (04-regions §3.1, Algorithm PREDICT, REG-28; `lastReadBlob` = the seat's view blob); the prediction is used **only** for G1/G2 and to record TENTATIVE local claims; it is never published. If locating fails entirely the edit is **never** turned into a whole-file claim or a deny: the gate answers G2 and the PostToolUse diff decides (so every deny has a buildable post-image).

### 3.6 Outcomes in detail

#### 3.6.1 Never `allow`, never `ask`

The gate never emits a permission decision. `allow` would skip the user's permission prompt and turn `dontAsk` auto-denies into approvals (DOCUMENTED, gate-returns-allow-skips-prompts). `ask` existed only for the v1-cut override. No coordination outcome (grant, reservation, wake work set) is ever expressed as a permission decision; each only changes whether G1 fires.

#### 3.6.2 G3 (offline or auth expired)

The daemon answers from the claim cache of the last successful fetch exactly as in §3.5.2; new claims stay TENTATIVE until reconnect (U4 races decide later; B1 is the hard boundary). The `OFFLINE` engine-event text (param `offline_for_s`, local Δmono, so the text states how long this PC has been offline; glossary §25.2 item 4) goes to the seat once per offline episode (additionalContext + systemMessage), once more at 10 min offline, and as a line in every digest while offline. On reconnect, lost tentative claims are listed once (SEC-/COO- text) before any conflict classification (offline-auth-claims).

#### 3.6.3 SUSPECT refresh

When check #12 applies, the daemon sends `extend{deadline_ms: 7000}` within 100 ms, starts (or joins) a fetch, and waits **≤ 5 s** (glossary §20 holder self-guard) for a fetch that *completed after this request arrived* and its fold. If the fresh fold still shows the claim HELD by this seat, evaluation continues at #13 on the fresh fold; if the fetch did not complete in 5 s or the claim is no longer this seat's (released by `presume_absent`, STALE, superseded), the answer is G1 `SUSPECT_LOST` ("cannot confirm this session still holds {label}: offline for {dur}"). Only SUSPECT may extend, at most once per request (sleep-offline-stale-and-suspect-claims).

#### 3.6.4 G4 (daemon unreachable; S3)

The loader spawns the daemon detached (no waiting on network) and retries the connection until its deadline; then exits 2 with the glossary §11 text verbatim: "cowork-sync is not running on this PC, so edits in this live repo are paused. It restarts automatically; if not, the user can run /cowork doctor or /cowork pause." Internal exceptions map to the same text with cause `hook error`. `/cowork pause` (human) is the escape: the loader checks the `paused` file before any IPC, so the escape works with a broken bundle; the daemon publishes the paused state as a seat health event so teammates see "not coordinated" (glossary §8 PAUSED; COO-/UX- rendering).

G4 applies to `Bash|PowerShell|Monitor` as well (TXN attribution needs the daemon; S3 fails closed). `Agent|EnterWorktree` are decided locally by core without IPC (§3.10) and therefore never take G4.

#### 3.6.5 G1 reason caps

T1 (first deny per `cid` in a turn, worst case with ≤ 1 optional clause) ≤ 1,050; every other deny reason ≤ 800; T1R repeat form ≤ 300 (glossary §19). Reasons contain template text, ids, names, labels and paths only — never teammate free text (COO- data-not-instructions rule).

#### 3.6.6 Record first: the K1 deny-time record

Every G1 at check #13 creates the SHADOW hold record (HLD-47) **before** the hook replies (U5 auto-record; P1). The record is the request's carrier: the `request` op (`req_id` = the record's `hold_id`) is published only when the record's offer becomes `offered` (glossary §7); until then the holder sees the `hold` op as a notice (glossary §10 K1).

1. **Shadow key** = (seat_id, claim_id, path) (REG-30), where claim_id is the earliest (board order, then local order for sibling TENTATIVE claims) foreign claim intersected; every intersected claim_id is listed in the eventual request (cross-check fix 28 in `docs/research/consolidation/cross.json`: key and base follow REG-/HLD-).
2. **Shadow base** at the first deny on that key: the current disk bytes of the path (one short share-all read, §3.7.6). **Shadow post-image**: the shadow's previous post-image (or the base at the first deny) with this `tool_input` applied on the normalized view (§3.5.3), so chained denials compose.
3. Write `{meta, base bytes (first deny only), post-image bytes}` to `<gitdir>/cowork/tmp/deny-<id>.bin` on the worktree's volume and fsync (≤ 5 ms budget). Crashpoint `deny.prerecord` (11-testing §3.6, TST-06; placed here per glossary §25.2 item 10) is called after this fsync and before step 4.
4. Reply G1.
5. Asynchronously: produce both blobs through the pinned clean path from the bytes of the tmp file (`hash-object -w --stdin --path=<p>`, so attributes and filters apply through `--path` and git never opens the working file, glossary §26 W1; via the SEC- git runner with `attr.tree=<EPOCH_BASE>` and `filter.<d>.required=true` for every discovered driver), create or update the HLD-47 PATCH record (SHADOW, `residence: OFF_DISK`, `state: PARKED`, `offer=pending_leftover`, guard `claim:<claim_id>`, `blobs.h0[p]` = base blob, `blobs.h1[p]` = post-image blob, `origin=<seat_id>[/<agent_id>]`, `displaced_by: null`; glossary §9), then delete the tmp file. A required-filter failure makes the record `local_only` (INV-SECRET; a content-free stub on the board, glossary §7) and raises the DAT-/SEC- filter-failure notice.
6. The record is mirrored to the board (`hold` op + tree entries `held/<hold_id>/<stage>/<repo path>` for stages `h0`, `h1`; glossary §3) with the next governed push; no extra push is made for it. A shadow is only ever built for a `LIVE` path (non-`LIVE` targets stop at check #5), so it satisfies the glossary §9 rule that only LIVE paths enter a mirrored record. If the fold deterministically rejects its `hold` op, the record stays unmirrored with status `HOLD_MIRROR_REJECTED` and its bytes stay in the local registry (glossary §9); the seat that created the record (else this peer's next seat to send a hook) is told `HOLD_MIRROR_REJECTED` at its next hook (glossary §25.2 item 9). Hold mirrors are among the ops allowed while frozen; `INCIDENT` and a `proto` VERSION pause forbid every push (glossary §8). The `request` op and its delivery to the holder follow COO- (K1 flow).
7. Daemon restart (ENG-) converts every surviving `tmp/deny-*.bin` before anything else.

No record ever carries raw `tool_input`, `old_string`/`new_string`, prompt text, transcript paths or OS user names; the working-tree-form tmp file never leaves `<gitdir>` (board-plaintext-and-permanence, handoff-patch-rot-and-orphaned-returns).

**Repeats.** A further G1 on the same shadow key in the same turn updates the same record (step 2–5), produces no new event and uses T1R (≤ 300 chars) naming `{cid}` and `{rid}`; from the 3rd deny on that key in the turn T1R carries COO-'s escalation clause. Reaching the same function another way (Bash, Write, a renamed copy, a changed signature) is held by K2/K3/K7 and joins records per HLD- (deny-workarounds-by-agent, deny-then-bash-workaround).

### 3.7 Leases, transactions and the defer set

One lease table replaces fences, INFLIGHT/READ_FOR_WRITE leases and Read leases (P3). All times are on the daemon's monotonic clock.

#### 3.7.1 INFLIGHT

- **Acquire:** at edit-class PreToolUse, only after G2/G3 (a denied call takes no lease), keyed by `tool_use_id`, refcounted per path. The pre-image bytes are captured in daemon memory by one short share-all read (§3.7.6; 64 MB total cap; beyond it the bytes are spilled to a file under `<gitdir>/cowork/tmp/stage/` that is deleted at release — no object is written, because a snapshot tick writes none and its blob id has no object behind it, glossary §26 W6).
- **Release:** PostToolUse or PostToolUseFailure with that id; PermissionDenied with that id; PostToolBatch for every listed id; the seat's UserPromptSubmit that opens a new turn (a mid-turn UserPromptSubmit carrying a wake nonce releases nothing, §3.12.2, glossary §25 F2), Stop, StopFailure, SessionEnd or seat end (all of the seat's leases); SubagentStop (leases whose PreToolUse carried that `agent_id`); backstop **120 s**.
- **Not released** by the seat's next PreToolUse: parallel siblings in one batch would release each other.
- On release without a PostToolUse (denied by another hook, permission "No", Esc, plan mode, cancellation), the lease's TENTATIVE claims are discarded (fence-and-claim-leak-without-post-event).

Why 120 s and not 20 s: PreToolUse runs before the permission prompt (DOCUMENTED) and the host's Write staleness check runs before hooks (VERIFIED), so a lease must survive a human reading the prompt (write-staleness-check-precedes-hooks, fence-vs-inflight-apply-and-stuck-fence).

#### 3.7.2 READ

- **Acquire:** at PostToolUse(Read) of a **full** read by the seat (no `offset`/`limit`, not truncated).
- **Release:** the seat's next edit-class PostToolUse on the path, or 120 s; renewed on the seat's hook activity at most 3 times; hard cap 300 s from first acquisition.
- **Ranged reads** create no lease; they are recorded with their ranges for attribution notes (§3.13) and the MOVED view blob.

Why: VERIFIED — Write refuses "modified since read" and fires no PreToolUse and no PostToolUseFailure, so with peer churn the refusal repeats and each retry regenerates the whole file. The lease keeps applies off a file the seat is about to rewrite (e-formatter-and-write-livelock). MEASURED (glossary §25 F7): an Edit whose `old_string` still matches applies cleanly after an external change elsewhere in the file, with the host note "the file had been modified on disk since you last read it", which confirms this fence design for Edit; Write after an external change is not measured (§8 question 12).

#### 3.7.3 TXN (Bash, PowerShell, Monitor)

- **Open:** PreToolUse(`Bash|PowerShell|Monitor`) of a seat that passed the advisory checks (§3.9) opens `TXN(seat_id, tool_use_id)` on the target worktree.
- **Effect:** while any TXN is open on a worktree the daemon takes **no snapshot and no apply** there; fetch and in-memory merge continue (bash-transactions-split-both-ways).
- **Pre-image:** `S_open` = the newest snapshot completed before the reply. Files already reported dirty against `S_open` (by fsmonitor when in use, else a stat of the private index's entries bounded at 20 ms) keep their pre-window attribution; when the bound is exceeded the window is marked *approximate* and gap writes are attributed to the seat (safe: B1 and HLD- act on content, not attribution).
- **Close:** PostToolUse or PostToolUseFailure with the same id; PermissionDenied; for `run_in_background` and `Monitor`, when the tool call returns; the seat's UserPromptSubmit that opens a new turn (not a mid-turn nonce-carrying one, §3.12.2), Stop, StopFailure, SessionEnd or seat end; cap **120 s**.
- At close the daemon snapshots the worktree (01-engine snapshot, staged-copy reads, glossary §26 W1); changes first seen inside the window are attributed to the seat with `cs_id` of its open CS and `tool_use_id` (§3.8.3).
- *(added in rev 2.4, glossary §27.1)* The close of a **Bash or PowerShell** TXN by its own call (PostToolUse, PostToolUseFailure, the return of a `run_in_background` call, or the 120 s cap) is an **edit checkpoint** when the close attributed at least one change to the seat's open CS: the candidate capture is taken from that close snapshot before the reply (or, for a close with no hook to reply to, at the close itself) and checked after it (§3.8.4). A `Monitor` TXN close, a PermissionDenied close and a close by a turn-boundary event (UserPromptSubmit, Stop, StopFailure, SessionEnd, seat end) are not edit checkpoints: glossary §27.1 names Bash/PowerShell only, a denied call wrote nothing, and a turn boundary is itself a closing trigger (§3.12.1).

#### 3.7.4 Expiry guard

If an INFLIGHT lease expires before its Post event and the verifying writer wrote that path after the lease was acquired, the hunks of that `tool_use_id` on that path lose the "observed edit" exemption and are taint-checked as UNOBSERVED by the HLD- revert detector. This closes the case of a Write approved after a long prompt overwriting an apply and publishing an unflagged revert. Expired leases are listed in `/cowork status`; more than 5 per seat-hour flags doctor.

#### 3.7.5 Defer set interface (to ENG-)

`deferredPaths(worktree)` returns:

- every path with an INFLIGHT or READ lease;
- every path, while any TXN is open on the worktree (the applier and snapshotter skip the worktree entirely);
- for each DEGRADED seat, its read set and edit set of the last 30 min;
- **apply coalescing** (glossary §20): a path fully read by a MID_TURN seat (hook traffic in the last 60 s) is applied at most once per 2 min, coalesced; for a seat in `PULL_MODE`, only at its Stop or UserPromptSubmit.

Each returned path enters ENG-'s defer set D with its reason (`fence`, `read lease`, `TXN`; ENG-31). Deferred incoming changes stay pending (`pathState(p) = pending(reason)`, INCOMING per ENG-) and later 3-way merge with whatever Claude wrote (ENG-). Publishing is never delayed by the defer set. INV-GROUP is kept by ENG-: a deferral of one path defers its whole write group (the applicable paths of its publication group; glossary §3, §21).

#### 3.7.6 Reading user files (staged copy)

Every read this chapter's code makes of a user's working file — INFLIGHT and TXN pre-images (§3.7.1, §3.7.3), edit-class post-images (§3.8.1), the deny shadow base (§3.6.6) and the post-images of K2 and `wake-scope` records (§3.8.2, §3.8.2a) — follows glossary §26 W1 and W3:

1. **One short read:** open with full sharing, read the whole file in one call, close. No handle on a user file is held longer than that one call. MEASURED (glossary §26 W3, spike 04): an editor's atomic replace (`MoveFileEx` REPLACE) fails with `EPERM` while **any** handle is open on the target, even a share-all read handle.
2. **Stability check:** `lstat` size and mtime before and after the read; if they differ, re-read once; if they still differ, the read is *unstable* (handling below).
3. **No git on the working file:** git never opens the user's file. When bytes must become an object they are hashed from the bytes in hand with `hash-object -w --stdin --path=<p>`, or from the staged copy `<gitdir>/cowork/tmp/stage/<path>`, so attributes and filters still apply through `--path` (SEC- git runner, `attr.tree=<EPOCH_BASE>`, `filter.<d>.required=true`). MEASURED (glossary §26 W1): `git add` on the working file memory-maps it while hashing, and concurrent in-place editor saves then failed 11.4 per 1,000 (Win32 1224, `ERROR_USER_MAPPED_FILE`); with staged copies, 0 of 963 in-place saves failed. This is one code path on every OS.
4. **Objects only for records:** in this chapter objects are written only for hold records (deny shadows, K2 and `wake-scope` PINs). Comparisons, change detection, claim confirmation, edit-checkpoint candidate captures and the edit check use `hash-object` without `-w`, in-memory bytes or staged copies (a candidate that fails its check leaves no object; one that passes is written by HLD-40 as a ready-pair capture, glossary §26 W6, §27.1; §3.8.4); a hook request to the engine for named paths (PostToolUse claim confirmation, REG mapping) is answered with ids and in-memory bytes (the `diskSnapshotId` of 04-regions), never by an object write; ready-pair captures, publishes and applies are ENG-/HLD-'s (glossary §26.1 W6: snapshot ticks never write objects; objects only for ready-pair captures, publishes, applies and hold records).

**Unstable reads.** A pre-image or deny base that stays unstable is taken from the second read, and the lease or TXN window is marked *approximate* like a TXN over its stat bound (§3.7.3): attribution may then include a concurrent human write, which is safe because B1 and HLD- act on content, not attribution. A record post-image that stays unstable is recorded from the second read and refreshed from the next stable read; the record's whole-CS PIN already holds, so no unstable bytes are ever published. **Empty or shrunk post-images** (glossary §26 W2: a staged read once captured a 0-byte file in the instant after an in-place editor truncated it): an edit-class post-image that is 0 bytes or more than 50 % smaller than its pre-image is used only after a second stable read at least 300 ms later (glossary §20 snapshot quiet period and shrink guard); until then its hunks confirm no claim and raise no K2 or `wake-scope` hit, and the result rides the seat's next hook (§3.8.1).

### 3.8 PostToolUse handling

#### 3.8.1 Confirmation (authoritative changed-region set)

For an edit-class PostToolUse, the worker diffs the captured pre-image against the post-image (current disk, read per §3.7.6, including its empty-or-shrunk rule) on the normalized view and drops EOL-only and BOM-only hunks (VERIFIED: Edit rewrites untouched lines' EOL; edit-eol-normalization-false-causer). REG- `confirm(seat, cs_id, p, preBlob, postBlob, A[p], claimView)` (REG-29) turns the remaining hunks into the authoritative region set; only those regions get the TENTATIVE claim sub-flag `confirmed` (glossary §3) and become eligible for publication, after which they are HELD (PRO- claim lifecycle; REG- `computeClaims` emits the claim ops). Every hunk is tagged with the seat's open `cs_id` and the `tool_use_id`. TENTATIVE claims never confirmed are discarded when the INFLIGHT lease is released. Confirmation answers within 250 ms p95; a later result rides the seat's next hook.

#### 3.8.2 K2: post-hoc foreign-claim hit

At edit-class PostToolUse and at TXN close, the daemon evaluates the authoritative hunks against the claims **as folded when the Pre (or TXN open) was answered** (the fold height is recorded with the lease or TXN). A hunk inside a foreign HELD non-STALE claim of that fold is **K2 claim_posthoc** (glossary §10); a claim that arrived between Pre and Post is not K2 (it becomes K3 at publish through B1, which gates P against the current claim view).

On K2:

1. **Record first:** the post-image of every touched path of the CS **whose scope class is `LIVE`** (read per §3.7.6) is stored as a clean-path blob into the HLD- PIN record (same pinned clean path as §3.6.6 step 5; `local_only` on filter failure). Only LIVE paths enter the record and its board mirror (glossary §9, which covers every record created from a CS: K2, K3, K6, K7, B1 PIN, `wake-scope`). A CS can contain non-`LIVE` paths (a NOT_SHARED edit at check #5 takes an INFLIGHT lease and is attributed to the open CS, §3.8.3); they stay on the author's disk under their path-class mask, are carried as `A[p]` in P (INV-MASK) and never reach `held/<hold_id>/…` (S8, INV-SECRET; e.g. a `.envrc` edited in the same turn). The K2 hunk itself is always on a `LIVE` path, because non-`LIVE` paths carry no claims (check #5), so the record is never empty.
2. **Hold the whole CS:** HLD- makes the CS's `LIVE` paths one PIN record; its publication group is no longer ready-and-unheld, so P carries `A[p]` on every path it touched (glossary §3 P, INV-MASK); the author's disk keeps every byte.
3. **No disk write:** PostToolUse handling and TXN close never write the author's working tree (glossary §22: K2 disk restore is v2; per-hunk subtraction is forbidden by glossary §9).
4. **Tell the seat:** PostToolUse returns `{"decision":"block","reason":…}` with COO-'s K2 text ("kept on this PC, not shared", ≤ 1,000 chars — the glossary §19 PostToolUse coordination-event row, which a PostToolUse `block` reason uses — naming `{rid}`, `{cs}` and the options). For a TXN closed by its cap or by a background return, the same text rides the seat's next hook.
5. Repeat hits on the same (seat, claim_id) join the same record and produce no new request or notice.

Why: per-hunk restore is the operator VERIFIED to duplicate or delete functions (intra-file-withdrawal-mangles-file), and a restore under the agent invites workarounds (posttooluse-restore-induces-workarounds, bash-powershell-bypass-after-deny).

#### 3.8.2a Wake-scope backstop (S5)

The gate check #3 and the shell deny of §3.9 are advisory; this is the hard bound of glossary S5 ("writes outside the wake work set, including by shell commands, are never published"). At every edit-class PostToolUse, every `cowork_resolve` restore write and every TXN close in a **wake-originated** turn (§3.12.2), the daemon checks the authoritative hunks (§3.8.1; for a TXN, every change first seen inside the window, §3.8.3) against the seat's wake work set (07-coordination §2 membership). Part (a), the paths of requests this seat accepted, is evaluated at that Post or TXN close (so an `accept` filed in the same tool batch counts). Part (b), regions contained in this seat's own claims, uses the own-claim set as it stood when the Pre or TXN open was answered: it is decided by REG- `confirm.notOwnContained` (REG-33, 04-regions §3.6 containment form), and a claim first confirmed during the current wake turn never widens it, so a write this backstop PINned cannot make its own unit "own" for the next edit. With `wake.turnEdits = deny` the wake work set is empty.

If any hunk on a `LIVE` path lies outside the wake work set:

1. **Record first**, exactly as K2 step 1 (§3.8.2): the CS's `LIVE` post-images go into a PIN record through the pinned clean path (`local_only` on filter failure; only LIVE paths, glossary §9).
2. **Hold the whole CS:** HLD-66 (05-holds) makes it one PIN with guard `wake-scope` (glossary §9: DECISION, owner the local human; record `origin = wake`), so nothing of the CS publishes until the local human decides; the record is never offered while the guard holds (05-holds owns the record and its resolution verbs).
3. **No disk write** (INV-CCI-NO-REWRITE); the author's disk keeps every byte.
4. **Tell the seat** at the same carrier as K2 step 4 with `OWN_CHANGE_HELD` (reason `wake-scope`); the local human sees the record in `T-WAKE_RECAP` at their next prompt (glossary S5; COO-25) and in status.
5. Writes to non-`LIVE` paths (for example ignored build output of a test run) never trigger this PIN and never enter the record: they are never published live anyway and stay under their path-class mask (glossary §3 scope classes, §9, §16).

A K2 hit in the same CS joins the same PIN (HLD- joins records); the K2 block reason (§3.8.2 step 4) takes precedence on the carrier. Changes inside the wake work set publish normally with `origin=wake` (§3.12.3).

#### 3.8.3 Attribution rules (one rule set)

| Write observed | Attributed to |
|---|---|
| Inside an INFLIGHT lease's tool call (pre/post diff) | the seat, `tool_use_id`, its open CS |
| First seen inside an open TXN window | the seat (all seats whose windows overlap; the stricter result applies to claims and conflicts) |
| Same path within 3 s after the seat's edit-class PostToolUse (formatter hooks, format-on-save) | the seat's CS (formatter grace, glossary §20) |
| After a TXN's cap, from a background process after its tool returned, or with no open window | **human-class** (the local `human` pseudo-seat; HLD- human CS) |

Every write in a Bash/PowerShell/Monitor window is also taint-checked as UNOBSERVED by the HLD- revert detector. `bashEditDiff` is never an input (DOCUMENTED beta, best effort). Attribution is published only via `Cowork-Seat`/`Cowork-CS` trailers (glossary §5); it never decides safety (formatter-whole-file-rewrites).

#### 3.8.4 Edit checkpoints *(added in rev 2.4, glossary §27.1)*

Glossary §27.1 (S1 rev 2.4) publishes a Claude CS at every **edit checkpoint** whose **edit check** passes, besides turn end, a green checkpoint and `cowork_checkpoint` (all three unchanged, §3.12.1). Ownership: this chapter owns the trigger, the candidate capture, the hook flow and the deadlines; the four checks are the 04-regions edit-check entry point (reusing `regionTripwire` and `interfaceCheck`, the K7/T0 machinery of HLD-50); turning a passing candidate into the CS's ready pair and its readiness are 05-holds' (HLD-39, HLD-40); the push is the governor's (02-protocol, glossary §27.2).

**Triggers.** An edit checkpoint is either
- (a) an edit-class **PostToolUse** (never PostToolUseFailure: nothing was written) whose `tool_use_id` matched a gate request holding an INFLIGHT lease, when the post-image differs from the pre-image in at least one hunk that is not EOL-only or BOM-only (§3.8.1); an unmatched Post (the DEGRADED trigger of §3.11.5) has no pre-image and is not a checkpoint; or
- (b) a **Bash or PowerShell TXN close** that attributed at least one change to the seat's open CS (§3.7.3; `Monitor`, PermissionDenied and turn-boundary closes are not checkpoints).

Formatter-grace writes (§3.8.3) join the CS and are covered by the next checkpoint or closing trigger; they are not checkpoints themselves. Calls carrying an `agent_id` checkpoint the CS they belong to (HLD-34). Edit checkpoints run in wake-originated turns as well (after the `wake-scope` backstop, step 3 below), in every permission mode, under DEGRADED and under `PULL_MODE` (they inject no text); in a paused repo no hook reaches the daemon, so none run.

**Skipped** (no candidate kept, no check, no record, no event, no message) when:
1. the CS is held as a whole by a PIN — K2 (§3.8.2), `wake-scope` (§3.8.2a) or any HLD- PIN the CS has joined, including one created at this same hook: the PIN decides its publication;
2. the CS has a SHADOW record (a K1 deny in this CS, §3.6.6): it publishes only at its close, where HLD-48 decides, because the edit check does not cover HLD-48's first condition (the SHADOW's H1 referencing a name the CS adds or changes);
3. the post-image falls under the empty-or-shrunk rule of §3.7.6 (check 4 would fail anyway) *(rev 2.5, F14; D1: recorded as `last_check{kind: skipped, skip: shrink}`)*;
4. the candidate capture misses its 150 ms bound or a read stays unstable (§3.7.6): the candidate is **dropped, never taken late**, because a capture at a later hook would not be the content "at that edit"; the next checkpoint or the closing trigger covers the edit *(rev 2.5, F14; D1: recorded as `last_check{kind: skipped, skip: slow_read}`)*;
5. `A[p]` changes on a candidate path (an apply, HLD-41) between the capture and the end of its check: the candidate is stale and dropped *(rev 2.5, F14; D1: recorded as `last_check{kind: skipped, skip: base_moved}`)*;
6. at the hook, another INFLIGHT lease of this seat (a sibling call of the same batch) or any TXN other than the one closing is open on the worktree: the CS may be half-written (a codemod that has touched 12 of 30 files can pass all four checks), and §3.7.3 allows no snapshot while a TXN is open, so the checkpoint is skipped and the last Post or close of the batch takes it (bash-transactions-split-both-ways) *(rev 2.5, F14; D1: recorded as `last_check{kind: skipped, skip: batch}`)*.

**Flow at one hook.**
1. **Before the reply — candidate capture** (≤ 150 ms, the same bound as capture-at-trigger): `A_cap` = the current `A` of the CS's paths; `R[p]` for the edited path = the post-image bytes already read for confirmation (§3.7.6, one short share-all read); for each other path of the CS, a stat against the CS's newest candidate or ready pair, reusing unchanged entries and taking one staged-copy read (glossary §26 W1) of each stat-dirty path; for a TXN close, the close snapshot of §3.7.3. The candidate gets the next `cand_seq` of its CS. One per-CS counter numbers every capture of the CS (edit candidates, green and tool checkpoints, closing captures), so the order between an edit-checkpoint capture and any other capture is total. No object is written (§3.7.6 item 4).
2. **Reply** with whatever the hook carries anyway (confirmation, K2 block, notes). The reply never waits for the edit check (§3.4.4). A TXN closed by its cap or a background return has no hook to reply to; its candidate is taken at the close.
3. **After the reply, in the worker pool, ordered per CS:** confirmation (§3.8.1), then K2 (§3.8.2) and the `wake-scope` backstop (§3.8.2a), record first as before; then, if no skip condition holds, the candidate enters the CS's edit-check queue: at most one check runs and one waits per CS, and a newer candidate replaces the waiting one (CPU bound; allowed by glossary §27.1, since a failed or unchecked candidate leaves the CS on its last passing capture). Edit checks run at lower priority than gate parses and confirmations, so neither the gate budget (§3.5.1) nor the confirmation bound (§2) moves.
4. **Edit check** (04-regions entry point, ≤ 0.5 s on a 1.3 MB file, glossary §27.1) on the merge of `A`, the candidate's R and TIP of the newest fold at check start, restricted to the CS's paths, computed without writing objects (the entry point's form): (1) no new ERROR/MISSING parse nodes relative to TIP in any touched file; (2) no breaking interface change whose callers in the merged tree are not updated in the same CS; (3) no reference to a name the merged tree does not define; (4) no label count above max(TIP, local) and no > 50 % shrink of a touched file. Files without a grammar pass (1)–(3) trivially; (4) still applies.
5. **Pass** → the candidate is handed to HLD-40 as the capture of signal `checkpoint{source: edit, cand_seq}` (§3.12.1): HLD-40 writes R to the object store and records the ready pair (trailer `state=checkpoint`, HLD-37), replacing the CS's ready pair only when `cand_seq` is newer than the one it holds (newest passing capture wins). Edits after the capture stay in the open CS (HLD-40). A newer failing edit never blocks the publication of an older passing capture (glossary §27.1).
6. **Fail, or an `incomplete` result** (over budget, mirroring HLD-50: never a pass) → the candidate and its staged copies are discarded; the CS keeps its last passing capture, if any. A failing edit check is not an error: no record, no event, no pushed message to Claude or the human (07-coordination: no message on a failing edit check). At turn end the normal path applies (a CS that still fails T0 becomes a K7 PIN, HLD-50; glossary §27.1). *(rev 2.5, F14 + F12; D1)* The first failed check (or the `incomplete` result) is kept in `last_check` (10-product §3.5.1; written for this CS by 05-holds HLD-67 step 4); nothing else is kept. `last_check` lives only in daemon memory, is cleared when the CS closes or a passing capture with a higher `edit_n` lands, is never persisted, logged, published or delivered to any carrier of §3.14.1, and is rendered only in the output of a `/cowork status --flow` or `/cowork wrap` run: the daemon puts it into every all-paths `flow` reply and every `wrap` reply, never a path-scoped `flow` reply (10-product §3.5.1, §3.20.4), so it is shown in full in a terminal and as a slash command, whose output the seat's Claude reads, which is intended (glossary §29.1 D1, final 2026-10-08). Claude learns it only by reading output that was asked for — a human-run slash verb, or a CLI call it makes itself from Bash — never from a push.

The edit check is not a safety boundary: B1 and T0 still run on every OUT at publish (HLD-45, HLD-50), so a capture checked against an older TIP is re-checked on the tip the push leases. Expected Claude-edit latency ≈ edit check (≤ 0.5 s) + governor window (G = 5 s; worst normal wait for 4 peers 9.5 s; G = 10 s for 30 min after a throttle signal) + receiver fetch/apply ≈ 10–30 s (glossary §27.1 model, §27.2; soak gate publish p95 ≤ 40 s). This chapter adds no push: every passing capture waits for the governor's next window, which coalesces all ready groups into one push (HLD-44).

### 3.9 Advisory shell gate (Bash, PowerShell, Monitor)

While live and not paused, core tokenizes the command (split on `;`, `&&`, `||`, `|`, newlines; strip leading `cd <dir> &&` and environment-variable prefixes; honour `git -C <dir>`; PowerShell aliases normalized) and the daemon answers G1 (exit 2) with a fixed reason pointing to the right tool or verb when the command contains:

| Class | Matches | Code |
|---|---|---|
| (a) git verbs that move HEAD, the index or the worktree | `stash` (except `list`/`show`), `checkout` (with a ref or a pathspec), `restore`, `switch`, `reset`, `pull`, `merge`, `rebase`, `cherry-pick`, `revert`, `am`, `apply` without `--check`, `bisect`, `commit`, `clean`, `worktree add`, `update-ref` or `push` naming `refs/cowork` | `SHELL_GIT` |
| (b) repo-wide formatters/fixers without explicit file arguments | `black .`, `ruff --fix .`/`ruff format .`, `prettier --write .`, `eslint --fix .`, `dotnet format`, `gofmt -w <dir>`, `clang-format -i` on globs | `SHELL_FORMATTER` |
| (c) in-place writers whose literal target holds a foreign HELD claim | `sed -i`, `perl -pi`, `Set-Content`, `Out-File`, `>`/`>>` redirection, `python -c` with `open(...,'w')`, `tee` | `SHELL_INPLACE` |
| (d) the cowork CLI's acting verbs, or files under `<gitdir>/cowork/` or `ipc.key` | any command naming `dist/cli.js` or `cowork` with `start`, `stop`, `pause`, `resume`, `save`, `done`, `resolve`, `review`, `release`, `recover`, `uninstall`, `revert` *(rev 2.5, F10)* (glossary §15 acting verbs); any command whose tokens name a path under `<gitdir>/cowork/` (in any spelling: relative `.git/cowork/…`, the absolute gitdir, either slash, any case on Windows/macOS) together with a remover, mover, creator or writer (`rm`, `del`, `erase`, `rmdir`, `rd`, `Remove-Item`, `mv`, `move`, `Move-Item`, `Rename-Item`, `cp`/`copy`/`Copy-Item` onto it, `touch`, `New-Item`, `ni`, `Set-Content`, `Add-Content`, `Out-File`, `Clear-Content`, `>`/`>>` redirection, `tee`, `truncate`, `sed -i`); and any command naming `ipc.key` at all (reads included: the key authenticates IPC) | `SHELL_COWORK_CLI` |

Otherwise the TXN opens and the call passes (exit 0). This list is **advisory**: obfuscated commands pass (for the `live` marker the daemon backstop of §3.17.4 restores it); the backstops are B1, the ENG-/LIF- epoch guard for HEAD/index moves, the HLD- revert detector and mass-change breaker, and in a wake-originated turn the `wake-scope` PIN (§3.8.2a) (bash-git-verbs-revert-and-markers, worktree-reset-commands-broadcast-revert, e-formatter-and-write-livelock). Read-only CLI verbs (`status`, `queue`, `show`, `doctor`, `log`, and *(rev 2.5)* `since` (F04) and `wrap` (F12); class (d) is unchanged for them, since neither is an acting verb) are not denied; Claude is pointed to the MCP tools instead by the RULES text. *(rev 2.5, F04; merge round 2)* A read-only verb run through Claude's Bash runs under a claude ancestor (and with `CLAUDECODE` set), so it is never a route-(a) request (glossary §29.2, 09-security §3.11), even when the host or a wrapper (`script`, winpty, ConPTY) gives it a PTY; its `since_ran` therefore never moves `run_h` (10-product §3.9a, FEAT-F04-18). Whether the host's Bash tool allocates a PTY is not measured, and the rule does not depend on it. *(rev 2.5, F14, F12; D1, final 2026-10-08)* Its all-paths `flow` replies and its `wrap` replies, like a human's, carry `last_check` (a path-scoped `show <path>` reply never does): a `status --flow` or `wrap` that Claude runs itself shows it the latest edit-check result, which is a pull Claude made, not a push (10-product §3.5.1, §3.20.4; INV-CCI-EDITCHECK). *(Wording: merge round 3.)* `!` lines of `/cowork` command files carry no `tool_use_id` and are not model tool calls; class (d) applies only to model tool calls.

In a wake-originated turn every file-writing command (class (b), and every class (c) writer or redirection whatever its target) is denied with `WAKE_TURN` in both `wake.turnEdits` modes, because a shell command's targets cannot be bounded to the wake work set (COO-25; §3.12.3); read-only and check commands run. A writing command the parser does not classify (a generator script, a snapshot-updating test run) is caught at TXN close by the `wake-scope` backstop (§3.8.2a): nothing outside the wake work set is published.

### 3.10 Subagents and worktrees

**Claims belong to the seat.** Subagents of one seat never conflict with each other through cowork (that is Claude Code's own concurrency). `agent_id` is used only for:

1. the SubagentStop sweep of INFLIGHT leases and TXNs whose PreToolUse carried that `agent_id`;
2. the per-agent list of denied, held and recorded changes in the parent's Stop block (subagent denials are hidden from the parent; false-completion-reports);
3. SubagentStart injecting RULES + the seat digest (≤ 2,500 chars, conflict lines first), because subagents start with fresh context;
4. `origin=<seat_id>/<agent_id>` on records (glossary §9);
5. deferring the Stop ask while `background_tasks` are running (§3.15).

Agent-team teammates are separate Claude Code processes and therefore separate seats. Records never depend on SubagentStop or Stop firing (§3.6.6).

**Worktrees.** While the repo is live, core answers PreToolUse(`EnterWorktree`) and PreToolUse(`Agent`) whose `tool_input.isolation` is `worktree` — or whose `subagent_type` names an agent definition with `isolation: worktree` in its frontmatter, looked up in `~/.claude/agents/`, `<repo>/.claude/agents/` and enabled plugins' `agents/` — with exit 2 `WORKTREE_DENY` ("worktree sessions are not coordinated by cowork-sync in v1"). This is decided locally from the marker and the definitions, without IPC. SubagentStart with a worktree `cwd` and SessionStart of a `claude -w` session get the `WT_NOTE` note through the loader's `.git`-file branch. The snapshot never includes `.claude/worktrees/**` or any directory holding `.git` (DAT-/ENG-) (worktree-isolation-gitlink-and-unmapped-edits, clones-worktrees-identity).

### 3.11 Seats

#### 3.11.1 Identity

A **seat** is one Claude Code process (glossary §2). Hooks and the MCP server compute `seat_key` independently (§2). `seat_id` is the random 128-bit id minted by the MCP server at process start and sent in `hello`; when no MCP server registers within the pairing window, the daemon mints one (seat wiring `NO_MCP`). The first `seat_id` bound to a `seat_key` is kept for the life of that claude process; a later MCP `hello` with a different id is stored as an alias and never re-keys claims. Claims, leases, TXNs, read sets, budgets, cursors and request queues are keyed by `seat_id`; `session_id`, `prompt_id` and `transcript_path` are attributes only (seat-identity-vs-session-id).

`seat_key` is computed per glossary §2 (`SHA-256(CLAUDE_CODE_MESSAGING_SOCKET)`, else the claude pid, i.e. `process.ppid` of an exec-form hook and of the MCP server, VERIFIED equal); the socket name is hashed and hooks never read the token.

`/clear`, `/compact`, in-process `/resume` and in-process `/fork`/`/branch` keep the seat: claims stay, leases of the previous `session_id` are swept by its SessionEnd, and SessionStart re-injects the digest with the "supersedes" line (§3.14.2) (clear-compact-resume-orphan-claims, compaction-clear-fork-lose-cowork-state). Several sessions of one person are several seats under one daemon; their conflicts follow the same rules and texts say "your other session ({label})" with `label` = "session N" numbered per daemon. A session touching a second live repo registers lazily with that repo's daemon through its hooks (wiring there: `NO_MCP`, because its MCP server serves the session's project repo).

#### 3.11.2 Registration and pairing

The first hook or `hello` for a `seat_key` creates the seat record. The daemon waits up to 3 s (glossary §20 MCP pairing) for the other side; SessionStart's 3 s loader deadline covers this. The seat's `seat_start` op (glossary §7: `seat_id, permission_mode`) is published with the next governed push that the current FREEZE reasons and publish pauses allow (glossary §8; it is not in the allowed-while-frozen set, so it waits in the outbox); its wiring and flags are published as a `health` event (codes only).

#### 3.11.2a Seat activity and `request_status` classification

Seat activity (glossary §3) is computed from hooks only: `MID_TURN` = hook traffic since the last UserPromptSubmit or wake start and no Stop yet, or a Stop with `background_tasks_running` > 0; `AWAITING_PERMISSION` = Notification `permission_prompt` with no hook since; `IDLE` = Stop/StopFailure seen or Notification `idle_prompt`; `ENDED` = seat end (§3.11.3). The holder daemon's `request_status` for a request addressed to the seat (PRO-33; glossary §7) follows it: `MID_TURN` → `queued_until_turn_end`; `AWAITING_PERMISSION` → `awaiting_human`; `IDLE` and asked now (the doorbell's delivery confirmed by a UserPromptSubmit carrying its nonce, glossary §25 F1, F2, or the ask rode a carrier) → `asked`; `IDLE` and not wakeable (wiring `HOOK_ONLY`/`NO_MCP`, flag `PULL_MODE`, `wake.enabled = false`, or the wake caps of glossary §20 exhausted) → `undeliverable`. A later change of the classification publishes one more `request_status` (PRO-33). `request_status` is an answer-class op and is allowed while frozen (glossary §8).

#### 3.11.3 Seat end

**SessionEnd is not a seat end**: it fires with reason `clear` inside a live process. A seat ends when (a) its MCP server's stdin reaches EOF (the server sends `seat_end` and exits within 1 s), or (b) the claude pid no longer exists (checked every 5 s). On seat end the daemon: sweeps all leases and TXNs of the seat; emits the CS boundary signal `seat_end` (HLD- closes the open CS and captures its ready tree); publishes `seat_end` and `release{reason: seat_end}` for the seat's claims (PRO-); hands requests addressed to it to COO- (returned to requesters). A resume or fork in a **new** process is a new seat; it re-claims on its next edit (glossary §22: seat adoption across processes is v2; this replaces the 5-min transcript adoption of research catalog item CCI-06 in `cat_claude.md`, which is not this chapter's rule CCI-06).

#### 3.11.4 Seat states

| State | Entered when | Effect | Left when |
|---|---|---|---|
| `FULL` | hooks and MCP paired, messaging env present, `crossSessionInbound` effective value not `hold`/`refuse`, not `--bare` | full delivery | — |
| `HOOK_ONLY` | hooks and MCP paired but the inbox is unavailable (no messaging env in the MCP server — inheritance is MEASURED for a project stdio MCP server on Windows only, glossary §25 F3 — `hold`/`refuse`, `--bare`, or the MCP IPC connection lost while the pid lives and hooks keep arriving) | gating and attribution work; no doorbell; requesters are told "queued; shown at their next action" (COO-) | cause removed (e.g. `/mcp` reconnect sends `hello`) |

#### 3.11.5 DEGRADED (transient host failure)

Entered when the daemon observes a PostToolUse or PostToolUseFailure for an edit-class `tool_use_id` with no matching gate request (the host timed the hook out or it failed open), or 60 s without hook traffic from a seat whose pid lives, whose MCP heartbeat continues and which is MID_TURN (glossary §11, §20), or when COO- reports a K3 on a claim that was already folded when the seat's edit was gated (COO-02: the gate was bypassed). **Silence** counts only while the seat has no open TXN, no open INFLIGHT lease and is not `AWAITING_PERMISSION`: a running tool call (a 15-min test run inside a TXN, the same case HLD-34 keeps open) or a pending permission prompt legitimately produces no hooks and never marks a seat DEGRADED. Effect: only that seat's read set and edit set of the last 30 min enter the defer set; incoming teammate changes to those files stay pending; the seat's own edits keep publishing through B1. Recovery after 3 consecutive matched Pre/Post pairs. Never a whole-repo stop.

**`DEGRADED` message facts** (for the 07-coordination template; Claude-facing, `L_c`): Claude Code skipped cowork-sync's checks for this session ({cause}); until checks work again, teammates' changes to {n} files this session recently read or edited are not written into them; this session's own edits are still checked before they are shared. Params: `{cause}` ∈ `host_timeout` (a Post without a matching gate request), `silence` (60 s without hooks mid-turn), `gate_bypassed` (K3 on a claim folded before the edit); `{n}` = size of the deferred set. Carrier: once per entry, on the seat's next exit-0 hook output as additionalContext (cap of that carrier, glossary §19), with the human-facing mirror as `systemMessage` (10-product). Recovery is not announced separately; it shows in `/cowork status`.

#### 3.11.6 NO_HOOKS (structural) and policy detection

Any hook from a `seat_key` proves hooks run (so a session opened before `/cowork start` is never misread). `NO_HOOKS` is inferred only when:

1. the seat calls a cowork MCP tool and no hook from its `seat_key` arrives within 10 s afterwards (PostToolUse `.*` fires for every tool call, so a working hook layer reports inside that window); or
2. the same seat produces ≥ 3 unmatched edit-class Posts within 10 min (persistent host-level fail-open; glossary §11, §20: a single unmatched pair is DEGRADED, persistent ones become NOHOOKS); or
3. the static check finds `disableAllHooks` or `allowManagedHooksOnly` effective in managed settings (`C:\Program Files\ClaudeCode\`, `/Library/Application Support/ClaudeCode/`, `/etc/claude-code/`, including `managed-settings.d`) or in user, project or local settings. The same check reports `deniedMcpServers`, `allowManagedMcpServersOnly`, `crossSessionInbound`, strict marketplace/plugin keys and a managed `statusLine` by setting name (SEC-28/SEC-29 own the policy model; this chapter runs the check at SessionStart and `/cowork start`).

Effect: FREEZE reason `NOHOOKS` on the checkout (glossary §8: no daemon-initiated working-tree write, no code publish, no adopt, no save; new claims stay TENTATIVE; allowed: fetch and fold, base moves, human `/cowork resolve`, board-only pushes of freeze/health events, answer-class ops `answer`/`request_status`, release-class ops `release`/`seat_end`/`leave`, and hold mirrors), `NOHOOKS` systemMessage through any channel that exists, status, and one OS notification naming the cause (UX-). Lifted when a hook from that seat arrives again (cases 1–2), the seat ends, or the static hit disappears (case 3). A session in which neither our hooks nor our MCP server run is invisible: its writes are human-class and B1 plus the revert detector still hold; doctor and the static check report the cause (policy-fail-open).

### 3.12 Turns, change-set signals and wake-originated turns

#### 3.12.1 CS boundary signals (to HLD-)

The daemon emits, per seat, the signals `prompt` (a UserPromptSubmit that opens a new turn; a nonce-carrying UserPromptSubmit never emits `prompt`: mid-turn it leaves the CS open, glossary §25 F2, and a wake-started turn's CS opens lazily as below), `stop`, `stop_failure`, `subagent_stop{agent_id}`, `session_end`, `seat_end`, `checkpoint{source}` (`source` ∈ `green`, `tool`, and since rev 2.4 `edit`, which carries the `cand_seq` of a candidate whose edit check passed, §3.8.4, glossary §27.1) and `idle_10min` (no hook from the seat for 10 min; glossary §20 seat CS fallback close). `idle_10min` carries the seat's activity (§3.11.2a) and whether any of its TXN windows is open; HLD-34 closes the CS on it only when the seat is `IDLE` or `ENDED` and no TXN is open (a `MID_TURN` seat running a 15-min test, or one `AWAITING_PERMISSION`, keeps its CS open). HLD- owns change-set identity (`cs_id = <seat_id>/<turn-seq>`), which signals close a CS, ready trees and publication; a CS opens lazily at the seat's first file effect after the previous boundary, so wake-started turns work without UserPromptSubmit (debounce-splits-every-multifile-turn).

**Capture-at-trigger:** for every closing signal and every `checkpoint{source: green|tool}` the daemon captures the CS's **ready pair** `(A_cap, R)` (glossary §3: `R = S_disk` at the trigger, not masked; MASK is applied only when P is built) for the CS's paths before replying to that hook, bounded at 150 ms; otherwise it captures at the seat's next hook and marks the window late. *(changed in rev 2.4, glossary §27.1)* An edit checkpoint differs: its candidate is taken before the reply under the same 150 ms bound but is **dropped**, never taken late, when it misses the bound, and it becomes the ready pair only after its edit check passes (`checkpoint{source: edit}`, §3.8.4).

**Green checkpoint:** a PostToolUse (not PostToolUseFailure) of a `Bash|PowerShell` call whose command starts with one of `checks.checkpoint` (glossary §17) and, when `tool_response` exposes an exit status, whose status is 0; or a `cowork_checkpoint` call. The CS's `checks=` trailer value is decided by HLD-.

**Nudge:** after 300 s of unpublished edits in an open CS (glossary §20), the seat's next PostToolUse carries one `CS_UNPUBLISHED_NUDGE` note per CS (the code is 05-holds' HLD-43; facts: this turn's changes to {n} files are not shared until an edit passes the edit check, the turn ends, the checks pass or `cowork_checkpoint` is called; the former `CS_NUDGE` code is dropped, §3.14.4). *(changed in rev 2.4, glossary §27.1)* The 300 s count from the oldest file effect of the CS that no passing capture covers, so a CS whose edits keep passing their edit checks is never nudged, and `{n}` counts only the files changed since the CS's newest passing capture. Claims are never delayed by CS state.

#### 3.12.2 Turn origin

Every doorbell carries a wake nonce; when its post is `sent` (§3.16.5) the daemon records the seat's last seen `prompt_id` and marks a wake *pending* for the seat. MEASURED (glossary §25 F2, spike 02, Windows, `claude -p`): an injected message fires UserPromptSubmit with its raw text — in an idle session as a new turn with a new `prompt_id` 30–36 ms after the post; mid-turn after the current tool result, in the same turn.

**Nonce rule (glossary §25 F2).** A UserPromptSubmit whose `nonces[]` is non-empty is a doorbell, never a human prompt: it does not refresh the seat's last human-origin prompt (attended window, glossary §20), does not open a human-origin turn, emits no `prompt` signal (§3.12.1) and, mid-turn, does not release leases or close TXNs (§3.7.1, §3.7.3); it confirms delivery of the doorbell whose nonce it carries (§3.16.5) and clears that pending wake.

A turn is **wake-originated** iff its `prompt_id` differs from the recorded one and (a) its UserPromptSubmit carries the posted nonce (glossary §25 F2: a wake turn is a new `prompt_id` whose UserPromptSubmit carries a nonce), or (b) — a conservative fallback for hosts on which SPIKE-0 has not measured UserPromptSubmit for injected messages (macOS, Linux, interactive TTY; follow-ups SF-U6, SF-U7) — its first hook after the post is not a UserPromptSubmit (where `prompt_id` is absent: the seat had no hook in the 60 s before the post and no Stop-less turn was open); in both cases no UserPromptSubmit without the nonce has arrived since the post. Fallback (b) can only classify a turn as wake, the more restricted origin. Hooks carrying the recorded `prompt_id` belong to a turn already running and are never wake-originated, including after a mid-turn doorbell. The origin is cleared at that turn's Stop/StopFailure.

**Slash expansions.** UserPromptExpansion fires before UserPromptSubmit (glossary §25 F5), so a `/cowork` expansion is classified at its own arrival: while a wake is pending for the seat and the expansion carries a `prompt_id` different from the recorded one, it is treated as wake-originated and no human evidence is minted from it (SEC-25). A pending wake ends when its nonce is seen or 60 s (local Δmono) after the post, whichever comes first, so an undelivered doorbell never blocks the human's verbs for longer; rule (a) above still classifies a later nonce-carrying turn as wake. A doorbell text never begins with `/` (the MCP server refuses to post one, §3.16.5), so a doorbell is not expanded as a slash command; whether the host would expand slash text inside an injected message is SPIKE-0 follow-up SF-U12 (§8 question 14). Every other turn has origin `human` (glossary §3). This is the single turn-origin rule (cross-check fix 24); COO- uses it for doorbell cascade prevention and `origin=wake` attribution, and SEC-25 refuses human evidence in a wake-originated turn.

**Human activity for the catch-up summary** *(rev 2.5, F04)*. Human activity for F04 (the seen marks and return detection of 10-product §3.9a, kept as heights in 01-engine `meta.since`) is exactly: a UserPromptSubmit with empty `nonces[]` from any seat of this peer; a `/cowork` UserPromptExpansion of any verb, read-only verbs included, that this section does not classify as wake-originated (whether evidence is minted is irrelevant: §3.4.1 step 4 mints it only for acting verbs, and a `/cowork since` expansion counts); and the opening of this peer's human CS (05-holds HLD-35) unless every path of its first delta is seat-tagged (HLD-35: a write after a TXN cap or from a background process a seat started). A nonce-carrying UserPromptSubmit, any hook of a wake-originated turn and any doorbell never count. Each activity sets the mark to the board height this daemon has folded; the return recap rides the first human-origin UserPromptSubmit after a return (§3.14.1) and never a wake turn. The CLI reads the marks with `since_query` and reports a printed run with `since_ran{to}` (CLI ↔ daemon frames: defined and schema-validated in 09-security §3.11 "CLI requests added in rev 2.5"; their use is 10-product §3.9a, FEAT-F04-18; §3.4.3 lists only hook and MCP frames). The daemon applies `since_ran` only for a route-(a) request (glossary §29.2: stdin and stdout TTYs, no claude ancestor, no `CLAUDECODE`; 09-security §3.11) or within 60 s (local Δmono) of a `/cowork since` UserPromptExpansion classified human by this section (FEAT-F04-18); any other run, such as a model Bash call of `cli.js since` with or without a PTY, leaves the `last-run` mark unchanged.

#### 3.12.3 Wake work set: gate and backstop (S5)

Wake policy (whether to ring, caps, what counts as accepted work) is COO- (COO-24, COO-25); the **wake work set** is glossary S5's (work the seat accepted, or that targets its own claims; exact membership in 07-coordination §2). This chapter enforces it twice. **Gate (advisory, early):** with `wake.turnEdits = allow` (default, S5; glossary §17 `user.json`), an edit-class call in a wake-originated turn passes check #3 only if every predicted region lies (a) in a path of a request this seat **accepted**, or (b) contained (04-regions §3.6 containment form, decided by REG- `predict.ownContained`, REG-33) in this seat's own HELD non-STALE or confirmed TENTATIVE claims as of the Pre, excluding every claim first confirmed during the current wake turn (07-coordination §2); quarantine-set paths are never in the set. A file-writing shell command in a wake-originated turn is G1 `WAKE_TURN` in both modes (§3.9; COO-25: its targets cannot be bounded). With `wake.turnEdits = deny`, every edit-class call in a wake-originated turn is G1 `WAKE_TURN` as well. **Backstop (hard):** whatever the gate let through, any hunk on a `LIVE` path outside the wake work set (edit-class prediction miss, unclassified shell writer) PINs the whole CS with guard `wake-scope` at PostToolUse or TXN close (§3.8.2a; 05-holds HLD-66), with no disk write, so it is never published. In both modes `cowork_*` tools and read-only tools are allowed. Every CS opened in a wake-originated turn carries `origin=wake` (glossary §5), every op it produces that has an `origin` field carries `wake` (`request.origin`, glossary §7; hold records follow HLD-59), every CS the turn closed is listed to the human at their next human-origin prompt (COO- `T-WAKE_RECAP`; glossary S5), and a wake-originated turn can never cause another doorbell (COO-). Per S5, the answer-only default of research catalog item CCI-20 (`cat_claude.md`, not this chapter's rule CCI-20) is replaced by "allow within scope".

### 3.13 The "file modified by user" reminder countermeasure

The host's changed-file reminder frames teammates' unfinished work as deliberate current state (VERIFIED H7), and 77 % of reminders arrive mid-turn after a tool result (VERIFIED H9). The host text cannot be changed, so:

1. **Co-located attribution.** The daemon journals every apply (path, line range, region label, teammate display name, whether that claim is still held). Every PostToolUse (`.*`) returns at most one coalesced `ATTRIBUTION` note (≤ 600 chars, glossary §19) for applies since the seat's previous tool call into files in its read set (full reads, or ranged reads overlapping ± 20 lines), stating that the lines were changed by teammate {name}'s session and, when the claim is still held, that this is their unfinished work and not a request from this user (change-reminder-frames-peer-wip-as-deliberate, helpful-fix-reverts-synced-in-progress-work).
2. **Held records in read files.** PostToolUse(Read) and SessionStart list ACTIVE hold records in files the seat reads (`HOLD_IN_FILE`), and the seat is told at once when a record was created from its own change (`OWN_CHANGE_HELD`) (held-bytes-mislead-local-claude).
3. **Read during replace.** A Read returning ENOENT or 0 bytes for a tracked path that the verifying writer replaced within the last 2 s gets `READ_REPLACED` ("reading it again returns the current file") (readers-see-missing-or-empty-files).
4. **Human edits in own claims.** A human-class change on this PC inside a region claimed by a seat of this same peer is not K5; that seat gets `HUMAN_EDIT_OWN_CLAIM` ("this user edited {label} lines {a}-{b} outside Claude") at its next hook (human-claim-breach-and-claude-tramples-human).
5. **Standing rule.** The RULES text (COO-) frames teammates' claimed code as their unfinished work.
6. **Volume.** Reminder volume is bounded by apply coalescing (§3.7.5) and the reminder budget (§3.16.1) (modified-file-notices-flood-context, reminder-context-accumulation).
7. **Claims ahead in read files** *(rev 2.5, F05)*. At PostToolUse(Read) of a LIVE path, teammates' claims in the claim view that overlap the read range are listed once per (seat, agent, claim_id) in `CLAIM_AHEAD` (a re-anchor does not re-note; a claim already named by a held-variant `ATTRIBUTION` is not repeated); `CLAIM_AHEAD_ENDED` follows only for listed claims (proposal F05 §2.1–§2.2). The note only reads the claim view: it creates no claim, reservation or record (it is not the "soft claim" 07-coordination §1.2 refuses) and decides nothing; the K1 gate (§3.5.2 #13) and B1 stay the only decisions, and a missing note never means "free to edit". For a Read by seat S (agent `a`, `main` for the top level) with a non-empty, non-ENOENT result:
   - (a) **Read range** `RR` = `[offset, offset + limit − 1]` from the payload `read{offset, limit, full}` (§3.4.3); without `offset`/`limit`, the rows the host returned (its default line limit, pinned with the payload schema; §8 rev 2.5 notes). Rows are disk rows, which equal stored rows (04-regions §3.2 item 5).
   - (b) **Candidates**: every claim in S's claim view on the path whose holder seat ≠ S (any `agent_id`), that is not STALE and on which S holds no active go-first grant: HELD folded claims of other seats of any peer, and all confirmed TENTATIVE claims of sibling seats on this peer. Unconfirmed TENTATIVE claims are never listed. The claim view's "earlier in local order" qualifier orders two K1 claimants and does not apply to a reader, which has no claim in the comparison.
   - (c) **Overlap**: the claim's ranges are mapped from its anchor blob (for a sibling's unpublished claim, its draft `srcBlob`) to S's view blob of the path (§2; set by this Read) with REG- `mapRanges(…, mode: local)` (04-regions §3.4); when the view blob equals the anchor blob they are used unmapped. Overlap is the closed-interval intersection with `RR`; a `granularity: file` claim and a `WHOLE_FILE` mapping result overlap every read, a `TOMBSTONE` never does.
   - (d) **Notice key** `(seat, agent_id, claim_id)`, deliberately without the anchor (a claim is re-anchored at every holder push that touches the path, 04-regions §3.5; `claim_id` is stable across re-anchors). A key already in the context's *noticed set* produces nothing. A key enters the set only when the batch carrying it is DELIVERED (`printed{batch_id}`, §3.14.3) and leaves it when its claim leaves the claim view, whether or not the ended line is delivered, so a later re-claim of the same `claim_id` is noted again. The noticed set lives in daemon memory per (seat, agent) and is cleared at SessionStart `compact|clear|resume|fork` and at SubagentStart/SubagentStop of that agent.
   - (e) **Render**: one `CLAIM_AHEAD` in the PostToolUse attribution slot (600 chars in total, §3.14.1), after `ATTRIBUTION` and only when both fit; items ordered by first row, at most 3 and fewer when the next item would pass the slot, the rest as the overflow clause "and k more: cowork_show({file})" (`cowork_status` does not list teammates' claims). A claim named by a held-variant `ATTRIBUTION` in the same reply or already DELIVERED to this context is not listed; its key enters the noticed set with that batch. If not even one item plus the overflow clause fits, the note waits for S's next PostToolUse in the same turn; a note still undelivered at that turn's Stop is dropped and its keys are not marked.
   - (f) **Ended line**: when a claim whose key is in a context's noticed set leaves the claim view, that context gets one `CLAIM_AHEAD_ENDED` at its next carrier (the PostToolUse attribution slot, else the next UserPromptSubmit digest delta); a re-anchor and a context never told produce none, and a requester that gets a 07-coordination `T5.*` result naming the same claim gets none for it. `{AHEADEND}` is chosen from the fold's record of the claim (02-protocol §3.3 release reasons): #1 `release` with reason `explicit`, `answer`, `stop` or `reservation_transfer`; #2 `release` with reason `save`; #3 `seat_end` (op or `release{reason: seat_end}`), `leave`, or the fold-derived `superseded` (a new-epoch `join` retired the holder's epoch); #4 an applied `presume_absent` on the holder's epoch (STALE; it exists only for a PC with an open request or grant, PRO-35, never as a general inactivity timer).
   - (g) **Cost and privacy**: both codes are non-mandatory (suppressed in `PULL_MODE`), count on the CCI-46 meter and stop for the rest of the seat-hour once they used 5,000 chars (§3.16.1); the reply path does ≤ 5 ms of main-thread work and a later result rides the next PostToolUse (§2 local numbers). Which files a seat reads, its read ranges and its noticed sets never leave the daemon (no board op, ref, `status.json` field, event or doorbell; the holder is never told its code was read); logs carry only codes and `claim_id`s; non-LIVE paths carry no claims and get no note; board-sourced strings pass `sanitize(…, "claude")` (SEC-34) and REG-34 label verification (`?` when a label cannot be re-derived).

Every test of items 1–6 runs in an interactive harness (ConPTY terminal or VS Code); `claude -p` emits zero reminders (VERIFIED H8). Item 7 *(rev 2.5, F05)* does not depend on host reminders; its tests (§7 tests 48–60) run in the simulator, except T-F05-reorder (real `claude -p`). File:line attribution from `tool_response` is v2 (glossary §22).

#### 3.14.3 Pull delivery and confirmation

The carrier of record is the per-(seat) pull cursor. Every event has an id in the daemon store; the daemon chooses events for a reply by COO- routing and the caps above; the reply lists them in `events[]`. Undelivered events are re-sent at the next carrier. ### 3.15 Stop hook

At most **one** `{"decision":"block"}` per turn, never when `stop_hook_active` is true, reason ≤ 1,200 chars (`STOP_SUMMARY`). It blocks only if:

- **(a) truthfulness:** this seat (any `agent_id`) has, in this turn, denied, held, recorded or not-shared changes, and the cowork ids of those items do not all appear in `ids_in_last_message` (when the host does not provide the last assistant message, (a) blocks whenever such items exist); or
- **(b) ask:** COO- says a request addressed to this seat is due to be asked at this Stop (U5: when its own work ends), this attempt of it — request identity `(req_id, to_holder.seat)` (glossary §3) and `attempt` (glossary §7) — has not been in a Stop block yet, and `background_tasks_running` is 0. All due requests go into the one block. The block **presents each request for the human's decision** (U5, glossary §24): its facts are that the holder's Claude shows the request to its human and asks whether to handle it, and that in this human-origin turn it answers `accept` only on the human's word (decline, later or release remain its own choices). The wording is 07-coordination's `T-STOP` template; no daemon check verifies the human's word (§3.16.3).

No Stop block of either kind is issued in a wake-originated turn (COO-25: the doorbell already asked); that turn's (a) items are carried by COO-'s `T-WAKE_RECAP` in the next human-origin digest.

Items of (a) come first, keyed by `agent_id` for subagent items. Each (request identity, attempt) appears in a Stop block at most once ever (glossary §19 Stop row; `asked_at` recorded per attempt when the block's batch is confirmed); a later attempt of the same request (after a decline and a human `--handoff`, or a re-request after a grant lapse) may be asked again. SubagentStop never blocks. Requests and records never depend on Stop firing: StopFailure, the next UserPromptSubmit, SessionEnd, seat end and 10 min without a hook are equivalent promoters (HLD-/COO-) (false-completion-reports, stop-handoff-silent-failure-and-reask-loop; VERIFIED: 2.1.284 renders nothing for Stop hook errors; DOCUMENTED: Stop does not run on interrupt).

### 3.16 Per-seat budget and the MCP server

#### 3.16.1 Per-seat cost budget and PULL_MODE

The daemon counts every character cowork causes to be injected into a seat (digests, notes, reasons, Stop blocks, doorbells, and *(rev 2.5, F04)* the F04 return recap, because a `systemMessage` can reach the model's context; tool results Claude requested are not counted), estimates host reminder volume as the applied diff chars into files in the seat's full-read set, and estimates wake cost as wakes × the seat's last observed context size. Per seat-hour (window anchored at the seat's first hook, monotonic): injected text ≤ 20,000 chars (glossary §20 per seat-hour context budget); host-reminder estimate ≤ 15 reminders and ≤ 20,000 chars (glossary §20 seat numbers); doorbells per the glossary §20 wake caps (per seat ≥ 10 min apart and ≤ 4 per 60 min; per PC ≤ max(2, floor(12 / max(1, |R ∪ {self}|))) per 60 min, R = ranked set, this peer always counted; applied by COO-); Stop blocks ≤ 1 per turn and ≤ 1 per (request identity, attempt) ever (glossary §19). Slash-mode CLI output (the `!` line of a human-typed `/cowork` verb) enters Claude's context but is not cowork-initiated: it is shown on the seat's budget line and does not count toward the 20,000-char threshold (10-product §8 Q2 default, adopted here).

Over any budget the seat enters `PULL_MODE` until the next window boundary: no doorbells; applies into its read set only at its Stop or UserPromptSubmit; digest only at its next UserPromptSubmit; non-mandatory notes (ATTRIBUTION, *(rev 2.5)* CLAIM_AHEAD and CLAIM_AHEAD_ENDED (F05), the `SINCE_POINTER` line `T-SINCE` (F04), CS_UNPUBLISHED_NUDGE, bystander lines) suppressed, and *(rev 2.5, F04)* the F04 return recap shrinks to its head and tail lines. Mandatory outputs — G1 reasons, the K2 block, `OWN_CHANGE_HELD` for a `wake-scope` PIN, Stop truthfulness — are never suppressed, only shortened to their compact forms (T1R). An idle seat costs 0 injected chars unless it is woken: nothing is pushed into it except doorbells within the wake caps (S5: sessions in every permission mode are woken when the user enabled wake). The attended window (last human-origin prompt ≤ 10 min) and the cache window are used only for wording and cost accounting and never suppress a doorbell the user enabled (glossary §20). `/cowork status` shows each budget and its use. Acceptance (glossary §20 cost row): ≤ 15 % extra input tokens per seat-hour at median context, ≤ 20 % for a 200k-window seat; ≤ 4 doorbells and ≤ 20,000 injected chars per seat-hour; 0 for idle seats unless woken; measured by the TST- cost soak (aggregate-cost-unbudgeted; VERIFIED H10: R = 60 requests/h, C = 511k median, 1.7k tokens per reminder; model: naive ≈ +65 %, budgeted ≈ +11 % at C = 511k).

**Shares added in rev 2.5.** *(rev 2.5, F05)* Inside the 20,000 injected chars per seat-hour, `CLAIM_AHEAD` and `CLAIM_AHEAD_ENDED` together use at most 5,000 (glossary §20 "Claims ahead" row); once a seat has used that share, no claim-ahead text is sent to it until its window ends (`cowork_show` still answers), so claim-ahead notes alone can never put a seat into `PULL_MODE`. The cost soak runs with claim-ahead notes on. *(rev 2.5, F04)* The F04 return recap (`systemMessage`) and its `T-SINCE` line are metered in full on the same meter (worst case ≈ 1,350 chars per return; idle seats get nothing). This chapter does not decide whether other `systemMessage` mirrors are metered.

**Cost impact of edit checkpoints** *(added in rev 2.4, glossary §27.1, §27.2)*. (1) **Injected text: none.** No outcome of an edit checkpoint produces a code (§3.14.4), so a seat's injected-chars meter, its doorbell count and its Stop blocks are unchanged, and `PULL_MODE` neither suppresses nor is triggered by edit checkpoints *(rev 2.5, F14 + F12; D1: 10-product's `UI_FLOW_LAST_*` codes render `last_check` only in the output of a `status --flow` or `wrap` run; the daemon injects nothing. When that run is a slash command, its output reaches the seat's context because the human asked for it, like the output of any read-only slash verb; it is slash-mode CLI output, which is not cowork-initiated, so by the rule above it is shown on the seat's budget line, does not count toward the 20,000-char threshold and triggers no `PULL_MODE`)*. (2) **Host reminders into other seats rise**, because Claude edits now reach teammates mid-turn (≈ 10–30 s instead of at turn end) and land as more, smaller applies. The existing bounds absorb this without new numbers: apply coalescing (a path fully read by a `MID_TURN` seat is applied at most once per 2 min; §3.7.5, glossary §20), the host-reminder estimate of ≤ 15 reminders and ≤ 20,000 chars per seat-hour, `PULL_MODE` when exceeded, and the governor, which coalesces every ready group into one push per window (HLD-44) and caps the team at B = 12 attempts per minute (B = 6 for 30 min after a throttle signal; glossary §27.2). The cost soak re-measures the ≤ 15 % / ≤ 20 % extra-input gates with edit checkpoints on. (3) **Daemon CPU:** at most one running and one waiting edit check per open CS (§3.8.4), each ≤ 0.5 s in the worker pool at lower priority than gate parses and confirmations, reusing the 300 MB parse cache by blob oid; the event loop is never blocked (CCI-12). (4) **Objects:** a failing candidate writes none; each passing capture writes the R blobs of its changed paths (HLD-40), which the soak's loose-object gate (glossary §26 W6) counts.

#### 3.16.2 Role and lifecycle

One stdio server per Claude Code process, started by Claude Code from `.mcp.json`. It does **no gating** (no `mcp_tool` hooks exist; DOCUMENTED: stdio servers are not reconnected, so an MCP-based gate would be disarmed by one crash).

1. At start: mint `seat_id` (128-bit random); compute `seat_key`; read `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN` from its own environment into memory only (MEASURED for a project stdio MCP server on Windows, glossary §25 F3; without the socket the seat is `HOOK_ONLY`). Resolve the plugin data directory: `CLAUDE_PLUGIN_DATA` when set, else derived from the plugin id under `~/.claude/plugins/data/` (glossary §25 F3: the variable was absent for a project MCP server; the same derivation is used by hooks and the CLI, §8 question 10).
2. On `initialize`: read `clientInfo.version`; below 2.1.270 → advertise only `cowork_status`, whose result carries `CC_TOO_OLD` (the human-facing refusal `REFUSE_CC_VERSION` is shown by `/cowork start` and doctor), and tell the daemon so edit-class calls get `CC_TOO_OLD`.
3. Resolve the session's repo from its `cwd` (same walk, canonical root form and case rule as §3.4.1 step 3). If not live: advertise only `cowork_status` (≤ 400 chars schema). Watch `<gitdir>/cowork/live` (`fs.watch` plus a 30 s re-check); when it appears or disappears, send `notifications/tools/list_changed` and switch tool sets.
4. When live: connect to the daemon (SEC- handshake). The MCP server never spawns the daemon (§3.17.2: the hook path is the in-session spawner); while no daemon answers it retries with backoff and the seat shows `HOOK_ONLY`. Then send `hello{seat_id, seat_key, claude_pid, cc_version, plugin_version, hook_proto, messaging_present}` (§3.4.3), then a heartbeat every 15 s; reconnect with backoff on loss (the seat shows `HOOK_ONLY` meanwhile).
5. On stdin EOF: send `seat_end`, exit within 1 s.

Tool results for `cowork_status` and `cowork_show` are never `isError`; a down daemon yields a structured `{"daemon":"down","cause":…}` result. Other tools return `isError: false` with `{"ok":false,"code":…,"text":…}` on refusal, so refusals are facts, not tool failures. Every tool result text is ≤ 400 chars except `cowork_show` (≤ 8,000, truncated with a count line) (glossary §19).

**Ops under FREEZE and publish pauses.** A tool's board op is published only when glossary §8 allows it: `answer`, `request_status`, `release`, `seat_end` and `hold` mirrors are allowed while frozen; `request` and `note` are not; no op at all is pushed under `INCIDENT` or a `proto` VERSION pause; under a regionSpec-only VERSION pause the allowed board ops are `join`, `leave`, `seat_end`, `release`, `request_status`, `answer` with `decline|later|release`, and `hold`. A tool whose op is not allowed now records it locally in the outbox (it is published when the reason lifts) and returns `{ok:true, queued:"<reason code>"}`, so Claude is told the record is not yet on the board.

**`cowork_show` path view** *(rev 2.5, F05)*. Teammate notes are not shown here (they stay in `cowork_show(<rid>)`). When the rows of the shown paths would pass 8,000 chars, whole paths are dropped from the end and counted in the same `R.show.more` line; only when the first path alone passes the cap are its rows cut after the last one that fits, with the count line of §3.16.2. **Polling guard:** a second call for the same (seat, sorted matched path set) within 30 s of the last full result whose claim-view digest over those paths is unchanged returns `SHOW_NO_CHANGE` (`R.show.throttle`), as `cowork_status` does; a changed digest returns the full result. The view reads only the claim view and fold this daemon already holds; nothing is written or sent.

**`cowork_show` undo view** *(rev 2.5, F10)*. Only text paths whose undo is a change inside an existing file are diffed; every other path (delete a file the CS created, re-create a file it deleted, binary, file mode, filtered: stored form, never smudged or diffed) gets one `T-SHOW_UNDO.human` line pointing to `/cowork revert {cs}`, because Edit can neither create nor delete a file and a whole-file Write is what the foot rules out. Claude learns its own cs ids from `cowork_checkpoint`'s result, from `T-WAKE_RECAP` or from an id the user pastes from `/cowork log`. The Edits that apply the view are an ordinary seat CS (observed, claim-gated by G1, wake-limited by S5, edit-checked, B1/T0-gated); no MCP tool writes (SEC-27 unchanged), and rendered diffs are never written to the board, logs, `status.json` or any file. *(rev 2.5, F10; added at merge)* **Secret scan:** because view mode has no `BUSY` guard, `ours` can hold content the scanner has not yet seen, so every rendered diff line passes `scanSecrets` (kind `status`, SEC-38) before it enters the result; a hit replaces the line's text with `[redacted: secret-scan]`, as `/cowork since` does for notes (10-product §3.9a). **Polling guard and priority:** a second `cowork_show(cs_id)` from the same (seat, cs_id) within 30 s of the last full undo view, while TIP and the materialized blobs of `C(t)`'s paths are unchanged, returns `SHOW_NO_CHANGE` (`R.show.throttle`, as the path view); REV view-mode jobs run at background priority, below every gate, CONFIRM, edit-check and T0 job and the loop's fetch, apply and publish, at most one at a time (as F12's `saveAttribution`, 10-product UX-52).

#### 3.16.4 Token custody

cowork code reads `CLAUDE_CODE_MESSAGING_TOKEN` only in the session's own MCP server (`dist/mcp.js`), from its own environment, and keeps it only in that process's memory (glossary §26.2 item 6). The host itself places the token in every hook's environment as well as the MCP server's (MEASURED, spike 02; glossary §26.2 item 6), so the rule binds cowork code, not the environment: the loader and core never read the variable (hooks hash only the socket name for `seat_key` and report only whether the socket variable is set), the token is never sent over daemon IPC, never written to disk or logs and never placed in hook output, and the daemon's environment never contains it because the DAEMON_ENV never-list drops every `CLAUDE_*` value of the spawning hook's environment (§3.17.2). Pairing uses `seat_key`, which is not a secret; it is safe because daemon IPC is key-authenticated (SEC-) (VERIFIED H6 and MEASURED glossary §25 F3: a project stdio MCP server inherits the session's own socket and token on native Windows; plugin-packaged servers, macOS and Linux are NOT MEASURED and degrade to `HOOK_ONLY` automatically if the variables are absent).

#### 3.16.5 Doorbell posting

COO- decides whether to ring and builds the text. The daemon sends `ring{event_ids, text (≤ 1,500), nonce}` to the seat's MCP server. A text that begins with `/` is not posted (`ring_result` `error`; §3.12.2). Otherwise the server connects to `CLAUDE_CODE_MESSAGING_SOCKET`, writes `{"type":"auth","token":<own token>}` as its first line, then exactly one line `{"type":"user","message":{"role":"user","content":<text>}}` with no `session_id`, and observes the connection for 100 ms (glossary §25 F1, MEASURED spike 02: the formerly assumed `{"type":"message",…}` frame and plain-text lines are silently dropped, and the host never answers in band). It replies `ring_result{nonce, sent|refused|error}` (glossary §25 F1, which supersedes the `accepted|held|refused|timeout` values of glossary §13): `sent` = both lines written and the connection not closed within 100 ms; `refused` = the server closed the connection within 100 ms (auth rejected; with no auth line it closes ≈ 2 ms later); `error` = connect or write failure, or the `/` refusal above. The daemon waits ≤ 5 s for the frame (glossary §20 doorbell post row) and counts a missing frame as `error`. `sent` is not delivery: a doorbell is **delivered** only when a UserPromptSubmit carrying its nonce arrives (glossary §25 F1, F2; §3.12.2), and only then are its events marked delivered (§3.14.3). After `refused` or `error`, and after `sent` until the nonce is seen, every event stays in the pull queue and rides the seat's next carrier; re-ringing and the requester's texts are COO-'s. The MCP server never posts anything the daemon did not ring, and never posts to any socket but its own session's.

### 3.17 Daemon lifetime, spawn and versions

#### 3.17.1 Leases (lifetime)

The daemon captures, applies and publishes only while it holds at least one valid lease: a **seat lease** renewed by that seat's MCP heartbeat or by any hook from that seat, or a **human lease** (glossary §15: every human acting verb renews a 60-min human lease; `/cowork start --human <1-480 min>` grants a longer one, LIF-41). With no valid lease for 2 min it goes **idle**: no snapshot capture and no working-tree write; already-captured ready trees and pending board ops (releases, `seat_end`, hold mirrors) still publish through the governor until the outbox is empty; the board shows the peer idle (health event). After 10 min without a lease it drains (finishes the cycle, writes state) and exits; its last `status.json` write sets `state: "down"` and `message_code: "IDLE_NO_SESSION"` (glossary §25.2 item 6; 10-product §3.19 renders it as "idle (no session)", LIF-41) (orphan-daemon-outlives-sessions-and-plugin; VERIFIED H5: the detached daemon escaped the job object and stayed alive > 60 s after claude exited; MEASURED glossary §25 F4, §3.17.2).

#### 3.17.2 Spawn and environment

**One spawn routine, one in-session spawner.** The daemon is started only by `spawnDaemon()` in `dist/core.js`. Inside a Claude Code session its caller is the **hook path**: core in a hook process, normally at SessionStart, or at any later hook that finds the daemon down (§3.4.2 step 1, §3.6.4). For human verbs the CLI calls the same routine (`/cowork start`, 08-lifecycle start step 1). The MCP server never spawns the daemon (§3.16.2 step 4). The routine spawns with `process.execPath` of the calling process, `detached: true`, `stdio: 'ignore'`, `windowsHide: true` and `unref()`, from `CLAUDE_PLUGIN_DATA/runtime/<version>/daemon.js` (data directory resolved as in §3.16.2 step 1 when the variable is absent); the SessionStart handler copies `daemon.js`, `worker.js` and the grammars there within its 3 s deadline, and a spawn before the copy exists uses `${CLAUDE_PLUGIN_ROOT}/dist/daemon.js`. Tree-sitter WASM is loaded eagerly.

MEASURED (glossary §25 F4, spike 02, Windows, normal `claude -p` exit): a daemon spawned this way from a SessionStart hook survives `claude` exiting, its heartbeats continue, and the spawning hook returned without waiting on it. SPIKE-0 item e therefore tests this hook spawner, not a spawn from `dist/mcp.js` (§8, cross-chapter notes). Hosts that run `claude` in a kill-on-close job object were not measured; such a host is made visible, not silent: when a spawn finds that the previous daemon ended without its final status write (a clean exit always writes one, §3.17.1, LIF- stop) and that previous daemon's last heartbeat (`status.json` `heartbeat_mono_ms`) lies ≤ 5 s after the last SessionEnd hook its log `log/daemon-<n>.jsonl` records, with no seat hook logged after that SessionEnd (both times on that daemon's own monotonic clock), doctor reports `DAEMON_DIED_WITH_HOST` (WARN) and status shows it once. Single instance is enforced by the SEC- endpoint bind (`daemon.lock` is advisory, glossary §6).

**Environment.** The daemon is spawned with exactly DAEMON_ENV as built by 09-security §3.4 (SEC-05): its base allowlist, credential and transport set, `user.json` `env.passthrough` names, never-list and forced values. That section is the single list; this chapter does not repeat or narrow it (everything not admitted there is dropped). In particular the never-list keeps `CLAUDE_*` (including `CLAUDE_CODE_MESSAGING_*`, which the host places in every spawning hook's environment, glossary §26.2 item 6), git redirections such as `GIT_DIR` and `GIT_INDEX_FILE`, `ELECTRON_*`, `VSCODE_*` and `NODE_OPTIONS` out of the daemon (§3.16.4). Plugin paths the daemon needs are passed as arguments. The git runner then sets its own environment (glossary §18).

#### 3.17.3 Version handshake

Every hook request and MCP `hello` carries `plugin_version` and `hook_proto`. If the caller's plugin version is **newer** (semver) than the daemon's, the daemon replies normally, then drains and exits; the next caller spawns the newer version. An **older** caller is served when its `hook_proto` is the daemon's current or previous one; otherwise its edit-class calls get G1 `VERSION_RESTART` ("cowork-sync was updated to {v}; restart Claude Code to load it"), a pause of that session only. Newest wins, so sessions on different versions never ping-pong the daemon (version-skew-board-and-guards, supply-chain-versions). Board-level version mismatch is a different mechanism, the publish pause `VERSION` (glossary §8; LIF-37/PRO-): a board `proto` different from ours → zero pushes of any kind; only `regionSpec` different from `teamRegionSpec` → code pushes paused, the listed board-only ops allowed, and claims written under another regionSpec gated as whole-file; a checkpoint that still differs after one refold → VERSION with `cause = checkpoint_mismatch` (glossary §7). In each case the seat sees the `VERSION_PAUSED` engine event ("update cowork-sync") through §3.14.6; the gate keeps working.

#### 3.17.4 Plugin disabled, uninstalled or key deleted

Every 30 s the daemon checks that `cowork-sync` is still enabled in `enabledPlugins` across settings layers, that `CLAUDE_PLUGIN_DATA/ipc.key` exists and that its runtime copy exists. If any check fails it runs LIF-36's shutdown sequence (08-lifecycle §3.10.2: remove the live markers it owns first, so surviving hooks exit 0 instead of G4 — this is the glossary §6 "plugin-removal shutdown"; no further working-tree write or snapshot; when online one board push of captured ready trees through every gate with `release{reason: stop}`, `seat_end` and `leave`, or a board-only push of those ops if frozen; `stop_mode := removed`; exit; one OS notification `DAEMON_REMOVED`) (cross-check fix 34: no stranded records). Correctness state lives under `<gitdir>` (ENG- storage), so deleting `CLAUDE_PLUGIN_DATA` loses only caches and the IPC key (orphan-daemon-uninstall, uninstall-deletes-state-daemon-orphaned).

**Live marker vanished.** The daemon also watches each `live` marker it owns (`fs.watch` plus the same 30 s check). If one disappears while no stop sequence (LIF- stop) and no shutdown sequence of the paragraph above is running, nothing legitimate removed it: hooks would then exit 0 with no IPC (§3.4.1 step 5), silently dropping the gate, K1 records and G4 for every seat while the daemon keeps publishing their edits as human-class. The daemon therefore re-creates the marker at once with the same content (the main-worktree realpath; the state ref already exists, so INV-LIF-MARKER's write precondition holds), writes a security event to `log/security.jsonl`, publishes a `health` event with `reason_code: LIVE_MARKER_RESTORED`, and raises one OS notification `LIVE_MARKER_RESTORED` (10-product class `NT_LIVE_MARKER_RESTORED`; UX- rate limit; human-facing code, §3.14.4), the same treatment LIF-16 gives an unexplained `paused` marker. If `<gitdir>/cowork/` itself is gone, it runs the shutdown sequence above instead. `/cowork pause` and `/cowork stop` are the only supported ways to stop coordination (glossary §24 default 8; decided, not re-opened here).

## 7. Tests

All integration tests run against a local bare remote (TST- simulator) unless stated; "interactive" means a ConPTY terminal or VS Code session, never `claude -p`.

**Loader and hooks**

1. *Unit — target repo resolution* (CCI-07): edit-class path in another repo than `cwd` resolves to the path's repo; `.git` file → not live; `.git` file whose common gitdir is live → `WT_NOTE` note only on SessionStart and edit-class PreToolUse; submodule path → `WT_SUBMODULE`; on Windows and macOS, an edit-class `file_path` and a `cwd` spelled in a different case than the marker (e.g. `c:\users\…\repo\src\a.ts` against marker `C:/Users/…/repo`), an 8.3 short name and an NFD spelling → live, the gate request reaches the daemon, and core and the MCP server derive the same endpoint as the daemon (no second daemon binds); a Write of a not-yet-existing file in a live repo → live.
2. *Unit — failure mapping* (CCI-06, INV-CCI-FAILCLOSED): `core.js` syntax error → exit 2 with the load line for each gating matcher, exit 0 for others; injected throw, rejected promise and malformed stdin → same mapping.
3. *Property — non-live fast path* (CCI-07, INV-CCI-NONLIVE): ≥ 200 invocations of every event in a non-live repo, in the exec form of glossary §13, produce zero IPC connections and zero stdout/stderr bytes (a UserPromptExpansion of an acting verb writes only its evidence line); p95 end-to-end wall time ≤ 80 ms on Windows (glossary §26.2 item 4), with the Defender state recorded.
4. *Unit — paused path* (CCI-08): paused repo → no IPC; exactly the glossary paused line on SessionStart and UserPromptSubmit; UserPromptExpansion `pause`/`resume` create/remove the file with `core.js` deleted, and an acting verb's UserPromptExpansion still writes an HMAC-tagged evidence line.
5. *Integration — loader protocol* (CCI-09, CCI-41): reply then `printed{batch_id}` on the same connection; killing the loader after stdout flush but before `printed` leaves events undelivered until the next hook, then delivered exactly once.
6. *Lint* (CCI-03, CCI-05, INV-CCI-NODECISION): build fails when a fixture introduces a shell-form hook, an `mcp_tool` hook, the string `permissionDecision`, a command without `disable-model-invocation`, `npx` in a command, a token read in `daemon.js`, `core.js` or `hook.js`, or a spawn call in `mcp.js`; `hooks.json` matches glossary §13 (with the glossary §25 F5 all-verb UserPromptExpansion matcher) byte for byte after JSON normalization.
