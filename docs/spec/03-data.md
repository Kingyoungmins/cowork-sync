# 03 — Data handling: canon, filters, conflicts, scope

**Status:** normative, conformed to glossary revision 2.3 (§23, §24, §25 rev 2.2 spike facts F1–F13 and pass-2 owner decisions, §26 rev 2.3 Windows contention W1–W6 and synthesis decisions; where they differ the newest section wins) · **Depends on:** 00-glossary (+ 01-engine `ENG-`, 04-regions `REG-`, 05-holds `HLD-`, 06-claude `CCI-`, 07-coordination `COO-`, 08-lifecycle `LIF-`, 09-security `SEC-`, 10-product `UX-`, 11-testing `TST-`)

This chapter defines what cowork-sync does to the *bytes* of the files it shares: the stored form of every blob it creates (canon), the use of the team's clean/smudge filters, the attribute source, the fsmonitor setting, the one conflict function (including the insertion-concat fast path and the S2 policy), the sync scope (U10), path portability, and the treatment of binaries, symlinks, submodules, LFS, huge and generated files. It defines functions that other chapters call; it does not define the loop that calls them (01-engine), the hold registry that stores what they withhold (05-holds), or the text that tells people about it (07-coordination, 10-product).

## 3. Design

### 3.1 Byte discipline (why first)

Every VERIFIED corruption in this area came from bytes leaving git's conversion path: cp949 Korean text became U+FFFD after a UTF-8 string round trip, the default `TextDecoder` dropped BOMs (daemon-text-handling-corrupts-cp949-bom), and a spliced blob written from working-tree text bypassed the clean filter (splice-text-from-worktree-leaks-secret). So:

1. File bytes are Node `Buffer`s end to end. Nothing in the daemon writes a file from a JS string.
2. A blob id is computed, and a blob created, only by (a) the private-index `git add` of a staged copy (it writes objects, so only at the steps of (2b)), (b) `git hash-object [-w] --path=<p>` of a staged copy or of stdin, under the glossary §18 flags (required filters, `attr.tree`), or (c) `git hash-object [-w] --stdin --no-filters` for bytes that are already stored form: `canon` output, insertion-concat output and restore output. Route (c) never receives working-tree bytes. Every git command that may run a filter (routes (a) and (b), `cat-file --filters`, D4) runs with cwd = the worktree root, because a driver may name its script by a repo-relative path (glossary §25 F12).
   - **(2a) No git process opens a user's working file** (glossary §26.1 W1, one code path on every OS). When routes (a) and (b) hash a file's content, they hash a *staged copy*: the daemon reads the file with one short read (open share-all, read the whole file, close), compares size and mtime before and after (re-read once if they changed, else the path is skipped this tick), writes the bytes to `<gitdir>/cowork/tmp/stage/<path>` and hashes that copy with `--path=<p>`, so the `EPOCH_BASE` attributes and the team's filters apply exactly as for the real path. The handle on the user's file lives for that one read call (W3). Measured cause: `git add` memory-maps the file while hashing, and a concurrent truncating editor save fails with Win32 1224 (11.4 failed saves per 1,000 with git on the working file, 0 of 963 in-place saves with staging, W1). The read mechanics and the 0-byte capture guard (the shrink guard, W2) belong to 01-engine; this chapter requires the staged copy for every hash it asks for: snapshot, D6 admission, D4 determinism, the `filter-failure` re-run (§3.4) and the collision capture (DAT-29).
   - **(2b) Snapshot ticks write no objects** (glossary §26.1 W6: 205 MB of loose objects in 20 min when every 2.5 s snapshot of a changing 1.3 MB file wrote its blob). At a snapshot tick, routes (b) and (c) run without `-w` and compute ids only, including the id of a `canon` output; route (a) does not run. Objects are written (`-w`, or route (a)) only at ready-pair capture, publish, apply and hold-record creation, from bytes whose id equals the id computed at the tick (01-engine owns how those bytes are kept until then). These four are the only object-writing steps (glossary §26.1 W6). A hook request for named paths (06-claude PostToolUse claim confirmation, 04-regions mapping by `diskSnapshotId`) is not one of them: it gets ids (routes (b)/(c) without `-w`) and the staged copy's in-memory bytes, and writes no object. D4's idempotency check writes only to a scratch object directory, never to the repository object store (§3.4, D4 step 2). Soak gate: loose-object growth ≤ 50 MB per busy peer-hour (W6, 11-testing).
3. Disk bytes come from blobs only through `git cat-file --batch --filters` (the writer, ENG-; cwd = the worktree root, glossary §25 F12) so the user's smudge filter and EOL conversion apply. The writer uses only the two-phase form (rename the target to `.old`, rename `.new` to the target), which succeeds while another process holds a share-all read handle (glossary §26.1 W4).
4. JS decodes text only for read-only analysis (region tables, tripwires, matched-line checks) with `TextDecoder('utf-8', {fatal: true, ignoreBOM: true})`. A decode failure means "not UTF-8": callers fall back (REG- uses raw `0x0A` rows; DAT-42 skips the UTF-8 tripwire leg).
5. Paths come from git only through `-z`/`--porcelain` output with `core.quotepath=off` (glossary §18); paths from hooks go through `canonPath` (DAT-34). Outcomes are classified by exit code and structured output, never by message text (glossary §18; path-quoting-and-git-locale VERIFIED octal-quoted Hangul).

### 3.2 Stored form and canon

The stored form is a property of each existing path, read from `ref(p)`. Without it, VERIFIED one-line edits became 280/280 and 500/500 whole-file diffs (e7, e14) and conflicted with unrelated edits 27 functions away; `-X renormalize` "fixes" that only by flipping the stored form (DH2: an i/crlf blob went to LF with both sides keeping CRLF) and runs the secret filter six times per merge (DH1). No `core.autocrlf` value can reproduce CRLF from an LF working file (e14), so per-peer or team-pinned autocrlf cannot work alone. A post-hash byte transform can, and once every blob the daemon creates is canonical, peers' differing autocrlf settings no longer matter for published blobs.

**Algorithm D1 — canon(new, ref)** (pure; input and output are stored-form bytes)

1. If `ref` is none, or the path is binary or filtered, or `new` is binary: return `new` unchanged.
2. BOM: if `form(ref).bom = yes` and `new` lacks `EF BB BF`, prepend it; if `form(ref).bom = no` and `new` starts with it, strip it.
3. Endings by `form(ref).eol`:
   - `LF`: replace every `0D 0A` with `0A`.
   - `CRLF`: replace every `0A` not preceded by `0D` with `0D 0A`.
   - `NONE`: no change.
   - `MIXED`: no change, but compute the matched-line check: diff `lines(ref)` and `lines(new)` with endings ignored (Myers diff in the worker); if any matched (equal) row pair differs in its ending, other than the presence of a terminator on the last row, return `REFUSE(eol-bom)`.
4. Tripwire: `lines(output)` ignoring endings and BOM must equal `lines(new)` ignoring endings and BOM. A failure is a bug: return `REFUSE(eol-bom)` and write a doctor record.
5. If output ≠ new, hash it with route (c) of §3.1: id only at a snapshot tick, object written only at the steps of §3.1 (2b) (glossary §26.1 W6).

Properties: `canon(canon(x, r), r) = canon(x, r)`; for `LF`/`CRLF`/`NONE` refs `form(canon(x, r)) = form(r)` when x is text; no row content changes. Region and claim logic read stored blobs by rows only (REG-), so EOL-only hunks cannot exist in published blobs (edit-eol-normalization-false-causer, transform-holds-as-hunks: canon is a per-path function, never a hold of line hunks).

**Where canon runs.** (a) Snapshot: for every path in `diff(A, S_raw)` that is an existing text path, `S_disk[p] := canon(S_raw[p], ref(p))` (ENG-26 builds S_disk in a scratch index while the private index keeps S_raw, glossary §3). (b) Concat output (DAT-42). (c) Restore output (DAT-45). Merges are plain `merge-tree`, never `-X renormalize`.

**New paths** (no ref): new paths are hashed in a call of their own (route (b) of a staged copy at a snapshot tick; route (a) or (b) with `-w` at the steps of §3.1 (2b), glossary §26.1 W1/W6) with `-c core.autocrlf=input`, unless `EPOCH_BASE` `text`/`eol` attributes decide, which yields LF blobs for text. No canon.

**Disk repair.** If canon changed a LIVE path's blob (`S_disk[p] ≠ S_raw[p]`, e.g. a Write dropped the BOM of the BOM+CRLF file), the published blob is already canonical, but the disk is not: the disk keeps a form that no published blob has, so every later stat change of p repeats the staged copy, the hash and canon for it (seeded-index-rehash-every-cycle cost), and the next Claude Read sees a different form. At the first quiet moment (no fence/lease on p, S_raw[p] unchanged across 2 snapshots) the daemon calls `writeLocal(p, S_raw[p], S_disk[p])` (ENG-37); after the write the daemon records p's new stat data against `S_disk[p]`, so p is no longer stat-dirty and the next ticks neither copy nor hash it (glossary §26.1 W1, W6). The affected seat is told once per (seat, path, episode) with `EOL_REPAIRED(path, bom, eol)` through PostToolUse additionalContext (§2 "Message codes"; template owned by COO-); CCI- applies its "file modified by user" countermeasure.

**MIXED files.** v1 refuses ending changes on unchanged rows of `MIXED` files: a `LIVE` path becomes one PATCH record (ON_DISK, guard `eol-bom`, released automatically when a later snapshot passes canon; re-evaluated on every snapshot) and MASK keeps `S_pub[p] := A[p]` (glossary §3: held path) until then; a path of any other class is already masked by its class and gets no record (§2). Because `eol-bom` is a whole-path guard, the rest of the change-set waits with it (05-holds HLD-42). Because Claude Code's Edit rewrites every ending of the file (VERIFIED edit-eol-normalization-false-causer), Claude effectively cannot edit a `MIXED` file in live mode; doctor lists `MIXED` text files at start with the fix "normalise line endings with an ordinary git commit".

**Form changes are git commits.** No cowork verb changes a stored form (changed per glossary §15: `/cowork eol` removed). A human commits the renormalisation on the branch; it reaches live through a base move (ENG-). If live has no edits on that path relative to the live base, the base-move merge is clean and live takes the new form; otherwise the whole-file EOL change conflicts and becomes a base-move conflict (glossary §22: hold, block save, tell the committer; the hold is ENG-48's base-move record). DAT-10 adds guard `eol-bom` to that record and has it reported with message code `EOL_CHANGE_VIA_GIT(path)` (glossary §19 registry; a guard name is never a `reason_code`) so the message can say: "save first, then commit the renormalisation while nobody is editing these files".

**Incoming form check (Algorithm D2).** For every live commit C on the first-parent chain `LA_C..TIP` and every text, unfiltered path p changed by C that exists in C's first parent P: if C is an ordinary commit, `form(C[p]) = form(P[p])`; if C is a base-move commit with second parent X, `form(C[p]) ∈ {form(P[p]), form(X[p])}`. A violation means a non-conforming writer (the VERSION publish pause, glossary §8, should prevent mixed versions). The path is not applied: it becomes an INCOMING record with guard `eol-form` (released automatically when TIP's form for p is conforming again), and ENG- defers the write group (glossary §3; INV-GROUP: the deferral defers the whole group). Both sides learn of it through the folded `hold` op.

**Save form check.** Save (08-lifecycle §3.7 step 5, LIF-21) runs `formCheckSave(Hb, L)` on every save candidate `L` before T0 and `checks.save`: for every text, unfiltered path present in both the branch head (`Hb == Hr`, glossary §12) and `tree(L)` with different blobs, the forms must be equal. A candidate that fails is skipped and is never `Lk`, so the committed `tree(Lk)` always passes; only when every candidate fails is save refused with `SAVE_EOL_BRANCH_FORM(paths)` (`paths` of the newest candidate). With canon and D2 this cannot fire for conforming peers; it is the last check before the real branch.

### 3.3 Attribute source

Every daemon git command that reads attributes runs with `-c attr.tree=<EPOCH_BASE>` (glossary §18): `add`/`update-index --add`, `hash-object --path`, `read-tree` into a private index, `checkout-index`, `cat-file --filters`, `merge-tree`, `merge-file --object-id`, `check-attr`, and any `diff` used for hunks or claims. The exemption is route (c) of §3.1 (`--no-filters`, reads no attributes). `EPOCH_BASE = live_base(LA_C)`; it changes at save completion and at every base move, and all attribute-derived data of this chapter (binary/filtered classification, filter drivers, merge attributes, scope attributes) is recomputed before the next snapshot after a change.

Why everywhere, not only on merges: DH4 VERIFIED that with the working-tree `.gitattributes` emptied by a peer's edit, `add` without `attr.tree` stored the plaintext `k=REAL v2`, and with `attr.tree=<base>` stored `k=HIDDEN v2` (gitattributes-edit-unfilters); e9 VERIFIED that `merge-tree` otherwise reads the local working tree, so the same three trees merged as `union` on one PC and conflicted on another (merge-attr-source-nondeterminism). DH4 also VERIFIED that personal attributes (`$GIT_DIR/info/attributes`, `core.attributesFile`) still apply with `attr.tree` set. Personal attributes therefore stay in effect; they can only change this peer's own decisions (e.g. a personal `cowork-sync=off` makes a path UNMANAGED here), never what other peers receive. `.gitattributes` itself is quarantined (glossary §16), so it changes only through a git commit and a base move.

**Merge attributes.** `merge=text|binary|union` declared at `EPOCH_BASE` are honoured by git itself inside `merge-tree`, deterministically because attributes are pinned. cowork never invokes union itself. A path whose `merge` attribute names a driver configured in the effective config (`merge.<name>.driver`) is `SAVE_ONLY` (reason `merge-driver`): its local changes never enter `S_pub`, so `merge-tree` runs the driver only on the apply side when a branch move changes a path the user has edited locally, which is exactly when the user's own `git pull` would run it. Doctor lists such paths.

### 3.4 Clean/smudge filters

Failing or missing clean filters are the only VERIFIED way for a secret to reach the remote: `add` exits 0 and stores plaintext when the tool is missing or the driver is undefined (filter-passthrough-leak e1, secret-filter-passthrough t1, secret-filter-fails-open-in-daemon-env, peer-normalization-secret-leak e2), and after a `required=true` failure `write-tree` silently returns the stale tree (t6). `-c filter.<d>.required=true` on the command line forces exit 128 even when the clone never set it (t7). SPIKE-0 confirmed this on a pilot team's real filter (glossary §25 F12, MEASURED): with `required=true` every failure mode (missing command, non-zero exit, empty value, undefined section) made `git add` exit 128 with the index byte-identical; without it a failing or undefined filter silently stored the plaintext secret with exit 0; round trip and idempotency held for 21/21 files.

**Algorithm D3 — discovery** (at start and whenever `EPOCH_BASE` changes):
1. `git -c attr.tree=<EPOCH_BASE> ls-files -z | git check-attr --stdin -z filter` (both through `runGit`), plus every driver named in `$GIT_DIR/info/attributes` or `core.attributesFile`.
2. The driver set D feeds glossary §18 (`-c filter.<d>.required=true` for every `d ∈ D` plus `filter.lfs`).
3. The `config_fingerprint.filter driver hashes` of the `join` op are SHA-256 of each driver's effective `clean`/`smudge`/`process`/`required` values (no paths, no user names).
4. For each `d ∈ D` the daemon resolves, at start, the PATH entries that d's configured commands need (a command given as a bare program name, such as `python`, needs the entry that resolves it; a command with an absolute path needs none) and keeps exactly those entries in DAEMON_ENV; doctor shows them (glossary §25 F12). Every git command that may run a filter runs with cwd = the worktree root (glossary §25 F12: a pilot team's driver names its script by a repo-relative path and fails with rc 128 from any other cwd).

**Algorithm D4 — preflight** (start and doctor; runs in the daemon's own environment, DAEMON_ENV of glossary §18 built per SEC-05 with the D3 step 4 PATH entries, cwd = the worktree root). *(Changed in rev 2.3: the previous steps, a scratch work tree checked with `update-index -q --refresh`, are removed. SPIKE-0 measured that the scratch tree carries no attributes, so the filter never ran (0 filter processes), that `-q` hid "needs update" while the command exited 0, and that the team's repo-relative driver fails outside the real work tree; glossary §25 F12, `spikes/RESULTS.md` finding 1.)* For each `d ∈ D`: `clean` and `smudge`, or `process`, must be defined (check `defined`). For each filtered path p (≤ 200 paths; beyond that a seeded rotating sample of 200, glossary §20), the base blob B is `HEAD:p` at `/cowork start` (glossary §26.2 item 3) and `EPOCH_BASE[p]` while live (doctor and the canary), and every command of the check runs with `-c attr.tree=` set to the same commit, so blob and attributes always come from one commit (DAT-13). No check compares a filter-converted id with a stored blob id, and none hashes a working file against a blob (glossary §26.2 item 3; ENG-11 VERIFIED that both misreport `i/crlf` files, a40da32 vs 32315a1):
1. **Round trip** (clean∘smudge = id; check `round-trip`): `cat-file --filters --path=p B | hash-object --path=p --stdin` must equal `cat-file blob B | hash-object --path=p --stdin`. Both sides pass through the same `--path=p` conversion (glossary §26.2 item 3, "both sides converted by the same path"): for a blob in its canonical stored form the right side is B itself, and for an `i/crlf` blob the paired form still compares like with like (`spikes/RESULTS.md` C2: the spike's 21/21 pass compared against the stored id, which was safe only because that repository has no `i/crlf` files).
2. **Idempotency** (clean∘clean = clean; check `idempotency`): let `c = cat-file blob B | hash-object -w --path=p --stdin` (the clean of the stored bytes; normally `c = B`); then `cat-file blob c | hash-object --path=p --stdin` must equal `c`. Object-store bytes only. Both commands run with `GIT_OBJECT_DIRECTORY=<gitdir>/cowork/tmp/d4-objects` and `GIT_ALTERNATE_OBJECT_DIRECTORIES=<the repository object store>`, so a `c ≠ B` object lands only in that scratch store, which D4 deletes when it ends; the repository object store is never written by D4 (glossary §26.1 W6: objects only for ready-pair captures, publishes, applies and hold records).
3. **Determinism** (check `determinism`; glossary §25 F12 "run twice gives the same id"): one staged copy of p's working file (§3.1 (2a); glossary §26.1 W1 forbids running git on the working file itself), hashed twice with `hash-object --path=p` and no `-w`, gives the same id both times. A non-deterministic clean (for example a fresh random IV on every run) would publish a phantom change on every snapshot.
4. **Positive control** (check `ran`): while steps 1–3 run, git's structured trace (`GIT_TRACE2_EVENT` to a file under `<gitdir>/cowork/tmp/`) must show at least one `child_start` event whose argv contains a configured command of d (git runs it through a shell, so the argv is `sh -c <command>`), for every `d ∈ D` with a sampled path. Zero runs for a driver is a failure. This is the only use of tool output beyond exit codes in D4, and it can only make start stricter (glossary §18: such output may make handling stricter, never cause a retry, publish or lift). It exists because a preflight that never runs the filter passes every other check (`spikes/RESULTS.md` finding 1).
5. **Canary** (check `canary`): if the user's index holds B for p and its cached stat data equals the file's current `lstat` (read from the index file only, with `GIT_OPTIONAL_LOCKS=0`; no git process opens the working file, glossary §26.1 W1), then `DISK_EQ(p, B)` (glossary §3; ENG-11, through a staged copy) must hold.

Any failure refuses `/cowork start` for this peer with `START_FILTER(driver, path, check, fix)` and no read-only mode (a read-only mode would still smudge on receive). Join is refused only on this; differing `core.autocrlf`/`eol` between peers is published in the fingerprint for display and is not a refusal, because canon makes published blobs identical (peer-normalization-secret-leak's autocrlf variant is covered by canon).

**While live.**
- The canary (step 5) repeats every 10 min on the sample, and the filter fingerprint is recomputed whenever a git config file changes (mtime/size). A canary failure or fingerprint change sets FREEZE `CONFIG` with detail `filter` (glossary §8: a filter change is a start-time invariant; lifted by `/cowork resume` after doctor passes). While frozen only the glossary §8 allowed operations run (fetch and fold, base moves, human `/cowork resolve`, board-only freeze/health events, answer- and release-class ops, hold mirrors); no snapshot is published.
- **Snapshot failure:** a snapshot hash (routes (a) or (b) of §3.1 over staged copies, glossary §26.1 W1) that exits non-zero while its list contains filtered paths fails the snapshot: ENG- runs no `write-tree`, `commit-tree`, board write or push in that cycle. The daemon then re-runs the hash one filtered path at a time (glossary §18: the failing path is located by exit code, never by parsing `fatal: <p>: clean filter` text) and runs the canary for that path's driver. Canary fails → FREEZE `CONFIG` (detail `filter`). Canary passes (the filter rejects this file's content) → each failing path becomes a `local_only` PATCH record (ON_DISK, guard `filter-failure`, no `h1`: glossary §9 makes `h1` optional for `filter-failure` records because the bytes cannot be hashed safely and stay on the user's disk; HLD-03) and is excluded from later snapshots while the record is non-terminal. `filter-failure` is a DECISION guard (05-holds Table 3, owner of the closed guard table, glossary §9). Its named event is a successful per-path re-run of the required clean filter on a staged copy of p's current disk bytes (§3.1 (2a)), checked at each snapshot of p (whenever p's stat data changes) and at human `--publish`; it is otherwise released only by the local human's `--discard` (HLD-58 Table 4: `A[p]` is written over the unfiltered local bytes through `writeLocal`, which publishes nothing, so INV-SECRET holds). `--publish` is refused with `HOLD_GUARDS_REMAIN` while the re-run still fails (05-holds Table 1); no other command releases it. The board receives only the content-free stub (glossary §7 `hold` op without `held/` entries and without blob oids). The record is never auto-parked (S6) and never blocks `/cowork stop` (glossary §22, `--export` row). The human and the affected seat are told with `FILTER_FAILURE_HELD(id, path, driver)` (§2 "Message codes"; templates COO-, UX-).
- **Apply failure:** a `cat-file --filters` (smudge) failure defers the write group (ENG-) and runs the driver canary; a canary failure sets FREEZE `CONFIG` (detail `filter`).
- Filtered paths get whole-file claims and holds only (REG-), no canon, no concat, never `-X renormalize` (which executes the filter, DH1). Viewers (`cowork_show`, `/cowork show`) show only the stored (clean) form. Logs, board records and doctor bundles carry oids, paths and row numbers only, never content.

### 3.5 fsmonitor and untracked cache

`-c core.fsmonitor=<v>` is explicit on every daemon git call (glossary §18); the user's configured value is never inherited, because a string value is a hook executable path (an execution surface, SEC-). `v = true` (git's builtin daemon) only when all hold: the platform is Windows or macOS, or Linux with git ≥ 2.55; the worktree is on a local, non-network filesystem; and `git fsmonitor--daemon status` or the first query succeeds. Otherwise `v = false`. DH5 VERIFIED that the builtin daemon serves a non-default `GIT_INDEX_FILE` (fsmn extension). fsmonitor is only a hint: a full stat rescan runs every 10 min, after a daemon restart and after any fsmonitor error. If cowork started the fsmonitor daemon and the user had not enabled fsmonitor, `/cowork stop` stops it. `false` is always safe: the persistent stat-fresh index already meets the budget (54 ms vs 750 ms, VERIFIED e1/e3).

`-c core.untrackedCache=true` is passed on the private index because U10 enumerates untracked files every cycle. This is ASSERTED, not verified with a private index; the TST- perf gate on a 5,000-file repo with ignored `node_modules`/venv trees must confirm it, otherwise the value is `false`.

### 3.6 Sync scope (U10)

**Scope classes** (glossary §3; DAT-23). Each path has exactly one class, evaluated per snapshot and per apply from the configuration at `EPOCH_BASE`, `EPOCH_BASE` attributes, the entry mode, the hold registry and disk facts. The glossary names the classes and their typical members; this table fixes what each class means for bytes:

| Class | Local changes | Incoming changes (TIP) | Typical members |
|---|---|---|---|
| `LIVE` | published as part of P (glossary §3) once their CS is ready and its publication group is unheld | written by the writer | everything tracked in live and not below |
| `SAVE_ONLY` | masked: `S_pub[p] := A[p]`, never in P, never in a save (a save commits `tree(Lk)`, which holds the team's entry); they reach the branch only through an ordinary git commit and push (glossary §3) | written by the writer like LIVE (they arrive only through branch moves) | `.gitignore` at any level, custom-merge-driver paths, blobs ≥ 50 MiB |
| `UNMANAGED` | masked; the path is not even hashed (S_disk keeps A's entry) | never written or deleted; `A[p]` follows `TIP[p]` without a write (ENG-) | `filter=lfs`, `linguist-generated`, `cowork-sync=off`, `sync.exclude` matches, existing `160000` (submodule) and `120000` (symlink) entries, tracked paths whose name fails SEC-35 `validPath` |
| `QUARANTINED` | masked (glossary §16); their local bytes never reach any remote ref through cowork (S8, INV-SECRET) | not applicable (INV-GROUP): an INCOMING record with guard `quarantine-review`, written only after the local human's `/cowork review <id> --accept` with preview/confirm (glossary §15; SEC-32, SEC-33); the rest of the write group applies | glossary §16 list |
| `NOT_ADMITTED` | new path never added; nothing to mask | an incoming path that exists locally is a collision (DAT-29) | ignored, secret-like (new file), temp, too-large, nested repo, new symlink/submodule, portability |
| `LOCAL_ONLY` | masked: covered by a non-terminal `local_only` record (`filter-failure`, `secret-scan`, a record on a secret-like path, HLD-03; host secret rejection, SEC-17) | an incoming merge that would displace it is deferred (HLD-55, guard `local-only-conflict`) | — |

`SAVE_ONLY ∪ UNMANAGED` is the glossary's "save-only set" used by MASK and INV-MASK; MASK (glossary §3) also resets quarantined and `local_only` paths and held regions to `A[p]`. Nothing local in either class ever reaches the live chain or a save (save commits `tree(Lk)`, which holds the team's entry); such paths change only through ordinary git commits and branch moves. UNMANAGED paths are not "synced paths" for INV-CONVERGE. Why UNMANAGED is never written: regenerated documents differ per PC by timestamps and absolute paths, so writing or merging them yields a conflict record per file per regeneration (generated-file-churn); LFS paths would need the LFS endpoint and pre-push hooks, which live pushes skip (lfs-and-prepush-hooks, lfs-paths); a gitlink or symlink cannot be "written" by the file writer at all (gitlink-ping-pong, symlink-placeholder-edit). After an adopt, `git status` may show an UNMANAGED path as modified (the disk holds the user's own copy); README and status explain this.

**Leaving UNMANAGED (DAT-26).** Because `A[p]` follows `TIP[p]` without a write, an UNMANAGED path's disk bytes may be older than `A[p]` (a branch or teammate change arrived while it was unmanaged). When p's class changes from `UNMANAGED` to any other class (a `sync.exclude` entry, `linguist-generated`, `cowork-sync=off` or `filter=lfs` removed at a new `EPOCH_BASE`, or a mode change away from `120000`/`160000`), the daemon MUST reseed `A[p]` with ENG §3.14's lost-state per-path primitive before the first snapshot that hashes p in its new class (and so before HLD-'s revert detector reads that `S_disk`): `A[p] :=` the newest version of p on TIP's first-parent chain that matches the disk (`DISK_EQ`, MANY CANDIDATES; ABSENT matches ENOENT); no match → `A[p] := TIP[p]` and the disk bytes become a `restart` PATCH record (held, not published, not overwritten; the local human decides; `local_only` with a content-free stub when the new class is not `LIVE`, glossary §9). 01-engine runs this reseed in its snapshot scope step (ENG-06 lists it). The difference between the stale disk and the old `A[p]` is never treated as a local delta. Without this, the next snapshot would see `diff(A, S_disk)` as a full revert of every change made to p while it was unmanaged, and HLD-27 taints it only while the journal lines are younger than the HLD-25 retention, so an older change would be reverted for every peer.

**Why `.gitignore` is SAVE_ONLY.** A teammate's live `.gitignore` edit would change every peer's ignore rules mid-session and turn a previously ignored local file (`.env.local`, a dump) into an auto-admitted new file on every PC, the same shape as gitattributes-edit-unfilters. As SAVE_ONLY, each peer's ignore rules are `EPOCH_BASE`'s plus only its own human's local edits; a teammate's `.gitignore` change reaches the branch only when that teammate commits and pushes it with git, and arrives on this PC with the next branch move (a `/cowork save` never carries it, glossary §3 SAVE_ONLY).

**Algorithm D5 — classification** (first match wins; the matching row also gives the not-shared reason):

For a path in `A` or `TIP` (tracked in live):
1. glossary §16 quarantine set → `QUARANTINED` (`quarantine`).
1a. the path string fails 09-security SEC-35 `validPath` (its path-string clauses: repo-relative POSIX, NFC, no `..` segment, no leading `/`, no drive letter, no `:`, no `\`, no NUL, ≤ 4,096 bytes) → `UNMANAGED` (`portability`). The test uses only the path string, so every peer classifies the path identically, and no claim op or hold op is ever written for it (the fold would reject such an op as invalid, PRO-/SEC-35; 02-protocol T-PRO-05). The stricter D7 rules are not applied to tracked paths here, so a Linux-only team keeps syncing a tracked `aux.c`; a Windows peer that cannot create `aux.c` gets an `unmaterializable` record for it (§3.7).
2. mode `160000` → `UNMANAGED` (`submodule`); mode `120000` → `UNMANAGED` (`symlink`).
3. `filter=lfs` → `UNMANAGED` (`lfs`).
4. `linguist-generated` set or `cowork-sync=off` → `UNMANAGED` (`generated`).
5. matches `sync.exclude` → `UNMANAGED` (`excluded-by-config`).
6. basename `.gitignore` → `SAVE_ONLY` (`save-only`).
7. `merge` attribute names a configured custom driver → `SAVE_ONLY` (`merge-driver`).
8. local file (its `lstat` size, taken before any staged copy, so a huge file is never copied to `tmp/stage/`, glossary §26.1 W1) or `TIP[p]` ≥ 52,428,800 bytes (50 MiB, glossary §20) → `SAVE_ONLY` (`huge`).
9. covered by a non-terminal `local_only` record → `LOCAL_ONLY` (reason `secret-scan` or `filter-failure` per its guard, else `secret-like`).
10. otherwise `LIVE`. Tracked-in-live paths are exempt from the 1 MiB new-file cap (U10 read as new-files-only; a pilot team's 1.3 MB hot file must sync).

For a new path (on disk, in neither A nor TIP), see Algorithm D6.

**Algorithm D6 — new-file admission** (every snapshot):
1. Enumerate with `GIT_INDEX_FILE=<abs private index> git ls-files -o --exclude-standard -z`. This honours the repo `.gitignore` files on disk, `info/exclude` and `core.excludesFile` (the publisher's full effective ignore rules; sec T5b VERIFIED that personal excludes differ between clones, so the following guards do not rely on them). Never `add -A` (untracked-sweep, untracked-sweep-editor-temp-and-secrets VERIFIED).
2. An entry covered by a non-terminal `collision` record (DAT-29: TIP added this path and the local file was left untouched) is skipped: it is never added to the private index, never hashed, and never enters `S_disk` or P; only its `collision` record handles it. For every other entry, first match wins → `NOT_ADMITTED` with that reason:
   1. entry is a directory (nested repository or worktree; git lists it with a trailing `/`) or lies under `.claude/worktrees/` → `nested-repo` (wt/e12 VERIFIED gitlinks).
   2. editor/OS temp list (case-insensitive basename): `*.swp`, `*.swo`, `4913`, `#*#`, `.#*`, `*~`, `*.orig`, `*___jb_tmp___`, `*___jb_old___`, `~$*`, `~*.tmp`, `.DS_Store`, `Thumbs.db`, `desktop.ini`, `.vs/**` → `temp` (e12 VERIFIED).
   3. glossary §16 secret-like list (case-insensitive basename) and not listed exactly in `sync.allowSecretLike` → `secret-like`.
   4. glossary §16 quarantine set, or `lstat` shows a symlink (new `120000`) → `quarantine`.
   5. `filter=lfs` → `lfs`; `linguist-generated`/`cowork-sync=off` → `generated`; `sync.exclude` → `excluded-by-config`; `sync.include` non-empty and no match → `not-included`; basename `.gitignore` → `save-only`; custom merge driver → `merge-driver`.
   6. fails the portability predicate (DAT-32) → `portability` (and a record, DAT-33).
   7. size > `sync.maxNewFileBytes` (default and maximum 1,048,576) → `too-large` (the `lstat` size, before any staged copy).
3. Admitted entries are hashed from staged copies (DAT-07 settings; §3.1 (2a), glossary §26.1 W1; ids only at a snapshot tick, W6) and every new blob passes the 09-security content scan (`scanSecrets`, glossary §16); a hit makes the path `LOCAL_ONLY` (`secret-scan`: a `local_only` record, HLD-03; SEC-07 repeats the scan before every push).
4. The 1 MiB cap applies only at first publication; once in live the path is tracked-in-live.
5. A sudden flood of admissible new files (e.g. a `node_modules` without ignore rules) is caught by the mass-change breaker (FREEZE `MASS`, glossary §8 and §20; run by HLD- on the new `S_disk`), not by a separate cap.

**Configuration semantics** (`.cowork/config.json` at `EPOCH_BASE`, glossary §17; schema and validation owned by SEC-):
- Globs use gitignore-style wildmatch without negation: a pattern without `/` matches the basename at any depth; a pattern with `/` matches the repo-relative path from the root; `**` crosses directories; matching is case-sensitive on canonPaths. The built-in temp and secret-like lists match basenames case-insensitively.
- `sync.include`: if non-empty, restricts auto-admission of new files to matches; it never removes tracked-in-live paths.
- `sync.exclude`: makes matching tracked paths `UNMANAGED` and matching new paths `NOT_ADMITTED`. It is also how a team extends the built-in temp and secret-like lists.
- `sync.allowSecretLike`: exact canonPaths admitted despite a secret-like name; the content scan still applies; doctor shows a WARN on every run.
- `sync.maxNewFileBytes`: ≤ 1,048,576.
- `merge.insertionMerge`: globs enabling the concat fast path for grammarless text (default `CHANGELOG*`, `HISTORY*`, `NEWS*`, `*.md`, `*.txt`).
- A config change takes effect for every peer when it reaches `EPOCH_BASE`. Paths that become `UNMANAGED` are carried through (never deleted anywhere); paths that become `LIVE` join at the next snapshot, and a path that leaves `UNMANAGED` first has `A[p]` reseeded from the disk (§3.6 "Leaving UNMANAGED", DAT-26), so a disk that fell behind while unmanaged is never published as a revert. An invalid config at a new `EPOCH_BASE` keeps the last valid one (glossary §17).

**Status.** `/cowork status` lists every present-but-unshared file with its one reason code (UX- renders and caps the list). `ignored` is reported only when a specific path is queried (`/cowork show <path>`, glossary §25.2 item 7; `scopeOf`), because ignored trees are large and deliberate.

**Receive-side collisions (DAT-29).** An incoming path absent from `A` that already exists on local disk but is not in `S_disk` (an ignored or not-admitted untracked file, or one still inside the snapshot quiet period; on case-insensitive filesystems also a case variant) is a collision. (A local new file this peer has already admitted into `S_disk` is local work, not a collision: the merge sees an add/add unit and D8 step 5 takes TIP with a K4 record.) It is never overwritten (ignored-file-overwrite VERIFIED: `read-tree -m -u` replaced an ignored `.env` with exit 0). The writer's creation check (ENG-33: creations only into ENOENT) leaves the local bytes untouched and the path becomes its own INCOMING record with guard `collision` (DECISION); it is not an applicable path of its write group, so the rest of the group still applies (glossary INV-GROUP). Until the local human decides, p is never written, is listed in `not_converged`, and the record stays; the human is told with `INCOMING_COLLISION(id, path)`. The two outcomes map to the 05-holds resolve verbs (glossary §24 default 5; HLD-58, Table 4): `/cowork resolve <id> --publish` = **take the team version**, `--discard` = **keep the local file**. Byte rules of "take the team version": the local file is first captured as a PATCH record through the pinned clean path (`hash-object -w --path=<p>` of a staged copy, §3.1 (2a), glossary §26.1 W1; HLD-03; `local_only` when HLD-03 says so, e.g. a secret-like `.env`), then p is written with `writeLocal(p, <captured blob>, TIP[p])` (ENG-37); a writer CAS failure leaves the `collision` record in place and the command is refused with `HOLD_DISK_CHANGED`. After the write the captured record is OFF_DISK and masks nothing (05-holds MASK step 2 applies only to ON_DISK records, INV-HLD-OFFDISK), so later edits of p publish normally. "Keep the local file" leaves the disk untouched and never writes p; p stays not applicable and the snapshot skips it, both as a new path (D6 step 2) and as a path now present in TIP (D5 would otherwise class it `LIVE`): it is never in the private index, `S_disk` or P, so the local file is never published as an add and in `not_converged` while TIP contains it; the decision is kept on the `collision` record, which ends (SUBSUMED) when TIP no longer contains p or `DISK_EQ(p, TIP[p])` holds (05-holds Table 4 owns the transition: the guard becomes `collision:keep` in a new rev).

### 3.7 Portability

A path valid on macOS/Linux can wedge or half-apply on Windows: `read-tree -m -u` exits 128 and writes nothing on invalid names (poison-path e4), long paths half-apply (unrepresentable-paths-wedge-or-half-apply e11), and case collisions silently drop one file (e9/e13). One fixed strictest rule on every OS keeps a later joiner on any OS safe.

**Algorithm D7 — portable(p, others)** (`others` = LA paths not deleted in this snapshot ∪ other new paths of this snapshot):
1. `p` equals its NFC normalisation (git's `core.precomposeUnicode` on macOS already composes; an NFD name that survives is refused).
2. Every component: non-empty; not `.` or `..`; not `.git` in any case; no `<`, `>`, `:`, `"`, `|`, `?`, `*`, `\` or U+0000–U+001F; no trailing `.` or space; stem (up to the first `.`, trailing spaces trimmed, upper-cased) not in `CON PRN AUX NUL COM0–COM9 LPT0–LPT9 COM¹ COM² COM³ LPT¹ LPT² LPT³`; ≤ 255 UTF-8 bytes.
3. Whole path ≤ 200 UTF-16 code units.
4. Collision key `k(x) = x.normalize('NFC').toUpperCase().toLowerCase()`: no file path and no directory prefix of p has the same key as a different file path or directory prefix in `others`. A case-only rename (old path deleted in the same snapshot) is allowed (VERIFIED to apply correctly).

**Claude side.** A Claude Write/Edit that would create such a path is denied at the gate: G1 (glossary §11 "non-portable path"), outcome `PORTABILITY` with a suggested valid name (06-claude §3.5.2 row 6, which calls `portable()`). The publish-side rule below is the backstop.

**Publish side.** A new path failing D7 (typically created by a human or a shell command) is `NOT_ADMITTED` (`portability`) and gets one PATCH record (ON_DISK, guard `portability`, DECISION, whole-path guard) so the person who meant to share it is told with `PATH_NOT_PORTABLE(id, path, rule)`. The record is `local_only` (content-free board stub): its path is not `LIVE`, and glossary §9 lets only LIVE paths into a mirrored record, so a non-portable name never appears in a board tree or a hold op. The change-set containing it is withheld whole (05-holds HLD-42: a whole-path guard pins the rest of the group), so a move into a non-portable name never publishes the deletion alone. **Release** (05-holds Table 3 "per DAT-"): the named event is a later snapshot in which p no longer fails D7 (the file was renamed or deleted, or the path it collided with under rule 4 was removed; a file that still exists is then an ordinary new path and goes through D6 again), checked at every snapshot; otherwise only the local human's `--discard` (05-holds Table 4) ends it. `--publish` never releases `portability` and is refused with `HOLD_GUARDS_REMAIN` (INV-DAT-PORTABLE).

**Receive side.** A TIP path this OS cannot materialise (D7 rules 2–4 evaluated against this disk; also `ENAMETOOLONG`/`EINVAL` from the writer) is never written and never deleted by a later snapshot (it is not in `S_pub` or P, and `OUT` keeps TIP's entry). It becomes its own INCOMING record with guard `unmaterializable` (PREDICATE: released when TIP no longer contains it or it becomes materialisable; the human sees `INCOMING_UNMATERIALIZABLE(id, path, rule)`), is listed in `not_converged`, and is not an applicable path of its write group, so the rest of the group still applies (glossary INV-GROUP). Windows always runs with `-c core.longpaths=true` (glossary §18).

**canonPath (DAT-34).** Hook-supplied paths (`tool_input.file_path`, Bash/PowerShell targets) are resolved in the canonical root form of glossary §24 default 12 and 06-claude §3.4.1 step 3 (CCI-07): `fs.realpathSync.native` (the on-disk case and long names; for a path that does not exist yet, the nearest existing ancestor is resolved and the remaining components appended), lower-case drive letter, `\` → `/`, NFC. The result is stripped of the main-worktree root in the same form, compared case-insensitively on Windows and macOS (the lower-cased form glossary §24 default 12 uses for endpoint naming is only a comparison key; the canonPath keeps the on-disk case). A path outside the worktree, under `.git/`, or under a nested repo/worktree is not a shared path (CCI- decides what the seat is told).

### 3.8 Special content

- **Binary** (DAT-35): new binary files ≤ the new-file cap are admitted (U10; a pilot team's `.xlsx` files ≤ 1 MiB sync). Binary paths get whole-file claims only (REG-), no canon, no concat; conflicts follow the general rule at whole-file level. An apply blocked by a file lock (Excel, AV, IDE) defers the write group and, after 60 s, becomes an INCOMING record with guard `lock` (ENG-, HLD-54; e2 VERIFIED locks break `read-tree`; glossary §26.1 W4 MEASURED that a `FileShare.Read` holder such as Excel refuses even the two-phase writer, which reports `deferred_locked`). Owner/lock files `~$*` are in the temp list. `.ipynb` is text with whole-file claims (glossary §22).
- **Symlinks** (DAT-36): existing `120000` entries are UNMANAGED (`symlink`): every snapshot keeps A's mode and target. New symlinks are quarantined (glossary §16). On a peer with `core.symlinks=false`, an edit of the placeholder file never publishes (e15 VERIFIED it would publish a symlink whose target is YAML text): a Claude edit is denied at the gate, G1 `SYMLINK` ("edit {target}"; glossary §11 "symlink", 06-claude §3.5.2 row 7), and a human edit of the placeholder is carried through as UNMANAGED (status `not shared (symlink)`).
- **Submodules, nested repos, worktrees** (DAT-37): every snapshot forces each `160000` entry to A's value (`update-index --cacheinfo 160000,<A oid>,<p>`, ENG-26 tree operation); an outgoing tree with a `160000` entry that differs from TIP is rejected (ENG-41 pre-push assert (g)). A submodule pointer changes only through an ordinary git commit; after a branch move that changes one, the human is told to run `git submodule update`. Edits inside a submodule's working directory are never live: its `.git` is a file, so the hook loader treats it as a separate, non-live repo and emits only the `WT_SUBMODULE` note (CCI-07). Directories holding a `.git` file or directory and `.claude/worktrees/**` are outside the shared tree (D6 step 2.1); live mode inside a linked worktree is refused at start by LIF- (`START_REPO_SHAPE`).
- **LFS** (DAT-38): `filter=lfs` paths are UNMANAGED in both directions. `-c filter.lfs.required=true` (glossary §18) makes an accidental LFS conversion fail loudly. If git-lfs is absent, live mode still runs and only those paths are unmanaged.
- **Huge and generated** (DAT-39): blobs ≥ 50 MiB are SAVE_ONLY (`huge`; GitHub warns at 50 MiB, blocks at 100 MiB). Generated content is excluded by attribute or config (UNMANAGED). A pilot team's initial config proposal (SEC-/LIF- first start) excludes a generated-docs folder (for example `docs/generated/**`); CHANGELOG is excluded only if the team confirms it is generated, otherwise insertion-concat covers it. **Churn guard** (thresholds: glossary §20 "Data numbers"): a LIVE path whose blob changed in ≥ 3 consecutive snapshots, each change with no hook attribution (CCI- attribution windows) and each rewriting ≥ 20 % of its rows (or the path is binary), becomes one PATCH record (ON_DISK, guard `generated?`, DECISION, whole-path guard) and is masked until the human answers; the human is asked with `GENERATED_SUSPECT(id, path, excludeLine)`. While the question is open, every change-set whose publication group contains p is PINned with it (glossary §24 default 4; 05-holds HLD-42, `dependency:<id>`), so no half change-set publishes. The two answers (the semantics glossary §24 default 4 assigns to this rule):
  - **"exclude"** (`/cowork resolve <id> --discard`; glossary §25.2 item 2: on a `generated?` record `--discard` means exclude, recorded as guard `generated?:exclude` in a new rev, 05-holds Table 4): the human will stop syncing p. The answer releases the HLD-42 PIN at once, so the rest of those change-sets publishes without p; the record stays non-terminal and keeps p masked (`S_pub[p] := A[p]`, never in P), the disk is not touched, and status prints the exact `sync.exclude` line to commit. When a new `EPOCH_BASE` makes p `UNMANAGED`, the path-class mask takes over and the record ends (SUBSUMED). `--discard` here never writes the disk (05-holds Table 4 special case).
  - **"keep syncing"** (`/cowork resolve <id> --publish`): the guard is released, p publishes with its group as an observed change, and the detector never asks again for that path while the registry holds that resolution.

### 3.9 The conflict function

There is exactly one conflict function. ENG- calls it for every conflict unit of every 3-way merge of local work, identically on the apply side (`M_disk`, LOCAL = `S_disk`) and the publish side (`OUT = merge-tree --merge-base=A P TIP`, LOCAL = `P`, glossary §3; including every re-merge after a CAS loss), and for every path REG `placementCheck` rejects after a clean merge (identity sub-check, REG-24; merge-misplaces-edit-into-same-tail-neighbor VERIFIED: exit 0 moved an edit into a neighbour). By construction it runs only on the peer whose local work meets an already-published TIP, i.e. the later publisher (U4).

**Merge invocation (DAT-40).** `git merge-tree --write-tree -z --merge-base=<explicit base tree> <ours> <theirs>` and `git merge-file --object-id` always carry the glossary §18 flags plus `MERGE_FLAGS`, and never `-X` (no `renormalize`, `ours`, `theirs`), `--union`, or a synthetic attribute tree. `merge.renormalize=false` neutralises a user config that would otherwise flip stored forms (DH2); `merge.directoryRenames=false` keeps an implicit directory rename from moving a local new file into a conflict; `merge.renames=true` makes merge-tree detect renames so that they are reported as rename units instead of an unrelated delete and add. For merges of local work (apply and publish) a local edit does **not** follow a rename made by TIP (glossary §24 default 2): 01-engine §3.10 "Rename carry" rebuilds TIP's renamed path as `TIP[q]` and routes the local source path to this function as a rename unit with stages `(A[p], LOCAL[p], ABSENT)`, which D8 step 5 sends to step 2 (TIP's entry, i.e. the absence, plus a K4 PATCH record holding the local version, created before any disk write). Re-keying the local edit onto the new path is v2 (§1.3). The opposite direction (the local side renamed p, TIP edited p) leaves the result on the local path, which the local change-set already covers. Inputs are object-store trees and blobs only. merge-tree's conflict-marker blobs are never written to disk, an index, a hold or a pushed tree (conflict-tree-applied-or-auto-resolved, conflict-markers-enter-live-ref VERIFIED: markers made a 1.3 MB, 26,436-line Python module unimportable).

**Algorithm D8 — conflict(p, s1, s2, s3, ctx)** → `CONCAT(blob)` or `TAKE_TIP` plus a record. Pure given its inputs, `EPOCH_BASE`, this peer's regionSpec (equal to `teamRegionSpec` whenever the result can be published, glossary §8 VERSION) and the claim view at the lease value (glossary §3).
0. If p is covered by a non-terminal `local_only` record, the conflict function MUST NOT displace it: it returns no result for p and ENG-/HLD- defer the incoming write group (HLD-55, guard `local-only-conflict`). Steps 0a–5 do not run.
0a. **Already concatenated** (glossary §24 default 1 as widened by §25.2 item 8; prevents a self-K4 after a publish-side concat without dropping later local edits). Applies only to a text, unfiltered content-conflict unit with `s1`, `s2`, `s3` all present. Run D9 construction step 1 (`merge-file -p --diff3 --marker-size=M --object-id s3 s1 s2`). If it reports at least one conflict region, and **every** conflict region has an empty base block B and LOCAL's block L occurs as a contiguous run of rows (endings ignored) inside TIP's block T, the result is TIP's entry: `CONCAT(s3)` with no record, no event and no message (nothing is lost: every row of L is already in TIP). If LOCAL also changed rows outside those regions (an edit made after the ready capture, which merge-file merged cleanly), returning `s3` would drop that edit, so the result is instead the merge-file output with each such region replaced by its T block, stored by route (c) of §3.1 and `canon(out, ref(p))`, and accepted only if the D9 step 5 tripwire passes (else continue at step 2, which keeps LOCAL whole in a record). When LOCAL has no change outside the regions, this blob is byte-identical to `s3`. Typical trigger: this peer's own publish resolved p by concat (`C[p] = T + sep + L`) while its apply was coalesced, and the next apply merges `A / S_disk = A + L / C` (01-engine §8 question 7, VERIFIED to conflict).
1. If the unit qualifies for insertion-concat (Algorithm D9) and D9 succeeds → `CONCAT(blob)`. No event, no record, no message (U7 cost).
2. Otherwise (general rule, S2): the result entry for p is `s3` (TIP's entry, including its absence) in OUT and in `M_disk`. On the apply side the writer puts it on disk (deferred while a fence/lease on p is live, ENG-/CCI-).
3. The whole LOCAL side of p becomes one hold record created before any disk write: kind `PATCH`, state `CONFLICTED`, residence `ON_DISK` (the writer's later replacement of p makes it `OFF_DISK`, HLD-), blobs `{s1, s2, s3}` (glossary §9), `paths [p]`, guards `[conflict]` plus `claim-breach` per step 4, `origin` and `cs_ids` of the local change-sets touching p, `local_only` per HLD-03 (true for a secret-like path or a scanner hit) and always when p's scope class is not `LIVE` (e.g. a `SAVE_ONLY` `.gitignore` edited locally and changed by a branch move: glossary §9 lets only LIVE paths into a mirrored record). It is mirrored to the board with the next push (no extra push) as a `hold` op plus `held/<hold_id>/<stage>/<p>` entries for each present stage (no entry for an `ABSENT` side; none at all for a `local_only` record, glossary §7). The minimum granularity is the whole path; 05-holds may widen it to the whole change-set, never narrow it. Record identity and dedupe across re-merges are HLD-. The displacement does not hold back the rest of the change-set: its other paths still publish (glossary §24 default 3; 05-holds INV-HLD-ATOMIC-PUB exception (c)), because the TIP version of p is the team-visible version under S2 and LOCAL is restorable from the record.
4. Tie-break (content = code order, blame = claim order). Map the conflict rows of s1 (the base rows covered by both sides' hunks) through REG's `touch` test against the claim view at the lease value; "earlier/later" is board position (glossary §3):
   - If the LOCAL side's holder has a claim covering those rows that is earlier in board order than any claim covering them on the TIP side's author (or the TIP author has none), the TIP change is a breach: add guard `claim-breach`; TIP still stays on disk and in OUT (nothing is ever rewound, INV-FF); this is K5 and its canonical event and `cid` belong to COO- (canonical-event table, K5 row). Publishing of p on this peer waits for the holder's restore (DAT-45), which 05-holds records as `RESOLVED_PUBLISH` and exempts from the revert detector.
   - Otherwise the causer is the side whose claim on those rows is later in board order, or, with no published claim on either side, the local side (the later code publisher). This is K4: one notice to the later publisher's seat or human (glossary §10; COO- creates the canonical event with `cid = H(winner op id, loser op id)` per glossary §3, where the K4 row of COO-'s canonical-event table fixes winner = the `Cowork-Writer` op id of the TIP live commit that last changed those rows and loser = the record creation op id).
5. Binary, filtered, mode, add/add, modify/delete, rename and directory/file units always go to step 2 (filtered and binary paths are whole-file; there is no stored-form base for add/add). A rename unit includes the source path that 01-engine §3.10 "Rename carry" routes here when TIP renamed a path the local side edited (DAT-40, glossary §24 default 2).

Why whole-path TIP: U4 makes the earlier publication the winner, so the team-visible content must be TIP. Leaving the path diverged until a human acts (option B) breaks U2 and makes later conflicts larger; `--union` produced a SyntaxError on the end-of-file append race and fused two different `def helper` bodies (e5, DH6 VERIFIED); `-X ours/theirs` dropped a side with exit 0 (e5); splicing corrupted bytes and duplicated functions (offset-units-form-drift, move-splice-duplicates). Under this rule nothing is lost: LOCAL is a stored-form blob in a board-mirrored record (or, for a `local_only` record, in the registry on its owner's disk) and TIP is in the live chain (INV-NOLOSS). Whole-path displacement on the 1.3 MB file costs one restore, not lost work.

**Algorithm D9 — insertion-concat** (the only automatic resolution; replaces union and the old CHANGELOG union list). Claude routinely appends helpers at end of file and imports at the end of the import block; without this path every such race costs a Claude turn and a U6 warning (d-shared-insertion-point-collisions, disjoint-claims-textual-conflict VERIFIED). Removing it leaves the system correct, only costlier.

Qualification (all must hold):
- (a) p is a text, unfiltered path; `s1`, `s2`, `s3` are all present; the unit is a content conflict; the `EPOCH_BASE` merge attribute is not `binary`.
- (b) p's language has a grammar in this peer's regionSpec (REG-: python, javascript, typescript, tsx, c_sharp) or p matches `merge.insertionMerge`.
- (c) No peer in the folded live set has a regionSpec different from this peer's (REG-04 disables the fast path otherwise).

Construction:
1. Run `git merge-file -p --diff3 --marker-size=M --object-id s3 s1 s2` (current = TIP, base, other = LOCAL; M = concat marker size, glossary §20 "Data numbers"). Exit code 0 (git found no conflict) → not qualified (step 2 of D8). Exit < 0 → not qualified.
2. Parse the conflict regions by the M-wide markers. Each region has blocks T (TIP), B (base), L (LOCAL). Every region must have B empty (both sides inserted at the same base position and changed no base row), T and L non-empty, and no non-blank row (ending ignored) occurring in both T and L. Any failing region → not qualified.
3. Replace each region by `T + sep + L` (the earlier-published TIP block first; both blocks byte-for-byte). If T's last row has no terminator, append the base's line ending first. `sep` = `max(0, need − (trailing blank rows of T + leading blank rows of L))` blank rows, where `need` = 2 if L's first non-blank row starts a top-level Python definition unit, 1 if it starts a nested Python definition or a C#/JS/TS definition unit (unit kinds from REG `regionTable(s2)`), else 0. Blank rows use the ending of the base row preceding the region (LF if none).
4. Store with route (c) of §3.1, then `canon(out, ref(p))`.
5. Tripwire (all must hold, else not qualified): (i) if `s1`, `s2`, `s3` decode as UTF-8, the output does; (ii) with a grammar: REG `regionTripwire(s3, s2, out)` (REG §3.15 relative forms, theirs = TIP, ours = LOCAL) reports no violation, i.e. `errorCount(out) ≤ errorCount(s3)` and, for every label key, `count ≤ max(count in s3, count in s2)` (no duplicated qualname); the parse completes within the parse budget (≤ 400 ms, glossary §20 "Parse") or the tripwire fails; (iii) every non-blank output row (ending ignored) occurs as a row in s1, s2 or s3. Inside D9 a tripwire violation means "not qualified" (D8 step 2), not a T0 failure; T0 (REG-24) then runs on the OUT that contains TIP's entry.

The grammar tripwire is the same on every publisher: code publishes only from peers whose regionSpec equals `teamRegionSpec` (glossary §8 VERSION: a peer whose regionSpec differs has code pushes paused), and qualification (c) disables concat on any peer that sees a differing regionSpec in the live set (REG-04).

**Restore (DAT-45).** S2 promises "restorable with one command": `cowork_resolve(id, "restore")` (Claude, glossary §15; accepted only for records whose `origin` is that seat, HLD-59) or `/cowork resolve <id> --restore` (human, HLD-58 Table 4). Only the record's owner peer restores. Let `D` = the current disk blob of p (snapshot now; `ABSENT` if missing). Restore never writes while the record is `ON_DISK` with the TIP write still pending; it waits for the writer.
1. Text path, `s2` present and `D` present: `git merge-file -p --diff3 -L "cowork:current" -L "cowork:base" -L "cowork:yours <id>" --object-id D s1 s2` (with MERGE_FLAGS and §18 flags; using `D`, not TIP, keeps any edit made after the displacement).
   - Exit 0: `out = canon(result, ref(p))`; `writeLocal(p, D, out)` (ENG-37). The change is an ordinary local edit attributed to the restoring seat or human, entering a new change-set and passing every publish gate (B1, revert detector, change-set rules). 05-holds transitions the record (RESOLVED_PUBLISH once published).
   - Exit > 0: the result with restore markers is written the same way, and the record gains guard `markers` (held while the disk file has any restore-marker row, re-evaluated every snapshot). While it holds, MASK keeps `S_pub[p] := A[p]` and p is not in P (`markers` is a whole-path guard, so the rest of the restoring change-set waits with it, HLD-42); the restoring seat or human is told with `RESTORE_MARKERS(id, path, rows[])` (§2 "Message codes"; template COO-). When the markers are gone the path publishes as an ordinary edit. This is git's own conflict workflow, confined to this PC and never published (glossary §23 decided default). Restore markers never reach any remote ref, neither as a live blob nor as a `held/` blob (glossary §9, INV-SECRET): a record carrying `markers` is still subject to S6 auto-park after 24 h (glossary §9 names "records of restore markers"), but only once the record is mirrored (glossary §25.2 item 1: a record that is not mirrored, offline or `HOLD_MIRROR_REJECTED`, is never auto-parked and stays on disk and visible). Its PARK is 05-holds' markers park (§3.4 item 3): the disk file with its marker rows is kept in a `local_only` OFF_DISK *marker companion* record on this PC only, so a captured blob that contains a restore-marker row is never a `held/` entry or a blob oid in a `hold` op; DAT-46 covers live blobs, the marker companion covers `held/` blobs. A restore whose written result contains a restore-marker row adds guard `markers` whatever the `merge-file` exit code (restoring a marker companion writes its rows back unchanged, 05-holds HLD-17). The FREEZE rule still applies: while any FREEZE reason is set, Claude's restore is refused (`HOLD_FROZEN`, HLD-) and only the human verb runs (glossary §8 allows human `/cowork resolve`).
2. `s2 = ABSENT` (local side deleted p): `writeLocal(p, D, DELETE)`.
3. `D = ABSENT` (TIP deleted p) and `s2` present: `writeLocal(p, ABSENT, s2)`.
4. Binary path: only the human verb restores. It writes `s2` whole ("take mine") with `writeLocal(p, D, s2)` when `DISK_EQ(p, s1)` or `DISK_EQ(p, A[p])` holds; otherwise it writes nothing and is refused with `HOLD_RESTORE_CONFLICT` (no restore markers are possible for a binary; glossary §25.2 item 3, 05-holds HLD-17). Claude's tool is refused with `RESTORE_BINARY_HUMAN_ONLY(id)` because the line-based revert detector cannot see a binary revert of a teammate's change.

`--handoff`, `--discard`, `--park` and `--publish` on conflict records are the 05-holds resolve verbs (HLD-58 Table 4; offering is COO-) over the same record; `cowork_show(id)` and `/cowork show <id>` render the three-way view from the stage oids (stored form only, DAT-20).

**Marker backstop (DAT-46).** No blob that any push adds may contain a restore-marker row: neither a blob in `diff(TIP, OUT)` nor a new `held/` blob of the board commit that is not already a blob of `tree(TIP)` (the set SEC-07 scans before every push). The ENG- pre-push assert (ENG-41 (e)) also rejects any blob that newly contains a git conflict-marker row absent from both its `P` and `TIP` versions. A failure aborts the push and opens a doctor record.

**Chapter-local invariants:**

- **INV-DAT-CANON** For every text, unfiltered path p in every pushed tree with an existing `A[p]` of form `LF`, `CRLF` or `NONE`: `form(pushed[p]) = form(A[p])`, and `lines(pushed[p])` ignoring endings and BOM equals `lines` of the raw local snapshot ignoring endings and BOM.
- **INV-DAT-BYTES** No daemon code path writes a working file or creates a blob from a JS string; every created blob comes from the three routes of DAT-01.
- **INV-DAT-STAGED** No git process started by the daemon reads a user's working file (it reads only staged copies, glossary §26.1 W1), and no snapshot tick or hook request writes an object to the repository object store (glossary §26.1 W6).
- **INV-DAT-NOMARKER** No pushed blob and no blob written by the writer (except a restore under guard `markers`) contains a merge-tree conflict-marker output or a restore-marker row that is absent from both its LOCAL (`S_disk` on apply, `P` on publish) and TIP inputs; no blob containing a restore-marker row is ever pushed to any remote ref, as a live blob or a `held/` blob (DAT-46).
- **INV-DAT-SCOPE** No pushed tree adds, removes or changes an entry whose class is not `LIVE` relative to TIP, and no apply writes or deletes an `UNMANAGED` or `NOT_ADMITTED` path.
- **INV-DAT-PORTABLE** No conforming peer publishes a new path that fails D7.
- **INV-DAT-PURE** `conflict()` and `canon()` are pure: for equal inputs, `EPOCH_BASE`, regionSpec, git version and claim view they return byte-identical results.
