# F14 — In-flight view: "why hasn't it gone across yet?" (`/cowork status --flow`)

**Status:** proposal (spec delta against glossary rev 2.4 and chapters 01–12). Nothing here is normative until merged by the edits of §8. · **Kind:** pull-only product surface; no op, no push, no new transport, no `status.json` field.

## 1. Purpose

"I can't see your change" is the first support question a team will ask. Today the daemon knows the answer for every path (open CS table, ready pairs, `meta.pending`, the governor's `wait(self)`, holds, scope classes) but `/cowork status` shows only counts (`pending.cs_ready/cs_open/incoming`, 10 §3.5 section 6). F14 prints, for every path whose disk differs from TIP, **exactly one stage per direction** with an estimate or the next thing that must happen, on both PCs, so neither person has to guess. It is shown only when a human asks; Claude gets no extra message.

## 2. User-visible behaviour

**Commands.**
- `/cowork status` — section 6 "Pending" becomes **"In flight"** (`UI_SECTION_IN_FLIGHT`): the counts line, the header line, then at most **5** entries (first in the Domain order below), then `UI_FLOW_SEE_ALL` "… {n} more; `/cowork status --flow` lists all." Masked entries (stage O2) are left out here because section 8 "Not shared" already lists them. With no entry, section 6 prints nothing (UX-07 no-empty-header rule); `UI_FLOW_NONE` appears only under `--flow` (`show <path>` has its own `UI_FLOW_PATH_CURRENT`).
- `/cowork status --flow [--json]` — headline + next line + the "In flight" section only, every entry. Caps: `tty`/`pipe` ≤ **200** entries then `UI_AND_MORE`; `slash` as many as fit the 4,000-char framed output (glossary §19, 10 §3.3) then `UI_TRUNCATED_SLASH`; `--json` ≤ **2,000** entries, rest counted in `data.truncated.flow` (in `slash` mode the array is cut further to the 4,000 cap, UX-04). The daemon's IPC reply carries at most 2,000 entries plus the omitted count, which keeps it inside the 1 MiB IPC frame (09 §3.11).
- `/cowork show <path>` on a `LIVE` path — after `UI_PATH_SHARED_LIVE`, its one or two flow lines, or `UI_FLOW_PATH_CURRENT` "Matches the team version (board height {h})." Non-LIVE paths keep today's view.

**Header and empty lines.** `UI_FLOW_HEAD` "Team version on this PC: board height {h}, fetched {dur} ago." `UI_FLOW_NONE` "Nothing in flight: every file here matches the team version at board height {h}. If a teammate still does not see a change, ask them to run /cowork status --flow and compare board heights." Board height (glossary §3) is the same number on every PC for the same board commit, so two people can compare without any clock (INV-CLOCK).

**Domain.** Entry = (path, direction). `out`: paths of open or ready CSs, of the journaled push intent, of ON_DISK hold records, of this loop's snapshot exclusions, and dirty non-LIVE paths — i.e. where `S_disk[p] ≠ A[p]` or an unpublished capture of p exists. `in`: paths with `A[p] ≠ TIP[p]` as the last iteration's apply trigger computed them (01 §3.11), **except `UNMANAGED` paths**, which are never written (their `A[p]` follows `TIP[p]` in the next apply's state update, DAT-26). A path that differs both ways prints two lines, `out` first: publishing is never delayed by the defer set (06 §3.7.5), so the two directions progress independently. Edits newer than the last snapshot (≤ one loop period, 2.5 s active) are not listed yet. Order: `out` before `in`, then stage row, then, for the stages that print an elapsed time (O4, O5, I3), that time descending, then path (no other age is defined, so no new per-entry timer is kept).

`{s}` is the seat's number on this PC, the same N as 07 §2's actor phrase "session N" and the seat order of status section 9: every seat on this PC belongs to the same human, so a display name would not tell two sessions apart. `{pass}` and `{last}` are the one reason-typed placeholder of their line (10 §3.2 renders one nested code per template through `params.reason_code`), which is why O10 prints two lines; O10 always has a `{last}`, because a latest effect covered by the newest passing capture would have matched O6.

`{pass}` (nested): `UI_FLOW_PASS_READY` "edit {k} is ready to share in about {dur} at the earliest" · `UI_FLOW_PASS_SHARED` "edit {k} was shared" · `UI_FLOW_PASS_NONE` "no edit has passed the edit check yet". `{last}` (nested), from the CS's `last_check` (§4) and its edit-check queue: `UI_FLOW_LAST_CHECKING` "edit {n} is being checked" (a check of a newer edit than `last_check` is running or waiting) · `UI_FLOW_LAST_FAIL` "edit {n} failed check {c} near {wpath}:{line}" · `UI_FLOW_LAST_FAIL_NOLINE` "edit {n} failed check {c} in {wpath}" (check 4, or no line) · `UI_FLOW_LAST_CONFLICT` "edit {n} overlaps a newer team change to {wpath}" (`merge_conflict`) · `UI_FLOW_LAST_INCOMPLETE` "edit {n} could not be checked in time" (`incomplete`, `no_snapshot`, `no_merge`) · `UI_FLOW_LAST_STALE` "edit {n} passed, but failed check {c} near {wpath}:{line} against the newer team version" · four flat skip codes (06 §3.8.4 skip conditions 3–6) `UI_FLOW_LAST_SKIPPED_SHRINK` "edit {n} was not checked (the file looked emptied or cut by half; it is read again)", `_SLOW_READ` "… (the file could not be read fast enough)", `_BASE_MOVED` "… (a teammate's change arrived during the check)", `_BATCH` "… (other edits or a shell command were still running)" · `UI_FLOW_LAST_NOT_YET` "the newest changes have not been checked yet" (`last_check` empty and nothing checking, e.g. a formatter write or a replaced waiting candidate) · `UI_FLOW_LAST_UNKNOWN` "no result since cowork-sync restarted". `{wpath}` is a path-typed param and `{line}` an n-typed param (10 §3.2 has no `path:line` type, and a capped path must not cut the line number). `{c}` = 1–4, explained once per output by `UI_FLOW_CHECK_LEGEND` "Edit checks: 1 new parse error · 2 changed interface, callers not updated · 3 name not defined · 4 large shrink or duplicate name. A failed check while Claude is still working is normal: the change is shared when a later edit passes or the turn ends." Example (en): `src/api.ts (Claude session 2): edit 3 is ready to share in about 4 s at the earliest.` / `later edits wait: edit 5 failed check 1 near src/api.ts:42.`

| I4 | otherwise | `UI_FLOW_IN_NEXT` "{path}: {name}'s change is written at the next apply, in about {dur}." | `max(0, 10 s − Δmono since the last apply)` + up to one loop period (glossary §20) |

A path held back only by apply coalescing takes I4a/I4b whatever reason value the engine stores for it in the defer set (06 §3.7.5 does not name one), never I3 `READ_LEASE`.

`UI_DEFER_*` (one per 01 §3.11 defer reason): `LOCKED` "another program has the file open and locked (for example Excel); written once it is closed" · `FENCE` "a Claude session here is editing it (at most 120 s)" · `TXN` "a Claude session here is running a shell command (at most 120 s)" · `READ_LEASE` "a Claude session here has just read it (at most 5 min)" · `DISK_LOW` "not enough free disk space" · `UNREADABLE` (unreadable, unstable) "it could not be read in a stable state" · `CONFLICTED_LEASED` "a conflict on it waits for a Claude edit to finish" · `EOL_FORM` "its line endings or byte-order mark differ from this PC's form" · `LOCAL_ONLY_CONFLICT` "it would replace a version kept on this PC only" · `MISMATCH` "the file kept changing while being written" · `RACE` "something new appeared at that path; checked again next loop" · `CLOSURE` "it is written together with {other}, which is waiting" · `FILTER_FAILURE` "a git filter (clean or smudge) failed for it on this PC; /cowork doctor names the filter" (Plan 2's `DeferReason` and `Exclusion` carry `filter_failure`; the full product turns it into a `LOCAL_ONLY` record, DAT-18, so it is then O2). The keys cover the same reasons as 07's `{DEFREASON}` #1–#12 (plus `FILTER_FAILURE`), but are a separate human-only set on purpose: the `MR_EV_DEFERRED` / `MR_T_INCOMING_WAITING` mirrors derive their en/ko text mechanically from 07's wording (10 §3.12), while these lines add the bound or the way out ("at most 120 s", "once it is closed"). Merging the two sets is left open (Review notes). For `TXN` without a `meta.pending` entry, I3's `{dur}` counts from the TXN's open. `{name}` = display name of the writer (`Cowork-Writer`) of the newest commit in LA_C..TIP that changes p, as HLD-53 reads the trailers of that range at the apply; the engine keeps that per-path writer from the last iteration, so the query reads no commit.

**Numbers.** Durations are local Δmono, rounded up to whole seconds, "about" for estimates; no wall-clock anywhere. `I3`'s `{dur}` restarts at daemon start; then `UI_FLOW_SINCE_RESTART` "(counted since cowork-sync restarted)" follows the line. Placeholders use the glossary §19 caps (path 80 for `{path}`, `{wpath}`, `{other}`; names 20); `{s}`, `{k}`, `{n}`, `{c}`, `{line}` and `{h}` are n-typed.

## 3. How it uses existing mechanisms

- **Data already in the daemon:** CS table and ready pairs (HLD-34..HLD-41, Plan 2 `ChangeSets`), the push intent (01 §3.12 step 7), `meta.pending` (01 §3.2) with the HLD-54 60 s transient-window anchor as the age, not-applicable paths and `not_converged` (ENG-31), the hold registry and the `{REASON}` key rule (05 §2), scope classes (03 `scopeOf`), the snapshot exclusion map (Plan 2 `Exclusion`), FREEZE/pause state (glossary §8), the governor (02 §3.8: `msUntilWindow`), the time of the last apply (Plan 2 `EngineCore.lastApplyMono`), the apply-coalescing state of 06 §3.7.5 (which the engine must keep to enforce "at most once per 2 min"), seat activity and `PULL_MODE` flags (glossary §3), and, from the last iteration, the in-memory sets `S_disk ≠ A` and `A ≠ TIP` plus the writer of each incoming path (HLD-53 reads the `Cowork-*` trailers of LA_C..TIP at the apply). Where Plan 2 does not yet expose one of these, §9 lists it as an interface ask; deriving it from tree oids instead would need a git process, which FEAT-F14-05 forbids.
- **One new piece of state:** `last_check` per open seat CS (§4). It is the verdict `editCheck` and T0 already return (REG-36, HLD-50: check, path, reason), kept instead of discarded, plus a line number. F12 (`/cowork wrap`) keeps "the latest `editCheck` result per open seat CS" for its own screen; the two proposals share this one store, with §4's shape, whichever merges first.
- **Transport:** the existing authenticated CLI→daemon IPC detail request of 10 §3.5 ("Inputs") gains a `flow` selector (all, or one path), registered in the IPC schema that 09 §3.11 validates every frame against; the reply is codes + typed params only (I18N-01), ≤ 2,000 entries plus the omitted count, inside the 1 MiB frame cap. The CLI renders through the one `render()` (10 §3.2). If IPC fails the section is `UI_DETAIL_UNAVAILABLE`, as today.
- **Not used:** no board op, no fold change, no hold record, no seat carrier (hook output, doorbell, MCP result, systemMessage), no OS notification, no `status.json` field (UX-08), no server, telemetry or new transport. `cowork_status` (MCP) is unchanged.
- **Visualizer (12):** unchanged. The viewer opens no IPC (VD-6, INV-VIZ-READONLY) and flow data lives only in daemon memory; an 8b desk tooltip would need a new data path and is out of scope.

## 4. New state and interfaces

```
last_check(cs) = { edit_n, kind: fail | conflict | incomplete | stale | skipped,
                   check?: 1..4, path?, line?, skip?: shrink | slow_read | base_moved | batch, more: n }
                   // a running or waiting check (06 §3.8.4 step 3 queue) is read from the queue, not stored here:
                   // it renders UI_FLOW_LAST_CHECKING when its edit_n is newer than last_check's
last_pass(cs)  = { ready: edit_n | none, shared: edit_n | none }   // edit_n of the CS's ready pair in journal/ready/ and of its
                                                                    // newest published capture; follows the journal (a stale drop or
                                                                    // HLD-41 withdrawal clears `ready`); per open seat CS, memory only
edit_n         = 1-based ordinal of the edit-checkpoint trigger within its CS (06 §3.8.4; skipped triggers count)
wait_detail()  = { ms, term: window | own_spacing | peer_cap | team_guard | in_flight | backoff }   // governor, read-only;
                 // the terms of may_attempt (02 §3.8) in that order; backoff = the ENG-44 transient backoff (Plan 2 R-20)
```

Written by: HLD-67 step 4 (`fail`: first entry of `editCheck.failed` with a check reason, ordered by check, path, line, `more` = the rest; `conflict`: a `merge_conflict` entry; `incomplete`: `incomplete`, `no_snapshot` or `no_merge`, 04 §3.20), the HLD-67 T0 drop of an open-CS capture at publish (`stale`, T0's first finding), 06 §3.8.4 skip conditions 3–6 (`skipped`). Cleared when the CS closes or a passing capture with a higher `edit_n` lands in the journal. `line` = 1-based stored-form row in the merged tree `M'` of 04 §3.20 (`M[p]` on the CS's checked paths, `TIP` elsewhere, because an un-updated caller of check 2 can sit outside the CS) where the first offending node, call or reference starts; none for check 4. **T0 → check number** (`stale`): HLD-50 has three items, not four, so a T0 finding is numbered by the REG-36 split that the edit check uses: T0 item 1 error-node count or UTF-8 → 1, its label count → 4; item 2 `incompatibleCallers` of a non-removal breaking change or `orphanCalls` → 2, `unresolvedImports` or `incompatibleCallers` of a removal → 3; item 3 shrink → 4. Never written to the state ref, `cs/<enc(b)>.json`, logs, the board or any file; lost at daemon restart (`UI_FLOW_LAST_UNKNOWN`). Size: ≤ 1 slot per open seat CS.

## 5. Privacy and safety

- What never leaves this PC: everything in F14. The flow reply crosses only the local authenticated IPC; `last_check` is never pushed, published, logged or persisted.
- What is never shown: file content, diff text, symbol labels or names from the failing check, notes, host text (`{hostmsg}`), tool input, prompt text. A flow line carries only message codes, check numbers 1–4, repo-relative paths (SEC-34 `sanitize`, path cap 80), line numbers, seat numbers, display ids, board heights, durations and counts — SEC-38's allowed set — plus teammates' display names (sanitized, name cap 20), which SEC-38's set does not include and which every status detail reply already carries (section 7 "Teammates"). A `local_only` path never reaches the edit check (REG-36 covers `LIVE` paths only) and shows only stage O2.
- Slash output enters Claude's context: framed (10 §3.3), ≤ 4,000 chars, no line begins with `/` outside catalog-quoted commands (UX-05). It is human-requested, like every slash verb; 06 §3.16.1 already adopted 10 §8 Q2's default (shown on the seat's budget line, not counted toward the 20,000-char `PULL_MODE` threshold), and F14 follows it. F14 adds no daemon-initiated Claude text, so COO-10's silence on a failing edit check holds on every pushed carrier.
- Teammates: nothing about a teammate's unpublished work is shown or exists on this PC; the only teammate facts are their already-published change (path, display name) and board heights, which `/cowork log` shows today. Failing edit checks of this PC's own sessions are shown to this PC's human only when asked, with the legend line saying that a failure mid-turn is normal, so the view does not invite interrupting a working Claude.
- Read-only: the query reads in-memory state of the last iteration only: no git process, no file read, no snapshot or materialization, no state/registry/board write (INV-UX-READONLY); computed in slices so the event loop blocks ≤ 20 ms (glossary §20).

## 6. Requirements

- **FEAT-F14-01** `/cowork status` MUST print section 6 as "In flight" when it has entries (counts line, `UI_FLOW_HEAD`, ≤ 5 entries without stage O2, `UI_FLOW_SEE_ALL` when more), and nothing when it has none; it MUST keep the UX-07 order.
- **FEAT-F14-02** `/cowork status --flow` MUST print the headline, its next line and the full "In flight" section within the §2 caps (200 / slash 4,000 / `--json` 2,000 + `data.truncated.flow`).
- **FEAT-F14-03** Every (path, direction) of the §2 domain MUST get exactly one stage, the first matching row of the §2 tables; no path of the domain MAY be omitted except by the stated caps and the O2 rule of FEAT-F14-01.
- **FEAT-F14-04** An estimate MUST be printed only for O6 and O10's `UI_FLOW_PASS_READY` (governor `wait_detail`, worded "at the earliest"), O8 (20 s quiet; for `_RECOVERED` only while no local seat is `MID_TURN` or `AWAITING_PERMISSION`), I4b (2-min apply coalescing) and I4 (10 s apply coalescing); O4, O5 and I3 MUST print elapsed time; every other stage MUST print its next action instead. All times MUST be local Δmono (INV-CLOCK).
- **FEAT-F14-05** The flow MUST be computed by the daemon only on a CLI IPC request, from in-memory state, with no git process, file read, snapshot, materialization or ref/registry/board write, blocking the event loop ≤ 20 ms.
- **FEAT-F14-06** The daemon MUST keep `last_check`/`last_pass` per open seat CS exactly as §4 and MUST NOT persist, log, publish or deliver them to any seat carrier.
- **FEAT-F14-07** `editCheck` MUST return `line` for checks 1–3 as a row of `M'` (§4); T0 findings MUST keep their `path:line` and MUST be numbered 1–4 by the §4 mapping when recorded as `stale`.
- **FEAT-F14-08** Flow output and the IPC reply MUST contain only the §5 allowed items (SEC-38's set plus teammates' display names) and MUST NOT contain file content, diff text, symbol names, notes or host text; every string in them MUST pass `sanitize` and `scanSecrets` as SEC-38 requires of its carriers.
- **FEAT-F14-09** F14 MUST NOT add a `status.json` field, a board op, a hold record, an event, an OS notification class, an MCP result change or any hook, doorbell or systemMessage text.
- **FEAT-F14-10** `/cowork show <path>` on a `LIVE` path MUST print its flow lines or `UI_FLOW_PATH_CURRENT`.
- **FEAT-F14-11** `--json` MUST carry the flow as one optional field `data.flow = {tip_height, fetched_age_ms, entries: [{path, dir, stage, code, params}]}` in `cowork-status/1` and in the path view of `cowork-show/1`, absent when IPC fails. - **FEAT-F14-12** Every new code MUST ship in the six human catalogs within I18N-07 caps at worst-case params.
- **FEAT-F14-13** The governor SHOULD expose `wait_detail()` read-only; reading it MUST change no governor state.
- **FEAT-F14-14** I3 ages SHOULD reuse the HLD-54 deferral anchor and MUST append `UI_FLOW_SINCE_RESTART` for anchors set at daemon start.
- **FEAT-F14-15** The guides SHOULD carry a troubleshooting entry "a teammate can't see my change → both run `/cowork status --flow` and compare board heights" (en, ko).
