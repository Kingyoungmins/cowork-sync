# cowork-sync 설계 요약 (2026-10-02 승인)

> **2026-10-02에 설계를 승인해 주셨습니다.** 기준 문서는 영어 설계서([2026-10-01-cowork-sync-design.md](2026-10-01-cowork-sync-design.md))와 상세 장([docs/spec/](../../spec/))입니다. 이 문서는 무엇이 정해졌는지 빠르게 확인하실 수 있게 쉬운 말로 줄인 것입니다. 사전 실험 결과(용어집 §25·§26)와 10-02 검토 답변(용어집 rev 2.4, §27)까지 반영했습니다.

## 한 줄 요약

팀원 각자의 PC에서 각자의 Claude가 **같은 파일을 동시에** 고치고, 바뀐 내용은 **GitHub를 통해 자동으로** 서로의 PC에 반영됩니다. Claude들은 누가 어느 함수를 고치는지 알고 서로 비켜 가며, 부딪히면 사람처럼 경고하고 양해를 구하고 일을 넘깁니다.

## 어떻게 움직이나

1. 내 Claude가 함수를 고치려 하면, 먼저 **"이 함수 누가 잡고 있나?"**를 확인합니다. 0.1초 안에 끝납니다(실험에서 약 0.065초).
   - 아무도 안 잡았으면 내가 잡고 바로 고칩니다. 팀원들은 **몇 초 안에** "누구 Claude가 이 함수 고치는 중"을 봅니다.
   - 남이 잡고 있으면 **막고**, 하려던 수정은 자동으로 보관합니다. 내 Claude는 다른 일을 먼저 합니다.
2. 내 Claude가 **한 번 고칠 때마다** 0.5초 안에 끝나는 빠른 검사 4가지를 합니다. 통과하면 그 상태를 바로 팀원 PC로 보냅니다. 보통 **10~30초** 걸립니다(계산값, 10-02에 "더 빨라야 한다"고 하셔서 바꾼 방식).
   - 빠른 검사 4가지: ① 문법이 깨지지 않았는지 ② 함수 이름·인자를 바꿨는데 그 함수를 부르는 곳은 그대로 두지 않았는지 ③ 없는 이름을 부르지 않는지 ④ 파일이 갑자기 반 넘게 줄지 않았는지.
   - 통과하지 못하면 아무 알림 없이 그냥 기다립니다. 다음 수정에서 통과하거나 요청 하나가 끝날 때 넘어갑니다. 요청을 끝낼 때나 테스트가 통과할 때도 지금처럼 넘어갑니다.
   - 반쯤 고친 상태, 특히 다른 코드를 깨뜨리는 상태는 여전히 넘기지 않습니다. 실험에서 그런 걸 넘기면 모두의 앱이 깨지는 게 재현됐습니다.
3. 사람이 VS Code에서 직접 고친 것은 **20초 동안 손을 안 대면** 넘어갑니다. 단, 이 저장소에서 Claude Code가 켜져 있거나 `/cowork start --human <분>`(최대 8시간)을 켜 둔 동안에만 넘어갑니다. 둘 다 아니면 다음에 세션을 켤 때 넘어갑니다.
4. 정식 커밋은 아무나 `/cowork save "설명"` 한 번으로 합니다. 누가 어느 함수를 고쳤는지 커밋에 자동으로 적힙니다. 저장한 뒤에는 **팀원들 PC의 git 상태도 자동으로 따라갑니다.**

## 부딪혔을 때

| 상황 | 결과 |
|---|---|
| 남이 잡은 함수를 고치려 함 | 막고, 하려던 수정은 보관합니다. 작업이 끝나면 그 함수 주인에게 넘깁니다. 주인 Claude는 자기 일이 끝나면 **주인(사람)에게 "영희가 넘긴 요청 1건: … 처리할까요?" 하고 물어봅니다.** 거절하거나 함수를 놓으면 요청은 나에게 **되돌아옵니다**. |
| 둘이 몇 초 차이로 같은 함수를 잡음 | 늦은 쪽이 '충돌 유발자'가 되고, 경고는 **1건만** 갑니다. 늦은 쪽 Claude는 기다리거나, "금방 끝나니 먼저 해도 될까요?" 하고 양해를 구하거나, 넘깁니다. 주인 쪽에도 알림이 1건 갑니다. 다른 팀원 Claude는 깨우지 않습니다. |
| 같은 줄을 거의 동시에 고침 | 먼저 올라간 내용이 디스크에 남고, 나중 내용은 **팀 보관함**에 들어갑니다. 명령 한 번으로 되살릴 수 있습니다. |
| 사람이 Bash나 에디터로 남의 함수를 고침 | 공유하지 않고 내 PC에만 둔 채 알려줍니다. |
| 팀원이 바꾼 함수 때문에 내 코드가 깨짐 | 공유하기 전에 미리 검사해서 멈추고, 무엇이 깨지는지 정확히 알려줍니다. |

**어떤 경우에도 코드가 사라지지 않습니다.** 밀려난 내용은 모두 보관함에 기록되고, 그 기록은 팀이 볼 수 있습니다. 단, 비밀 파일, 설정·CI 파일처럼 실시간으로 공유하지 않는 파일, 충돌 표시가 남은 파일의 내용은 예외로 내 PC에만 남습니다. 팀에는 "보관 중인 것이 있다"는 표시만 갑니다.

## 정해 주신 것들 (20개 모두)

20개 결정을 모두 정해 주셨습니다. 마지막으로 남았던 설정·CI 파일 보안 기본값도 10-02에 동의해 주셨습니다(아래 칸).

- **통로:** GitHub(git 원격)만 씁니다. 콜라보레이터만 접근할 수 있습니다.
- **잡기:** 함수 단위이고, 먼저 고친 뒤 겹치면 경고합니다.
- **경고:** 대표 1건만 보냅니다. 구경꾼 Claude는 깨우지 않습니다.
- **auto 모드 Claude도 알림이 오면 깨웁니다.** 시간당 횟수 제한이 있습니다. 세션 하나당 10분에 1번, 1시간에 4번까지입니다.
- **깨어난 Claude는 바로 작업까지 합니다.** 추천안이 아니라 고르신 선택입니다. 그래서 이렇게 정리했고, 아래 범위 제한도 10-02에 확인해 주셨습니다.
  - 내가 자리에 있고 Claude가 일하는 중이면, 받은 요청은 **지금 하던 일이 끝난 뒤 내 Claude가 나에게 물어봅니다**("처리할까요?"). 내가 하라고 해야 받아들입니다. 나는 `/cowork release`로 직접 함수를 놓을 수도 있습니다.
  - 쉬다가 알림으로 깨어난 Claude는 내가 없어도 바로 처리합니다. 단, **자기가 받아들인 일과 자기 함수에 관한 일만** 합니다. 그 밖의 파일을 건드리면(명령어로 고친 것 포함) 공유하지 않고 보류합니다.
  - 그렇게 한 수정에는 모두 **"팀원 요청으로 한 작업"(origin=wake)** 표시가 붙고, 돌아와서 다음에 입력할 때 목록으로 보여 줍니다.
- **응답 없는 PC:** 요청을 보냈는데 그 PC가 30분 동안 아무 반응이 없으면 잡은 함수를 풉니다. 그 사람의 공유 안 된 내용은 보관됩니다. "받았다"고만 하고 30분 동안 답이 없으면 한 번 더 자동으로 요청합니다.
- **동기화 프로그램이 멈추면:** Claude의 수정도 멈추고 알립니다.
- **저장 후 내 브랜치:** 저장 내용이 내 파일에 다 들어 있으면 자동으로 따라갑니다. 저장 뒤에 추가로 고친 게 있어도 따라갑니다. 파일은 건드리지 않습니다.
- **같은 줄 충돌:** 먼저 올라간 쪽이 디스크에 남고, 나중 쪽은 보관함에 들어갑니다. 사람 편집도 똑같습니다.
- **오래 보류된 변경:** 팀 버전과 다르게 내 디스크에 남아 있는 보류 변경(팀 보관함에 기록된 것)은 24시간 뒤 디스크를 팀 버전으로 되돌립니다. 내 내용은 보관함에 남습니다. 비밀 파일처럼 내 PC에만 두는 보류는 자동으로 되돌리지 않습니다.
- **새 파일:** 자동으로 공유합니다. 단 .gitignore 대상, 비밀처럼 보이는 파일(.env, 인증서·키 등), 설정·자동실행 파일(아래 보안 기본값), 1MB 넘는 새 파일은 빼고 넘깁니다.
- **언어:** TypeScript(Node)
- **README:** 6개 언어(기본 영어, 한·중·일·프·스)이고, 맨 위에 언어 전환 버튼이 있습니다.
- **공개 범위:** 처음에는 비공개 저장소로 시작하고, 완성되면 공개합니다.

## ⚠️ 새로 넣은 보안 기본값 — 이의 있으면 말씀해 주세요

**설정·자동실행 파일은 실시간으로 공유하지 않습니다.** 대상은 `.claude/`, `CLAUDE.md`, `.github/workflows/`, `.vscode/settings.json`, `.gitattributes`, git hooks 폴더 등입니다. 이 파일들은 **평소처럼 git 커밋으로만** 넘어갑니다.

- **이유:** 이 파일들은 내 PC에서 프로그램을 자동으로 실행시킬 수 있습니다. 실시간으로 넘기면, 팀원이(또는 팀원의 Claude가 실수로) 바꾼 설정이 내 확인 없이 내 PC에서 실행될 수 있습니다.
- **불편한 점:** 예를 들어 CLAUDE.md를 고치면 팀원에게 몇 초 만에 가지 않고, 커밋하고 저장해야 갑니다. 들어온 변경은 내가 `/cowork review`로 확인한 뒤에야 내 PC에 적용됩니다.

## "라이브"의 실제 속도

| 무엇 | 보통 |
|---|---|
| 팀원이 "누가 어느 함수 잡았는지" 보기 | 3~11초 |
| Claude가 고친 코드가 팀원에게 도착 | 약 10~30초 (한 번 고칠 때마다 빠른 검사를 통과하면 바로. 통과 못 하면 다음 통과 때나 요청 하나가 끝날 때) |
| 사람이 고친 코드가 팀원에게 도착 | 손 뗀 뒤 20초 + 차례 기다리기(PC 4대 기준 최대 약 10초, 서로 부딪히면 더 걸림) + 올리는 데 약 2초 + 받는 쪽 반영 최대 10초 (받는 쪽 Claude가 그 파일을 읽고 작업 중이면 최대 2분 더) |
| GitHub 푸시 | 팀 전체 어느 1분을 재도 12회 이하. GitHub가 느려지거나 거절 신호를 보내면 30분 동안 자동으로 6회 이하로 줄이고, 다른 팀원 PC도 함께 줄입니다. 팀마다 처음 시작할 때 6~24회 사이로 정할 수 있습니다. 한 번 올리는 데 약 2초 |
| 추가 사용량 | 일하는 Claude 기준 입력 토큰 +15% 이내. 쉬는 Claude는 깨우지 않으면 0 |

엑셀처럼 한 글자씩 실시간은 아닙니다. 대신 **한 번 고칠 때마다 10~30초 안에** 모두에게 갑니다. 사전 실험에서 GitHub는 분당 24번까지도 문제가 없었습니다. 그래서 10-02에 "더 빨라야 한다"고 하신 대로 GitHub 공식 권장치(분당 6번)의 두 배인 **분당 12번**을 기본으로 하고, GitHub가 느려지거나 거절 신호를 보내면 자동으로 6번으로 내립니다. 위 표의 코드 도착 시간은 아직 계산값이고, 실제 프로그램이 나온 뒤 장시간 시험으로 잽니다.

## v1에서 안 되는 것 (명확한 메시지로 거부합니다)

- **이런 변경:** 서브모듈, 심볼릭 링크, LFS 파일 수정, 대소문자만 다른 파일 이름
- **오래된 도구:** git 2.43 미만, Node 20 미만, Claude Code 2.1.270 미만
- **팀과 다른 설정:** 줄바꿈·비밀 필터 설정이 팀과 다른 PC는 참가할 수 없습니다.
- **공개 저장소:** 로그인 없이 누구나 읽을 수 있는 저장소에서는 켜지지 않습니다(작업 중인 코드가 그대로 공개되므로). 공개 여부를 확인할 수 없으면 `--private-confirmed`로 비공개임을 확인해야 합니다.
- **v2로 미룬 기능 19개:** 강제로 끼어들기, 비슷한 코드 복사 감지, 서로 기다리는 교착 자동 감지, 원격 정리 명령 등입니다. 모두 v1에서 대신할 방법이 있습니다.

## 사전 실험 결과 (2026-10-01)

PC 한 대(Windows), 네트워크 하나, 비공개 연습 저장소로 10가지를 시험했습니다. 쉬운 설명은 [사전 실험 결과 정리](../../../spikes/RESULTS.ko.md)에, 숫자와 기록 파일은 영어판 [RESULTS.md](../../../spikes/RESULTS.md)에 있습니다.

**설계를 무너뜨리는 문제는 없었습니다.** 결과는 합격 1개, 고칠 방법이 정해진 불합격 3개, 범위가 모자란 것 5개, 아직 못 한 것 1개입니다.

**잘 된 것**
- 두 사람이 동시에 올려도 100번 모두 한 명만 성공했습니다.
- GitHub에 분당 24번 올려도 실패나 차단이 없었습니다. 우리 전용 저장 위치에서는 GitHub 자동 실행(Actions)이 돌지 않았습니다.
- 시범 팀의 실제 비밀값 필터가 21개 파일 모두 정확했고, 필터가 고장 나면 안전하게 멈췄습니다.
- 쉬고 있는 Claude가 알림을 받고 0.03초 만에 깨어났습니다(새 형식으로 보냈을 때).
- Claude를 꺼도 동기화 프로그램은 살아 있었습니다.

**그래서 바뀐 것** (용어집 §25·§26에 반영)
- **알림 보내는 형식:** 설계서의 원래 형식은 Claude Code가 조용히 버려서, 실제로 들어가는 형식으로 바꿨습니다. "받았다"는 답이 없으므로, Claude 쪽에 알림 표식이 보였을 때만 도착으로 칩니다.
- **"사람이 직접 친 명령" 확인:** 원래 쓰려던 신호가 명령 실행 뒤에 와서, 실행 전에 오는 다른 신호(UserPromptExpansion)로 바꿨습니다.
- **파일 읽는 방법:** 동기화 프로그램이 파일을 직접 읽는 동안 편집기 저장이 1,000번 중 약 11번 실패했습니다. 이제는 파일을 짧게 한 번 읽어 복사본을 만들고 그 복사본만 다룹니다. 그랬더니 동기화 프로그램 때문에 생긴 실패가 없어졌습니다. 모든 운영체제에서 같은 방식입니다.
- **임시 데이터:** 20분에 205MB가 쌓여서, 주기적으로 찍는 상태 기록은 저장하지 않도록 했습니다.
- **수정 검문 시간 기준:** 0.06초는 맞출 수 없어 0.1초로 올렸습니다. 200번 이상 재서 확인합니다.
- **필터 사전 점검:** 원래 절차가 필터를 실제로 돌리지 않는 결함이 있어 새 절차로 바꿨습니다.
- **GitHub가 올리기를 거절할 때:** 메시지 글자가 아니라 결과를 보고 판단합니다. 같은 거절이 3번 연속이면 멈추고 사람에게 알립니다.

**사용자 도움이 필요한 것** (이것만 끝나면 실제 PC·네트워크에 기대는 부분도 시작할 수 있습니다)
1. **다른 네트워크에 있는 두 번째 PC**(약 1~2시간). 집 인터넷이나 휴대폰 테더링이면 됩니다. 서로 다른 곳에서도 "한 명만 성공"이 유지되는지 봅니다.
2. **24시간 로그인 유지 시험**(PC를 24시간 켜 두고, 마지막에 15분). 마지막에 GitHub 로그인을 일부러 끊어서, 동기화가 "로그인 필요" 상태로 제대로 멈추는지 봅니다.
3. **터미널·VS Code에서 직접 해 보는 시험**(약 1~2시간). `/cowork` 명령을 각각 50번 쳐 보고, Claude 창을 닫는 여러 방법(입력으로 종료, 창 닫기, 강제 종료, VS Code 닫기)을 시험합니다.
- (선택) 맥·리눅스 기기, 다른 팀원 PC에서 필터 점검 한 번.

## 개발 순서

1. 사전 실험 (2026-10-01에 대부분 마침. 위 "사용자 도움이 필요한 것" 3가지가 남음)
2. **핵심:** 동기화, 보관함, 수정 검문, 저장·따라가기, 시뮬레이터
3. 함수 인식(Python·JS·C#)과 충돌 처리
4. 실시간 깨우기와 협상
5. 진단 도구, 알림, 6개 언어 README, 배포
6. 시범 팀이 실제로 써 보기
7. 공개

시간은 구현 계획서를 쓸 때 단계별로 다시 계산합니다. 앞서 말씀드린 12~20시간은 규칙이 이렇게 많아지기 전의 숫자라 맞지 않습니다.

## 검토 부탁드리는 것

1. 위 **보안 기본값**(설정·CI 파일은 커밋으로만)에 동의하시는지
2. **"깨어난 Claude는 바로 작업"**을 "받아들인 일·자기 함수만 + 표시, 그 밖의 수정은 공유하지 않고 보류"로 제한한 것이 괜찮은지 (고르신 "바로 작업까지"에 제가 안전장치로 덧붙인 범위입니다. 지금 설계는 이대로 되어 있습니다)
3. **속도 숫자**(코드는 30초~3분)가 기대하신 "라이브"에 맞는지
4. **"먼저 해도 될까요?"를 허락하면**, 허락한 쪽 Claude는 상대가 그 함수를 다 고쳐 올릴 때까지 **그 함수만** 잠깐 손을 떼는데, 괜찮은지 (기본값으로 그렇게 동작합니다)
5. **원격 기록을 손으로 지운 뒤 다시 시작**하는 `/cowork start --fresh`(미리보기 확인 후에만 동작)를 두는 것이 괜찮은지
6. **설계 승인:** 승인해 주시면 구현 계획서를 쓰고, 실제 GitHub 없이 내 PC 안에서 도는 부분(시뮬레이터, 테스트 도구, 자동 검사 규칙, 핵심 동기화 엔진)부터 만들기 시작합니다. 실제 PC·네트워크·Claude 동작에 기대는 부분은 위 사전 실험 3가지가 끝난 뒤에 만듭니다.
7. 그 밖에 빠졌거나 바꾸고 싶은 동작
