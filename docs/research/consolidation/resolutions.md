# engine-model
## Live-ref shape: fast-forward only (INV-FF)
CHOSEN: INV-FF. (a) Every update a daemon makes to refs/cowork/<b>/code and refs/cowork/<b>/board is a fast-forward: the new tip's FIRST parent equals the leased old tip. The push always uses --force-with-lease=<ref>:<old>, never '+' or --force; the only exception is human-typed `/cowork recover`. (b) An ordinary live commit has exactly one parent, the previous tip. A BASE-MOVE commit (a save re-parent, R2, or a live-rebase onto a moved branch, R3) has exactly two parents [previous live tip, X]. X is a commit on refs/heads/<b> and never a live commit. The commit carries the trailer `Cowork-Base: <X>`. The live base of any live commit is the X of the newest base-move commit on its first-parent chain, or the base recorded in the session's first live commit. Branch commits never have a live commit as an ancestor. (c) Receiver check, every loop before any merge: LA_C (R5) must be on TIP's first-parent chain. Either TIP == LA_C, or `git rev-list --first-parent LA_C..TIP` is non-empty and the oldest listed commit's ^1 == LA_C. A bare `merge-base --is-ancestor` is NOT sufficient, because a rewrite that keeps the old chain as its second parent would pass it. The same check runs on the board ref against the last applied board commit. A failed check, or a remote ref that has vanished, is a REWRITE INCIDENT. The daemon applies nothing and pushes nothing for that branch, stores the observed value at refs/cowork-local/<b>/incident-<n>, shows the old and new oids to the human, and injects the same into that session's Claude. The only exit is human-typed `/cowork recover`. It pushes this peer's newest first-parent-valid live commit with --force-with-lease=<ref>:<observed bad value>. A peer whose LA_C is on the restored tip's first-parent chain resumes. A peer that is further ahead runs recover itself; ancestry, not clocks, decides which tip is newer. The normal loop then republishes unpushed deltas. (d) Ancestry is used ONLY for the guards in (c) and for choosing among BRANCH commits in R3. Every 3-way merge of local work passes the explicit tree A (R5) as --merge-base. A CI lint forbids merge-tree without --merge-base and `git merge-base` on cowork refs.
WHY: Only a fast-forward-only chain lets one rule tell a legitimate save apart from a destructive rewind. ref-rewind-silent-revert (VERIFIED t3) shows that a non-FF update cannot be distinguished from a rewind and reverts work silently. So the save must be FF, and the FF form costs nothing. My experiment sweep/core_engine/x1_save_completion.sh (VERIFIED) shows: first-parent(Ls) == old tip; S (the save commit) is not on the live first-parent chain; the save commit's ancestry contains no live commit; and diff(old tip, Ls) is empty, so peers apply nothing and no join is triggered. The 'never use ancestry' intent of INV-BASE (explicit-base-not-ancestry, VERIFIED e2) still holds where it matters: ancestry never picks a merge base, it only gates. Because the chain is never reset, pre-save history stays on the remote, visible to the team. That addresses no-history-undo (VERIFIED e7) and keeps live-chain blame across saves (save-squash-erases-provenance).
V1/V2: v1: no chain compaction (the chain is permanent history, per P1); rewrite recovery is manual via /cowork recover. v2: epoch rollover or compaction protocol, and automatic recovery.

## Save content and procedure
CHOSEN: SAVE (human-typed only). The saved tree is the exact tree of an EXISTING live commit: no splicing, no exclusion, no synthesized tree. Steps: 1) Final sync round: publish this peer's own non-held delta (wait for a governor slot), then fetch. TIP = the code tip, Hb = the live base of TIP (R1b), Hr = the remote refs/heads/<b>. 2) If Hr != Hb, run the R3 base move first and restart (at most 3 tries, then refuse loudly). 3) Candidate Lk = TIP. If .cowork/config defines save.check, walk TIP's first-parent chain while the live base is still Hb (at most 20 commits). Materialize each candidate in a throwaway `git worktree add --detach <gitdir>/cowork/tmp/save-<n> <Lk>`, run the check there, and remove the worktree. The newest passing candidate wins; if none passes, refuse and show the output. 4) S = `commit-tree tree(Lk) -p Hb`. The message is the human's summary plus per-symbol attribution trailers plus `Cowork-Saved-Live: <Lk>`. Before pushing, assert: tree(S) == tree(Lk); Lk is on TIP's first-parent chain; live base of Lk == Hb == Hr. 5) Ls = `commit-tree tree(TIP) -p TIP -p S` with `Cowork-Base: <S>`; assert tree(Ls) == tree(TIP). 6) `push --atomic` with --force-with-lease=refs/heads/<b>:Hb, --force-with-lease=refs/cowork/<b>/code:TIP and the board save event. Both ref updates are fast-forwards. If rejected, refetch: if only the live ref moved, rebuild Ls on the new TIP and keep S (Lk is still on the chain); if the branch moved, go back to step 2. If the outcome is ambiguous, fetch: success iff the branch head == S and Ls is on the code first-parent chain. Never force. 7) On hosts without --atomic (detected by the start-time probe), push the branch first (lease Hb), then Ls. A crash between the two is completed by any daemon through the R3 save-completion rule. The save includes everyone's published work at Lk, in progress or not, because U8 says 'the shared tree'. The save report lists the included in-progress change-sets per author, plus the saver's own held (unpublished) hunks, which stay held. Choosing a candidate by change-set state is a pluggable hook (atomicity group), but it must return an existing live commit.
WHY: Several findings rule out the alternatives. Splicing produces commits that fail while every PC is green (save-splice-commits-untested-tree, VERIFIED X6a TypeError and X6b ImportError). Saving from the saver's working tree erases a teammate's work (f-save-lagging-tree-reverts-peers, VERIFIED). A reset drops edits made during the save (save-race-reverts-concurrent-edits, VERIFIED). Committing on top of a moved branch reverts external commits (save-reverts-external-commits, VERIFIED e9), which is why the branch head must equal the live base, with the merge done earlier as a live base move. Because tree(S) is exactly a live tree that every peer already has on disk, U9's precondition 'files equal the saved content' holds for every peer with no unpublished edit on a saved path, and peers apply an empty diff (x1, VERIFIED). One shape (an existing live tree) serves save, the smoke check and adopt alike, which follows P3.
V1/V2: v1: if the branch push is rejected by policy (protection, rulesets), save stops and reports; a PR-branch fallback belongs to the security/host group. The save smoke check is opt-in. v2: barrier option asking live sessions to reach Stop before the save.

## Branch moves and save completion (live base move)
CHOSEN: When the fetched Hr != Hb (live base of TIP): (i) If Hb is NOT an ancestor of Hr (the branch was rewritten or force-pushed), v1 refuses: freeze save and base moves, continue live on Hb, and tell the humans and their Claude sessions. (ii) SAVE-COMPLETION: if Hr has the trailer `Cowork-Saved-Live: <Lk>`, Hr^1 == Hb, tree(Hr) == tree(Lk), and Lk is on TIP's first-parent chain, then the new live tree = tree(TIP). This is equivalent to `merge-tree --merge-base=tree(Lk) TIP Hr`. (iii) Otherwise (external commits, PR merges, a teammate's plain `git push`), the new tree = `merge-tree --write-tree --merge-base=<tree(B)> TIP Hr`. B is the newest commit among Hb and earlier base-move second parents on TIP's first-parent chain that is an ancestor of Hr; normally B = Hb. On merge conflict (exit 1): no base move, save is blocked, one board event lists the conflicting paths, and live continues on Hb. On a clean merge: diff(TIP, newtree) passes the same outgoing guards as a local delta (the hold registry's revert/provenance guard). Hunks that re-introduce content the live chain removed pause the base move for those paths and the humans are asked. Then L' = `commit-tree newtree -p TIP -p Hr` with `Cowork-Base: <Hr>`, pushed with lease TIP. Every daemon may attempt it; the lease admits one, and the others refetch and see Cowork-Base already == Hr. A base move never moves the branch. After any base move, every peer runs R10 adopt toward the new base. A local `git commit` while live does not move the live base (R8 epoch guard). Pushing that commit is a branch move handled by (iii).
WHY: My experiment sweep/core_engine/x1_save_completion.sh is VERIFIED. Setup: Lk adds line y, a later live commit deletes y, the branch push of S lands, and the live push does not. Using `--merge-base=tree(Hb)` resurrects y ('y present? 1'). Using `--merge-base=tree(Lk)` gives exactly tree(TIP) ('equals tree(L3)? yes'). One rule therefore covers both --atomic hosts and a crash-interrupted non-atomic save, so no separate recovery mechanism is needed (P3). Case (iii) is the VERIFIED fix in save-reverts-external-commits and branch-moves-under-live, made FF by the two-parent shape. Case (i) is a P4 refusal.
V1/V2: v1: refuse when the branch is rewritten or force-pushed, or when the base-move merge conflicts. v2: guided rebase-onto for rewritten branches, and conflict resolution inside the base move.

## Daemon git storage
CHOSEN: All daemon git state lives in the USER'S OWN repository, using the same GIT_DIR, object store, config, attributes and filters. There is no private GIT_DIR, no alternates, no refs/worktree, and no state.json as a source of truth. Refs, all in the common namespace, with every daemon ref update run under `-c core.logAllRefUpdates=always`:
- refs/cowork-remote/<b>/{code,board,branch}: fetch targets. A local '+' is allowed only because the INV-FF check runs before any use.
- refs/cowork-local/<b>/state: the single source of truth (R5), changed by exactly one CAS `update-ref` per transition.
- refs/cowork-local/<b>/holds: the hold registry, owned by the hold-lifecycle group.
- refs/cowork-local/<b>/incident-<n>.
Files under `git rev-parse --git-path cowork/`:
- <b>.index: the private index, a cache that can be rebuilt with `read-tree <state:snap>` + `update-index -q --refresh`.
- tmp/: writer temp files and the displaced .old ring.
- daemon.lock: pid and process start time; a second daemon on the same clone refuses to start.
- IPC rendezvous info.
Nothing correctness-critical lives in CLAUDE_PLUGIN_DATA. Every daemon git call uses: LC_ALL=C and LANGUAGE= (empty); `-c gc.auto=0 -c maintenance.auto=false`; `fetch --no-auto-maintenance --no-write-fetch-head` against the pinned URL; and -z/porcelain parsing. The daemon never runs gc. The user's own auto-gc is safe because everything the daemon needs across loops is reachable from refs/cowork-local/* and their reflogs. Between `add` and the state update-ref (sub-second), a user `gc --prune=now` can only make write-tree fail, and the loop then retries from the bytes on disk. v1: live mode only in the main worktree of a clone. Starting in a linked worktree, including .claude/worktrees/*, is refused.
WHY: The deciding reason is secrets. A private GIT_DIR must MIRROR the user's filter, autocrlf and attribute config, and any drift is the filter-passthrough-leak / secret-filter-fails-open class (critical, VERIFIED). Running in the user's own GIT_DIR uses exactly the user's clean filter. Adopt (R10) needs S and its trees in the user's object store; fetching into the user's repo provides them with no second fetch. Refs under refs/cowork-local protect objects from `git prune` (objects-only-in-private-index, VERIFIED e8). refs/worktree state vanishes with the worktree (park-refs-in-worktree-namespace-vanish, VERIFIED). Custom namespaces get no reflog by default, so logAllRefUpdates=always is needed (no-history-undo, VERIFIED e7). Fetch triggers maintenance and overwrites FETCH_HEAD (fetch-head-hijack-and-auto-maintenance, DOCUMENTED and VERIFIED). One object store and one state ref replace the alternates, config mirroring, state.json and its write-ahead file (P3).
V1/V2: v1: main worktree only; daemon refs are visible to `git log --all`. v2: per-worktree live sessions keyed by worktree id, and optionally hiding refs via transfer.hideRefs/log.excludeDecoration guidance.

## LAST_APPLIED semantics (LA_C + per-path base A) and the state ref
CHOSEN: refs/cowork-local/<b>/state points to one commit:
- parents = [LA_C]
- tree = { base -> tree A, snap -> tree S_disk (last snapshot), journal -> blob (JSON: apply intent, push intent or adopt intent; empty when idle), meta -> blob (JSON: live base Hb, adopted HEAD H_adopt, pending paths with reasons, expected epoch fingerprint, protocol version) }.
LA_C is the newest REMOTE live commit this peer has processed: every change in tree(LA_C) is either written to disk or recorded as a pending INCOMING path. LA_C is only ever a commit that exists on the remote (fetched, or our own push confirmed by 'ok' or by a fetch). It moves only forward along the first-parent chain and is used only for the INV-FF guard and as the 'processed up to' marker. A is the per-path merge base: A[p] = tree(LA_C)[p] for every p except pending INCOMING paths, where A[p] keeps the older team blob actually underlying the disk. A[p] changes only after the verified write of p (R6), or after a confirmed push in which p went out without an incoming merge. Every 3-way merge of local work uses --merge-base=A. A is never computed from ancestry and never seeded from TIP. When nothing is pending, A == tree(LA_C). Each loop transition is exactly one `update-ref refs/cowork-local/<b>/state <new> <old>`, so a crash leaves the old or the new state, never half of one. The previous states remain reachable through the reflog for gc.reflogExpire.
WHY: Pending (locked, fenced, deferred) paths must keep their old base, or the next push reverts them (naive-push-reverts-unapplied-paths, VERIFIED e1; pending-path-base-misset-reverts, VERIFIED). At the same time, the rewind guard needs a real remote commit. Splitting the two removes the conflict. A commit-shaped state makes every transition atomic and keeps every needed object gc-reachable. This replaces state.json + a reflogged base ref + a separate journal file (P3), and resolves the stale-base-after-crash and ambiguous-push cases via the journal (VERIFIED e3, e3b, e10). The masked tree is never the base (masked-tree-as-apply-base-starves, VERIFIED).
V1/V2: Same in v1 and v2.

## Apply mechanism: per-path verifying writer
CHOSEN: No git command ever writes the user's working tree. read-tree -u, checkout-index, checkout, reset --hard and stash are forbidden in the daemon (lint). Compute M_disk = `merge-tree --write-tree --merge-base=A S_disk TIP`, where S_disk is the full snapshot including held bytes. Conflicted paths (exit 1) are never written and never published; they go to the conflict policy (another group's resolution). Let D be the defer set: fenced, locked, in a running Bash/PowerShell transaction, the change-set closure from the atomicity group, conflicted, or failing portability. For each p in diff(S_disk, M_disk) minus D:
1) Write bytes = `git cat-file --filters --path=p <M_disk[p]>` to <gitdir>/cowork/tmp/<n>.new. tmp must be on the same volume as the worktree; otherwise v1 refuses at start.
2) Rename p to tmp/<n>.old. On EBUSY/EPERM/EACCES, defer p with reason 'locked'.
3) Check `git hash-object --path=p tmp/<n>.old` == S_disk[p]. On mismatch (a concurrent edit), put the file back with link-no-replace and re-merge with `git merge-file -p`, base = S_disk[p], ours = found, theirs = M_disk[p]. If clean, retry with that result as the target (at most 3 times). If it conflicts, restore the found bytes and defer p.
4) fs.link(new, p), then unlink new. EEXIST means someone recreated p; treat that file as 'found' and apply step 3. Deletions skip step 4. Creations skip steps 2-3 and use link-no-replace, so an existing untracked or ignored local file is never overwritten; it is deferred and the user is told.
5) Post-write round-trip: `hash-object --path=p p` must equal M_disk[p]. Otherwise the path is a phantom path: hold it and alert (this is the ping-pong breaker).
6) Update the private index for p with `update-index --cacheinfo` + `--refresh -- p`.
.old files stay in the ring for at least 2 s and are re-hashed before deletion. A changed .old means a late write through an open handle; merge it back as a local edit (its pre-image is already in git as S_disk[p]). Volumes without hard links fall back to rename-over, and the residual window is logged once at start. Accepted cost: readers can see ENOENT during the rename-to-link gap. After the batch: A[p] := TIP[p] for each written p; deferred paths keep A[p]; LA_C := TIP; one state update-ref.
WHY: read-tree -u is unsafe in two VERIFIED ways. It overwrote concurrent saves with exit 0 in 6/6 trials (apply-clobbers-concurrent-save, ed/e3). It also half-applied under a Windows lock while leaving the index stale (partial-apply-on-lock, e2; apply-partial-on-file-lock, e6). A temp index without stat data fails 'not uptodate' on every apply (VERIFIED in the protocol and atomicity lenses). Per-path compare-then-replace keeps every displaced version either in git (S_disk) or merged (P1), turns locks into a visible per-path deferral instead of a wedge (P2), and expresses the per-path holds and deferrals other groups need (INCOMING holds, change-set closure) with no tree surgery (P3). Link-no-replace on creation fixes ignored-file-overwrite (VERIFIED). The post-write round trip enforces the convergence assumption (phantom-delta-pingpong-convergence).
V1/V2: v1: refuse when tmp is on a different volume, and for symlink and gitlink entries (no live apply). v2: Windows ReplaceFile-based atomic swap via a native helper, and symlink support.

## Snapshot: explicit path list into a persistent private index
CHOSEN: The snapshot is an explicit path list added to the persistent private index; never `git add -A`. The list = (tracked paths of A) ∪ (missing tracked paths, which the same pathspec stages as removals) ∪ (U10-admitted new files: `git ls-files -o --exclude-standard -z`, minus secret-like patterns, minus files > 1 MB, minus the per-repo include/exclude config, minus portability failures). Command: `GIT_INDEX_FILE=<gitdir>/cowork/<b>.index git add --ignore-errors --pathspec-from-file=- --pathspec-file-nul`. It uses the user's own config, attributes and filters, and keeps index context so the stored form is preserved. On exit 1, each `unable to index file '<p>'` (parsed under LC_ALL=C) marks p UNREADABLE for this loop. Its index entry keeps the previous value; it is excluded from the outgoing delta (S_pub[p] := A[p]) and added to the apply defer set. It never fails the whole snapshot. Paths whose content was not stable get the same treatment for that loop: size or mtime changed between the pre-stat and post-stat, or the file went from non-empty to empty with no hook event. S_disk = `write-tree` of the private index. The private index is never reseeded per loop. Reseeding happens only on join or recovery, always followed by `update-index -q --refresh`. Exact EOL/BOM handling is owned by the EOL group. The engine requires only that bytes which did not change produce the same blob (round trip).
WHY: My experiment sweep/core_engine/x2_snapshot_list.sh is VERIFIED on git 2.55.0.windows.3. With b.txt opened FileShare.None by another process: exit=1, stderr 'unable to index file b.txt'. a, c and n were indexed with new content; the deleted d.txt was staged as a removal; b kept its old blob; .env (not listed) was not added; the user's own index was untouched. After the unlock, a retry of b alone succeeded. This fixes locked-file-stalls-snapshot (VERIFIED), where `add -A` failed fatally. It honours U10 scope explicitly instead of through `add -A` (untracked-sweep, VERIFIED), and a persistent index avoids a full re-hash every cycle (seeded-index-rehash-every-cycle, reseeded-index-full-rehash, VERIFIED about 750-1000 ms vs about 60 ms).
V1/V2: v1: list-based add. v2: Node-side reads plus `hash-object -w --path` if git's file mapping is shown to break editor saves on Windows (open question in editor-fs).

## The loop, step by step (push rule, epoch guard)
CHOSEN: One daemon per clone; per branch; one iteration at a time.
0 EPOCH GUARD. Read: symbolic HEAD; HEAD oid; refs/stash oid; the marker set {index.lock (wait ≤ 10 s, then report), MERGE_HEAD, CHERRY_PICK_HEAD, REVERT_HEAD, BISECT_LOG/BISECT_START, rebase-merge/, rebase-apply/, sequencer/, AUTO_MERGE}; unmerged entries in the user index. The expected epoch = (refs/heads/<b>, H_adopt from state, stash oid in state). Any unexpected difference FREEZES the branch: no publish, no apply. The human and that session's Claude are told. The freeze lifts when the epoch returns to expected (for example, HEAD back on <b> at H_adopt, or a pushed local commit becoming the new live base via R3), or via `/cowork resume`, which runs R9 lost-state recovery. The daemon's own adopt pre-registers the new epoch in the journal.
1 FETCH code, board and branch into refs/cowork-remote/<b>/*.
2 INV-FF check (R1). If the branch moved, run R3.
3 SNAPSHOT (R7), giving S_disk.
4 OUTGOING GUARDS: S_pub = mask(S_disk), from the hold registry (claims/push gate, revert/provenance detector, mass-change breaker, change-set holds; owned by other groups). Assert INV-MASK.
5 APPLY if TIP != LA_C. First write the journal {A, S_disk, M_disk, TIP, paths} into state (update-ref). Then run R6. Then one state update with the new A and LA_C and the journal cleared.
6 PUBLISH if diff(A, S_pub') is non-empty, where S_pub' is recomputed after step 5. OUT = `merge-tree --write-tree --merge-base=A S_pub' TIP`. Conflicted paths are not pushed; they go to the conflict policy. Pre-push asserts:
(a) parent == TIP == lease value;
(b) paths(diff(TIP, OUT)) ⊆ paths(diff(A, S_pub'));
(c) for every p with S_pub'[p] == A[p]: OUT[p] == TIP[p];
(d) OUT is a valid, non-empty tree oid, and the merge introduced no conflict-marker lines.
Any failure aborts the push and raises doctor plus a loud notice. Then C = `commit-tree OUT -p TIP` (with trailers), pushed with --force-with-lease=refs/cowork/<b>/code:TIP when the governor gives a slot. On ok: LA_C := C; A[p] := C[p] wherever C[p] == S_pub'[p]; other paths keep A[p]. On reject: nothing changes. On no answer or timeout: fetch; success iff C is on the new TIP's first-parent chain, otherwise treat it as rejected (C's oid is deterministic). Never push a raw snapshot or a stack of local commits.
WHY: Committing on top reverted teammates' work (naive-push-reverts-unapplied-paths, VERIFIED e1; pushed-tree-must-be-merge-result). Asserts (b) and (c) make 'never push a change to a path you did not change' mechanical (INV-DELTA). Assert (d) covers empty-oid-push-deletes-live-ref (VERIFIED) and conflict-markers-enter-live-ref (VERIFIED). The epoch guard is the git-detectable part of user-git-ops-broadcast-as-revert, branch-switch-publishes-other-branch and in-progress-ops (all VERIFIED: bisect leaves only BISECT_LOG, stash leaves no markers). Content-level reverts that git cannot see (/rewind, stale buffers, checkout -- .) are caught in step 4 by the hold registry's detector, not by the engine.
V1/V2: v1: freeze on any unexpected epoch change; branch switch while live = refuse/freeze (P4). v2: live sessions on several branches with automatic rebinding.

## Join and restart recovery
CHOSEN: JOIN (no state ref for <b>). Require symbolic HEAD = refs/heads/<b> and HEAD == Hb (live base of TIP). If HEAD is an ancestor of Hb, refuse with 'run `git pull --ff-only`, then /cowork start' (safe because cowork is not live yet). If HEAD is ahead of or diverged from Hb, v1 refuses ('push or move your local commits first'). Then set A := tree(HEAD) and take a snapshot S_disk. Preview: N files will change on disk (diff A->TIP); M local changes would be published (diff A->S_disk). Local changes are published only if the human confirms in the preview (with per-path opt-out). Unconfirmed changes become park-join holds in the hold registry: kept on disk, masked, mirrored to the board. The first apply runs via R6, and LA_C := TIP only after it. If nothing was opted in, assert that the first push changes nothing (OUT == tree(TIP)).
RESTART (state ref exists). If the journal is non-empty, decide each path p in it: clean(disk[p]) == M_disk[p] -> A[p] := TIP[p]; == S_disk[p] -> A[p] unchanged; otherwise p is held (unknown) for a human. A push intent is resolved as an ambiguous push (R8 step 6). An adopt intent is finished or rolled back per R10. Nothing is snapshot-published before recovery completes.
LOST STATE (state ref or one of its objects missing, or `/cowork resume` after a freeze). Never seed A from TIP or from the live base, and never silently re-join. Rebuild A per path: A[p] := the NEWEST blob of p on TIP's first-parent chain (bounded: back to the live base or 500 commits) that equals clean(disk[p]). For an unmatched p: A[p] := TIP[p], the bytes on disk are kept as a 'restart' hold (not published, not overwritten; apply defers p), and the human is shown the list. Set LA_C := TIP.
WHY: late-join-wrong-merge-base (VERIFIED): the live-tip base reverted all live work, the live-base base reverted a saved edit, and only the joiner's own HEAD was correct. Requiring HEAD == Hb makes the own-HEAD base also the team base, so P4 refuses the rest. crash-between-apply-and-state-resurrects-deletes (VERIFIED) and ambiguous-push-and-crash-stale-base (VERIFIED e3, e3b) are fixed by the per-path journal decision. The newest-match rebuild never invents a base that would resurrect deleted lines; unknown paths pause instead (P2).
V1/V2: v1: refuse to join when HEAD is ahead of or diverged from the live base. v2: join with local commits, by proposing a base move or a save.

## U9 safe adopt (local branch follows a save or base move)  [SIGNOFF]
CHOSEN: Trigger: the live base X (R1b) of LA_C differs from H_adopt in state. Automatic adopt runs only if ALL of these hold:
(1) symbolic HEAD == refs/heads/<b>, HEAD == H_adopt, and H_adopt is an ancestor of X (branch commits);
(2) no git operation is in progress (the R8 marker set);
(3) .git/index.lock is created with O_EXCL (if busy, retry next loop);
(4) for every p in diff(H_adopt, X): user index[p] == H_adopt[p] (nothing staged on that path), clean(disk[p]) == X[p] (U9 literally: the files equal the saved content), and p is not pending, deferred or held.
Action: write journal {adopt: H_adopt -> X} into state. Copy .git/index to a temp file. With GIT_INDEX_FILE=temp, update ONLY the entries for diff(H_adopt, X) (`update-index --index-info`, then `update-index -q --refresh`). Move the temp file to .git/index.lock and rename it to .git/index. Then `git update-ref -m 'cowork adopt' refs/heads/<b> X H_adopt` (CAS). Then a state update: H_adopt := X, journal cleared. The order is index first, then ref. A crash in between is finished on restart: if the index entries equal X and HEAD == H_adopt, redo the update-ref. If a CAS fails, roll the index entries back to H_adopt. No file is touched, and the user's staged entries on other paths are preserved. If any condition fails, nothing moves. The human gets one status line naming the failing paths and the reason, and that session's Claude gets the same. The check is retried every loop, so a peer that is not adopted now catches up at a later save when its disk matches. Human-typed `/cowork adopt` (not model-invocable) may adopt under a relaxed per-path test: `git merge-file -p --object-id H_adopt:p <clean(disk[p]) blob> X:p` is clean and equals clean(disk[p]), meaning the disk already contains the saved change plus later edits. It shows the paths and asks for confirmation first. The stale refs/remotes/origin/<b> may show 'ahead by 1' until the user's next fetch; this is harmless and documented.
WHY: My experiment sweep/core_engine/x3_adopt.sh is VERIFIED. B's disk held the saved content and B's human had staged an unrelated u.py. After the per-path adopt: the preconditions held, the CAS update-ref succeeded, `git status` showed only 'M  u.py' (staged work preserved), file mtimes were unchanged, `git pull --ff-only` exited 0, and a stale CAS was refused. This matches head-drift-after-pull-or-save (VERIFIED: adopt left status clean and pull at 0) and post-save-head-drift (VERIFIED: without adopt, pull is refused and stash reverts). The per-path index update is the added guard that keeps U9 safe even with a dirty index. The literal equality check is kept as binding. It can leave busy peers un-adopted after a save, and a walked-back save candidate makes it fail for paths changed after Lk. That state is safe, because the epoch guard freezes on stash and the revert detector covers the rest, but it is noisy. Hence the manual relaxed path and the sign-off question below.
V1/V2: v1: automatic adopt only on literal equality; relaxed adopt only through a human-typed command. v2 (if signed off): automatic relaxed adopt using the 3-way 'already contains' test.

## Engine invariants and property tests
CHOSEN: Invariants, each asserted in code where cheap and checked by the harness after every operation:
- INV-FF: every observed code or board tip change is a first-parent fast-forward, except during an incident.
- INV-BASEPARENT: second parents occur only on base-move commits and are branch commits; no branch commit has a live ancestor.
- INV-BASE: every 3-way merge of local work uses --merge-base=A; A[p] changes only after a verified write or a confirmed push of p.
- INV-DELTA: R8 asserts (b) and (c) hold for every pushed commit.
- INV-STATE: refs/cowork-local/<b>/state changes only by a CAS update-ref; LA_C is monotone on the first-parent chain.
- INV-NOCLOBBER: no byte sequence written to a working file by a human or Claude is lost; it is in a live commit, a hold, or the merged file.
- INV-SAVE-TREE: tree(saved commit) == tree of some live commit on the chain, and parent == the branch head it was leased on.
- INV-ADOPT: an adopt changes no file, preserves the index entries of unaffected paths, and happens only when R10's conditions hold.
- INV-REACH: after `git gc --prune=now` at any step boundary, every object referenced by state, holds or the journal still exists.
- INV-NOLOSS: every edit marker is at all times in the live tip, the saved branch, or a hold reachable from the remote board, unless a later edit by a peer whose A contained it changed it.
- INV-CONVERGE: with no new edits, every peer reaches snap == A == tree(tip), modulo its own holds, within K loops.
Shared harness: 3-4 simulated peers with real git on a file:// bare remote. Fixtures include a BOM+CRLF Python file of at least 5k lines, autocrlf=true, and a clean/smudge filter. Each edit carries a unique marker string. A seeded random generator interleaves: edit, fetch, push ok, push reject, push ambiguous (landed but reported failed), apply under a FileShare.None lock, concurrent write during apply at 0-1500 ms, kill -9 at every step boundary, `gc --prune=now`, git stash/checkout/bisect/commit, external commit to main, two concurrent saves, non-atomic save interrupted between branch and live push, remote ref rewind and deletion, late join with HEAD behind/equal/ahead, and adopt with staged and unstaged index states. Deterministic regressions to keep: x1 (save completion base), x2 (locked-path snapshot), x3 (adopt), e1, e2, e3, e3b, t3, ed/e3 lost.js, e10 and the late-join variants.
WHY: One harness checks every engine finding (P3). The VERIFIED experiments become fixed regressions (P6). INV-SINGLE-PARENT/INV-LINEAR is replaced by INV-FF + INV-BASEPARENT so that saves are not incidents. Convergence alone is not correctness, so INV-NOLOSS stays the acceptance gate (naive-push e1 converged to a reverted tree).
V1/V2: v1: harness on Windows plus one Linux runner. v2: a mixed-OS team matrix (macOS case-insensitive/NFD, Linux).

NEW RISKS:
- The live chain grows without bound: FF-only and no compaction in v1, by P1. A new joiner fetches the whole chain, and every peer's object store grows with each published change to the 1.3 MB file. Delta compression and pack size on GitHub have not been measured. A v2 epoch rollover would need a ref-naming convention beyond U2's fixed refs/cowork/<branch>/code.
- Daemon refs (refs/cowork-local/*, refs/cowork-remote/*) are visible in `git log --all`, gitk and some IDE graph extensions. A peer running `git push --mirror` would upload them, and would delete remote refs/cowork/* missing locally; the deletion is detected as a rewrite incident, but it pauses the whole team.
- Literal U9 adopt leaves peers who keep editing saved files (or any peer after a walked-back save candidate) with HEAD drift until a later save finds their disk equal. Their `git status` shows teammates' saved work as their own changes. Only the epoch freeze on stash and the revert detector protect them meanwhile.
- A base move for an external commit can bring back content the live chain deleted: a teammate commits from a working tree holding old live content, then pushes it. Correctness then depends on the hold registry's revert/provenance guard inspecting the base-move diff.
- Branch names whose cowork ref paths collide (e.g. branch 'x' gives refs/cowork/x/code, and a branch named 'x/code' would need refs/cowork/x/code/code) cause D/F ref conflicts. v1 should refuse such names at start.
- Verifying-writer gap: between rename-away and link, the file is briefly missing (ENOENT). Dev-server reloaders and watchers may see a delete and then a create, causing reload storms. Volumes without hard links fall back to rename-over, which leaves a small lost-write window.
- Editors that keep a file handle open and write after the daemon's rename put their bytes into the .old file. The ring re-hash recovers them only within its retention window. Windows handles opened without FILE_SHARE_DELETE instead block the rename, which defers the path (safe but slow).
- On hosts without --atomic, a save leaves a window where the branch holds S and live has not re-parented yet. Correctness then depends on every peer's plugin version implementing the save-completion rule identically, so protocol version skew must block saves.
- The save smoke check runs repository code in a throwaway `git worktree add` inside the user's repo. That is an execution surface, and it adds and removes worktree metadata. The check command must be explicit per-repo config, and worktree pruning must survive a crash.
- Adopt writes the user's index while IDE git integrations refresh it. O_EXCL index.lock collisions cause retries. A tool that writes the index without honouring index.lock could race with it (rare, not measured).
- Lost-state rebuild matches disk bytes against older chain blobs. If the content equals an older version that was later changed back (ABA), the newest-match rule picks the right base only if that newer equal version is within the 500-commit walk bound.
- Parsing `unable to index file` depends on the locale; daemon calls must set LC_ALL=C and an empty LANGUAGE. A git version that changes the message wording would silently turn locked-path detection into a whole-snapshot failure, so doctor should run a lock canary.
- v1 requires the cowork tmp directory (inside .git) to be on the same volume as the worktree. Setups using --separate-git-dir on another drive are refused.

## Conflict policy: what happens when merge-tree reports a conflict (contradiction 4, core)  [SIGNOFF]
CHOSEN: ONE conflict function. It runs only on the peer whose push needs OUT = merge-tree(LA, S_pub, TIP), which is by definition the later publisher. (0) merge-tree --write-tree runs with the fixed -c set (R4/R6/R9) and NO -X option (no renormalize/ours/theirs), no --union, no per-symbol splice. Clean paths proceed (subject to the region group's pre-merge withdrawal and post-merge identity check). (1) Each conflicted path (content, add/add, modify/delete, rename, binary) is first offered to the insertion-concat fast path (see the separate resolution). If it does not qualify or its tripwire fails: (2) TIP's entry for that path (including a deletion) goes into the outgoing tree AND onto local disk, written by the per-path verifying writer and deferred while a local lease on that path is live (R8). (3) The whole LOCAL blob of that path becomes ONE record in the single hold registry: kind PATCH, guard 'conflict', stages 1/2/3 = (LA, LOCAL, TIP) stored-form blob oids, origin (session id or 'human'), causer and holder per the tie-break resolution. It is mirrored to the board ref with the next push, with no extra push. The minimum granularity is the whole path; the change-set atomicity group may widen it to the whole change-set, never narrow it. (4) The conflict-markered tree from merge-tree exit 1 is never written to disk, the private index, a pushed tree or a hold. (5) Notices follow U6: one canonical warning to the causer's Claude ('cowork-sync on behalf of <holder>'s session'), one notice to the holder's Claude, and a status/OS line for each human. (6) Human/Claude commands: /cowork resolve <id> --restore runs merge-file -p --object-id (TIP_now, LA, LOCAL) and re-applies the result as an ordinary local edit through every gate (claims, revert detector, change-set rules). Also --handoff (U5 queue), --show (3-way view from oids) and --discard (logged human event). Binary paths follow the same rule at whole-file level.
WHY: U4 makes earlier publication the winner, so the team-visible content must be the TIP. Option B leaves the path diverged and unsynced until a human acts. The causer keeps editing on a stale base, and others never see the causer's change, so B contradicts U2's two-way shared tree and makes later conflicts bigger. Option C is VERIFIED unsafe: git --union produced a SyntaxError on the EOF-append race (e5, and again in DH6) and silently fused two different 'def helper' bodies into one (DH6). -X ours/theirs drops a side with exit 0 (e5). Splicing corrupted bytes (offset-units-form-drift) and duplicated functions (move-splice-duplicates). Option D is subsumed by the concat fast path, which is safer because it never uses git's zealous union. Under A, nothing is lost (P1): LOCAL is a stored-form blob in a registry mirrored to the remote board, and TIP is in the live chain. The rule is deterministic (no pause needed for a decided outcome), and there is one store and one policy (P3). Taking the whole path keeps disk equal to a known-published state rather than a mixed theirs-on-conflict result. The restore command recovers every clean hunk in one step, so whole-path displacement costs one command, not lost work.
V1/V2: v1: whole-path displacement plus the restore command. v2: optional per-hunk theirs-on-conflict auto-restore of clean local hunks, but only once the region group's identity check has been proven on the 1.3 MB file.

## Tie-break: what 'earlier publication' compares (code order vs claim order)
CHOSEN: CONTENT = code order: the conflict policy never rewinds the TIP, and live refs stay fast-forward. BLAME = claim order: the 'conflict causer' (U4/U6) is the side whose claim on the overlapping lines was published LATER, ordered by board commit order of the claim records, never by timestamps. If neither side had a published claim covering the overlap, the later code publisher (the peer running the merge) is the causer. Divergent case: the TIP holds a non-holder's change inside a region the LOCAL side claimed earlier. Then the TIP stays on disk and in the tree. The holder's local version becomes the conflict hold, flagged 'claim-breach'. Publishing of that path pauses on the holder side (P2), and the holder's Claude and human are told. When the holder runs /cowork resolve <id> --restore, its version is published (allowed because it holds the claim, and recorded as RESOLVED_PUBLISH so the revert detector does not flag it). The breaching change, still in the live chain, is then recorded as a handoff in the holder's queue (U5). Nothing is rewound automatically.
WHY: Automatic rewind would make a live commit revert a published change and break fast-forward-only live refs. That breaks the ancestry checks other groups depend on, and the revert detector would have to whitelist it. Keeping content in code order means one ordering for bytes. Blame in claim order keeps U4's meaning ('later claim = causer') and U6's wording. The breach case is an anomaly: the push gate should have stopped it, so it pauses and asks instead of resolving cleverly.
V1/V2: v1: as chosen. v2: none planned.

## Insertion-concat fast path (the only automatic resolution; replaces union and the CHANGELOG union list)
CHOSEN: For a conflicted path, auto-resolve ONLY when ALL of the following hold. (a) The path is text (not binary per git's NUL-in-first-8000-bytes rule or a -text/binary attribute) AND either has a grammar pinned in the board regionSpec (py/js/ts/cs) or matches the config list 'insertionMerge' (default CHANGELOG*, HISTORY*, NEWS*, *.md, *.txt). (b) git diff -U0 <LA blob>..<TIP blob> and <LA blob>..<LOCAL blob> each have, for this conflict region, exactly one hunk of the form -N,0 at the same N (pure insertions, no base line modified or deleted). (c) No non-blank line occurs in both inserted blocks. (d) Output bytes = LA[1..N] + TIP block + separator + LOCAL block + LA[N+1..]. The earlier-published (TIP) block comes first. Each block is kept byte-for-byte. A separator is synthesized only when neither block already supplies blank lines at the seam (Python: 2 blank lines between top-level defs, C#/JS: 1, prose: 0), and it uses the LA blob's line ending. (e) The output passes canon (EOL/BOM rule) and the tripwire: valid UTF-8 where the input was valid; no new tree-sitter ERROR nodes compared with TIP; no (kind, qualname) count above max(count in TIP, count in LOCAL); every output line appears in LA, TIP or LOCAL. Otherwise the path falls through to the general conflict rule. No events are emitted for a successful concat. Git's union driver is never invoked by cowork. (A repo's own committed merge=union attribute is honoured by git itself; see the attr.tree resolution.)
WHY: Measured in DH6: git --union gave a SyntaxError for two EOF-appended functions and silently fused two different 'helper' bodies into one. The ordered concat parsed, and the duplicate-qualname case is caught by precondition (c) and the tripwire. Claude routinely appends helpers at EOF and imports at the end of the block, so without this path every such race costs a Claude turn and a U6 warning (U7 cost). Removing the fast path leaves the system correct, only costlier, which is why it is safe as an optimization under P3/P4. The product-ux-ops CHANGELOG union list is deleted because concat covers prepends and appends to CHANGELOG/patch notes with one mechanism.
V1/V2: v1: same-anchor pure insertions only, parsed languages plus the prose list. v2: JSON/YAML/XML-aware insertion merge (trailing commas and so on), which in v1 go to the conflict hold.

## EOL / BOM stored-form handling (contradiction 6), including byte safety
CHOSEN: The stored form is a property of each existing path, taken from its LA blob (falling back to EPOCH_BASE): bom in {yes,no}, eol in {LF, CRLF, MIXED, NONE}. ONE deterministic byte transform canon(newBlob, refBlob) is applied to every blob the daemon creates for an existing text path (snapshot output, hold restore, concat output). (1) Add or strip the EF BB BF prefix to match ref. (2) ref LF: every CRLF becomes LF. ref CRLF: every lone LF becomes CRLF. Lone CR is untouched. (3) ref MIXED or NONE: no change; but if any line differs from ref only in its ending, then v1: refuse. That path becomes a PATH hold with guard 'eol-bom' and the session and human are told. (4) canon skips binary paths. Input is git-produced stored-form bytes (private-index add or hash-object --path, run through required filters). Output is written with hash-object -w --stdin --no-filters and passes a tripwire: output lines with EOL/BOM stripped equal input lines. New paths (no ref) are hashed with the user's config plus -c core.autocrlf=input unless text/eol attributes decide, which yields LF blobs. Merges are plain merge-tree, NEVER -X renormalize. Incoming: a TIP blob whose form differs from LA's form for an existing path is a protocol violation. It is not applied; it becomes an INCOMING hold and both sides are told. Checkout side (writes into the user's worktree): the user's own core.autocrlf/core.eol plus pinned attributes, so files look exactly like the user's normal git checkout. Disk repair: if a local file's form differs from canonical (for example a Write dropped the BOM), the session is told once in PostToolUse context. The verifying writer then rewrites the disk form at the next quiet moment (path not leased, stable across 2 polls), so the private index regains stat data and the path is not re-hashed every cycle. EOL/BOM changes happen only through /cowork eol <path> --lf|--crlf|--bom|--no-bom, a human command that publishes a whole-file change under a whole-file claim. There is no team-pinned autocrlf, no join refusal on autocrlf mismatch, and no separate 'drop EOL-only hunks' step (canon makes EOL-only hunks impossible in published blobs). Region/claim logic reads stored blobs by line rows only. The daemon never round-trips file bytes through JS strings to write. JS decodes only for read-only analysis, with {fatal:true, ignoreBOM:true}. canon works on raw bytes (0x0D/0x0A never occur as cp949 trail bytes).
WHY: DH2 (VERIFIED this round): -X renormalize flipped an i/crlf blob to LF (10 CRs to 0) even though both sides kept CRLF. On hub.py, if stored i/crlf, that is a 26k-line diff. DH1: renormalize ran the secret filter 6 times per merge. DH3: a whole-file flip conflicts under a plain merge, and renormalize 'fixes' it only by flipping the stored form. So preservation must happen on the outgoing side, before any merge. e14 VERIFIED that no autocrlf value can reproduce CRLF from an LF working file, so per-path or team-pinned autocrlf (options 1-3) cannot work alone. A post-hash transform does, and once every blob is canonical the peer-config fingerprint and join refusal are unnecessary (P3). e7/e14 VERIFIED that 1-line edits became 280/280 and 500/500 whole-file diffs without this. daemon-text-handling VERIFIED cp949/BOM corruption through JS strings.
V1/V2: v1: LF/CRLF/BOM canon; MIXED-form files refuse EOL-only changes with a clear message. v2: per-line ending preservation for MIXED files.

## Fence / lease TTLs (contradiction 15, TTL part)
CHOSEN: ONE local apply-deferral lease per (seat, path), timed only by the local monotonic clock (P5), with two kinds. INFLIGHT: taken at PreToolUse of Edit/Write/MultiEdit/NotebookEdit and keyed by tool_use_id. It is released by PostToolUse or PostToolUseFailure with that id, a PostToolBatch that lists it, the same seat's next PreToolUse or UserPromptSubmit, Stop/StopFailure/SubagentStop, or MCP disconnect. Backstop TTL 120 s. READ_FOR_WRITE: taken at PostToolUse(Read) of a full read. It is released by that seat's next Edit/Write PostToolUse on the path or after 120 s, and can be renewed while the seat is active up to 5 min total, once per file per turn. While any lease is live, the applier skips that path (the incoming change stays pending) and the snapshot does not re-read it. After expiry, the daemon writes only through the verifying writer's up-to-date check, and expired leases are shown in status. The Bash/PowerShell transaction cap uses the same 120 s constant. Tentative claims taken at PreToolUse are separate: they are published only after PostToolUse confirms a real change, so lease length never affects other peers.
WHY: A lease only defers LOCAL applies of one path, so a long backstop costs nothing to the team. ## Hook types per event (one loader, command hooks only)
CHOSEN: All hooks are exec-form command hooks {"command":"node","args":["${CLAUDE_PLUGIN_ROOT}/dist/hook.js","<event>"],"timeout":10}. There are ZERO mcp_tool hooks. hook.js is a dependency-free loader of at most about 150 lines. (1) Its first statement is process.on('uncaughtException') and process.on('unhandledRejection'), both mapped to exit 2 plus a fixed stderr message for gating events and to exit 0 for non-gating events. (2) It finds the gitdir by walking up from cwd, without spawning git. If <gitdir>/cowork/live is absent, or <gitdir>/cowork/paused exists, it exits 0 immediately with no IPC. This matters because the user-scope plugin fires in every repo. (3) It loads require(dist/core.js) inside try/catch, mapped to exit 2 with 'cowork-sync hook failed to load (version X); edits paused for this repo. Human: type /cowork pause to continue without coordination, or /cowork doctor'. Event map: SessionStart (startup|resume|clear|compact|fork); UserPromptSubmit; PreToolUse matchers 'Edit|Write|NotebookEdit', 'Bash|PowerShell', 'Agent|EnterWorktree'; PostToolUse matcher '.*' (Read registers the read set, edit tools confirm, Bash/PowerShell closes the transaction, every tool carries attribution notes); PostToolUseFailure '.*'; PostToolBatch; Stop; StopFailure; SubagentStart; SubagentStop; SessionEnd; Notification (idle_prompt|permission_prompt). A single crash of the MCP server would therefore silently disarm gating for the rest of the session. A command hook's failure modes are a strict subset: a throw or load error can be mapped to exit 2, and only ENOENT, SIGKILL and host timeout escape. One loader and one hook type replace two gate implementations (P3). VERIFIED sweep/e11: a node exec-form hook with named-pipe IPC costs p50 30.8 ms / p95 42.8 ms, and exits 2 in 32 ms with the daemon down. Shell form is rejected because on Windows it routes through Git Bash or PowerShell and changes the parent process.

## Gate failure semantics (exact outputs)  [SIGNOFF]
CHOSEN: The PreToolUse(Edit|Write|NotebookEdit) gate has exactly four outcomes. (G1) The daemon answers and reports a conflict: exit 2, stderr reason ≤800 chars, fixed template (see the injected-text rule). (G2) The daemon answers with no conflict: exit 0 and stdout either empty or JSON containing only hookSpecificOutput.additionalContext. The gate NEVER emits permissionDecision 'allow' and never emits 'ask'. The only 'ask' in the product is the human-typed /cowork override flow. CI greps the bundle for permissionDecision "allow" and for "ask" outside override.ts. (G3) The daemon answers but the remote is unreachable or auth has expired: this is a KNOWN state. The gate decides from the daemon's claim cache as of the last successful fetch (G1/G2 as usual). New claims are tentative, published on reconnect, and races are resolved by publication order (U4). A notice is sent ONCE per offline episode: systemMessage to the human and additionalContext to Claude ('cowork-sync offline since <local time> (<reason>); edits continue but are coordinated only when the connection returns'). It escalates once more at 10 min offline and is shown in every digest. No 'ask'. (G4) The daemon is unreachable: the loader spawns the daemon detached (no waiting on network) and retries connecting until the 1.5 s internal deadline. If it is still unreachable, exit 2 with 'cowork-sync background sync is not running for this repo; this edit was not made. Human: /cowork doctor, or /cowork pause to edit without coordination.' /cowork pause writes <gitdir>/cowork/paused, which the loader checks before any IPC, so the escape works even with a broken bundle. The human-typed /cowork resume removes it. The paused state is shown in status and published on the board so teammates see 'X: not coordinated'. Internal exceptions map to exit 2 (same message, cause 'hook error'). PreToolUse(Bash|PowerShell) follows the same G1-G4 for its advisory denies. The MCP server never returns isError for status tools (it returns a structured 'daemon down' result).
WHY: 'allow' skips the user's permission prompt and turns dontAsk auto-denies into approvals (DOCUMENTED gate-returns-allow-skips-prompts), so it is never emitted. 'ask after 30 s offline' would raise a permission dialog on every edit during a Wi-Fi drop, which trains blind yes-clicking. Offline editing is exactly U4's optimistic model, and conflicts become handoff records (P1), so G3 continues. G4 is the 'uncertain' case of P2 and pauses the session with a human-only escape. Because nothing publishes without the daemon (B1), G4's pause buys no publish safety. It does keep Claude from building on stale claims and makes the outage loud, which is why its friction is a user choice.
V1/V2: v1: G4 = pause (pending sign-off; the alternative is 'continue with notice, publish gate re-checks'). G3 continue-with-notice.

## Gate deadlines
CHOSEN: Host timeout: every hook declares "timeout": 10. The loader's internal deadline is 1.5 s from start for gating events, 3 s for SessionStart, and 1.5 s for all others. On expiry it takes outcome G4 for gating events and exit 0 for others, so the host timeout (which fails open, VERIFIED) never fires first. The daemon answers gate queries only from memory: a claim and region cache plus trees parsed in a worker_threads pool and cached by blob oid. Hook handling never waits on git, the network or a parse. If the current file's tree is not ready, the conservative fallback region (enclosing indentation block or top-level def via a regex scan) is used, and PostToolUse is authoritative anyway. If the verifying writer is mid-write on the same path, the reply waits for that one single-path write, bounded at 250 ms; whole-apply waits do not exist because the applier writes path by path. Budgets: daemon-side ≤15 ms p95, end-to-end ≤60 ms p95 on Windows, event-loop blocking ≤20 ms (monitorEventLoopDelay; exceeding it is shown in status).
WHY: VERIFIED sweep/e12: a main-thread parse of the 1.3 MB file blocks the event loop 337-368 ms, so a 400 ms deadline produces spurious G4 pauses unless parsing moves off-thread. Moving it off-thread makes 400 ms unnecessary, and 1.5 s leaves headroom for Windows Defender and cold starts. VERIFIED sweep/e11 p50 30.8 ms / p95 42.8 ms shows the normal path is far below any deadline. VERIFIED run1: a 3 s host timeout cancelled the hook and the Write proceeded, so ours must fire first. ## Degraded seat: whole-repo 'no fence, no apply' vs per-session UNGUARDED
CHOSEN: A seat becomes DEGRADED when the daemon observes any of: a PostToolUse or PostToolUseFailure for an edit-class tool_use_id with no matching PreToolUse (the host timed the hook out, or it failed open); hook traffic stopping while that seat's claude process (ppid) is alive and its MCP heartbeat continues for more than 60 s during an active turn; or a SessionStart registration whose hooks then never reach the daemon. Effect: the applier holds incoming changes ONLY for paths in that seat's read set and edit set from the last 30 min (incoming changes stay pending in memory, nothing is dropped). Publishing continues through B1. A loud notice goes out on the seat's next working hook: additionalContext plus systemMessage 'cowork-sync: checks for this session were skipped by Claude Code (<cause>); changes to <n> files are held until checks work again'. The board shows the seat as degraded. The seat recovers after 3 consecutive matched Pre/Post pairs. No whole-repo stop: other seats on the PC keep syncing. A session whose hooks never run at all (node missing) has no seat. Its edits are 'human-class' to the daemon (outside any tool window) and follow the human rule. ## File fence lifecycle incl. PostToolUseFailure, interrupts and permission prompts
CHOSEN: A fence is a lease keyed by tool_use_id, with a refcount per path. PreToolUse(Edit|Write|NotebookEdit) acquires it for the target path, and only after the gate has decided G2 (a denied call takes no fence). Maximum life 20 s. After expiry it writes only through its CAS check. Fences exist to avoid churn and are not a safety mechanism (B2 and the revert guard cover a lost race). WHY: DOCUMENTED: PostToolUseFailure does not fire for permission denials or cancellation, PermissionDenied fires only in auto mode, and Stop does not fire on user interrupt. So any fence that needs a Post event leaks. ## Claim confirmation: PreToolUse prediction vs PostToolUse authority
CHOSEN: PreToolUse predicts the edited symbols on a normalized view (BOM stripped, CRLF→LF, U+2018/2019/201C/201D folded) mapped back to raw offsets, listing every match for replace_all. The prediction is used ONLY to decide G1/G2 and to record TENTATIVE local claims. The fence captures the pre-image (blob oid). At PostToolUse the daemon diffs pre-image against post-image (EOL/BOM-only hunks dropped) to get the authoritative changed-symbol set. Only symbols in that set become CONFIRMED claims eligible for publication. Tentative claims not confirmed are discarded at fence release. Every resulting hunk is tagged change_set = (seat_id, tool_use_id) so that the atomicity group can withhold or apply per change-set. If the authoritative set contains a foreign-held symbol the prediction missed, it goes through the same record-then-restore rule as Bash (next resolution). If locating fails entirely, the edit is never treated as a whole-file claim: it proceeds (G2) and the post-diff decides.
WHY: VERIFIED sweep/edit: Edit applied a LF old_string to a BOM+CRLF file and a straight-quote old_string to curly quotes, so raw matching misses. DOCUMENTED: there is no Post event on deny, rejection or interrupt, so claims published from PreToolUse would be phantoms. The change_set tag is needed because per-hunk withdrawal publishes trees that never existed (VERIFIED, atomicity gap).
V1/V2: v1 as stated.

## Attribution and handling of Bash/PowerShell edits
CHOSEN: ATTRIBUTION by tool window. PreToolUse(Bash|PowerShell) of a seat that passed G2 opens a TRANSACTION (seat_id, tool_use_id). The daemon records stat (mtime,size) for tracked and in-scope files, and on this PC takes NO snapshot and does NO apply into the working tree until the transaction closes (TXN-1/TXN-2). Fetch and merge continue in memory. Close triggers: PostToolUse or PostToolUseFailure with the same id; a run_in_background call closes when the tool returns; UserPromptSubmit, Stop, StopFailure or SessionEnd of the seat; or the cap of 120 s on the daemon's monotonic clock. Changes seen at close are attributed to that seat and tagged change_set=(seat_id, tool_use_id). Changes written after the cap, or with no open window, are attributed to '<this PC's human>'. If two seats' windows overlap, the change goes to both, and claims and conflicts use the stricter result. DISK RULE, one policy keyed by attribution: (1) Hunks inside symbols that a foreign claim holds earlier in publication order are never published (B1). (2) Before anything else, the attempted version is recorded DURABLY: a board handoff/request record with the attempted blob (via the pinned clean path, so filtered secrets never leak) addressed to the holder's queue (U5 'auto-record'). (3) If the writer was a Claude tool (Bash, PowerShell, or an Edit/Write whose authoritative post-diff hit a foreign-held symbol), the daemon then restores the holder's current version for exactly those hunks through the verifying writer, after the transaction closes. The local disk then equals the team version, the same end state as a pre-hoc deny. Claude is told through PostToolUse {decision:'block', reason ≤800 chars}: '<file>: changes to <symbol> were not kept. cowork-sync on behalf of <holder>'s session: <symbol> is claimed. Your version is saved as request R<id> and will be offered to them.' (4) If the writer was the human (outside any window), nothing is restored, because editor buffers and typed work must not be rewritten under the user. The hunk is held on disk in the hold registry (defined by the hold-lifecycle group) and the human is notified. Claude edits are never classed as human. The mass-change breaker and revert guard (other groups) remain the backstop for anything attribution gets wrong.
WHY: Tool-window attribution is observable and accurate for Claude's shell writes. Classing them as human (editor-fs) would leave a Claude's denied work on disk, divergent, and invite the agent to keep routing around denies. Restoring human edits would fight the editor. Record-before-restore satisfies P1 (the attempted bytes live on the board, not only on this PC's disk) and gives Bash the same end state as an Edit deny (U5). The transaction also stops snapshots splitting a codemod mid-run and stops applies landing mid-test. bashEditDiff is not used for enforcement: it is DOCUMENTED as beta and best effort.

# protocol
## (9) Hosts without --atomic: board ref is the single authority, and the code ref is a derived mirror  [SIGNOFF]
CHOSEN: D, the same rule on every host. (1) Refs: refs/cowork/<b>/board is the AUTHORITY and refs/cowork/<b>/code is the MIRROR. (2) Every board commit has the previous board commit as first parent (genesis has none) and the live code commit as LAST parent. When code did not change, the last parent repeats the previous code commit. live_code(board_tip) := last parent of board_tip, everywhere in the spec. Every other group's term 'live tip' means live_code(board tip) and never the code ref. (3) A publish is ONE `git push` with no --atomic and two refspecs: `--force-with-lease=refs/cowork/<b>/board:<observed board tip> <newBoard>:refs/cowork/<b>/board` and `--force-with-lease=refs/cowork/<b>/code:<observed mirror value> <live_code(observed board tip)>:refs/cowork/<b>/code`. The mirror is always set to the code pointer of the board tip the push is leased on, which is already authoritative. It is NEVER set to the pusher's own new code commit. So the mirror lags by at most one publish, never points at an unauthorized commit, and moves monotonically in board order. If the mirror lease fails, ignore it; the next publish heals it. (4) Daemons fetch only `+refs/cowork/<b>/board:refs/cowork-remote/<b>/board`. The code objects travel with it through the last-parent link. (5) The start-time probe checks: custom refs accepted, lease semantics, delete refused or allowed, and push-options. It does NOT check atomic, because the protocol never needs atomic. (6) Fallback namespace refs/heads/cowork/<b>/{board,code}: only with explicit per-repo opt-in after the probe passes, and every commit carries [skip ci] / ***NO_CI*** / 'skip-checks: true'. v1: refuse if the probe shows that 2-parent commits are rejected there (linear-history rulesets). (7) A non-retryable rejection of the board ref (policy, ruleset, pre-receive) pauses the publish loop and alerts loudly (see the governor rule). (8) Change-set manifests (Cowork-CS trailers) ride in the board commit's ops, which reference the code commit. The board and the code are one CAS unit on every host, so the change-set membership in cs-manifest-must-ride-code-commit is atomic for free.
WHY: non-atomic-pair-and-fence (VERIFIED) and x1 step 4 (VERIFIED, sweep/dp2/x1.sh) show that a two-ref push without atomic lands the code while the board is rejected, so code reaches a region the board says someone else holds. x1 steps 2 and 3 (VERIFIED) show that a board commit pushed alone carries the code commit's objects, and that a peer can resolve the code from board^2. Making one ref the authority means the CAS on that single ref is the only serialization point (P3). It works the same on Azure and on GitHub, so atomic-capability detection disappears, and so does the 'two-ref mode vs single-ref mode' split (P3, P4). Unlike option B, code trees never contain board data, so no strip step is needed in merge, apply or save. Unlike option C, it costs no extra push. The board chain never resets (saves move only the code pointer), so a fast-forward check on the board alone detects rewinds (ref-rewind-silent-revert, VERIFIED). That check uses ancestry on the board chain only. It does not violate INV-BASE, whose 'no ancestry' lint applies to merge-tree on code. The cost: the code ref lags by one publish (about 10-40 s), and a human who reads it directly sees slightly old content.
V1/V2: v1: one layout for every host that accepts refs/cowork/*. Hosts that reject custom refs work only with an explicit refs/heads opt-in; hosts that also reject 2-parent commits there are refused. v2: optional --atomic, when advertised, to remove the one-publish mirror lag.

## Board data model and compaction
CHOSEN: BOARD COMMIT = {parents: [prev board, live code commit]; message: '[skip ci] ***NO_CI***' + trailers 'skip-checks: true', 'Cowork-Proto: <n>', 'Cowork-Writer: <peer_id>/<epoch>'; tree: ops.jsonl = ONLY the ops introduced by this commit (replaced each commit, never appended); protocol.json = {proto, minReader, minWriter, budget: 6, G_s: 10, S_s: 3, T_ack_s: 120, K_evict: 200}; checkpoint/state.json = the full fold state, rewritten only on first-parent heights divisible by 256 and otherwise carried as the same tree entry at zero cost; held/<hold_id>/<n> = blobs of displaced versions that are not yet resolved}. CODE CONTENT on the board is ONLY blob ids produced through the pinned clean path (hash-object -w --path=<p>, or the private index). Never raw tool_input, prompt text or inline patch text. Notes are free text of at most 280 characters, only from an explicit MCP tool, after a local secret scan. OP = {id: '<peer_id>/<epoch>/<seq>', type, ...}. Types: join{display, plugin_version, proto, config_fingerprint (filter driver hash, autocrlf, eol attrs, git version)}, leave, seat_start{seat}, seat_end{seat}, claim{key, anchor{path, base_blob, stored-form byte range}, holder{peer, seat, agent}}, release{claim_ids, reason}, request{req_id, kind: handoff|go_first, from{peer, seat, user}, to_holder, key, base_blob, intended_blob, intent_note, attempt}, request_status{req_id, status: asked|queued_until_turn_end|awaiting_human|undeliverable}, answer{req_id, accept|decline|release|grant}, presume_absent{peer, epoch, last_seq_seen}, event{conflict_id = H(winner_op_id, loser_op_id), kind}, hold{hold_id, path, base_blob, held_blob, owner, reason}, hold_resolve{hold_id, outcome}, save{chain_base, save_commit}, reset{code_commit}. The request object is BORN AT DENY TIME (PreToolUse), with status pending_leftover. Stop, StopFailure, SubagentStop, SessionEnd, EOF and idle are only promoters, and none of them is required for the record to exist. FOLD: state = deterministic fold over the board's first-parent chain, in commit order and then line order inside ops.jsonl. An op whose id is already folded is a no-op. An op that is invalid against the state before it (for example a claim on a key held by an earlier claim, or a presume_absent whose last_seq_seen is not the peer's current highest seq) is a deterministic no-op, and the writer is told. Every daemon folds incrementally from its own persisted state. A joiner starts from the nearest checkpoint and replays at most 255 commits. A checkpoint that differs from a daemon's own fold is a P2 alert (version bug), and that daemon goes read-only. COMPACTION never rewrites history. The board ref is fast-forward-only for its whole life. 'Compaction' means: resolved requests, holds and events older than 2 checkpoints are dropped from state.json and their held/ entries are removed from the tree (they stay in history, P1). Unresolved requests, holds and claims are never dropped. Rotating the board (a new genesis) is v2: an explicit human command that archives the old tip under refs/cowork-archive/<b>/<n> first. Numbers: at most 6 board commits/min, with ops.jsonl typically under 2 KiB. Measured code-chain growth for a 1.38 MB BOM+CRLF file is about 0.9 KiB per commit packed (x2: 301 versions = 280 KiB). Even with every live snapshot kept reachable through the last-parent links, the worst case is about 3 MB/day at 6/min over 10 h. Doctor reports the size.
WHY: A fast-forward-only board keeps the rewind detector free of exceptions and keeps commit-oid cursors valid, which removes the failure class in op-identity-cursors-board-merge (REASONED) and the compaction race and queue loss in board-growth-compaction (P3: one order, one storage location). Per-commit op batches mean no peer ever rewrites another peer's data, so version skew cannot drop unknown records (version-skew-board-loss, version-skew-board-and-guards). minWriter gating covers incompatible changes. Blob-id-only payloads follow board-plaintext-and-permanence (VERIFIED: the clean path stores @@HIDDEN@@ and inline text stores plaintext). held/ keeps every displaced version durable and visible to the team rather than on one disk (P1; local-only-holds-break-nothing-lost, park-refs-in-worktree-namespace-vanish). Creating the request at deny time follows stop-handoff-silent-failure-and-reask-loop (VERIFIED: a failing Stop hook is invisible).
V1/V2: v1: FF-only board with no rotation, plus a doctor size report. v2: explicit archived rotation.

## Ordering and identity without wall clocks
CHOSEN: (1) ORDER: the only order is position on the board's first-parent chain, then line order inside ops.jsonl. 'Earlier claim', 'conflict causer', FIFO queues and the LRU push ranking are all functions of that order. Wall-clock fields may exist in ops for DISPLAY ONLY and are never an input to any decision. (2) IDENTITY: peer_id = 128-bit random per (clone, worktree), stored under `git rev-parse --git-path cowork`. epoch = random, new whenever the daemon's local state is (re)initialized. seq = monotonic per (peer_id, epoch) and persisted before the push. seat_id = random per MCP-server process. holder = (peer_id, seat_id, agent_id|'main'). User and display names are display-only. (3) AMBIGUOUS PUSH: a push with no explicit ok or reject is UNKNOWN. Resolve it by fetching and checking whether its op ids are on the first-parent chain since the leased base. Never resolve it by content, and never blindly re-send. (4) LOCAL TIME RULE: every timer is a delta from a LOCAL anchor taken by the same process ('time since I observed X'). Absolute readings are never stored as deadlines or compared across processes. A lint forbids Date.now() comparisons except through the anchor helper. The governor model's two clock-offset bugs (bucket init and turn-window init) are the regression tests for this lint. Observer-side waits use Δmono, which does not count suspend, so it errs toward waiting longer. A peer measuring its OWN staleness uses max(Δwall, Δmono), which errs toward 'I may be stale'. Suspend gap = Δwall − Δmono > 5 s on the same machine, and it marks own claims SUSPECT. (5) CURSOR: a session's delivery cursor = the last delivered board commit oid, plus a seen-op-id set for retries. This is valid because the board is fast-forward-only. (6) REWIND: a new board tip whose first-parent chain does not contain the last folded tip is a REWRITE INCIDENT. Apply nothing, push nothing, alert all humans and Claudes, and recover only through `/cowork recover`. A code-pointer move that does not descend from the previous code pointer is legal only when the same board commit carries a reset op (save); otherwise it is an incident.
WHY: lease-expiry-clocks-heartbeats (DOCUMENTED: CLOCK_MONOTONIC does not count suspend) and the skew scenarios show that any cross-machine timestamp causes spurious takeovers or immortal claims. Board order is total because the board is one CAS-serialized ref. The asymmetric local rule (observers wait on Δmono, self-staleness uses max) makes every error land on the safe side. The sim bugs showed how easily absolute readings creep in, so the rule is a lint rather than a guideline (P6, P5). ambiguous-push-and-crash-stale-base (VERIFIED) needs resolution by op-id.
V1/V2: v1: all of the above.

## (10b) Liveness within the push budget: no renewals, and liveness is proven only when contested  [SIGNOFF]
CHOSEN: Claims carry NO TTL and NO renewal. Liveness is proven only on contest: (1) A request op (handoff or go_first) against a claim obliges the holder's daemon, not its Claude, to publish request_status{asked | queued_until_turn_end | awaiting_human | undeliverable} at its next push window. The daemon knows its own seats' turn state locally, so the seat state is never published separately. (2) The requester's daemon starts a Δmono timer when it observes its own request in the folded board. If no op from the holder's (peer, epoch) appears within T_ack = 120 s, it publishes presume_absent{peer, epoch, last_seq_seen}. The fold applies it ONLY if that peer's highest seq in board order is still last_seq_seen. Any holder op earlier in board order makes it a no-op, so an acknowledgment that wins the race always wins. (3) Effect of an applied presume_absent: that peer's claims become STALE (visible, non-blocking) and its seats ENDED. Requests addressed to it are RETURNED to their requesters (status returned: holder_unreachable), so the requester can now do the work itself. Nothing is deleted. (4) Holder self-guard, stricter than the requester's wait: if the holder's own last successful fetch or push is older than 60 s by max(Δwall, Δmono), or a suspend gap is detected, its own claims become SUSPECT. PreToolUse on a SUSPECT symbol waits up to 5 s for a fresh fetch. If the board still shows the claim valid, the edit is allowed; otherwise it is denied with 'cowork cannot confirm you still hold f: offline since <local duration>'. That is a P2 notice to both the human and Claude. (5) A returning peer that finds itself presumed absent re-joins with a new epoch. Its unpublished hunks in symbols now held by others are LATER by board order, so they are withdrawn to held/ and queued to the new holder (U4/U5, P1). INV-FENCE blocks any zombie code push regardless. (6) Ghosts: a peer with no op in the last K_evict = 200 board commits is excluded from governor ranking, a deterministic fold rule, but keeps its claims until they are contested. Consequence: an uncontested, quiet team makes ZERO liveness pushes, and a contest costs exactly 1 push from the holder side (plus 1 presume_absent if the holder is unreachable). Margins: the push window is at most G + (N−1)·S = 19 s for 4 peers and about 40 s under full contention, and polling is 2.5 s active. So T_ack = 120 s is 3-6x the worst normal acknowledgment latency, and the 60 s self-guard expires before any observer can act.
WHY: Every periodic cadence spends budget in proportion to time × peers whether or not anyone is waiting (lease-expiry-clocks-heartbeats, claims-held-all-day-starvation). Liveness only matters when someone wants the symbol, so tying the proof to the request makes the cost proportional to contests (P3: one mechanism, the request/acknowledgment, replaces four cadences). The acknowledgment comes from the daemon, so an idle or absent HUMAN never loses a claim this way. Only an unreachable MACHINE does, and its version is preserved (P1). The fold-level seq check removes the takeover-vs-renewal race without clocks (P5). Self-guard 60 s < T_ack 120 s, using max(Δwall, Δmono), follows sleep-offline-stale-and-suspect-claims and lease-expiry-clocks-heartbeats.

## (10a) Push governor: LRU-ranked windows anchored on the locally observed board tip
CHOSEN: Parameters live in protocol.json on the board, and each daemon uses the stricter of local and board values: B = 6 attempts/min team, G = 10 s, S = 3 s, poll = 2.5 s while any local seat is active or work is pending, 10 s when idle. RULE: (1) The ranked set R = peers that are live in the fold (joined, not left, not presumed absent, with an op in the last 200 board commits). It is identical on every peer that folded the same tip. Never derive it from local observation. (2) rank(p) = position of p when R is sorted by (first-parent height of p's most recent board commit ascending, never-written first; peer_id), i.e. least-recently-written first. (3) When a daemon observes a new board tip, it sets anchor := its local monotonic now. For its own successful push, the anchor is when the ok was received. A peer with pending work may START an attempt only once Δ since anchor ≥ G + (rank−1)·S. This guarantees a spacing of at least G = 10 s between landed publishes as observed, which bounds the sustained team rate at 6/min. (4) If the tip moves before the window, re-anchor and re-rank. A peer that just wrote becomes last, and a CAS loser rises to rank 1, so no peer can starve. Worst-case wait = G + (|R|−1)·S = 19 s for 4 peers, plus one cycle per collision. (5) Every attempt (landed, rejected or ambiguous) is counted locally. Per-peer sanity cap: at most B attempts per 60 s of Δmono. (6) A CAS (lease) reject is retryable: fetch, fold, merge with --merge-base=A, then wait for the newly computed window. Never retry immediately. An ambiguous result is resolved by op-id presence before anything else. A non-retryable rejection (pre-receive or ruleset declined, GH013, protected ref, size, any 'remote rejected') stops publishing on that branch. It is excluded from retries, shows the host's exact message to every local seat (P2), and rebuilds the unpushed segment on the last accepted tip with the offending path held. Host throttling (HTTP 429/5xx or slow responses) doubles G locally, up to 60 s, and shows it in status. (7) Coalescing: everything pending (the code delta and all ops) goes in the one push of that window. There are no priority classes. Acknowledgments and requests simply ride the next window, which is at most about 40 s away at full contention, well inside T_ack. MODEL RESULTS (sweep/dp2/gov_sim.py, discrete-event, per-peer clock offset ±600 s and drift, fetch 0.45 s, push RTT 0.2-0.8 s, 1 h × 8 seeds, LABEL = MODEL, not measured on a host): 4 busy peers: 5.05 attempts/min sustained, peak 8 in some 60 s window (observation skew), 1.00 attempts per landed, publish latency p50 44 s / p95 47 s / max 48.5 s, equal shares (76/76/76/75). 2 busy: p50 31 s / p95 35 s. 1 busy with 3 idle-live peers: 3.06/min, p50 16 s / p95 19 s (the honest cost: idle-live peers' windows are skipped at S each). Light load (edit/60 s each): p50 9 s / p95 39 s, 1.08 attempts per landed. Baseline naive: 79 attempts/min and 2.12 per landed. Rejected variants: a token bucket gave a 637 s max latency with unequal shares, and membership from local observation starved one peer completely (0 landed/h, max 2628 s).
WHY: LRU over board history is deterministic for everyone who folded the same tip, and timing uses only each peer's own Δmono since its own observation. So no clock is compared (P5), and the CAS loser's rise in rank is an intrinsic backoff (P3: one mechanism handles fair share, burst and storm backoff). The model reproduced the measured baseline problems (cas-storm-starvation-governor e6c 2.5x; push-herd-governor-undercount sweep/e5) and showed that the alternatives either starve a peer or overshoot. The G spacing bounds the sustained rate. The 60 s peak can reach 8 because observation times differ by up to one poll interval. GitHub's 6/min is a recommendation, and the sustained rate stays at or below 6. Non-retryable classification follows push-rejection-poisons-chain. Budgeting attempts rather than successes follows push-herd-governor-undercount.

## (11) Claim lifecycle: no dormancy, no auto-grant, and the holder is asked
CHOSEN: STATES: TENTATIVE (taken locally at PreToolUse, unpublished, published once PostToolUse confirms that the symbol changed) → HELD (published, blocking). A HELD claim leaves that state only through these EVENTS: (a) the holder's explicit cowork_release, or its answer 'release' to a request; (b) a save that includes the symbol while the holder seat is not mid-turn (U8; the save op lists the released claims); (c) seat end: the MCP server reads stdin EOF, which happens only when the claude process exits (seat-identity-vs-session-id VERIFIED). The server tells the daemon seat_end, the daemon makes a final flush push (governed, but taking the next window) and publishes release + seat_end in that same push. An IPC drop WITHOUT seat_end (an MCP crash while claude lives) marks the seat UNGUARDED: claims are KEPT, the daemon does not write that seat's recently edited files, and both the human and Claude are alerted loudly; (d) /cowork stop, which runs the same sequence as (c); (e) presume_absent (liveness rule) → STALE. /clear, /compact and /resume keep the same seat (same MCP process), so claims persist, and SessionStart re-injects a digest of the claims held and the requests pending. There is NO time-based dormancy and NO auto-grant, ever. REQUESTS (born at deny time, see the data model): the holder daemon classifies each request by its seat's local state. Seat mid-turn → queued_until_turn_end, and the holder's Claude is asked at its Stop, StopFailure or SubagentStop (for the agent concerned) through the Stop block. Each request is asked at most once (asked_at recorded); after that, only digest lines. Seat idle (Notification idle_prompt, or no turn running) → asked now with ONE inbox message, batched with anything else pending for that seat. Wake budget per seat: at most 1 per 5 min and at most 4 per hour; over budget the status is undeliverable and the request waits for the holder's next prompt, where the digest carries it. Seat waiting at a permission prompt (Notification permission_prompt) → awaiting_human. No Claude is woken. Both humans see it at once (an OSC desktop notification on the holder's next hook, and status for the requester), and the request is asked at that turn's end. ANSWERS: accept → the holder's Claude does the handed-off work. A wake-started turn MAY edit, subject only to Claude Code's own permission mode for that session (no extra turn-origin lock), and every action of that turn is listed to the holder's human at their next prompt. decline → returned to the requester (U5). After 2 declines of the same (requester, key, intended_blob), it goes to the requester's HUMAN, not back to Claude. release → the requester gets a reservation: the first claim on the key goes to it, until the requester's next turn end. grant (go_first) → the holder's claim on that key is suspended until the requester's next landed push containing the change, or the requester's turn end, whichever comes first, and then returns automatically. No timers. Cycles in the wait-for graph (A waits on B and B on A) are detected when a request edge is published. The later edge in board order becomes a handoff, not a wait. STARVATION BOUND: a request against a reachable holder waits at most for the holder's current turn, or for its human to clear a permission prompt. Both humans see its age (measured locally since observed) in status, plus a desktop notification when it passes 30 min. It is never silently stuck (P2), and it is never auto-granted (U5/U6).
WHY: U5/U6 are binding: the holder is asked and preemption is never unconditional, which rules out auto-grant and 'dormant = non-blocking' (zombie-claims-idle-holder, claims-held-all-day-starvation). The starvation those fixes targeted is handled instead by asking an idle holder at once with a batched, budgeted wake (idle-wake-amplification, idle-wake-cost-shift-and-unsupervised-action) and by liveness on contest for machines that are truly gone. Release at EOF is safe because EOF means process exit (VERIFIED). The MCP-crash case is separated so it never fails open or silently (mcp-or-daemon-death-fails-open-and-stuck-fences, P2). The turn-origin lock was dropped because U5 has the holder do the work and Claude Code's permission modes already govern unattended edits (P3). Event-only transitions need no clocks (P5). Creating the request at deny time and asking once follows stop-handoff-silent-failure-and-reask-loop (VERIFIED). The deadlock rule follows deadlock-and-return-to-sender-pingpong.
V1/V2: v1: as specified. A human take-over of a claim whose holder is reachable but stuck at a permission prompt is v2 (v1 surfaces it to both humans and refuses to preempt).

## Convergence proof sketch, when the team is quiet
CHOSEN: DEFINITION: converged at board tip T* ⇔ for every live peer i and every synced path p not listed in the peer's NOT-CONVERGED report: snap_i[p] == A_i[p] == tree(live_code(T*))[p] (normalized blob OIDs), and every peer folds an identical board state. Working-tree BYTES are identical among peers with the same config_fingerprint. join REFUSES a peer whose fingerprint differs from the board's team fingerprint (v1: refuse, P4); the 3-4 person team (autocrlf=true + the same filter) therefore converges byte-identically. ASSUMPTIONS, each mapped to a rule: (A1) quiet = a finite number of edits, then no edits, human answers or Claude actions. (A2) every path can eventually be applied; a path that cannot (lock, fence leak, ping-pong breaker) is paused and listed in NOT-CONVERGED, and the proof covers the rest. (A3) round-trip: clean(smudge(x)) == x for synced paths, checked at start, with breaking paths excluded loudly. (A4) governor liveness: a peer with a pending delta reaches a window within G + (|R|−1)·S after any tip, and a CAS loser rises in LRU rank, so every pending publish lands within finitely many rounds. (A5) INV-BASE / INV-DELTA: a push carries merge-tree --merge-base=A_i(snap_i, tip), and after landing A_i := pushed tree on the written paths. PROOF: (1) The board is one CAS-serialized fast-forward chain, which gives a total order, and the fold is deterministic. Same tip ⇒ same state on every peer. (2) In quiet, no op is generated without a cause. No renewals or heartbeats exist. Acknowledgments and presume_absent are triggered only by requests, and requests only by actions. All causes are finite under A1. So the number of board commits is finite, and the tip becomes fixed at T*. (3) For each peer i, after the last landed push D_i = diff(A_i, snap_i) = ∅ (A5). At T*, peer i applies merge3(A_i, A_i, live_code(T*)) = live_code(T*) on applyable paths (A2), re-snapshots, and gets snap_i == A_i == T* by A3. No delta remains, so it does not push. That confirms T* is a fixed point. (4) HOLDS: a held, withdrawn or parked hunk is never on a peer's disk at convergence. Its bytes go to board held/ (durable, P1), and the working-tree region is restored to the tip version when its fence is free. A hold that cannot be removed from disk (an editor buffer, or a human-held revert awaiting a decision) makes that path NOT-CONVERGED, reported in status and to that session's Claude (P2), never silently tolerated. CONVERGENCE ≠ CORRECTNESS: correctness is INV-NOLOSS (every hunk is either in live_code(tip) or in board held/ or requests), proven by the property harness. Convergence alone would also hold for a team that converged on a revert. TEST: the INV-CONVERGE harness on file://: N peers with random edits, rejects, ambiguous pushes, a partition and a presume_absent, then quiet; assert the fixed point within bounded rounds and zero pushes after it.
WHY: This follows the INV-CONVERGE definition in phantom-delta-pingpong-convergence (REASONED) and e6c (VERIFIED: snap == tip on all 4 peers when every path round-trips). Requiring removal of held bytes or an explicit report closes permanent-hold-never-converges. The 'no renewal' rule is what makes step (2) hold: with any periodic heartbeat, the tip would never be fixed. Fingerprint refusal makes the byte-level claim true for a pilot team rather than aspirational (P4).
V1/V2: v1: refuse joins with a mismatched conversion fingerprint. v2: mixed Win/macOS teams with tree-OID convergence only.

NEW RISKS:
- UNKNOWN: whether GitHub (and other hosts) count one receive-pack session updating two refs (board + mirror) as one of the '6 pushes/min', and whether a lease-rejected push counts. The governor budgets attempts per session. Needs a hosted load test on a throwaway repo before the B=6 / G=10 s numbers are trusted.
- Board commits are 2-parent merges. Under the refs/heads fallback, a 'require linear history' (or signed-commits) ruleset rejects every publish. The start probe must push a 2-parent commit and refuse the fallback (v1) if it is rejected.
- The mirror refs/cowork/<b>/code lags the authority by one publish (about 10-40 s). Any component in another group that reads the code ref instead of live_code(board tip) works on stale or racy data. This needs a CI lint: daemon code may not read refs/cowork/*/code.
- Governor numbers come from a MODEL (gov_sim.py), not a network measurement. Observation skew produced 60 s peaks of 8 attempts against a sustained ≤6. A lone busy peer gets only about 3/min (p50 16 s) when 3 idle-but-live peers keep their windows.
- Every live snapshot stays reachable forever through the board's last-parent links, which makes history and any leaked secret permanent in refs/cowork/*. Measured growth is small (about 0.9 KiB/commit for the 1.38 MB file), but there is no rotation in v1.
- presume_absent can free a claim held by a machine that is alive but cannot fetch or push for over 120 s (for example a corporate proxy hiccup). Its self-guard (60 s, SUSPECT) makes it deny its own further edits, but its human may see unexpected 'you lost f' notices after short outages.
- No auto-grant means a holder stuck at a permission prompt for hours blocks requesters for that long. v1 only surfaces it, with a desktop notification after 30 min; no take-over exists until v2.
- Allowing wake-started turns to edit (no turn-origin lock) means a handed-off change can be applied with no human watching in acceptEdits or auto permission modes. It relies on Claude Code's permission mode, and on the post-hoc listing to the holder's human at the next prompt.
- Deterministic fold rejection (an invalid op becomes a no-op) depends on every peer running the same fold semantics. A fold bug in one version silently diverges board state, and only the checkpoint mismatch every 256 commits detects it. minReader/minWriter gating must be strict from release 1.

# messaging-security
## (12) Board content: no inline code text; attempted changes stored as clean-path blobs
CHOSEN: RULE BOARD-CONTENT. (1) The board schema is a typed allowlist (record types: CLAIM, RELEASE, REQUEST, HANDOFF, RESPONSE, CONFLICT, NOTE, HEALTH, CAPS). No record may hold raw tool_input, prompt text, transcript paths, OS usernames, file content or patch text. Fields intendedSymbolText and newSymbolText are deleted from the spec. (2) Code appears on the board only as git object ids: a record carries {path (repo-relative POSIX NFC), base_blob, proposed_blob, symbol_key}. Symbol text is derived at use time by reading the blob by OID and running region detection; it is never copied into a record. (3) Recording a denied Edit/Write/MultiEdit/NotebookEdit at PreToolUse: the daemon builds the full-file post-image in working-tree form (current disk bytes with the tool_input edit applied; for Write, the new content), then writes it with `git -c attr.tree=<base commit> -c filter.<F>.required=true ... hash-object -w --stdin --path=<path>` where <F> is every filter name that `git check-attr filter -- <path>` (under the same attr.tree) reports. The same `-c filter.<F>.required=true` is mandatory on every blob-producing daemon call (hash-object and `git add` into the private index). base_blob is the stored-form blob the edit was made against (from the private-index snapshot / LAST_APPLIED, read by OID). (4) The proposed blob is kept reachable by the board commit's own tree (records/<id>/proposed -> blob), so it is fetched by every peer and survives any single PC (P1). (5) If the required-filter call fails (driver missing or broken, rc!=0), the record is NOT published: the post-image is stored in <gitdir>/cowork/ as a local-only record flagged SECRET-FILTER-UNAVAILABLE, the path is paused for publish, and the human (systemMessage + status line + OS notification) and that session's Claude (additionalContext) are told in one fixed sentence. (6) Before every push (code or board) a tripwire scans every new blob: the repo's configured canary values/patterns recorded at /cowork start plus high-confidence patterns (PEM private-key headers, AKIA[0-9A-Z]{16}, ghp_/github_pat_, xox[abp]-). A hit withholds that push, pauses the path, and alerts loudly. The tripwire is a second line, not the primary defense. (7) Free text exists only in NOTE.text and REQUEST.reason, written only through an explicit MCP tool, capped at 280 chars, passed through the same local secret scan (hit -> refused with a message, not silently trimmed). Peer display names are chosen at setup, not taken from the OS. Daemon logs keep hashes and ids, never content. (8) /cowork doctor and README state: everything under refs/cowork/* is readable by everyone with repo read access and practically permanent on the host; the remedy for a leaked secret is rotation.
WHY: Measured: `hash-object --stdin` without --path stores plaintext + CRLF; with --path the clean filter runs (T5c, region/git1). New experiment sweep/msgsec/r: with --path, a broken clean command OR a driver missing from the daemon's config still exits 0 and stores 'REAL-SECRET' (fails open); adding `-c filter.secret.required=true` makes both cases exit 128 with no object written. So --path alone is insufficient; required=true closes the daemon-environment leak. Storing blobs (not text) also keeps CRLF/BOM handling in one place (stored form) and lets the holder reconstruct through smudge. Option C violates P1 (only one disk).
V1/V2: v1: blob-id records + required filter + tripwire; local-only fallback when the filter cannot run. v2: optional encryption of NOTE text; scrubbing tool for leaked board history.

## (13) Messaging token custody and delivery path, with fallback
CHOSEN: RULE MSG-TOKEN. (1) Only the session's own stdio MCP server (a true child of claude) ever connects to that session's inbox socket, using CLAUDE_CODE_MESSAGING_SOCKET/TOKEN from its own environment and the documented first line {"type":"auth","token":...}. The token lives only in that process's memory: it is never sent over daemon IPC, never written to disk, never logged, never placed in hook output. The daemon's environment is scrubbed of CLAUDE_CODE_MESSAGING_* at spawn and the daemon has no code path that opens an inbox socket. (2) Session pairing without the token: the SessionStart command hook sends the daemon {session_id, permission_mode, messaging_present, pairing_key = SHA-256(CLAUDE_CODE_MESSAGING_SOCKET value)}; the MCP server sends the same pairing_key at connect. When the messaging env is absent in both, pairing falls back to the nearest claude ancestor PID of each process; if pairing still fails within 3 s the session is UNPAIRED and is reported loudly (see managed-policy rule). The pairing key is not a secret; it is safe only because daemon IPC itself is key-authenticated (RULE IPC). (3) The inbox is a doorbell only. Every event is a board/daemon record with an id; Claude always receives it through hook pull (PreToolUse/PostToolUse/UserPromptSubmit additionalContext, SessionStart re-injection after compact/resume, Stop for handoff offers) using a per-(session, channel) cursor. An event is 'delivered' only when a later hook from that session reports its id as seen; an inbox send that is refused, held, times out or returns burst-refusal counts as not delivered and stays in the pull queue. (4) Fallback when the MCP server lacks the env (older Claude Code, --bare, messaging unavailable, crossSessionInbound refuse/hold): delivery state = HOOK-ONLY, shown in /cowork status and published in the session's HEALTH record so a requester is told 'not reachable live; queued as R<id>; shown at their next action'. There is no other fallback carrier (no token relay, no files).
WHY: VERIFIED H6 (sweep/host/EVIDENCE.txt, native Windows, Claude Code 2.1.27x/2.1.28x): the stdio MCP server env contains the session's own CLAUDE_CODE_MESSAGING_SOCKET (\\.\pipe\LOCAL\cc-msg-...) and 32-char token, identical to the SessionStart hook env. DOCUMENTED (cross-session-messaging.md): own-child verification is token-only on native Windows but process-evidence on Linux, so a detached daemon (not a child) posting with a relayed token would be unverified on Linux and held by bypass-mode receivers; the own-child exemption also applies only when no crossSessionInbound value applies, and 'refuse' shows no visible change. Hence the inbox can never be the carrier of record, and a daemon-held token is both less portable and a larger exposure. H6 is measured on one platform/version; other platforms fall into HOOK-ONLY automatically if the env is missing.
V1/V2: v1: MCP-child-only posting, hook-pull authoritative, HOOK-ONLY degrade. v2: re-measure H6 on macOS/Linux per Claude Code release in CI; per-session IPC keys.

## Batching, rate limits, dedupe, and the wake matrix (when a holder is woken vs not)
CHOSEN: RULE MSG-DELIVERY. (1) One canonical event per conflict: conflict_id = H(earlier claim op id, later op id), computed only from a fetched board tip. Only the causer's own daemon emits T1 and only the holder's own daemon emits T2. Bystander daemons emit nothing; their sessions get T4 in the next pull digest. (2) Per-(session, conflict_id, channel) dedupe: if T1 was delivered as a PreToolUse deny reason, no inbox or pull copy of T1 for that conflict_id is ever sent; a later race-detection of the same conflict_id is a no-op. Further edits by the causer to the same held symbol are denied with a one-line reason referring to {cid}/{rid} and do not create new events. Dedupe key for all events = (type, symbol_key, peer pair), not text. (3) Coalescing: at most one inbox message per session per 10 s; all pending events for that session go in one message (<=1,500 chars, priority order: this session's conflicts, requests addressed to it, its claims, count of others). Pull digest also capped at 1,500 chars, full detail via cowork_status. (4) Inbox is used only for action-required event classes: CONFLICT (to causer, when detected after the edit) and GO_FIRST_REQUEST (to holder). Never for: holder notice without a request, bystander status, RESPONSE/acks/thanks, decisions, health. HANDOFF_OFFER is delivered at the holder's Stop (Stop hook blocks once per offer, guarded by stop_hook_active) or at its next UserPromptSubmit, never by waking. (5) Wake matrix (receiver state -> action-required event): ACTIVE (mid-turn) -> inbox now (no new turn). IDLE and last human UserPromptSubmit <= 10 min ago and wake budget available (<= 1 wake per 10 min, <= 4 per hour per session, plus a team-wide budget recorded on the board, default 12 per hour) -> inbox (wakes). IDLE longer than 10 min, or budget exhausted -> pull-only, plus a human-facing OS notification (at most once per 30 min) and status line; the requester is told 'queued; shown at their next action'. permission_mode bypassPermissions/auto/dontAsk/plan -> never woken unless that user opted in at /cowork start. Effective crossSessionInbound hold/refuse or no messaging env -> HOOK-ONLY (pull). Informational events -> pull-only in every state. (6) No cascades: a turn started by a cowork wake never causes another inbox message (its RESPONSE is pull-delivered). (7) Go-first is a closed protocol: REQUEST -> RESPONSE(accept|decline|later) -> DONE; at most one open go-first per (conflict_id, requester); no answer = wait; preemption only on an explicit accept. (8) Our own limits sit far below the host's (burst refusal, identical-repeat drop, 50-message queue), so host throttling is never the governor; any host refusal is treated as not-delivered (RULE MSG-TOKEN 3).
WHY: Measured cost baseline (sweep/host H10): median context 511k tokens per request; a cold idle wake re-sends the whole context and is billed to the receiver (costs.md, cross-session-messaging.md). The host only drops identical repeats, so varied-wording loops (wake-loop-billing) need our own dedupe by key. U6 limits recipients to causer + holder and says bystanders are not woken; U5 says the holder is asked when its work finishes, which the Stop delivery implements without a wake.
V1/V2: v1: fixed budgets (configurable per user). v2: adaptive budgets from measured /usage.

## Local IPC security (Windows named pipes, Unix sockets) and key storage
CHOSEN: RULE IPC. (1) A 256-bit random IPC key is created at first start in a per-user directory (CLAUDE_PLUGIN_DATA; never in the repo or <gitdir>, which may be on a shared drive). After creation the daemon verifies the ACL is user-only (Windows: icacls shows only the user, SYSTEM, Administrators; Unix: file 0600 in a 0700 dir) and refuses to start otherwise. (2) The pipe/socket name contains a 128-bit nonce derived from the key file (not from user/repo hash alone). Unix sockets live in a 0700 directory. (3) Mutual challenge on every connection: the client sends nonce1; the server must reply HMAC(key, nonce1||'srv'||server_nonce2) before the client sends anything; the client replies HMAC(key, nonce2||'cli'). The server sends zero bytes (no greeting, no events) before the client proves the key; the client sends nothing (no session data) before the server proves it. Failed auth closes the connection and is logged as a security event. (4) On listen EADDRINUSE, the daemon connects as a client and runs the challenge: pass = a legitimate daemon is already running (reuse it); fail = squatter -> refuse to start and alert loudly (never assume 'another daemon'). (5) The IPC API grants nothing beyond the user's own git permissions: no exec, no paths outside the repo root, no token retrieval. (6) Threat model (documented): same OS user = trusted; any process holding the key can act as any of that user's sessions to the daemon. (7) Uninstall deletes CLAUDE_PLUGIN_DATA and thus the key; the daemon checks the key file and plugin enablement every 30 s and flushes and exits when either is gone.
WHY: VERIFIED sweep/sec/pipe_server.js: Everyone/ANONYMOUS LOGON read on the default DACL; a read-only client received the first line. New experiment sweep/msgsec/pipe2.js: a second listen on the same name gets EADDRINUSE (squatter-first blocks the daemon), and a client via \\127.0.0.1\pipe\... and \\127.0.0.1\pipe\LOCAL\... received server bytes, so the LOCAL\ prefix gives no protection. Node cannot set a pipe DACL, so confidentiality must come from authentication before any byte.
V1/V2: v1: shared per-user key, mutual HMAC. v2: per-session keys; native DACL via a small helper if ever needed.

## Unprotected refs/cowork/*: malicious or careless overwrite, deletion, ref spam, forged records
CHOSEN: RULE REF-TRUST. (1) Poll and fetch only explicit refspecs for branches this user has started: +refs/cowork/<b>/code and +refs/cowork/<b>/board (never refs/cowork/<b>/* or refs/cowork/*), with -c fetch.fsckObjects=true. # local-change-mgmt
## LCM-1 One hold registry replaces seven holding stores
CHOSEN: Exactly ONE store, the HOLD REGISTRY, records every reason this PC's disk or outgoing tree differs from (team tip + its own unpublished CLOSED change-sets). Kinds: PATCH (an unpublished sub-file change held by a guard, e.g. revert taint), PIN (whole paths pinned to their LA entry in the outgoing tree: held change-sets, portability/scope/unreadable residue), SNAPSHOT (worktree-wide freeze), INCOMING (receiver-side deferred change-set closure). CONFLICTED is a STATE of a record, not a store. DELETED: refs/cowork-held/*, refs/worktree/cowork/*/parked*, .git/cowork/quarantine/*.patch, .git/cowork/conflicts/*, refs/cowork-local/<b>/conflicts/*, separate board conflict/handoff record types (a handoff IS a registry record in state OFFERED), TRANSFORM holds (EOL/BOM/mode normalisation is the EOL group's canonicalisation function applied to every blob; never a hold, never a hunk, never a claim), and the write ring as a store (it survives only as the apply journal, a detector input whose loss degrades detection but loses no bytes; see LCM-5). Storage requirements (binding whichever git store the storage group picks for contradiction 3): an append-only commit chain (each update = a new commit whose parent is the previous registry commit; nothing overwritten), in the COMMON ref namespace shared by all worktrees (never refs/worktree/*), updated with update-ref --create-reflog, reachable from a ref so gc keeps it, and acting as the OUTBOX of the board ref: every registry commit is carried onto the board by the next push of any kind (code or board-only), exactly like a locally taken claim under U4. Record = {id (ULID), peer, kind, paths, H0 blob, H1 blob (or stage1/2/3 when CONFLICTED), guards (set), origin (human | session_id[/agent_id] | daemon), cs_ids, peer_authors, state, escalation_level, local_seq, created_at (display only)}. Blob content enters the registry only through the pinned clean path (git hash-object -w --path=<p> or a private-index add with the user's filters, as security-hosts requires). Records whose guards include filter-failure, secret-scan hit, a U10 secret-like path, or unreadable are LOCAL-ONLY: the board gets a content-free stub {id, peer, path, guard, state}. A board record changes only on a state transition or when a PIN's H1 is refreshed at a change-set close; never per loop (age is computed by readers). STATE MACHINE (the only one; other resolutions refer to it): DETECTED -> ACTIVE (bytes on disk, masked from S_pub). Evaluated in this order after every apply-loop rebase (LCM-2): CONFLICTED (rebase or mask conflict; path withheld) > SUBSUMED (H1' == LA; terminal) > GONE (PATCH only: MASK(S_disk) == S_disk; terminal) > ACTIVE. ACTIVE|CONFLICTED -> OFFERED (handoff to the holder's or peer author's queue: causer's Stop under U5, the U6 handoff option, or the escalation ladder) -> ACCEPTED (holder published it; requester's next rebase -> SUBSUMED; terminal) | RETURNED (holder declined or released the claim; back at the requester as ACTIVE, see LCM-12/LCM-13). ACTIVE|CONFLICTED|RETURNED -> PARKED (bytes removed from disk by the PARK operator; registry and board keep them) on /cowork stop, /cowork resolve --park, SNAPSHOT --restore, or the sign-off-gated 24 h timer; PARKED -> ACTIVE on RESTORE (/cowork start offer or command). Any non-terminal -> RESOLVED_PUBLISH (human command; the change passes every guard again, LCM-7) | RESOLVED_DISCARD (human command, logged); both terminal. SNAPSHOT records have only ACTIVE -> released (auto or command, LCM-6); INCOMING records have only ACTIVE -> released (lock cleared, 3-way merge, LCM-16). Transitions happen only on: the apply-loop rebase, a local write (guards re-run), a human command, the creator's escalation timer, save (rebase onto the save commit), stop (PARK), start (re-attach from the registry BEFORE the first publish), and holder-side CAS updates on the board ref.
WHY: P3: one registry, one representation (blob pairs), one durability path (the same outbox that already carries claims). P1: every displaced non-secret version becomes reachable from the remote board within one push, so re-clone, purge or disk loss cannot erase it. VERIFIED park-refs-in-worktree-namespace-vanish: refs/worktree and unlogged refs are deleted by git worktree remove (exit 0, no prompt), overwritten with no reflog, and pruned by gc --prune=now. Secret-bearing kinds stay local because mirroring them is the leak path (board-plaintext-and-permanence VERIFIED, filter-passthrough-leak VERIFIED).

## LCM-2 Hold identity and the single merge-file operator family
CHOSEN: Identity = the record id. Content = the ORIGINAL pair (H0 = LA blob of the path when the record was made, H1 = the held version). For a revert-taint PATCH, H1 = LA with ONLY the -U0 hunks of diff(LA, S_disk) that contain a tainted line applied (taint-only H1), so the human's untainted typing in the same save still publishes. One primitive: git merge-file -p --object-id (git >= 2.43; merge-tree --write-tree needs >= 2.38; /cowork start refuses older git and never falls back to file-based merge-file). REBASE (every loop, after the apply step): H1' = merge-file(cur=LA_blob, base=H0, other=H1), single step from the originals; H0' = LA_blob. Merge conflict -> state CONFLICTED (whole path withheld from publish, escalate); H1' == LA_blob -> SUBSUMED (auto-close, one event 'your held change is now the team version'); else if MASK(S_disk) == S_disk (the held change is no longer on disk) -> GONE (auto-close, one event; bytes stay in the append-only chain); else ACTIVE. Content hashes are used only for dedup and display. WHY: Presence by computation, not matching, is the only variant that passed every VERIFIED fuzz: rebased mask 160/160 (stale-hold-resurrects-team-revert) vs static mask wrong in 19/19 team-revert trials; line-range and patch-id masks shipped the revert (line-range-hold-misses-and-corrupts, hunk-identity-key-unstable); git apply landed a quarantined change in the wrong function with exit 0 (positional-patch-quarantine-misapplies). ## LCM-6 Git-op epoch guard and mass-change breaker = one SNAPSHOT freeze of both directions

## LCM-14 Tiered checks (T0 on every publish, T1 at checkpoints and save)

## LCM-16 Receiver side: change-set closure apply
