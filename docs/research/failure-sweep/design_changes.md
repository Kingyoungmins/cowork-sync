## git-integrity
- Run the daemon in a private GIT_DIR (bare repo under .git/cowork/ with alternates pointing at the user's objects, its own refs, private index and gc), with GIT_WORK_TREE = the user's worktree. Reasons: objects referenced only by the daemon are prunable today (objects-only-in-private-index); the 2-3 s fetch triggers auto-maintenance in the user's repo; and daemon refs would clutter `git log --all`, IDE branch lists and `push --mirror`.
- Make the apply tolerant per path instead of all-or-nothing. Pending paths are handled by tree surgery (M' = M with unmaterializable, locked, fenced or colliding paths taken from S) plus `read-tree -m` to sync the private index. Reason: read-tree -m -u is not atomic when a write fails (partial-apply-on-lock), and an all-or-nothing failure on one path stops a peer for good (poison-path).
- Keep a persistent private index (keep stat info) and reseed from a tree only on join or recovery, not every loop. Reasons: reseeding re-runs clean filters and EOL conversion on every file each loop (eol-renormalization), and costs about 3x (204 ms vs 68 ms on 3,000 files).
- Push invariants: each push is one freshly built commit with parent = the exact lease tip and tree = merge-tree(--merge-base=LAST_APPLIED, snapshot, tip), never the raw snapshot and never a stack of local commits. LAST_APPLIED is a ref updated only after a fully successful apply. Reason: pushed-tree-must-be-merge-result and untracked-sweep (an unpushable object must not block pushes permanently).
- Specify the conflict policy (currently undefined): on merge-tree exit 1, never apply the result tree and never use union, ours or theirs. The published version goes on disk, the local stage-2 blob is kept in a ref and recorded as a handoff with a patch, and modify/delete conflicts are retried first with a walked-back base.
- Set the sync scope by allow-list rather than `git add -A`: tracked paths of the live base, plus new files created through Claude Write/NotebookEdit hooks or `/cowork add`. Exclude gitlinks, LFS paths, generated paths and files over 5 MB. Run a portability gate (reserved names, invalid characters, case and NFC collisions, length) on publish.
- Bind the daemon to HEAD (symbolic ref + oid) and freeze publishing on any change. Add a revert detector and a mass-change breaker before every push. Defer applies while a Bash tool call runs in that worktree.
- At save, move every peer's branch ref and index to the saved commit without touching files (equivalent to `git reset --mixed C` under index.lock). This is a narrow exception to 'never touch the user's index or HEAD', needed because otherwise pull is blocked and stash causes a revert (post-save-head-drift). When the real branch moves, publish a live 'rebase' commit; save always uses a lease, never force.
- Fixed flags on every daemon git call: `-c filter.<name>.required=true` for each filter in use; `merge-tree --write-tree -X renormalize`; `fetch --no-auto-maintenance`; `push --no-verify` (with LFS paths out of live scope); `add -A --ignore-errors`, parsing 'unable to index file'.

## editor-fs
- Decision 4 says the apply is all-or-nothing and fails only with 'not uptodate'. Three experiments show that is false on Windows:
- e1: partial write when a file is locked;
- e11: partial write on a long path;
- e3: a concurrent save clobbered with exit 0.
The change below supports the approved engine rather than replacing it. Keep merge-tree for computing MERGED, but replace `read-tree -m -u` on the user's working tree with a per-path verifying writer:
1. Write a temp file in .git/cowork/tmp.
2. Rename the original away and check it against the expected blob.
3. Create the new file with link-no-replace; fall back to rename-over.
4. On a mismatch, run a 3-way merge through git.
Track last-applied as a per-path map. For the next merge-tree, build the local base tree from that map (update-index --cacheinfo on the private index, then write-tree, or mktree). A path that did not land keeps its old blob, so the next cycle offers it again.
- Keep a long-lived, stat-fresh private index updated by the applier, with core.fsmonitor and core.untrackedCache, instead of re-seeding from a tree each cycle. Measured: about 750 ms versus 53 ms per cycle on 3,004 files. Re-seed only for recovery.
- The snapshot covers tracked paths plus paths explicitly introduced through a Claude Write or Edit hook or `/cowork track`, never `git add -A` of untracked files. Add the editor and OS temp deny list, a churn quarantine, and a publish-side portable-path validator.
- Snapshot reads use Node (no memory mapping) with a stability gate, then `hash-object -w --stdin --path` using per-path eol settings that reproduce the base blob's stored form. Plain `hash-object --stdin --path` flips i/crlf blobs to LF (verified in e14); fall back to `git add -- P`. Stored-form (EOL/BOM) preservation is a hard invariant: EOL or BOM changes happen only through an explicit command.
- Add a per-path daemon write ring (pre- and post-write blobs), persisted for 14 days or more. It enables the stale-base rebase of editor saves and a 'revert-of-others' publish gate, so a hunk that restores a pre-peer version is never published automatically.
- Before every snapshot, watch HEAD, refs/stash, ORIG_HEAD and the tracked-path count. Freeze outbound when any changes, and gate changes that touch more than 50 paths or more than 20% of tracked paths. Cap the index.lock pause and surface it.
- Daemon git invocations force `filter.<driver>.required=true` for every driver referenced in attributes, plus a canary check at start and periodically.
- Humans get soft claims, attributed by the absence of Claude hooks; Bash edits by Claude are accepted as being classed human. The holder side adds breach stamps that deny the next Edit until a Read. Conflict markers are never written into a working file; conflicts go to .git/cowork/conflicts and the board.
- The file fence becomes a per-path mutex shared with the applier. PreToolUse waits for an in-flight write of that path. The fence is released on PostToolUse, PostToolUseFailure, Stop, MCP disconnect or a TTL. The fence also covers Read, so Read never sees a path mid-write.

## claude-code
- Claims taken at PreToolUse stay local and tentative. They are published only after PostToolUse confirms, by diffing the pre-image captured under the fence against the post-image, that the symbol really changed. This removes phantom claims from denied, rejected or interrupted calls. Causer ordering uses the confirmed publish time.
- The gate's source of truth is an exec-form command hook (node + args) that fails closed (exit 2) when cowork is active and the daemon or MCP heartbeat is missing or slow (2 s internal deadline, 10 s hook timeout). mcp_tool hooks are only a fast path, never the only gate, because they fail open by design and stdio servers are not reconnected.
- The gate never returns permissionDecision 'allow'. It returns no decision, or deny.
- The fence is a lease keyed by tool_use_id with a refcount per file. It is released by PostToolUse/PostToolUseFailure, PostToolBatch, the next PreToolUse or UserPromptSubmit from the same (session, agent_id), Stop/StopFailure/SubagentStop, or lease expiry.
- Holder key = (machine-id, checkout realpath, session_id, agent_id or 'main'). Re-key on SessionStart sources clear, resume and fork.
- Handoff triggers go beyond Stop: SubagentStop per agent; Stop only when background_tasks has no running subagents; StopFailure; the next UserPromptSubmit (catches interrupts).
- Bash/PowerShell calls run as transactions: a tree-wide fence plus a stat snapshot before, a diff after, and restore-and-record for hunks in foreign-claimed symbols. While live, git verbs that move HEAD, the index or the worktree are denied, as are repo-wide formatters.

- A provenance-based revert guard: local changes that undo recently applied remote hunks (from /rewind, a stale editor buffer or a read-modify-write script) are re-merged against the pre-apply blob instead of pushed. ## human-git-lifecycle
- Decision 4 ('never touch the user's index or HEAD') needs one guarded exception, ADOPT. After a save or base move, each daemon CAS-updates refs/heads/<b> from the old base to the new one and rewrites the user's index from the new base tree, holding .git/index.lock. It does this only when HEAD is on that branch at the old base and nothing is staged. Without this, every peer's `git pull` is refused after the first save or pull (VERIFIED), and git's own advice ('stash them') leads into the team-wide revert (VERIFIED).
- 'save' must not 'reset the live ref onto that commit'. It must re-parent the CURRENT live tip onto the saved commit: new live = commit(tree = merge-tree(base Lsaved, S, Lcur)) with parent S, leased on Lcur. The branch is leased on a freshly fetched tip and merged if it moved. Branch and live are pushed atomically, or ordered with a `Cowork-Live:` trailer for crash completion. The naive reset deleted concurrent edits from every disk (VERIFIED); re-parent preserved them (VERIFIED).
- Replace the pause list (index.lock, MERGE_HEAD, REBASE_HEAD) with a git-epoch guard and QUARANTINE state. Inputs: HEAD symbolic-ref and oid, refs/stash, reflog size, the full marker set (CHERRY_PICK_HEAD, REVERT_HEAD, AUTO_MERGE, rebase-merge/, rebase-apply/, sequencer/, BISECT_START), unmerged index entries and detached HEAD. A changed epoch makes the snapshot non-pushable, rather than merely pausing and later resuming on the changed tree.
- Add an outgoing peer-revert guard in the daemon. Human edits, git working-tree commands, /rewind and stale editor buffers never pass through PreToolUse claims, so any outgoing hunk that removes or changes a region authored by another peer since the last save is held for explicit local confirmation instead of being pushed.

## distributed-protocol
- INV-LINEAR: the live ref advances only by a compare-and-swap (CAS) push from an OID the daemon observed. Every live commit has exactly one parent, the previous tip. The only exception is a reset commit, whose parent is the save commit and which carries a 'Cowork-Prev-Tip: <oid>' trailer for diagnostics. Reason: this gives one total order, which everything below depends on.
- INV-BASE: each peer persists A, the per-path applied base, as a local ref (refs/cowork-local/<branch>/applied, per worktree). A[p] changes only after the working-tree write it describes, with a write-ahead journal for crash recovery. The merge base is always `--merge-base=<A>` and is never computed from commit ancestry. The temp index is seeded from A, never from the fetched tip. Reason: findings naive-push-reverts-unapplied-paths, explicit-base-not-ancestry and ambiguous-push-and-crash-stale-base (VERIFIED reverts and resurrections).
- INV-DELTA: the pushed tree is merge-tree --write-tree --merge-base=A snap(W) tip, never 'snapshot on top of the tip'. Before every push, assert that every path with snap[p]==A[p] has C[p]==tip[p]; a violation aborts the push and raises a doctor alert. In words: a peer never pushes a change to a path it did not change locally.
- INV-FENCE: a code commit may change region ρ only if it is pushed in the same atomic CAS as a board commit whose parent is the validated board tip and in which the pusher holds the earliest active claim on ρ. This is checked on the delta before the push, not only at PreToolUse, so it also covers hooks that fail open, a dead MCP server and human edits. Hunks that lose are withdrawn to the queue.
- Fallback for hosts without atomic push: SINGLE-REF mode. The board is a reserved '.cowork/' subtree inside the live commit and is stripped before merge, apply and save. Never use sequential two-ref pushes. Atomic support is detected from the receive-pack capability advertisement at /cowork start. Reason: finding non-atomic-pair-and-fence (VERIFIED partial update). This hardens the approved fallback rather than replacing decision 2.
- INV-OPID: the board is an op log, not text that git merges. Op ids are (peer_id, epoch, seq), with an append-only file per peer plus a state snapshot. State is a deterministic fold of the ops in board order, applying an op twice does nothing, and pending ops are re-validated after a CAS reject. A session's cursor is a vector {peer/epoch → seq}.
- INV-CLOCK: no timestamp from one machine is ever compared with another machine's clock. Leases are (holder, epoch, seq, ttl ≥ 10 min). Each observer expires a lease by its own monotonic timer started when it first saw that seq. The holder's validity runs from its push success minus a margin, so the holder always expires first. A takeover is a CAS op naming the exact (holder, epoch, seq). After a detected suspend or stall, the holder revalidates against a fresh board before allowing edits. Renewals ride on pushes that happen anyway.
- INV-CAUSAL: an event about code commit C is delivered only once A covers C on the referenced paths; otherwise it carries a 'not applied yet' marker and is re-delivered once applied. Conflict verdicts are a pure function of board order and keyed by conflict_id. Exactly one active message goes to the causer, generated by its own daemon. The holder is notified only for requests, and everyone else gets passive context without a wake.
- INV-NOLOSS (acceptance gate): every hunk a peer produced is, at all times, either in the tip or in the handoff queue, unless a later commit by a peer whose A contained the hunk changed it. Build one property-test harness: N simulated peers on a file:// remote, a unique marker string per edit, and random interleavings of {edit, fetch, push-ok, push-reject, push-ambiguous (landed but reported failed), apply-partial (fence or not-uptodate), crash at each step, stash/restore, external commit to main, concurrent save/reset, partition}. This one test is the shared test for most findings above.
- INV-CONVERGE (definition): convergence means equal git tree OIDs of the normalized trees, snap_i(W_i) == A_i == tree(tip) for every peer i. It does not mean byte-identical working trees, which legitimately differ by CRLF/LF and smudge output. Proof sketch: INV-LINEAR gives a total order. INV-DELTA means each successful push adds only that peer's local delta D_i, after which D_i is empty and A_i equals the pushed tree. After edits stop, each peer with a nonempty D_i lands it in one successful push (assumes bounded fairness). A peer with an empty D_i and A_i≠tip applies merge3(A,A,T)=T (assumes paths can eventually be applied) and re-snapshots to T (assumes round-trip). No delta is then left, so no further push happens, the tip is fixed and every peer equals it. Each assumption maps to a finding: bounded fairness to cas-storm-starvation-governor, eventual apply to naive-push-reverts-unapplied-paths (hot files and fence leaks), round-trip to phantom-delta-pingpong-convergence. Convergence is NOT correctness: without INV-DELTA and INV-BASE the peers still converge, but to a tree with a teammate's work reverted (e1). Correctness is INV-NOLOSS.
- Save semantics: save = merge3(base = the board's chain_base, ours = live tip, theirs = current branch head), committed with the branch head as parent and pushed fast-forward only. The reset commit's tree includes any live commits that landed during the save, and the same atomic board commit sets chain_base := save commit. Reason: finding save-reverts-external-commits (VERIFIED revert of an external PR commit).
- Push governor derived from the chain: the budget lives on the board (each daemon uses min(local, board)); N_active comes from presence ops on the board; rate is measured by counting observed chain commits on the observer's own monotonic clock; peers take turns by ring order of peer id after each observed tip; rejected attempts count against the peer's share; priority classes are conflict, then claim, then code. Reason: e6c measured 2.5x attempts per landed commit with one peer never rejected.
- Daemon git hygiene: every fetch uses --no-write-fetch-head, --no-auto-maintenance, -c gc.auto=0 and -c maintenance.auto=false. The daemon never writes refs/heads, refs/remotes, FETCH_HEAD or ORIG_HEAD. One daemon per clone/worktree, with the IPC endpoint as the lock. A revert-to-HEAD and mass-change breaker runs before every push, and a PreToolUse(Bash) deny list covers stash, restore, checkout --, reset --hard, clean and branch switching while live. Reason: findings fetch-head-hijack-and-auto-maintenance and local-git-ops-propagate-as-reverts (VERIFIED).

## negotiation
- PUSH GATE / QUARANTINE (addition to decision 2/6). The snapshot builder must never publish a change inside a symbol that someone else holds (ACTIVE or DORMANT), and never publish a change the revert detector flags as reverting a peer's newer version since the last save. It splices the published symbol text into the outgoing blob, falling back to the whole file from base. Reason: VERIFIED E5 shows git checkout -- on one PC erased a teammate's work on the teammate's own disk, and without the gate 'earlier claim wins' has no effect on code. Quarantine ends at the causer's Stop for Claude-made hunks (they become a handoff); human-made hunks stay pinned locally until /cowork resolve.
- SAVE (change to decision 10's 'live ref is reset onto that commit'). The save tree is derived from the fetched live tip T and asserted before pushing. Symbols with ACTIVE claims, and files that fail to parse, are excluded by splicing. The new live head is commit(tree=tree(T), parent=S'), pushed with a lease on T, never a reset that changes the live tree. Reason: VERIFIED E6 shows a lagging-tree save erased a peer's in-progress work although the lease was accepted.
- CLAIM LIFECYCLE (addition to decision 10). ACTIVE -> DORMANT (Stop, Notification idle_prompt or permission_prompt, or 10 min without an edit to the symbol) -> RELEASED (save, explicit release, 60 min dormant, or stdin EOF). DORMANT claims allow patch-bound auto-grants after a grace period, symbols over 300 lines are claimed by sub-block, and expiry uses the observer's monotonic clock. Reason: release only at session end starves teammates for hours and makes waiting deadlock.
- REQUIREMENT 4 IMPLEMENTATION. Exactly one daemon creates each conflict event: the integrator, the daemon whose unpublished changes meet published state. It is created in the same push with a deterministic id. Only the causer is pushed one coalesced message; holder and bystanders are pull-only. Reason: the literal reading means N−1 warnings and N−1 billed wakes per conflict, and the inbox drops bursts and identical repeats.
- NON-ATOMIC FALLBACK ORDER. On hosts without --atomic, push the board ref (claims and events) BEFORE the code ref. Reason: otherwise code can land on peers without the claim or event that explains it.
- GRANTS ARE PATCH-BOUND, NOT TIME-BOUND. 'Go first' grants the right to make the symbol equal one specific text (by hash), and the push gate enforces it. Open-ended time leases need the holder's human and are capped at 10 min / 5 edits. Reason: a board round trip (30 s to 2+ min) outlasts a 'quick job', and LLM time estimates can't be enforced.
- TURN-ORIGIN TRACKING. Turns started by a cowork inbox message cannot modify files except through cowork_apply_patch, and only under the owner's standing policy (default off). Reason: waking an idle session otherwise lets a teammate's message drive edits without the owner's consent, on the owner's usage.
- MERGE RESOLUTION LADDER for text collisions without claim overlap: union for pure insertions at a shared point, followed by separator normalisation; then per-symbol splice; then the conflict path. Reason: VERIFIED E1/E2 show EOF and import-tail insertions conflict, and merge-file --union resolves them but drops blank-line separators.

## security-hosts
- State the threat model explicitly. Collaborators with write access are trusted for code, since they can push anyway. The design defends against careless or buggy peers, prompt-injected Claude sessions, outsiders (other OS or domain users and repo readers), and any leakage beyond what plain git already allows. Several of the rules above only make sense once this line is drawn.
- Live refs are fast-forward only (changes approved decision 2/10). Daemons accept an incoming code or board tip only if it descends from the last applied tip. The 'reset onto the save commit' step after a save must be a commit whose parents include the old live tip, for example parents (save commit, old live tip). That keeps the chain fast-forward, so a legitimate save never looks like a rewind. Verified in t3: a non-fast-forward update cannot be told apart from a destructive rewind, and it reverts silently.
- Every daemon git invocation uses a fixed set of -c overrides: attr.tree=<base commit>; filter.<d>.required=true for each referenced driver; core.hooksPath=<empty private dir>; core.fsmonitor=false; fetch.fsckObjects=true; commit.gpgSign=false. Prompts are disabled with GIT_TERMINAL_PROMPT=0, GCM_INTERACTIVE=never and SSH BatchMode=yes. Commands target the pinned URL, never the remote name. ## gap:Publication units versus logical change units (cross-file and cross-symbol atomicity)
