## 결론부터

- **설계의 뼈대를 무너뜨리는 문제는 나오지 않았습니다.**
  - 두 사람이 동시에 올려도 한 명만 성공했습니다(100번 중 100번).
  - 비밀값 보호 장치는 고장 나도 안전한 쪽으로 멈췄습니다.
  - GitHub 자동 실행(Actions)은 우리 전용 저장 위치에서 돌지 않았습니다.
- **10개 질문 중 3개(g, i, j)는 설계서가 정한 합격선을 넘지 못했습니다.** 세 개 모두 고칠 방법은 이미 있습니다.
- **나머지 중 1개(h)는 합격입니다.** 5개(a~e)는 PC 한 대·네트워크 하나·Windows만으로 재서 범위가 모자랍니다. 1개(f)는 아직 제대로 시작하지 못했습니다.
- **그래서 설계서 자체 규칙("구현 전에 10개 실험을 모두 끝낸다")은 아직 충족되지 않았습니다.**
  - 테스트 도구와 기반 코드는 지금 시작해도 됩니다.
  - 실제 PC·네트워크·Claude 동작에 기대는 부분은 남은 실험과 설계서 수정이 끝난 뒤 시작해야 합니다.

## 먼저 알아두면 좋은 말

| 말 | 한 줄 풀이 |
|---|---|
| 스파이크(사전 실험) | 본 개발 전에 "이게 정말 되나?"를 짧게 확인하는 실험 |
| MEASURED / 측정함 | 실제로 돌려 봤고, 기록 파일이 남아 있음 |
| NOT MEASURED / 측정 안 함 | 아직 안 해 봄(이유를 같이 적음) |
| 리스(lease) | "내가 마지막으로 본 값 그대로일 때만 덮어써라"라는 조건부 저장. 동시에 써도 한 명만 성공하게 함 |
| 커스텀 ref | 일반 브랜치가 아닌, 따로 이름 붙인 Git 저장 위치(`refs/cowork/...`) |
| 훅(hook) | Claude Code가 파일을 고치기 직전·직후 등에 자동으로 부르는 작은 프로그램 |
| 받은편지함 / 초인종 | 다른 프로그램이 실행 중인 Claude 세션에 메시지를 넣는 통로 / 그 알림 메시지 |
| 데몬(daemon) | 화면 없이 뒤에서 계속 돌며 동기화하는 프로그램 |
| 필터(clean/smudge) | 비밀값을 저장소에 넣을 때는 지우고, 꺼낼 때 다시 채우는 장치 |
| GCM | Git 로그인 정보를 대신 관리해 주는 프로그램(Git Credential Manager) |
| 스냅샷 | 데몬이 2.5초마다 파일 상태를 찍어 두는 것 |

## 이게 무슨 뜻인가요

**좋은 소식**
- GitHub는 우리가 쓰려는 방식(커스텀 ref, 리스, 두 갈래 합치기 기록)을 모두 지원합니다.
  - 분당 6번(설계 기준)은 물론 분당 24번까지도 실패 0번이었습니다.
  - 차단 신호(429 등)도 한 번도 없었습니다.
- 시범 팀의 비밀값 필터(`hub.py`의 주소 숨기기)는 저장할 때와 꺼낼 때 모두 정확히 동작합니다.
  - 필터가 고장 나면 `git add`가 실패하며 멈춥니다. 비밀값이 새어 나가지 않습니다.
- 파일 하나를 고칠 때마다 붙는 감시(훅)는 오류가 나면 "막는 쪽"으로 처리하도록 만들 수 있습니다(종료 코드 2).

**바뀌어야 하는 것(설계를 고침)**
- **초인종 메시지 형식이 달랐습니다.**
  - 설계서에 적힌 형식은 Claude Code가 **아무 말 없이 버립니다**.
  - 실제로 들어가는 형식은 하나뿐이고, 받았다는 답장도 오지 않습니다.
  - 그래서 "받았는지"는 메시지에 넣은 표식을 Claude 쪽 훅에서 다시 보는 방식으로만 확인해야 합니다.
- **"사람이 직접 명령했다"는 증거를 받는 시점이 틀렸습니다.**
  - 설계서는 UserPromptSubmit(사용자가 입력을 보낼 때 부르는 훅)을 증거로 썼습니다.
  - 그런데 이 훅은 명령 실행이 **끝난 뒤에야** 불립니다. 이대로 만들면 매번 60초 기다리다 실패합니다.
  - 대신 UserPromptExpansion(명령을 펼치기 직전에 부르는 훅)을 쓰면 됩니다.
- **Windows에서 데몬이 파일을 읽는 방식을 바꿔야 합니다.**
  - 데몬이 Git으로 파일을 직접 읽는 동안 편집기가 저장하면, 1,000번 중 약 11번 저장이 실패했습니다(합격선: 1번).
  - 원인: Git이 파일을 읽는 동안 그 파일을 "붙잡고" 있기 때문입니다.
  - 파일을 먼저 복사해 두고 복사본을 읽게 하자, 데몬 때문에 생긴 실패는 0번이 됐습니다.
- **훅 한 번에 걸리는 시간 기준을 바꿔야 합니다.**
  - 실제로는 약 63밀리초(0.063초)가 걸려서 설계 기준 60밀리초를 넘었습니다.
  - 설계서는 이미 100밀리초로 기준을 올렸습니다.
  - 다만 이 값은 5번만 잰 결과라, 더 재 봐야 합니다.

**아직 모르는 것**
- 서로 다른 집·회사 네트워크에 있는 두 PC에서도 "한 명만 성공"이 유지되는지
- GitHub 로그인이 24시간 넘게 자동으로 유지되는지, 로그인이 끊기면 제대로 멈추는지
- 터미널·VS Code에서 사람이 직접 칠 때도 훅 순서가 같은지
- 맥·리눅스에서는 어떻게 동작하는지

## 사용자 도움이 필요한 것

1. **다른 네트워크의 두 번째 PC 한 대**(약 1~2시간). 집 인터넷이나 휴대폰 테더링이면 됩니다. a, b의 "서로 다른 네트워크" 조건을 채웁니다.
2. **24시간 뒤 GitHub 로그인 끊어 보기**(약 15분). 데몬이 "로그인 필요" 상태로 제대로 멈추는지 봅니다. 그 전에 PC가 24시간 넘게 켜져 있어야 합니다(f).
3. **직접 키보드로 하는 대화형 시험**(약 1~2시간).
   - 터미널과 VS Code에서 `/cowork` 명령을 각각 50번 칩니다.
   - Claude 창을 닫는 여러 방법(입력으로 종료, 창 닫기, 강제 종료, VS Code 닫기)을 시험합니다(c, e, g).
4. **관리자 권한 확인**(약 30분). Windows 보안(Defender)의 예외 목록을 확인하고, 실험 중 19초 동안 파일을 붙잡은 프로그램을 추적합니다(i).
5. (선택) **맥·리눅스 기기**. 없으면 설계서 기본값대로, 그 운영체제에서는 초인종 없이 동작하게 둡니다(c, d).
6. (선택) **시범 팀의 다른 PC에서 필터 점검 한 번**(약 30분, h).

**테스트용 저장소는 따로 요청하지 않아도 됩니다.**
- 이미 만든 비공개 저장소 `Kingyoungmins/cowork-sync-sandbox`로 남은 GitHub 실험을 모두 할 수 있습니다.
- 자동 테스트(CI) 전용 저장소가 따로 필요한지는 구현 단계에서 정하면 됩니다.

나머지 실험(약 8시간, 대부분 혼자 돌아감, Claude 실행 약 10번)은 사람 손 없이 할 수 있습니다.

## 설계서에서 바뀌어야 할 것(쉬운 요약)

정확한 위치와 새 값은 영어판 "What changes in the spec" 표(A1~A12, B1~B12, C1~C3)에 있습니다.

**이미 용어집(§25)에 정했지만, 다른 장에 아직 옛 내용이 남은 것(A)**
- 초인종 형식과 "보냈다/받았다"를 판단하는 방법(용어집 §13·§20, 07장, 06장)
- 사람 명령의 증거를 UserPromptExpansion에서 받기(용어집 §13·§15, 09장 SEC-25, 11장 시험 기준)
- GitHub의 일시적 거절을 "영구 중단"으로 처리하지 않기(01장 ENG-44/45)
- 필터 사전 점검을 실제 작업 폴더에서 하기(03장 D4)
- 훅 시간 기준 60밀리초를 100밀리초로(11장)

**새로 넣어야 하는 것(B)**
- Windows에서는 처음부터 복사본 방식으로 파일 읽기(01장 ENG-27)
  - 복사하는 동안 파일이 바뀌었으면 그 차례는 건너뛰기
  - 실험에서 빈 파일을 한 번 찍은 일이 있었음
- "저장 실패 1,000번 중 1번 이하" 시험의 계산 방법 정하기
  - 지금 기준(2시간)으로는 저장 횟수가 약 2,400번이라 통계적으로 인증이 안 됨
  - 3,000번 이상(약 2.5시간)이 필요
  - 데몬을 끈 상태와도 비교해야 함
- 하드링크(파일에 이름을 하나 더 붙이는 기능)가 안 되는 드라이브에서 쓰는 예비 저장 방식은 훨씬 약하다고 경고 띄우기
- 데몬이 남기는 임시 데이터가 빨리 쌓이므로(실험에서 20분에 205MB) 정리 규칙 만들기
- 초인종 열쇠(토큰)가 Claude 쪽 모든 훅에 이미 들어 있으므로, "열쇠는 한 프로그램에만 있다"는 문장을 "우리 코드는 한 곳에서만 읽는다"로 고치기(09장)
- 11장 i번 시험을 둘로 나누기
  - 지금 할 수 있는 부분(저장 실패)과 실제 데몬이 있어야 하는 부분(지연·메모리 등)을 분리
  - 그렇지 않으면 구현 전 조건을 영원히 못 채움
- (선택, 결정 필요) GitHub가 "여러 위치를 한 번에 함께 저장"하는 기능(`--atomic`)을 지원하니 쓸지 정하기
